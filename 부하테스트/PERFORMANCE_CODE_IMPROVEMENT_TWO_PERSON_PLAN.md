# 160 VU 결과 기반 코드 성능 개선 2인 분담 계획

작성일은 2026-08-11이다.

## 1. 목적

이 계획은 개선 코드로 실행한 브라우저 부하테스트에서 확인된 실패를 애플리케이션 코드 수준에서 줄이기 위한 작업 계획이다. 인프라 증설, ALB 설정 변경, 부하 생성기 설정 변경은 범위에서 제외한다.

테스트 횟수가 제한돼 있으므로 각 항목마다 부하테스트를 반복하지 않는다. 담당자별 단위·통합 테스트와 빌드로 먼저 검증하고, 두 작업을 합친 뒤 마지막에 한 번의 공식 부하테스트를 실행하는 방식으로 진행한다.

## 2. 테스트 결과에서 확인된 문제

파일명은 200 VU지만 실제 생성된 VU는 160명이었다. 96명이 완료하고 64명이 실패해 성공률은 60%였다.

| 항목 | 결과 |
| --- | ---: |
| 생성 VU | 160 |
| 완료 VU | 96 |
| 실패 VU | 64 |
| `toBeVisible` 실패 | 43 |
| 로그인 입력 `fill` timeout | 14 |
| 대량 메시지 입력 `fill` timeout | 3 |
| 금칙어 메시지 입력 `fill` timeout | 3 |
| 금칙어 시나리오 `click` timeout | 1 |
| HTTP 502 | 3 |
| HTTP 504 | 171 |
| 로그인 최대 TTFB | 약 17.82초 |

`toBeVisible` 오류는 보고서에 locator가 없어 정확한 화면 요소를 구분할 수 없다. 따라서 한 요소의 timeout만 늘리지 않고, 로그인·방 입장·메시지·금칙어·프로필의 완료 상태를 실제 API 또는 Socket 응답과 연결하는 방향으로 수정한다.

## 3. 작업 분담 원칙

두 담당자는 프론트엔드와 백엔드를 기술 영역으로 나누지 않는다. 서로 겹치지 않는 사용자 흐름을 끝까지 담당한다.

- 담당자 1은 로그인부터 방 목록과 방 입장 요청 전까지의 HTTP 요청 흐름을 담당한다.
- 담당자 2는 방 route 진입 이후 Socket 준비, 메시지 처리와 UI 완료 상태를 담당한다.

담당자 1은 HTTP 연결 상태와 요청량을 줄이고, 담당자 2는 Socket과 채팅 처리 비용 및 화면 완료 판정을 안정화한다.

## 4. 공통 계약

### 4.1 연결 상태

HTTP 상태와 Socket 상태를 하나의 `connectionStatus`로 표현하지 않는다.

- HTTP API는 각 요청의 성공과 실패로 상태를 판단한다.
- Socket 상태는 `disconnected`, `connecting`, `connected`, `joining`, `ready`, `error`로 구분한다.
- `/api/health` 실패만으로 로그인 폼이나 방 입장 버튼을 비활성화하지 않는다.
- 채팅 입력은 Socket 연결만으로 활성화하지 않고 `joinRoomSuccess` 처리까지 끝난 `ready` 상태에서 활성화한다.

### 4.2 재시도

- GET과 HEAD만 자동 재시도할 수 있다.
- 자동 재시도는 최대 1회다.
- POST, PUT, PATCH, DELETE는 기본적으로 자동 재시도하지 않는다.
- 동일 GET 요청이 진행 중이면 새 요청을 만들지 않고 기존 Promise를 공유한다.
- 502·503·504가 연속 발생하면 짧은 cooldown 동안 자동 요청을 중단한다.

### 4.3 화면 완료 상태

- 로그인 폼은 health check 완료 여부와 관계없이 즉시 표시한다.
- 방 입장은 URL 변경이 아니라 `joinRoomSuccess` 처리 완료로 성공 판정한다.
- 메시지는 `clientMessageId`를 기준으로 `pending`, `sent`, `rejected` 상태를 가진다.
- 금칙어 오류는 Toast만 사용하지 않고 메시지 전송 상태에도 보관한다.
- 프로필 변경은 API 성공 후 사용자 상태와 이미지 URL 반영이 완료됐을 때 성공 처리한다.
- 모든 loading 상태에는 정상 종료와 오류 종료 경로가 있어야 한다.

### 4.4 파일 소유 경계

담당자 1은 로그인, 공통 HTTP client, health check, 방 목록과 서버 HTTP 설정을 소유한다. 담당자 2는 채팅방 Socket 초기화, 채팅 입력, 메시지 이벤트, 방 입장 backend와 메시지 backend를 소유한다.

공통 파일 수정이 필요하면 먼저 계약 변경 내용을 문서에 반영하고 한 담당자만 수정한다. 같은 파일을 두 브랜치에서 동시에 수정하지 않는다.

## 5. 담당자 1 계획

담당자 1의 목표는 로그인 입력 timeout과 요청 재시도 폭증을 줄이고, 방 입장 버튼이 HTTP health 상태에 묶이지 않게 만드는 것이다.

### A-1. 로그인 폼에서 health gate 제거

#### 문제

현재 로그인 화면은 `/api/health` 결과를 기다리는 동안 로그인 입력창을 렌더링하지 않는다. 부하테스트에서 로그인 입력창 `fill` timeout이 14건 발생했고 로그인 TTFB는 최대 약 17.82초였다.

#### 변경

- 로그인 폼을 첫 렌더부터 표시한다.
- health check는 화면 상단 안내 문구 갱신에만 사용한다.
- health 결과와 관계없이 로그인 입력과 submit을 허용한다.
- 로그인 API 응답으로 실제 서버 접근 가능 여부를 판단한다.
- 4초 fallback으로 폼을 여는 기존 구조는 제거한다.

#### 완료 조건

- health 요청이 pending이거나 실패해도 로그인 입력창이 즉시 렌더링된다.
- health 실패 중 로그인 요청을 실행할 수 있다.
- 로그인 API 실패는 기존 오류 메시지로 표시된다.
- 로그인 성공과 인증 실패 동작은 유지된다.

### A-2. health preflight 제거와 요청 공유

#### 문제

방 목록 조회 전에 `/api/health`를 호출한다. 연결 실패 시 공통 Axios 재시도와 화면별 재시도가 겹쳐 한 사용자 행동이 여러 요청으로 늘어날 수 있다.

#### 변경

- `/api/rooms` 요청 전 `attemptConnection` 호출을 제거한다.
- 방 목록 API 결과로 HTTP 연결 상태를 갱신한다.
- health check가 꼭 필요한 화면에서는 진행 중 Promise를 공유한다.
- 연결 확인용 5초 interval을 제거하거나 실제 오류 복구 상태에서만 한 번 실행한다.
- health 결과는 짧은 시간 동안 재사용하고 화면마다 새 요청을 만들지 않는다.

#### 완료 조건

- 방 목록 최초 조회는 health 요청 없이 `/api/rooms` 한 번으로 시작한다.
- 동시에 같은 health check를 호출해도 실제 HTTP 요청은 한 건만 발생한다.
- health 실패가 방 목록의 무한 loading으로 이어지지 않는다.

### A-3. 공통 HTTP 재시도 정책 수정

#### 문제

현재 Axios interceptor는 method를 구분하지 않고 502·503·504 요청을 재시도한다. timeout 전에 backend write가 완료됐다면 POST 재시도로 중복 데이터가 생길 수 있다.

#### 변경

- GET과 HEAD만 최대 1회 재시도한다.
- POST, PUT, PATCH, DELETE의 자동 재시도를 막는다.
- retry delay에 full jitter를 사용한다.
- 동일 GET의 중복 요청을 Promise 단위로 합친다.
- 연속 5xx에 짧은 cooldown을 두고 자동 요청을 제한한다.
- 401은 기존처럼 자동 재시도하지 않는다.

#### 완료 조건

- 502·504를 받은 POST가 다시 전송되지 않는다.
- GET은 최대 1회만 재시도한다.
- 동시에 같은 GET을 호출해도 한 요청만 전송된다.
- retry 이후에도 기존 오류 객체와 사용자 메시지가 유지된다.

### A-4. 방 목록 polling과 입장 버튼 상태 수정

#### 문제

방 목록 화면은 30초마다 전체 목록을 다시 요청한다. 비슷한 시간에 접속한 사용자의 polling이 겹칠 수 있다. 방 입장 버튼은 HTTP health 기반 `connectionStatus`가 `CONNECTED`가 아니면 비활성화된다.

#### 변경

- 방 생성·수정·활동은 Socket 이벤트를 우선 사용한다.
- 전체 polling은 재연결 후 보정 또는 긴 간격의 fallback으로 제한한다.
- polling을 유지하면 사용자별 jitter를 넣는다.
- 이전 목록 요청이 진행 중이면 다음 요청을 만들지 않는다.
- 방 입장 버튼을 HTTP health 상태와 분리한다.
- REST 방 입장 요청 중에만 해당 버튼의 중복 클릭을 막는다.

#### 완료 조건

- HTTP health 실패만으로 모든 입장 버튼이 비활성화되지 않는다.
- 같은 시점에 방 목록 요청이 중복 실행되지 않는다.
- Socket room event가 기존 목록에 정상 반영된다.
- 추가 페이지와 최초 페이지가 room ID 기준으로 중복 없이 합쳐진다.

### A-5. Tomcat 설정 환경변수화

#### 문제

현재 Tomcat 최대 thread 10개, accept queue 10개, 최대 connection 50개가 코드에 고정돼 있다. 160 VU 결과에서는 504가 171건 발생했다.

#### 변경

- thread, accept queue, connection 값을 환경변수로 주입할 수 있게 한다.
- 기본값은 현재 값으로 유지해 로컬 동작을 바꾸지 않는다.
- 배포 환경에서만 인스턴스 자원에 맞는 값을 주입할 수 있게 문서화한다.

#### 완료 조건

- 환경변수가 없으면 기존 값으로 실행된다.
- 환경변수를 설정하면 Spring 설정에 반영된다.
- 잘못된 숫자 입력 시 애플리케이션이 명확한 설정 오류로 시작 실패한다.

### A-6. 프로필 이미지 전달 시 전체 메모리 로딩 제거

#### 문제

S3 프로필 이미지는 조회 시 object 전체를 byte 배열로 JVM 메모리에 올린다. 여러 사용자가 동시에 이미지를 조회하면 파일 크기만큼 heap 사용이 겹친다.

#### 변경

- 우선안은 짧은 TTL의 presigned URL을 반환하는 것이다.
- 기존 파일 API 계약을 유지해야 하면 S3 stream을 응답으로 전달한다.
- 프로필 이미지에 적절한 cache header를 적용한다.
- 채팅 첨부파일의 로컬 저장 정책은 변경하지 않는다.

#### 완료 조건

- S3 프로필 조회가 `getObjectAsBytes`를 사용하지 않는다.
- 기존 로컬 프로필 fallback이 유지된다.
- 프로필 업로드, 조회, 교체, 삭제가 모두 동작한다.
- 채팅 첨부파일은 계속 로컬 저장소를 사용한다.

- [ ] 방 목록 polling과 입장 버튼 상태 수정.
- [ ] Tomcat 설정 환경변수화.
- [ ] S3 프로필 응답의 전체 메모리 로딩 제거.
- [ ] 담당 범위 Frontend 테스트 통과.
- [ ] 담당 범위 Backend 테스트 통과.

## 6. 담당자 2 계획

담당자 2의 목표는 `toBeVisible` 43건과 채팅 입력 timeout을 줄이고, Socket 방 입장과 메시지 처리의 반복 DB·CPU 작업을 줄이는 것이다.

### B-1. 방 입장 완료 상태를 `joinRoomSuccess`와 연결

#### 문제

URL이 채팅방 주소로 바뀌거나 Socket transport가 연결돼도 초기 메시지와 room 상태 적용이 끝나지 않았을 수 있다. 이 상태에서 입력창이나 메시지를 기다리면 `toBeVisible` 실패가 발생할 수 있다.

#### 변경

- 방 상태를 `connecting`, `joining`, `ready`, `error`로 명시한다.
- Socket 연결 후 `joinRoomSuccess` payload 검증과 상태 반영이 끝나야 `ready`가 된다.
- 채팅 입력은 `ready`에서만 활성화한다.
- join timeout, payload 오류, disconnect는 모두 `error` 상태로 종료한다.
- 재연결 시 이전 Socket의 늦은 응답이 현재 상태를 덮어쓰지 못하게 Socket ID를 확인한다.

#### 완료 조건

- URL만 변경된 상태에서는 채팅 화면을 완료로 판단하지 않는다.
- `joinRoomSuccess` 처리 후 입력창과 초기 메시지가 함께 준비된다.
- join 실패 시 무한 loading이 발생하지 않는다.
- 재연결 후 같은 방이 중복 초기화되지 않는다.

### B-2. 메시지 UI를 `clientMessageId` 상태로 관리

#### 문제

메시지 성공 여부를 DOM에 최종 메시지가 나타났는지만으로 판단하면 Socket 응답 지연 시 화면 완료 상태가 불명확하다.

#### 변경

- 전송 직후 `clientMessageId` 기준 pending 메시지를 표시한다.
- 서버 message 이벤트가 오면 동일 `clientMessageId`의 pending 항목을 확정 메시지로 교체한다.
- Socket error가 오면 해당 메시지를 `rejected`로 변경한다.
- 금칙어 오류는 Toast와 함께 rejected 메시지 상태에 보관한다.
- 동일 `clientMessageId` 응답은 한 번만 적용한다.

#### 완료 조건

- 정상 메시지는 pending에서 sent로 한 번만 변경된다.
- 금칙어 메시지는 sent로 표시되지 않고 rejected 상태가 된다.
- 중복 Socket 이벤트가 와도 메시지가 두 개 생성되지 않는다.
- Toast가 사라져도 실패 상태를 확인할 수 있다.

### B-3. 방 입장 참가자 조회 batch화

#### 문제

현재 Socket 방 입장은 참가자 ID마다 사용자 repository를 호출한다. 참가자가 많아질수록 방 입장 한 번의 조회 수가 증가한다.

#### 변경

- 참가자 ID를 한 번에 `findAllById`로 조회한다.
- 조회 결과를 Map으로 만들어 기존 participant 순서에 맞춘다.
- creator도 같은 Map에서 찾고 누락된 경우에만 별도 처리한다.
- 기존 권한 확인, 참가 여부, 응답 구조는 유지한다.

#### 완료 조건

- 참가자 수가 증가해도 사용자 batch 조회는 한 번이다.
- creator를 위한 중복 사용자 조회가 발생하지 않는다.
- 참가자 누락과 존재하지 않는 ID의 기존 처리 의미가 유지된다.

### B-4. 메시지당 사용자·방 조회 축소

#### 문제

메시지마다 사용자 전체 document와 방 전체 document를 조회한다. 대량 메시지 시나리오에서는 같은 사용자와 방 정보가 반복 조회된다.

#### 변경

- 메시지 응답에 필요한 사용자 기본 정보는 인증된 Socket 사용자 정보 사용을 우선한다.
- 사용자 정보가 Socket에 충분하지 않으면 짧은 TTL cache를 사용한다.
- 방 권한 검증은 전체 Room 조회 대신 참가 여부 projection 또는 전용 exists query를 사용한다.
- 방 퇴장·강퇴·권한 변경 시 관련 cache를 즉시 무효화한다.
- 인증과 방 참가 검증 자체는 제거하지 않는다.

#### 완료 조건

- 일반 text 메시지 한 건에서 불필요한 User 전체 조회가 제거된다.
- 방 전체 document를 읽지 않고 참가 여부를 검증할 수 있다.
- 퇴장한 사용자는 cache 때문에 메시지를 보낼 수 없다.
- 기존 메시지 응답의 사용자 ID와 이름은 유지된다.

### B-5. 금칙어 검사 구조 개선

#### 문제

현재 메시지마다 약 10,000개 금칙어를 순회하면서 `contains`를 실행한다. 대량 메시지와 금칙어 시나리오가 동시에 실행되면 CPU 사용량이 메시지 수와 금칙어 수에 함께 비례한다.

#### 변경

- 애플리케이션 시작 시 금칙어 탐색 구조를 한 번 생성한다.
- Trie 또는 Aho-Corasick 중 기존 포함 문자열 의미를 유지할 수 있는 방식을 사용한다.
- 메시지마다 금칙어 전체 collection을 stream으로 순회하지 않는다.
- 대소문자 정규화와 빈 문자열 처리 의미를 유지한다.

#### 완료 조건

- 기존 금칙어 fixture 전체의 탐지 결과가 변경되지 않는다.
- 금칙어가 포함되지 않은 메시지와 포함된 메시지 테스트가 통과한다.
- 검사 과정에서 금칙어 collection 전체 stream을 사용하지 않는다.
- 탐색 구조는 요청마다 다시 생성되지 않는다.

### B-6. UI 완료 상태 명시

#### 문제

부하테스트에서 `toBeVisible` 실패가 43건 발생했지만 보고서에는 locator가 없다. timeout을 늘리는 것만으로는 원인을 해결할 수 없다.

#### 변경

- 방 준비, 메시지 전송, 파일 메시지, 금칙어 오류마다 명시적인 상태를 둔다.
- 비동기 작업 시작 시 loading 또는 pending 상태를 설정한다.
- API·Socket 성공 응답에서 success 상태를 설정한다.
- timeout, disconnect, 서버 error에서 error 상태를 설정한다.
- 화면 요소는 이 상태를 기준으로 결정적으로 렌더링한다.
- transient Toast는 상태 표현의 보조 수단으로만 사용한다.

#### 완료 조건

- 각 비동기 작업이 success 또는 error 중 하나로 끝난다.
- Socket disconnect 중 입력창이 잘못 활성화되지 않는다.
- 파일 업로드 성공과 파일 메시지 수신 상태가 구분된다.
- 금칙어 오류가 Toast 표시 시간과 관계없이 상태에 남는다.

### 담당자 2 체크리스트

- [ ] 방 입장 참가자 조회 batch화.
- [ ] 메시지당 사용자·방 조회 축소.
- [ ] 금칙어 탐색 구조 개선.
- [ ] 채팅 UI 완료 상태 명시.
- [ ] 담당 범위 Frontend 테스트 통과.
- [ ] 담당 범위 Backend 테스트 통과.
- [ ] Frontend production build 통과.
- [ ] Backend package 통과.

## 8. 구현 순서

두 사람은 1단계와 2단계를 병렬로 진행할 수 있다.

### 1단계. 담당자 1

1. 로그인 health gate를 제거한다.
2. health preflight와 연결 확인 interval을 정리한다.
3. Axios retry 정책을 method 기준으로 제한한다.
4. 방 목록 polling과 입장 버튼 상태를 정리한다.
5. Tomcat 설정을 환경변수화한다.
6. 핵심 항목 완료 후 프로필 S3 전달 방식을 개선한다.

### 2단계. 담당자 2

1. room ready 상태 계약을 구현한다.
2. 메시지 pending·sent·rejected 상태를 구현한다.
3. 방 입장 참가자 조회를 batch화한다.
4. 메시지 사용자·방 조회를 축소한다.
5. 금칙어 탐색을 개선한다.
6. 파일·금칙어·메시지 UI 완료 상태를 통합한다.

### 3단계. 통합

1. 담당자 1의 REST 방 입장 성공 후 담당자 2의 Socket joining이 시작되는지 확인한다.
2. HTTP health 실패가 Socket 상태를 덮어쓰지 않는지 확인한다.
3. `joinRoomSuccess` 전에는 채팅 입력이 비활성화되는지 확인한다.
4. ready 이후 메시지 pending·sent·rejected가 정상 전환되는지 확인한다.
5. 두 담당자의 전체 테스트와 production build를 실행한다.
6. 모든 코드 검증이 끝난 뒤 제한된 공식 부하테스트를 한 번 실행한다.

## 9. 검증 계획

### 담당자 1 검증

- health 응답 지연 중에도 로그인 폼이 렌더링되는 테스트.
- health 실패 중 로그인 submit이 가능한 테스트.
- GET만 한 번 재시도되는 테스트.
- POST가 502·504에도 재시도되지 않는 테스트.
- 동일 GET 요청이 한 건으로 합쳐지는 테스트.
- 방 목록 요청 전에 health 요청이 발생하지 않는 테스트.
- polling 요청이 겹치지 않는 테스트.
- Tomcat 환경변수 binding 확인.
- 프로필 업로드·조회·삭제와 로컬 fallback 테스트.

### 담당자 2 검증

- `joinRoomSuccess` 전후 room 상태 전환 테스트.
- join timeout과 disconnect의 error 종료 테스트.
- 재연결 시 오래된 Socket 응답 무시 테스트.
- 메시지 pending·sent·rejected 전환 테스트.
- 동일 `clientMessageId` 중복 이벤트 방지 테스트.
- 참가자 batch 조회 횟수 검증.
- 방 권한 cache 무효화 테스트.
- 기존 금칙어 fixture 회귀 테스트.
- 파일·금칙어 UI 완료 상태 테스트.

### 통합 검증

- Backend 전체 테스트.
- Backend package.
- Frontend 전체 테스트.
- Frontend production build.
- 로그인, 방 목록, 방 입장, 일반 메시지, 대량 메시지, 금칙어, 프로필 수동 smoke.

Frontend 전체 테스트가 외부 CDN 접근 때문에 실패하면 assertion 결과와 process 종료 코드를 분리해 기록한다. 테스트 명령이 종료 코드 1이면 전체 성공으로 기록하지 않는다.

## 10. 제한된 최종 부하테스트 판정 기준

최종 부하테스트는 코드 통합과 모든 로컬 검증이 끝난 뒤 한 번만 실행한다.

비교할 항목은 다음으로 제한한다.

- VU 생성 수와 완료 수.
- 전체 성공률과 실패율.
- `toBeVisible`, `fill`, `click` timeout 수.
- 502와 504 수.
- 로그인 TTFB.
- 메시지와 금칙어 시나리오 완료 여부.
- 중복 메시지 수신 여부.

테스트의 실제 생성 VU가 목표와 다르면 파일명이 아니라 `vusers.created`를 기준으로 기록한다. 이전 160 VU 결과와 생성 VU가 다르면 지연시간 개선율을 직접 계산하지 않고 오류 유형과 성공률을 조건 차이와 함께 기록한다.

## 11. 완료 기준

- 두 담당자의 파일 소유 경계가 지켜진다.
- 로그인 폼이 health 요청에 차단되지 않는다.
- health preflight와 중복 재시도가 제거된다.
- write 요청이 자동 재시도되지 않는다.
- 방 입장 성공은 `joinRoomSuccess` 처리 완료로 판정된다.
- 메시지와 금칙어 실패 상태가 Toast에만 의존하지 않는다.
- 방 입장 참가자 N+1이 제거된다.
- 메시지당 사용자·방 전체 조회가 줄어든다.
- 금칙어 전체 stream 순회가 제거된다.
- Backend 전체 테스트와 package가 성공한다.
- Frontend 테스트와 production build 결과가 기록된다.
- 두 작업 통합 후 공식 부하테스트 결과가 기존 160 VU 결과와 비교된다.

## 12. 컨텍스트 노트

- 160 VU 결과에서 64건의 실패 중 43건은 `toBeVisible`이었다.
- 로그인 입력 timeout 14건은 채팅 처리보다 앞에서 발생했으므로 담당자 1이 우선 처리한다.
- 금칙어와 대량 메시지 입력 timeout은 Socket room 준비와 메시지 상태가 연결되지 않은 문제일 수 있어 담당자 2가 처리한다.
- 504가 여러 pod에 분산됐으므로 단일 사용자나 단일 방 데이터 문제로 보지 않는다.
- 현재 보고서에는 실패 locator가 없어 특정 UI 요소 하나의 수정으로 완료 판정하지 않는다.
- 테스트 횟수가 제한돼 있어 단계별 부하테스트는 하지 않는다.
- 성능 개선과 무관한 UI 리팩터링, API 이름 변경, 데이터 구조 전면 변경은 하지 않는다.
