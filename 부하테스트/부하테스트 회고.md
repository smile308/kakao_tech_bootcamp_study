## 1. 목적

이번 작업의 목적은 주어진 코드의 부하 상황에서 반복되는 실제 사용자 흐름을 안정화해서 더 높은 부하를 견디는 것입니다. 프론트엔드와 백엔드를 따로 나누지 않고 한 사용자 행동이 화면, API, Socket, DB로 이어지는 흐름을 기준으로 두 사람이 업무를 분담했습니다. 배포와 인프라 구축은 코드를 바탕으로 다른 두 사람이 업무를 처리했습니다.

회고의 작성자는 담당자 1로 참여했습니다. 부하테스트 결과와 코드의 연관성을 정리한 뒤, 업무를 프론트엔드와 백엔드로 단순 분리하지 않고 메시지·읽음 처리와 방 입장·조회처럼 사용자 흐름 단위로 나누는 분담안을 만들었습니다. 두 작업이 따로 진행돼도 통합 시 동작이 맞도록 공통 상태와 완료 조건을 정리했고, 진행 상황과 충돌 가능성을 확인하면서 남은 업무를 다시 배치하는 역할도 맡았습니다.

작업은 1차 개선 후 첫 번째 200 VU 테스트를 실행하고, 그 결과에서 새로 확인된 문제를 다시 나누어 2차 개선한 뒤 두 번째 200 VU 테스트로 확인하는 순서로 진행했습니다. 마지막에는 배포와 다중 서버 환경에 필요한 수정도 역할을 나누어 반영했다.

부하테스트는 실행 가능한 횟수가 제한되어 있었습니다. 각 개선 항목을 하나씩 적용하고 같은 조건으로 여러 번 반복하는 방식이 가장 정확하지만, 이번에는 그렇게 진행할 수 없었습니다. 따라서 여러 개선을 한 번에 반영한 뒤 제한된 테스트 결과로 다음 우선순위를 정했습니다. 이 때문에 특정 수치의 변화가 어느 한 수정만으로 발생했다고 단정하지 않고, 완료율과 오류 유형이 전체적으로 어떻게 달라졌는지를 중심으로 해석했습니다.

## 2. 1차 개선과 역할 분담

첫 번째 200 VU 테스트 전에는 코드 구조와 초기 측정 자료를 바탕으로 메시지·읽음 처리와 방 입장·조회 흐름을 나누어 개선했습니다.

### 담당자 1

담당자 1인 나는 실시간 메시지 전송과 읽음 처리 흐름을 맡았습니다. 동시에 전체 개선 항목을 기능 흐름별로 정리하고, 담당자 2와 수정 파일이 겹치지 않도록 작업 범위와 순서를 조율했습니다.

- 프론트엔드에서 메시지별로 발생하던 읽음 요청을 짧은 시간 동안 모아 batch로 전송합니다.
- 백엔드에서 메시지별 조회와 저장을 반복하지 않고 MongoDB bulk update로 처리합니다.
- 발신자 직접 전송과 방 broadcast가 겹쳐 같은 메시지가 두 번 수신되던 문제를 제거합니다.
- 메시지 처리 중 반복되던 Session 저장을 줄였습니다.
- Rate Limit을 원자적 갱신으로 변경했습니다.
- 같은 방에서 연속으로 발생하는 활동 count와 방 목록 알림을 합쳐 처리했습니다.

로컬 환경에서의 독립된 테스트를 실행했을 때, Before/After 측정에서는 25 VU 메시지 중복 수신이 223건에서 0건으로 줄었고, 읽음 집중 P50은 98.3ms에서 23.3ms로 감소했습니다. MongoDB에서 메시지 정보를 찾기 위해 실행한 조회 명령은 11,906회에서 2,648회로 약 77.8% 줄었습니다. 메시지에 읽은 사용자 정보를 반영하기 위해 실행한 수정 명령도 10,595회에서 1,274회로 약 88.0% 줄었습니다. 기존에는 여러 메시지를 읽을 때 메시지마다 조회와 수정을 반복했지만, 개선 후에는 읽음 요청을 묶어 한 번의 bulk 작업으로 처리했기 때문입니다.

### 담당자 2

담당자 2는 방 목록에서 채팅방에 입장해 초기 메시지를 받는 흐름을 맡았습니다.

- REST 방 입장과 Socket 방 입장의 역할을 분리해 중복 참가 처리와 초기화를 줄였습니다.
- 초기 메시지마다 반복되던 사용자와 파일 조회를 batch 조회로 변경했습니다.
- 메시지 조회에 pagination과 복합 인덱스를 적용했습니다.
- 방 목록 전체 조회와 애플리케이션 정렬을 DB pagination과 정렬로 변경했습니다.
- 참가자 정보와 최근 메시지 수를 방마다 반복 조회하지 않고 일괄 집계했습니다.
- 목록 응답에 필요한 데이터만 전달해 payload를 줄였습니다.

1차 개선에서는 담당자 1이 메시지 전송과 읽음 처리 경로를, 담당자 2가 방 입장과 초기 데이터 조회 경로를 맡았습니다. 각자 다른 기능을 수정하더라도 통합 후 동작이 어긋나지 않도록 공통 처리 규칙도 먼저 정했습니다. 예를 들어 메시지는 `clientMessageId`를 기준으로 중복 여부를 판단하고, 읽음 처리는 여러 `messageId`를 배열로 묶어 전달하며, 방 입장은 Socket 연결만으로 완료된 것으로 판단하지 않고 `joinRoomSuccess`로 방 정보와 초기 메시지 적용이 끝난 뒤에만 완료 처리하도록 규칙을 맞췄습니다. 또한 응답 데이터의 ID 형식, 메시지 정렬 순서, 오류와 timeout의 처리 기준도 통일했습니다. 이러한 계약을 문서로 공유한 뒤 서로의 핵심 파일을 동시에 수정하지 않도록 작업 영역을 나누어, 별도 브랜치에서 작업해도 병합 과정에서 데이터 형식이나 상태 처리 방식이 충돌하지 않도록 했습니다.

## 3. 1차 200 VU 테스트

1차 테스트는 목표 200 VU 중 실제 160 VU가 생성됐습니다. 96명이 완료하고 64명이 실패해 완료율은 60%, 실패율은 40%였습니다.

| 항목 | 결과 |
| --- | --- |
| 생성 VU | 160명 |
| 완료 VU | 96명 |
| 실패 VU | 64명 |
| `toBeVisible` 실패 | 43건 |
| 로그인 입력 `fill` timeout | 14건 |
| 대량 메시지 입력 `fill` timeout | 3건 |
| 금칙어 입력 `fill` timeout | 3건 |
| 금칙어 시나리오 `click` timeout | 1건 |
| HTTP 502 / 504 | 3건 / 171건 |
| HTTP 요청 | 44,428건 |

1차 개선으로 메시지와 읽음 처리의 반복 작업은 줄였지만, 높은 부하에서는 다른 문제가 드러났습니다. 가장 큰 실패는 `toBeVisible` 43건이었고, 로그인 입력 요소가 나타나지 않아 발생한 timeout과 504도 함께 확인됐습니다.

URL 변경이나 Socket transport 연결만으로 화면 준비가 끝났다고 판단하는 구조, `/api/health` 결과를 기다린 뒤 로그인 폼을 표시하는 구조, 여러 단계의 HTTP 재시도가 겹치는 구조가 다음 개선 대상이 됐습니다.

## 4. 2차 개선과 역할 분담

1차 200 VU 결과를 바탕으로 로그인부터 방 입장 전까지의 HTTP 흐름과, 방 진입 이후의 Socket·화면 완료 흐름을 다시 나누었습니다.

### 담당자 1

담당자 1인 나는 로그인, 공통 HTTP 요청, 방 목록과 반복 조회 비용을 맡았습니다. 1차 테스트 결과를 기준으로 추가 개선 항목을 다시 분류하고, 담당자 2의 진행 상황을 확인해 충돌하지 않는 남은 작업을 이어받았습니다.

- health 결과와 관계없이 로그인 폼을 즉시 렌더링합니다.
- 방 목록 조회 전 health 선행 요청과 5초 polling을 제거합니다.
- GET·HEAD만 최대 한 번 재시도하고 동일한 GET 요청은 진행 중 Promise를 공유하도록 합니다.
- 방 목록 polling 주기를 늘리고 입장 버튼을 HTTP health 상태에서 분리합니다.
- S3 프로필 이미지를 백엔드가 전부 읽지 않고 presigned URL로 전달하게 합니다.
- 금칙어 목록 전체를 메시지마다 순회하던 방식을 애플리케이션 시작 시 생성한 Trie 탐색으로 변경합니다.

담당자 2의 우선 작업이 끝난 뒤 남은 작업은 충돌하지 않는 범위에서 담당자 1이 이어받았습니다.

- 방 입장 참가자 조회를 batch화합니다.
- 메시지마다 반복되던 사용자·방 document 조회를 줄입니다.
- 파일과 금칙어를 포함한 메시지 완료 상태를 화면에 명시합니다.
- 한글 IME 입력 시 마지막 글자가 별도 메시지로 중복 전송되는 문제를 수정합니다.

### 담당자 2

담당자 2는 채팅방 진입 이후의 Socket 준비와 메시지 전송 상태를 맡았습니다.

- Socket 연결만으로 완료 처리하지 않고 `joinRoomSuccess` 반영 후 `ready`가 되도록 했습니다.
- 메시지를 `clientMessageId` 기준의 `pending`, `sent`, `rejected` 상태로 관리했습니다.
- 정상 응답과 금칙어 거부를 화면 상태로 구분했습니다.
- 배포 환경의 Tomcat 값을 최대 thread 30, 최소 spare thread 10, accept queue 100, 최대 connection 8192로 수정하고 해당 값은 인프라 담당자분들이 찾은 값입니다.

2차 개선에서는 처음 계획을 고정하지 않고 진행 상황에 따라 남은 업무를 재분배했습니다. 두 사람이 공유하는 `ready`, `pending`, `sent`, `rejected` 계약은 유지해 각자 다른 파일을 수정해도 병합 후 동작이 맞도록 했습니다.

## 5. 2차 200 VU 테스트

2차 테스트는 목표 200 VU 중 실제 168 VU가 생성됐습니다. 131명이 완료하고 37명이 실패해 완료율은 78%, 실패율은 22%였습니다.

| 항목 | 1차 | 2차 | 변화 |
| --- | --- | --- | --- |
| 생성 VU | 160명 | 168명 | 8명 증가 |
| 완료 VU | 96명 | 131명 | 35명 증가 |
| 실패 VU | 64명 | 37명 | 27명 감소 |
| 완료율 | 60% | 78% | 18%p 증가 |
| `toBeVisible` 계열 실패 | 43건 | 8건 | 35건 감소 |
| 로그인 입력 `fill` timeout | 14건 | 18건 | 4건 증가 |
| 금칙어 입력 `fill` timeout | 3건 | 8건 | 5건 증가 |
| 대량 메시지 입력 `fill` timeout | 3건 | 1건 | 2건 감소 |
| HTTP 502 | 3건 | 0건 | 제거 |
| HTTP 504 | 171건 | 216건 | 45건 증가 |
| HTTP 요청 | 44,428건 | 51,351건 | 15.6% 증가 |

실제 생성 VU가 8명 늘었는데도 완료 사용자는 35명 증가하고 실패 사용자는 27명 감소했습니다. `toBeVisible` 계열 실패도 43건에서 시나리오별 합계 8건으로 줄었습니다. 방 준비와 메시지 완료 상태를 명시한 코드 변경이 화면 판정 안정화에 기여한 것으로 해석할 수 있습니다.

반면 로그인 입력 timeout과 금칙어 입력 timeout은 증가했고 HTTP 504도 216건으로 늘었습니다. 전체 HTTP 요청 대비 504 비율도 약 0.385%에서 0.421%로 소폭 증가했습니다. 다만 이 테스트 시점에는 코드뿐 아니라 백엔드 WebSocket 인스턴스 확장과 ALB 구성 같은 인프라 변경도 함께 적용됐습니다. 따라서 504 증가와 일부 채팅 실패를 코드 문제만으로 단정할 수 없습니다.

특히 Socket.IO를 여러 인스턴스로 수평 확장할 때는 인스턴스 간 상태 공유와 연결 고정이 함께 고려되어야 합니다. Redis Pub/Sub 어댑터가 없으면 한 인스턴스에서 발생한 이벤트가 다른 인스턴스의 사용자에게 전달되지 않을 수 있습니다. 또한 polling transport를 사용하는 Socket.IO 요청이 ALB에서 서로 다른 인스턴스로 분산되면 동일한 Socket 세션을 이어가지 못할 수 있으므로 `ktb-chat-b-ws-tg` 타겟 그룹의 stickiness 설정도 필요합니다. 두 설정이 충분히 적용되지 않은 상태에서 인스턴스만 늘리면 처리 용량이 증가하기보다 메시지 누락이나 연결 불안정이 발생할 수 있습니다.

두 실행은 실제 생성 VU, HTTP 요청 수, 코드와 인프라 구성이 모두 달랐고 같은 조건에서 반복 실행하지도 못했습니다. 따라서 개별 지연시간이나 오류 변화가 특정 코드 수정 하나의 효과라고 해석하지 않았습니다. 확인 가능한 결과는 더 많은 VU가 생성된 2차 테스트에서 완료율과 화면 판정 오류는 개선됐지만, 로그인·금칙어 처리와 504 문제는 코드와 인프라가 함께 영향을 준 미해결 영역으로 남았다는 것입니다.

## 6. 최종 수정

2차 테스트 이후에는 인증·Socket 확장성과 파일 저장으로 역할을 다시 나눴습니다. 이 변경들은 2차 테스트 이후에 적용됐으므로 앞의 테스트 결과를 해당 변경의 효과로 해석하지 않았습니다.

### 담당자 1

담당자 1인 나는 채팅 첨부 파일의 저장 경로를 맡았습니다. 최종 단계에서도 인증·Socket 영역과 저장소 영역을 분리해 두 사람이 같은 핵심 파일을 동시에 수정하지 않도록 업무를 나눴습니다.

- 기존 S3 모드가 프로필 이미지만 처리하던 범위를 채팅 첨부 파일까지 확장합니다.
- 프로필과 채팅 파일을 모두 S3에 저장하도록 라우팅합니다.
- 기존 로컬 파일은 S3에 없을 때 계속 조회할 수 있도록 fallback을 유지합니다.
- 삭제 시 S3 객체와 기존 로컬 파일을 함께 정리합니다.

### 담당자 2

담당자 2는 로그인 DB 작업과 다중 서버 Socket 상태를 맡았습니다.

- 인증 과정에서 이미 조회한 사용자 정보를 세션 생성, JWT 발급과 로그인 응답에 재사용합니다.
- 로그인 과정의 중복 사용자 조회와 세션 관련 중복 작업을 줄입니다.
- Socket.IO 브로드캐스트를 Redisson과 Redis Pub/Sub으로 공유하도록 합니다.
- 접속 사용자와 사용자별 방 상태를 Redis Set으로 관리합니다.
- 여러 백엔드 인스턴스가 같은 Socket 상태를 공유하도록 구성합니다.
- 단일 서버와 테스트에서는 인메모리 저장소를 사용할 수 있도록 유지합니다.

저장소 영역과 인증·Socket 영역으로 나누어 같은 핵심 파일을 동시에 수정하지 않도록 했다.

## 6. 최종 결과

최종 상태는 25 VU에서는 정상적으로 동작했지만, 50명 부하에서는 대량 메시지 시나리오가 97%, 파일 업로드 시나리오가 93%의 성공률을 기록하며 오류가 발생했습니다. 오류 당시 방 입장 API는 200으로 성공했고 URL도 이미 `/chat/{roomId}`였기 때문에 단순 라우팅 실패는 아니었습니다. 대량 메시지 실패에서는 열린 WebSocket이 0개였고 채팅 입력창이 나타나지 않았으며, 파일 업로드 실패에서는 WebSocket이 열려 있어도 파일 메시지가 제한 시간 안에 화면에 표시되지 않았습니다.

코드를 확인한 결과, 같은 사용자로 판단되는 기존 연결이 있으면 10초 뒤 기존 세션을 종료하는 로직이 존재했습니다. 낮은 부하에서는 기존 연결 정리가 빠르게 끝나 문제가 드러나지 않을 수 있지만, 부하가 증가하면 연결 종료와 재연결 순서가 엇갈리면서 정상 재연결도 중복 로그인으로 판단될 가능성이 있습니다. 특히 Redis에는 연결 상태가 공유되지만 기존 클라이언트를 찾는 부분은 현재 인스턴스 내부 클라이언트만 조회하므로, 여러 WebSocket 인스턴스에서는 처리 결과가 달라질 수 있습니다.

## 7. 느낀 점

이번 작업에서는 내가 담당자 1로서 메시지·읽음 처리와 방 입장·초기 조회처럼 연관된 실행 흐름을 기준으로 업무를 나누고, 공통 이벤트 이름과 응답 규칙을 문서화했습니다. 이 방식은 두 사람이 같은 핵심 파일을 동시에 수정하는 상황을 줄이고 각자 하나의 흐름을 끝까지 개선할 수 있다는 장점이 있었습니다. 따라서 1차 코드 개선 단계의 분담 방식 자체는 잘못된 판단이 아니었습니다.

다만 최종 부하테스트를 통해 코드 개선만으로 전체 서비스의 안정성을 보장할 수 없다는 점을 확인했습니다. 프론트에서는 입력창이 사라지는 현상으로 보이지만, 실제 원인은 백엔드의 세션 종료 정책, Redis에 저장된 연결 정보, ALB의 WebSocket 분산 방식, 인스턴스별 로컬 소켓 상태가 함께 영향을 줄 수 있었습니다. 코드 담당자는 API가 200으로 끝났다는 사실만으로 성공이라고 판단해서는 안 되고, 인프라 담당자도 타깃이 정상이라는 사실만으로 애플리케이션 이벤트가 전달됐다고 판단해서는 안 됐습니다.

특히 Socket.IO 수평 확장에서는 Redis 기반 이벤트 동기화와 ALB 연결 정책을 코드의 재연결·중복 로그인 처리와 함께 검증해야 했습니다. 이번에는 코드 담당자와 인프라 담당자가 각자의 범위에서는 작업했지만, 배포 단계에서 소켓 ID, 서버 인스턴스, Redis 연결 상태, 이벤트 송수신 결과를 하나의 흐름으로 확인하는 협업이 부족했습니다. 그 결과 25명에서는 보이지 않던 문제가 50명에서 발생했을 때 코드와 인프라 중 어느 계층에서 문제가 시작됐는지 빠르게 구분하기 어려웠습니다.

앞으로는 구현 단계에서는 현재처럼 기능 흐름 단위로 분담하되, 배포와 부하테스트 단계에서는 프론트·백엔드·인프라 담당자가 함께 하나의 요청을 추적하는 방식이 더 적절하다고 느꼈습니다. 단순히 프론트엔드와 백엔드를 완전히 분리하는 것보다 각자 주요 영역을 맡으면서 상대 영역의 이벤트 계약과 배포 구조를 교차 검토해야 합니다.

성능 테스트는 문제가 발생하는 조건을 보여주고, 코드 해석은 그 문제가 왜 발생하는지를 설명합니다. 이번 경험을 통해 두 작업을 함께 수행해야만 실제 원인에 가까워질 수 있다는 점을 배웠습니다.
