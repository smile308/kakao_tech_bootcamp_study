# 프로젝트 전체 코드 읽기 순서 가이드

이 문서는 기존 장별 교안이 아니라 실제 저장소의 파일을 어떤 순서로 열어야 하는지를 정리한 지도다. 목표는 파일을 많이 보는 것이 아니라, 하나의 요청이 어디에서 시작해 어디까지 흐르는지 연결하는 것이다.

## 읽는 규칙

각 파일을 열 때 다음 순서로 확인한다.

1. 파일의 package/import와 class 또는 함수 선언을 먼저 본다.
2. 외부에서 호출되는 public 메서드를 찾는다.
3. 그 메서드가 호출하는 파일로 이동한다.
4. 같은 문법을 다시 만나면 문법 설명은 생략하고, 이 파일에서 달라지는 역할만 확인한다.
5. 아래에 `스킵`이라고 적힌 파일은 열지 않아도 된다. 대신 역할만 기억한다.

`문법` 항목은 그 문법이 이 순서에서 처음 등장하는 지점이다. 처음 등장한 문법은 반드시 이해한 뒤 다음 파일로 이동한다.

`dto/user/UserPatch*`, `UserInfoResponseDto`, `UserDeleteResponseDto`, `UserPassword*`는 UserService의 수정·탈퇴 기능용 DTO다. 회원가입에서 DTO/Entity/Controller 흐름을 이해한 뒤 각각의 field와 endpoint만 확인하면 되므로 같은 DTO 문법은 다시 공부하지 않는다.

## 12. 최종 연결 확인

마지막에는 아래 네 가지 요청을 실제 코드에서 처음부터 끝까지 따라간다.

1. 회원가입: `SignupPage` → `SignupForm` → `authApi` → `api.js` → `UserController` → `UserService` → `UserRepository` → `User`.
2. 게시글 목록: `PostsPage` → `postApi` → `api.js` → `PostController` → `PostService` → `PostRepository` → `PostPageResponseDto`.
3. 인증 요청: `api.js` → `JwtAuthenticationFilter` → `CustomUserDetailsService` → `SecurityContext` → Controller.
4. Refresh: `api.js`의 공유 refresh Promise → `SessionController` → `SessionService` → `AuthSessionRepository` row lock → Cookie/Access Token 응답.
5. 조회수: `PostDetailPage` → post API → Redis `ViewCountUpdater` → Lua/dirty set → flush scheduler → `PostViewCountRepository`.
6. 배포: GitHub Actions → container image → SSM → deploy script → Compose → Nginx → health endpoint.

이 여섯 흐름을 따라가며 이미 읽은 파일은 다시 처음부터 읽지 않는다. 같은 파일이 두 흐름에 등장하면 두 번째에는 새로 연결되는 메서드만 확인한다.
