# 10장. 테스트 범위와 테스트 코드

## 10.1 학습 목표

테스트마다 무엇을 진짜로 사용하고 무엇을 가짜로 대체하는지, 그리고 Gradle과 CI가 어디까지 자동 실행하는지 학습한다.

```text
순수 단위 테스트
→ 대상 객체만 생성

Mockito 단위 테스트
→ 대상 객체 + 가짜 의존성

Spring 통합 테스트
→ Spring Context + H2 + 실제 Repository

Redis 통합 테스트
→ Testcontainers + 실제 Redis

MySQL 통합 테스트
→ Testcontainers + 실제 MySQL 8.4 + Flyway + JPA validate + DB lock

CI check
→ 일반 테스트 + Redis 테스트 + MySQL 테스트 + JaCoCo 기준
```

## 10.2 테스트의 기본 구조

대부분의 테스트는 다음 세 단계로 읽는다.

```text
Given
→ 필요한 객체와 가짜 응답 준비

When
→ 검사할 메서드 실행

Then
→ 반환값, 상태 변화, 호출 여부 검증
```

테스트 메서드 이름은 “어떤 조건에서 어떤 결과를 기대하는가”를 먼저 알려준다. 현재 프로젝트 테스트에는 `@DisplayName`을 사용하지 않고 한글 method 이름으로 의도를 표현한다. `@DisplayName`은 JUnit에서 사용할 수 있는 선택 기능이지만 현재 실제 코드라고 보면 안 된다.

## 10.3 실제 코드 발췌: 순수 단위 테스트

```java
@Test
void 발급한_액세스_토큰에서_사용자_ID와_인증_버전을_다시_꺼낼_수_있다() {
    JwtProvider jwtProvider = new JwtProvider(SECRET, ONE_HOUR_MILLIS);

    String accessToken = jwtProvider.createAccessToken(42L, 3L);
    AccessTokenClaims tokenClaims =
            jwtProvider.getAccessTokenClaims(accessToken);

    assertThat(accessToken).isNotBlank();
    assertThat(tokenClaims.userId()).isEqualTo(42L);
    assertThat(tokenClaims.authVersion()).isEqualTo(3L);
}
```

Spring Context나 DB가 필요하지 않다. 실제 `JwtProvider`를 직접 만들고 입력과 결과만 검사한다.

이 유형은 가장 빠르며 Entity의 상태 변경, Provider의 계산과 검증에 적합하다.

## 10.4 실제 코드 발췌: Mockito 단위 테스트

```java
@ExtendWith(MockitoExtension.class)
class RedisViewCountStoreTest {

    @Mock
    private StringRedisTemplate redisTemplate;

    private RedisViewCountStore store;

    @BeforeEach
    void setUp() {
        ViewCountProperties properties = new ViewCountProperties(
                true,
                "bamboo:{post-view}:count:",
                "bamboo:{post-view}:dirty",
                "bamboo:{post-view}:flush-lock",
                Duration.ofSeconds(5)
        );
        store = new RedisViewCountStore(redisTemplate, properties);
    }
}
```

중요한 줄:

```java
@Mock
// 실제 Redis에 연결하지 않는 가짜 StringRedisTemplate을 만든다.

@BeforeEach
// 각 테스트 메서드 실행 전에 새로운 대상 상태를 준비한다.
```

행동 설정과 검증:

```java
when(redisTemplate.execute(
        ArgumentMatchers.<RedisScript<Long>>any(),
        eq(List.of(
                "bamboo:{post-view}:count:42",
                "bamboo:{post-view}:dirty"
        )),
        eq("100"),
        eq("42")
)).thenReturn(101L);

long updatedViewCount = store.increment(42L, 100L);

assertThat(updatedViewCount).isEqualTo(101L);

verify(redisTemplate).execute(
        ArgumentMatchers.<RedisScript<Long>>any(),
        eq(List.of(
                "bamboo:{post-view}:count:42",
                "bamboo:{post-view}:dirty"
        )),
        eq("100"),
        eq("42")
);
```

```text
when
→ Mock이 어떤 호출을 받으면 무엇을 반환할지 준비

실제 대상 메서드 실행
→ RedisViewCountStore.increment

assertThat
→ 반환 결과 검증

verify
→ 의존성에 기대한 요청을 보냈는지 검증
```

Mock 테스트는 Java 코드의 분기와 협력 순서를 검사하지만 Lua가 실제 Redis에서 동작하는지는 증명하지 못한다.

## 10.5 실제 코드 발췌: Spring·H2 통합 테스트

```java
@ActiveProfiles("test")
@SpringBootTest
@Transactional
class PostRepositoryIntegrationTest {

    @Autowired
    private UserRepository userRepository;

    @Autowired
    private PostRepository postRepository;

    @Autowired
    private EntityManager entityManager;
}
```

```text
@ActiveProfiles("test")
→ Gradle·IDE 실행 방식과 관계없이 application-test.yaml 적용

@SpringBootTest
→ 실제 Spring Context와 Bean 설정을 준비

@Autowired
→ 실제 Repository Bean 주입

@Transactional
→ 각 테스트가 끝날 때 DB 변경 rollback
```

대표 검증:

```java
Page<Post> result = postRepository
        .findByDeletedFalseAndReportCountLessThanOrderByPostIdDesc(
                Post.REPORT_BLOCK_THRESHOLD,
                PageRequest.of(0, 100)
        );

assertThat(result.getContent())
        .extracting(Post::getPostId)
        .contains(visiblePost.getPostId())
        .doesNotContain(hiddenPost.getPostId());
```

이 테스트는 JPQL, Entity mapping, 신고 기준 조건이 H2에서 함께 동작하는지 검사한다.

H2와 MySQL은 서로 다른 DB이므로 H2 통과가 모든 MySQL 전용 동작을 보장하지는 않는다. 현재 프로젝트는 이 한계를 보완하기 위해 별도의 `mysqlTest`에서 실제 MySQL 8.4를 실행한다.

### 세션 Origin 보안 통합 테스트

`SecurityConfigTest`는 허용된 Origin, Origin 누락, 허용되지 않은 Origin을 MockMvc로 검증한다. 전체 원문과 라인별 주석은 5장에서 이미 다루므로 여기서는 테스트 경계만 정리한다.

```text
허용 Origin + 빈 로그인 DTO
→ Origin 보안 단계 통과
→ DTO 검증에서 400

Origin 없음
→ SessionOriginInterceptor에서 403 Forbidden_Origin

허용되지 않은 Origin
→ Spring CORS 처리 또는 interceptor에서 403
```

MockMvc의 기본 `servletPath`는 실제 Servlet 요청과 다르게 빈 값일 수 있다. 따라서 세션 요청 판정은 현재 `request.getRequestURI()`로 `/sessions`와 `/sessions/refresh`를 읽는다. 이 테스트는 단순히 status만 확인하는 것이 아니라 Origin 보안 코드가 Controller 입력값 검증보다 앞에서 동작하는지도 구분한다.

## 10.6 실제 코드 발췌: Redis Testcontainers

```java
@Tag("redis-integration")
@Testcontainers
class RedisViewCountStoreIntegrationTest {

    @Container
    private static final GenericContainer<?> REDIS =
            new GenericContainer<>(
                    DockerImageName.parse("redis:7.4-alpine")
            )
                    .withExposedPorts(6379)
                    .waitingFor(Wait.forListeningPort());
}
```

중요한 줄:

```java
@Tag("redis-integration")
// 일반 test가 제외하고 redisTest가 선택할 태그다.

@Testcontainers
// JUnit 생명주기에서 Testcontainers를 관리한다.

@Container
// 테스트 전 Redis 컨테이너를 시작하고 종료한다.
```

동시성 검증:

```java
@Test
void 동시에_200번_증가해도_조회수가_유실되지_않는다()
        throws Exception {
    int requestCount = 200;
    CountDownLatch startSignal = new CountDownLatch(1);
    List<Future<Long>> results = new ArrayList<>();

    try (ExecutorService executor =
                 Executors.newFixedThreadPool(20)) {
        for (int index = 0; index < requestCount; index++) {
            results.add(executor.submit(() -> {
                startSignal.await();
                return store.increment(42L, 100L);
            }));
        }

        startSignal.countDown();

        for (Future<Long> result : results) {
            assertThat(result.get(10, TimeUnit.SECONDS))
                    .isBetween(101L, 300L);
        }
    }

    assertThat(redisTemplate.opsForValue().get(COUNT_KEY))
            .isEqualTo("300");
    assertThat(redisTemplate.opsForSet().size(DIRTY_SET_KEY))
            .isEqualTo(1L);
    assertThat(redisTemplate.opsForSet().isMember(
            DIRTY_SET_KEY,
            "42"
    )).isTrue();
}
```

여러 스레드를 한 시점에 출발시켜 실제 Redis Lua의 원자성을 확인한다. 각 `Future.get(10, TimeUnit.SECONDS)`는 작업이 예외 없이 제한 시간 안에 끝났는지도 확인한다. 최종 count뿐 아니라 dirty set에 같은 post ID가 한 번만 들어 있는지도 검증한다.

## 10.7 테스트 실행 범위

```text
./gradlew test
→ test profile
→ 일반 단위·Spring 통합 테스트
→ redis-integration과 mysql-integration 제외
→ JaCoCo 보고서 생성

./gradlew redisTest
→ redis-integration만 실행
→ Docker 필요

./gradlew mysqlTest
→ mysql-integration만 실행
→ 빈 MySQL에 B3 적용
→ Hibernate validate
→ 실제 MySQL 동시 좋아요와 비관적 lock 검증
→ Docker 필요

./gradlew check
→ 일반 검증
→ JaCoCo 80% 확인
→ redisTest와 mysqlTest 포함
```

현재 JaCoCo 80% 강제 범위:

```text
entity/**
auth/**
config/**
service/**
controller/**
```

핵심 Service와 HTTP Controller가 이제 80% 계산에 포함된다. Repository는 대부분 구현 line이 없는 Spring Data interface이므로 line coverage 강제 범위에서는 제외한다. DTO와 Exception 같은 단순 전달 객체도 현재 강제 범위에는 넣지 않는다.

이 rule은 각 class가 각각 80%를 넘어야 한다는 설정이 아니라, 선택된 class directory 묶음의 line covered ratio 하한을 0.80으로 둔 설정이다. 별도의 class별 rule은 없다.

범위를 Service와 Controller까지 확장한 직후 기존 테스트만으로는 78%여서 검증이 실패했다. 기준을 낮추지 않고 `ControllerDelegationTest`를 추가했고, 현재 일반 테스트 기준 선택 범위는 83.14%로 80% 검증을 통과한다.

실제 `build.gradle`의 task 설정:

```groovy
tasks.named('test') {
	systemProperty 'spring.profiles.active', 'test'
	useJUnitPlatform {
		excludeTags 'redis-integration', 'mysql-integration'
	}
	finalizedBy jacocoTestReport
}

tasks.register('redisTest', Test) {
	description = 'Runs integration tests against a Testcontainers Redis server.'
	group = 'verification'
	testClassesDirs = sourceSets.test.output.classesDirs
	classpath = sourceSets.test.runtimeClasspath
	useJUnitPlatform {
		includeTags 'redis-integration'
	}
	shouldRunAfter test
}

tasks.register('mysqlTest', Test) {
	description = 'Runs schema and locking integration tests against a Testcontainers MySQL server.'
	group = 'verification'
	testClassesDirs = sourceSets.test.output.classesDirs
	classpath = sourceSets.test.runtimeClasspath
	useJUnitPlatform {
		includeTags 'mysql-integration'
	}
	shouldRunAfter test
}

def coverageIncludes = [
		'kr/adapterz/springdatajpa/entity/**',
		'kr/adapterz/springdatajpa/auth/**',
		'kr/adapterz/springdatajpa/config/**',
		'kr/adapterz/springdatajpa/service/**',
		'kr/adapterz/springdatajpa/controller/**'
]

tasks.named('jacocoTestReport') {
	dependsOn test

	reports {
		html.required = true
		xml.required = true
		csv.required = false
	}

	classDirectories.setFrom(files(sourceSets.main.output.classesDirs.collect {
		fileTree(dir: it, include: coverageIncludes)
	}))
}

tasks.named('jacocoTestCoverageVerification') {
	dependsOn test

	classDirectories.setFrom(files(sourceSets.main.output.classesDirs.collect {
		fileTree(dir: it, include: coverageIncludes)
	}))

	violationRules {
		rule {
			limit {
				counter = 'LINE'
				value = 'COVEREDRATIO'
				minimum = 0.80
			}
		}
	}
}

check.dependsOn jacocoTestCoverageVerification
check.dependsOn tasks.named('redisTest')
check.dependsOn tasks.named('mysqlTest')
```

`test` task의 system property와 각 `@SpringBootTest`의 `@ActiveProfiles("test")`가 함께 test profile을 고정한다. Gradle 전체 실행뿐 아니라 IDE에서 단일 Spring test를 직접 실행해도 `application-test.yaml`이 적용된다. base profile group 설정에 의해 local H2 설정도 함께 사용하고, test 설정은 Redisson auto configuration을 제외하며 Redis 조회수 구현을 비활성화한다. `redisTest`의 tagged test는 Spring Context를 띄우지 않고 Testcontainers와 Redis client를 직접 구성한다.

현재 JaCoCo report와 verification의 기본 execution data는 일반 `test` 실행에서 생성된 자료를 기준으로 한다. 별도 `redisTest`·`mysqlTest` coverage를 합치도록 `executionData`를 추가한 코드는 없다. 실제 Redis·MySQL 연동 검증은 별도 성공 조건이며, 80% line coverage는 빠른 일반 테스트가 실행한 Java code를 기준으로 한다.

Backend CI의 실제 실행 command는 다음 한 줄이다.

```yaml
- name: Run existing tests and verification
  run: ./gradlew clean check --no-daemon
```

`check`가 `redisTest`와 `mysqlTest`에 의존하므로 CI runner에는 Testcontainers가 사용할 Docker 환경도 필요하다. GitHub-hosted Ubuntu runner에서는 Docker를 사용할 수 있지만, local에서 같은 command를 실행할 때 Docker가 꺼져 있으면 두 integration task 중 컨테이너가 필요한 단계가 실패한다. Docker가 없을 때 자동 skip하도록 설정하지 않은 이유는 CI에서 외부 연동 검증이 빠졌는데도 성공하는 거짓 통과를 막기 위해서다.

각 `@SpringBootTest` class에는 `@ActiveProfiles("test")`가 명시되어 있다. Gradle task를 거치지 않는 IDE/JUnit 직접 실행도 test profile을 사용한다.

## 10.8 프론트엔드 테스트 범위

현재 `package.json`에는 테스트 스크립트와 테스트 라이브러리가 없다.

실제 scripts 원문:

```json
"scripts": {
  "dev": "vite",
  "build": "vite build",
  "lint": "oxlint",
  "preview": "vite preview"
}
```

`test` 항목이 없고 devDependencies에도 Vitest·Jest·Testing Library·Playwright 같은 test runner가 없다.

CI 검증:

```text
npm ci
→ npm run lint
→ npm run build
```

따라서 현재 자동으로 보장되지 않는 예:

- 버튼 클릭 결과
- 페이징 상태 변화
- 401 후 자동 재요청
- Form 입력과 오류 메시지
- React 컴포넌트 렌더링

lint와 build 성공은 문법·정적 검사와 production bundle 생성 가능성을 확인하지만 사용자 행동이 올바르다는 것을 증명하지 않는다.

## 10.9 어떤 테스트를 어디까지 작성할 것인가?

```text
Entity 내부 상태 규칙
→ 순수 단위 테스트

Service 분기와 Repository 호출 순서
→ Mockito 단위 테스트

JPA query와 mapping
→ Spring DB 통합 테스트

락과 동시 수정
→ 여러 Thread를 사용하는 통합 테스트

Redis 명령·Lua·분산 락·AOF
→ Testcontainers 실제 Redis 테스트

HTTP 보안 경로
→ Security Filter Chain과 MockMvc 테스트
```

모든 메서드를 같은 테스트 유형으로 반복하지 않는다. 실패했을 때 위험한 규칙과 외부 기술의 실제 연동 경계를 중심으로 선택한다.


## 10.9.1 전체 원문 코드 라인별 주석본

아래 주석은 학습을 위해 추가한 것이며 실제 프로젝트 파일에는 없다. 줄 끝 주석을 붙인 주석본은 의미를 따라가기 위한 설명용이므로 그대로 복사해 실행하지 않는다.

### Gradle 테스트 범위 설정

```groovy
tasks.named('test') { // Gradle Java plugin이 만든 기본 test task를 설정한다.
	systemProperty 'spring.profiles.active', 'test' // test JVM에 Spring active profile system property를 전달한다.
	useJUnitPlatform { // JUnit Platform의 test 선택 규칙을 설정한다.
		excludeTags 'redis-integration', 'mysql-integration' // Docker가 필요한 Redis·MySQL tagged test는 일반 test에서 제외한다.
	}
	finalizedBy jacocoTestReport // test 종료 뒤 성공·실패와 별개로 report task를 최종 작업으로 연결한다.
}

tasks.register('redisTest', Test) { // Test type의 별도 Gradle task를 새로 등록한다.
	description = 'Runs integration tests against a Testcontainers Redis server.' // task 설명이다.
	group = 'verification' // Gradle task 목록의 verification group에 표시한다.
	testClassesDirs = sourceSets.test.output.classesDirs // 일반 test가 compile한 test class 위치를 사용한다.
	classpath = sourceSets.test.runtimeClasspath // test runtime dependency와 main/test classpath를 사용한다.
	useJUnitPlatform { // JUnit Platform 선택 규칙을 설정한다.
		includeTags 'redis-integration' // 해당 tag가 붙은 test만 실행한다.
	}
	shouldRunAfter test // 둘 다 task graph에 있으면 일반 test 뒤에 실행하도록 순서를 권고한다.
}

tasks.register('mysqlTest', Test) { // 실제 MySQL 전용 Test task를 등록한다.
	description = 'Runs schema and locking integration tests against a Testcontainers MySQL server.' // task 목적을 설명한다.
	group = 'verification' // verification task 목록에 표시한다.
	testClassesDirs = sourceSets.test.output.classesDirs // compile된 test class를 사용한다.
	classpath = sourceSets.test.runtimeClasspath // MySQL driver와 Testcontainers를 포함한 test classpath를 쓴다.
	useJUnitPlatform { // JUnit tag 선택 규칙을 설정한다.
		includeTags 'mysql-integration' // MySQL tag가 붙은 test만 실행한다.
	}
	shouldRunAfter test // check 안에서는 빠른 일반 test 뒤 실행하도록 권고한다.
}

def coverageIncludes = [ // coverage 대상 class path pattern 목록을 변수에 저장한다.
		'kr/adapterz/springdatajpa/entity/**', // Entity package를 포함한다.
		'kr/adapterz/springdatajpa/auth/**', // 인증 package를 포함한다.
		'kr/adapterz/springdatajpa/config/**', // 설정 package를 포함한다.
		'kr/adapterz/springdatajpa/service/**', // 핵심 business logic package를 포함한다.
		'kr/adapterz/springdatajpa/controller/**' // HTTP 요청 위임 package를 포함한다.

        throws Exception { // latch 대기와 Future.get에서 발생 가능한 checked exception을 선언한다.

)).isSameAs(fixResponse); // Controller가 Service 응답을 바꾸지 않고 반환하는지 확인한다.
```

게시글 생성·조회·삭제·좋아요·신고와 Comment·Session·User Controller도 같은 “입력 전달 → Service 호출 → 응답 반환” 구조다. Session·User의 인증 변경 method는 추가로 `Set-Cookie` 만료 또는 회전 header까지 검증한다. 동일 Mockito 문법의 반복은 스킵한다.

## 10.10 스킵할 코드

- Entity 생성자 테스트의 반복되는 getter assertion
- Service 테스트마다 반복되는 Mock 생성 문법
- Testcontainers 연결 객체 생성의 동일 구조
- 테스트용 이메일·닉네임 문자열
- 네 Controller에서 반복되는 Mock 위임 검증 문법
- H2·Redis·MySQL 동시성 helper의 동일한 latch·Future 문법

다음은 스킵하지 않는다.

- 성공뿐 아니라 실패·경계값 시나리오
- Transaction과 rollback
- 락과 동시성 출발 방식
- Mock으로는 검증되지 않는 실제 Redis 동작
- H2로는 검증되지 않는 실제 MySQL migration·validate·row lock
- `test`, `redisTest`, `mysqlTest`, `check`의 포함 범위


## 10.10.1 이 장에서 필요한 JUnit·Mockito·동시성 문법

### 테스트 annotation 생명주기

- `@Test`: 실행할 테스트
- `@BeforeEach`: 각 테스트 전에 실행
- `@AfterEach`: 각 테스트 후 실행
- `@BeforeAll`: 클래스의 모든 테스트 전에 한 번
- `@AfterAll`: 클래스의 모든 테스트 후 한 번
- static `@BeforeAll`은 테스트 객체 생성 전 클래스 수준에서 실행된다.

### Arrange, Act, Assert

코드에 주석이 없어도 다음 경계를 찾아 읽는다.

```text
객체·Mock 준비
→ 대상 메서드 한 번 실행
→ 결과·상태·호출 검증
```

테스트 하나에는 가능한 한 하나의 행동 이유를 둔다.

### AssertJ fluent assertion

```java
assertThat(value)
    .isEqualTo(expected)
    .isNotNull();
```

`assertThat`이 검증 객체를 반환하고 점을 이어 여러 조건을 표현한다.

예외 검증:

```java
assertThatThrownBy(() -> target.call())
    .isInstanceOf(...)
    .hasMessage(...);
```

lambda 안의 실행이 어떤 예외를 던지는지 검사한다.

### Mockito Mock과 Stub

- Mock: 실제 구현 대신 호출을 기록하는 가짜 객체
- Stub: `when(...).thenReturn(...)`으로 특정 입력의 가짜 결과 설정
- `verify`: 기대한 상호작용이 실제 발생했는지 확인
- `verifyNoInteractions`: 의존성을 전혀 호출하지 않았는지 확인

### Matcher

```java
any()
eq("42")
```

- `any`: 해당 타입의 어떤 값도 허용
- `eq`: 기대값과 동등한 값만 허용
- 한 호출의 인자 중 Matcher를 사용하면 나머지도 Matcher 형태로 맞추는 것이 Mockito 규칙이다.

### `@InjectMocks`

Mock 필드를 대상 객체 생성자에 넣어 주는 편의 annotation이다. 직접 생성자를 호출하는 테스트와 목적은 같지만 생성 과정을 Mockito가 돕는다.

### `@SpringBootTest`

실제 애플리케이션과 가까운 Spring Context를 올린다. 테스트는 느려지지만 자동 설정, Bean 연결과 Repository를 함께 검증할 수 있다.

### 테스트 Transaction rollback

Spring Test의 `@Transactional`은 기본적으로 테스트가 끝날 때 rollback한다. 테스트 간 DB 오염을 막는다. 실제 운영 commit 이후 동작까지 동일하게 검증하는 것은 아니므로 commit 경계가 중요한 경우 별도 설계가 필요하다.

### `flush`와 `clear`

- `flush`: JPA 변경 SQL을 즉시 DB에 보냄
- `clear`: 1차 cache의 관리 Entity를 비움

둘을 함께 사용하면 이후 조회가 메모리 Entity가 아니라 실제 DB query 결과인지 더 명확히 확인할 수 있다.

### Generic wildcard `<?>`

```java
GenericContainer<?>
```

정확한 Generic 타입 인자를 현재 코드에서 알 필요가 없거나 사용하지 않음을 나타낸다. 아무 타입이나 대입한다는 의미와 완전히 같지는 않고, 알 수 없는 특정 타입 하나를 뜻한다.

### Thread pool과 Future

- `ExecutorService`: worker Thread pool 관리
- `submit`: 비동기 작업 등록
- `Future`: 나중에 완료될 결과
- `get(timeout, unit)`: 제한 시간 안에 결과 대기

### `CountDownLatch`

여러 Thread가 하나의 count가 0이 될 때까지 기다리게 한다. 테스트에서는 작업을 미리 등록한 뒤 `countDown()`으로 함께 출발시켜 동시 충돌 가능성을 높인다.

### 테스트가 증명하는 범위

Mock 테스트는 대상 Java 분기를 증명하지만 실제 Redis·DB 동작을 증명하지 않는다. 통합 테스트는 실제 연동 범위를 넓히지만 외부 환경, 성능과 모든 장애를 증명하지 않는다. 테스트 이름과 준비한 경계를 보고 “무엇을 보장하지 않는가?”도 함께 판단한다.

### Gradle task 연결 문법

- `dependsOn`: 대상 task를 실행하기 전에 필요한 task도 task graph에 포함한다.
- `finalizedBy`: 대상 task가 끝난 뒤 정리·report 성격의 task를 실행하도록 연결한다.
- `shouldRunAfter`: 두 task가 모두 graph에 있을 때 선호 실행 순서를 지정하지만, 그 task 자체를 graph에 추가하지는 않는다.
- `includeTags`와 `excludeTags`: compile 대상이 아니라 JUnit 실행 대상을 tag로 선택한다.
