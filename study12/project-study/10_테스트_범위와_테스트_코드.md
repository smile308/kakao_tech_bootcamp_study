# 10장. 테스트 범위와 테스트 코드

## 10.1 학습 목표

테스트마다 무엇을 진짜로 사용하고 무엇을 가짜로 대체하는지, 그리고 Gradle과 CI가 어디까지 자동 실행하는지 학습한다.

```text
순수 단위 테스트
→ 대상 객체만 생성

Mockito 단위 테스트
→ 대상 객체 + 가짜 의존성

Spring 통합 테스트
→ Spring Context + H2 + 실제 Repository

Redis 통합 테스트
→ Testcontainers + 실제 Redis

CI check
→ 일반 테스트 + Redis 테스트 + JaCoCo 기준
```

## 10.2 테스트의 기본 구조

대부분의 테스트는 다음 세 단계로 읽는다.

```text
Given
→ 필요한 객체와 가짜 응답 준비

When
→ 검사할 메서드 실행

Then
→ 반환값, 상태 변화, 호출 여부 검증
```

테스트 메서드 이름과 `@DisplayName`은 “어떤 조건에서 어떤 결과를 기대하는가”를 먼저 알려준다.

## 10.3 실제 코드 발췌: 순수 단위 테스트

```java
@Test
@DisplayName(
        "발급한 액세스 토큰에서 사용자 ID와 인증 버전을 다시 꺼낼 수 있다"
)
void createAndParseAccessToken() {
    JwtProvider jwtProvider =
            new JwtProvider(SECRET, ONE_HOUR_MILLIS);

    String accessToken =
            jwtProvider.createAccessToken(42L, 3L);

    AccessTokenClaims tokenClaims =
            jwtProvider.getAccessTokenClaims(accessToken);

    assertThat(accessToken).isNotBlank();
    assertThat(tokenClaims.userId()).isEqualTo(42L);
    assertThat(tokenClaims.authVersion()).isEqualTo(3L);
}
```

Spring Context나 DB가 필요하지 않다. 실제 `JwtProvider`를 직접 만들고 입력과 결과만 검사한다.

이 유형은 가장 빠르며 Entity의 상태 변경, Provider의 계산과 검증에 적합하다.

## 10.4 실제 코드 발췌: Mockito 단위 테스트

```java
@ExtendWith(MockitoExtension.class)
class RedisViewCountStoreTest {

    @Mock
    private StringRedisTemplate redisTemplate;

    private RedisViewCountStore store;

    @BeforeEach
    void setUp() {
        ViewCountProperties properties =
                new ViewCountProperties(
                        true,
                        "bamboo:{post-view}:count:",
                        "bamboo:{post-view}:dirty",
                        "bamboo:{post-view}:flush-lock",
                        Duration.ofSeconds(5)
                );

        store = new RedisViewCountStore(
                redisTemplate,
                properties
        );
    }
}
```

중요한 줄:

```java
@Mock
// 실제 Redis에 연결하지 않는 가짜 StringRedisTemplate을 만든다.

@BeforeEach
// 각 테스트 메서드 실행 전에 새로운 대상 상태를 준비한다.
```

행동 설정과 검증:

```java
when(redisTemplate.execute(
        ArgumentMatchers.<RedisScript<Long>>any(),
        eq(List.of(
                "bamboo:{post-view}:count:42",
                "bamboo:{post-view}:dirty"
        )),
        eq("100"),
        eq("42")
)).thenReturn(101L);

long updatedViewCount =
        store.increment(42L, 100L);

assertThat(updatedViewCount).isEqualTo(101L);

verify(redisTemplate).execute(
        ArgumentMatchers.<RedisScript<Long>>any(),
        eq(List.of(
                "bamboo:{post-view}:count:42",
                "bamboo:{post-view}:dirty"
        )),
        eq("100"),
        eq("42")
);
```

```text
when
→ Mock이 어떤 호출을 받으면 무엇을 반환할지 준비

실제 대상 메서드 실행
→ RedisViewCountStore.increment

assertThat
→ 반환 결과 검증

verify
→ 의존성에 기대한 요청을 보냈는지 검증
```

Mock 테스트는 Java 코드의 분기와 협력 순서를 검사하지만 Lua가 실제 Redis에서 동작하는지는 증명하지 못한다.

## 10.5 실제 코드 발췌: Spring·H2 통합 테스트

```java
@SpringBootTest
@Transactional
class PostRepositoryIntegrationTest {

    @Autowired
    private UserRepository userRepository;

    @Autowired
    private PostRepository postRepository;

    @Autowired
    private EntityManager entityManager;
}
```

```text
@SpringBootTest
→ 실제 Spring Context와 Bean 설정을 준비

@Autowired
→ 실제 Repository Bean 주입

@Transactional
→ 각 테스트가 끝날 때 DB 변경 rollback
```

대표 검증:

```java
Page<Post> result = postRepository
        .findByDeletedFalseAndReportCountLessThanOrderByPostIdDesc(
                Post.REPORT_BLOCK_THRESHOLD,
                PageRequest.of(0, 100)
        );

assertThat(result.getContent())
        .extracting(Post::getPostId)
        .contains(visiblePost.getPostId())
        .doesNotContain(hiddenPost.getPostId());
```

이 테스트는 JPQL, Entity mapping, 신고 기준 조건이 H2에서 함께 동작하는지 검사한다.

H2와 MySQL은 서로 다른 DB이므로 H2 통과가 모든 MySQL 전용 동작을 보장하지는 않는다. MySQL migration은 별도로 검토해야 한다.

동시성 검증:

```java
int requestCount = 200;
CountDownLatch startSignal = new CountDownLatch(1);

try (ExecutorService executor =
             Executors.newFixedThreadPool(20)) {
    for (int index = 0; index < requestCount; index++) {
        results.add(executor.submit(() -> {
            startSignal.await();
            return store.increment(42L, 100L);
        }));
    }

    startSignal.countDown();
}

assertThat(
        redisTemplate.opsForValue().get(COUNT_KEY)
).isEqualTo("300");
```

여러 스레드를 한 시점에 출발시켜 실제 Redis Lua의 원자성을 확인한다.

```text

```

Service, Controller, Repository 테스트는 존재하지만 80% 계산 대상에서는 제외된다.

## 10.8 프론트엔드 테스트 범위

현재 `package.json`에는 테스트 스크립트와 테스트 라이브러리가 없다.

CI 검증:

```text
npm ci
→ npm run lint
→ npm run build
```

따라서 현재 자동으로 보장되지 않는 예:

- 버튼 클릭 결과
- 페이징 상태 변화
- 401 후 자동 재요청
- Form 입력과 오류 메시지
- React 컴포넌트 렌더링

lint와 build 성공은 문법·정적 검사와 production bundle 생성 가능성을 확인하지만 사용자 행동이 올바르다는 것을 증명하지 않는다.

## 10.9 어떤 테스트를 어디까지 작성할 것인가?

```text
Entity 내부 상태 규칙
→ 순수 단위 테스트

Service 분기와 Repository 호출 순서
→ Mockito 단위 테스트

JPA query와 mapping
→ Spring DB 통합 테스트

락과 동시 수정
→ 여러 Thread를 사용하는 통합 테스트

Redis 명령·Lua·분산 락·AOF
→ Testcontainers 실제 Redis 테스트

HTTP 보안 경로
→ Security Filter Chain과 MockMvc 테스트
```

모든 메서드를 같은 테스트 유형으로 반복하지 않는다. 실패했을 때 위험한 규칙과 외부 기술의 실제 연동 경계를 중심으로 선택한다.


## 10.9.1 전체 원문 코드 라인별 주석본

아래 주석은 학습을 위해 추가한 것이며 실제 프로젝트 파일에는 없다. 줄 끝 주석을 붙인 주석본은 의미를 따라가기 위한 설명용이므로 그대로 복사해 실행하지 않는다.

### 순수 `JwtProviderTest`

```java
@Test // JUnit이 실행할 하나의 테스트 메서드임을 표시한다.
@DisplayName("발급한 액세스 토큰에서 사용자 ID와 인증 버전을 다시 꺼낼 수 있다") // 테스트 의도를 보고서에 문장으로 표시한다.
void createAndParseAccessToken() { // 발급과 파싱의 정상 흐름을 검사한다.
    JwtProvider jwtProvider = new JwtProvider(SECRET, ONE_HOUR_MILLIS); // Spring 없이 실제 대상 객체를 직접 만든다.

    String accessToken = jwtProvider.createAccessToken(42L, 3L); // 사용자 42와 authVersion 3으로 실제 JWT를 발급한다.
    AccessTokenClaims tokenClaims = jwtProvider.getAccessTokenClaims(accessToken); // 같은 Provider로 서명·만료를 검증하고 claim을 파싱한다.

    assertThat(accessToken).isNotBlank(); // 발급 결과가 빈 문자열이 아닌지 확인한다.
    assertThat(tokenClaims.userId()).isEqualTo(42L); // subject에서 원래 사용자 ID가 복원되는지 확인한다.
    assertThat(tokenClaims.authVersion()).isEqualTo(3L); // custom claim에서 원래 인증 버전이 복원되는지 확인한다.
}
```

### Mockito 준비와 행동 검증

```java
@ExtendWith(MockitoExtension.class) // JUnit 5가 @Mock 필드를 생성하고 관리하도록 Mockito 확장을 연결한다.
class RedisViewCountStoreTest { // 실제 Redis 없이 Java 분기를 검사하는 테스트 클래스다.
    @Mock // 아래 타입의 가짜 객체를 만든다.
    private StringRedisTemplate redisTemplate; // Redis 서버 대신 호출 기록과 설정 응답만 제공한다.

    private RedisViewCountStore store; // 실제로 검사할 대상 객체다.

    @BeforeEach // 각 테스트 전에 매번 실행한다.
    void setUp() { // 공통 대상 객체를 깨끗하게 준비한다.
        ViewCountProperties properties = new ViewCountProperties( // 테스트에 사용할 실제 설정 객체를 만든다.
                true, // 조회수 기능 활성값이다.
                "bamboo:{post-view}:count:", // count key prefix다.
                "bamboo:{post-view}:dirty", // dirty set key다.
                "bamboo:{post-view}:flush-lock", // 분산 락 key다.
                Duration.ofSeconds(5) // flush interval이다.
        );
        store = new RedisViewCountStore(redisTemplate, properties); // Mock Redis와 실제 설정으로 대상 객체를 직접 만든다.
    }
}
```

```java
when(redisTemplate.execute( // Mock의 특정 execute 호출 행동을 미리 정의한다.
        ArgumentMatchers.<RedisScript<Long>>any(), // 어떤 Long 반환 Lua script든 허용한다.
        eq(List.of("bamboo:{post-view}:count:42", "bamboo:{post-view}:dirty")), // key 목록은 정확히 일치해야 한다.
        eq("100"), // DB 기준값 인자는 100이어야 한다.
        eq("42") // 게시글 ID 인자는 42여야 한다.
)).thenReturn(101L); // 조건과 맞는 호출이면 Redis 결과처럼 101을 반환한다.

long updatedViewCount = store.increment(42L, 100L); // 실제 대상 메서드를 실행한다.

assertThat(updatedViewCount).isEqualTo(101L); // 대상이 Mock 반환값을 올바르게 사용자 결과로 전달했는지 확인한다.
verify(redisTemplate).execute( // 대상이 Redis dependency를 실제로 호출했는지 검증한다.
        ArgumentMatchers.<RedisScript<Long>>any(), // script 타입 조건이다.
        eq(List.of("bamboo:{post-view}:count:42", "bamboo:{post-view}:dirty")), // 기대 key 목록이다.
        eq("100"), // 기대 기준값이다.
        eq("42") // 기대 게시글 ID다.
);
```

### Redis Testcontainers

```java
@Tag("redis-integration") // Gradle 일반 test는 제외하고 redisTest가 포함할 태그다.
@Testcontainers // JUnit이 선언된 Testcontainer 생명주기를 관리하게 한다.
class RedisViewCountStoreIntegrationTest { // 실제 Redis 명령과 Lua를 검사한다.
    @Container // 테스트 클래스 실행 전에 컨테이너를 시작하고 끝난 뒤 종료한다.
    private static final GenericContainer<?> REDIS = // 모든 메서드가 공유할 Redis 컨테이너를 선언한다.
            new GenericContainer<>(DockerImageName.parse("redis:7.4-alpine")) // 운영과 같은 Redis image를 선택한다.
                    .withExposedPorts(6379) // container의 Redis 포트를 임의 host port로 공개한다.
                    .waitingFor(Wait.forListeningPort()); // 포트가 실제로 열릴 때까지 테스트 시작을 기다린다.
}
```

```java
int requestCount = 200; // 동시에 발생시킬 전체 증가 요청 수다.
CountDownLatch startSignal = new CountDownLatch(1); // worker들이 같은 시작 신호를 기다리게 한다.

try (ExecutorService executor = Executors.newFixedThreadPool(20)) { // 20개 Thread pool을 만들고 종료도 자동 관리한다.
    for (int index = 0; index < requestCount; index++) { // 총 200개 작업을 등록한다.
        results.add(executor.submit(() -> { // 비동기 증가 작업의 Future를 결과 목록에 추가한다.
            startSignal.await(); // 모든 작업 등록이 끝날 때까지 출발하지 않는다.
            return store.increment(42L, 100L); // 신호 후 실제 Redis 조회수를 증가시킨다.
        }));
    }
    startSignal.countDown(); // 대기 중인 worker를 가능한 같은 시점에 출발시킨다.
}

assertThat(redisTemplate.opsForValue().get(COUNT_KEY)).isEqualTo("300"); // 기준 100에 200회 증가가 모두 보존됐는지 확인한다.
```

## 10.10 스킵할 코드

- Entity 생성자 테스트의 반복되는 getter assertion
- Service 테스트마다 반복되는 Mock 생성 문법
- Testcontainers 연결 객체 생성의 동일 구조
- 테스트용 이메일·닉네임 문자열

다음은 스킵하지 않는다.

- 성공뿐 아니라 실패·경계값 시나리오
- Transaction과 rollback
- 락과 동시성 출발 방식
- Mock으로는 검증되지 않는 실제 Redis 동작
- `test`, `redisTest`, `check`의 포함 범위


## 10.10.1 이 장에서 필요한 JUnit·Mockito·동시성 문법

### 테스트 annotation 생명주기

- `@Test`: 실행할 테스트
- `@BeforeEach`: 각 테스트 전에 실행
- `@AfterEach`: 각 테스트 후 실행
- `@BeforeAll`: 클래스의 모든 테스트 전에 한 번
- `@AfterAll`: 클래스의 모든 테스트 후 한 번
- static `@BeforeAll`은 테스트 객체 생성 전 클래스 수준에서 실행된다.

### Arrange, Act, Assert

코드에 주석이 없어도 다음 경계를 찾아 읽는다.

```text
객체·Mock 준비
→ 대상 메서드 한 번 실행
→ 결과·상태·호출 검증
```

테스트 하나에는 가능한 한 하나의 행동 이유를 둔다.

### AssertJ fluent assertion

```java
assertThat(value)
    .isEqualTo(expected)
    .isNotNull();
```

`assertThat`이 검증 객체를 반환하고 점을 이어 여러 조건을 표현한다.

예외 검증:

```java
assertThatThrownBy(() -> target.call())
    .isInstanceOf(...)
    .hasMessage(...);
```

lambda 안의 실행이 어떤 예외를 던지는지 검사한다.

### Mockito Mock과 Stub

- Mock: 실제 구현 대신 호출을 기록하는 가짜 객체
- Stub: `when(...).thenReturn(...)`으로 특정 입력의 가짜 결과 설정
- `verify`: 기대한 상호작용이 실제 발생했는지 확인
- `verifyNoInteractions`: 의존성을 전혀 호출하지 않았는지 확인

### Matcher

```java
any()
eq("42")
```

- `any`: 해당 타입의 어떤 값도 허용
- `eq`: 기대값과 동등한 값만 허용
- 한 호출의 인자 중 Matcher를 사용하면 나머지도 Matcher 형태로 맞추는 것이 Mockito 규칙이다.

### `@InjectMocks`

Mock 필드를 대상 객체 생성자에 넣어 주는 편의 annotation이다. 직접 생성자를 호출하는 테스트와 목적은 같지만 생성 과정을 Mockito가 돕는다.

### `@SpringBootTest`

실제 애플리케이션과 가까운 Spring Context를 올린다. 테스트는 느려지지만 자동 설정, Bean 연결과 Repository를 함께 검증할 수 있다.

### 테스트 Transaction rollback

Spring Test의 `@Transactional`은 기본적으로 테스트가 끝날 때 rollback한다. 테스트 간 DB 오염을 막는다. 실제 운영 commit 이후 동작까지 동일하게 검증하는 것은 아니므로 commit 경계가 중요한 경우 별도 설계가 필요하다.

### `flush`와 `clear`

- `flush`: JPA 변경 SQL을 즉시 DB에 보냄
- `clear`: 1차 cache의 관리 Entity를 비움

둘을 함께 사용하면 이후 조회가 메모리 Entity가 아니라 실제 DB query 결과인지 더 명확히 확인할 수 있다.

### Generic wildcard `<?>`

```java
GenericContainer<?>
```

정확한 Generic 타입 인자를 현재 코드에서 알 필요가 없거나 사용하지 않음을 나타낸다. 아무 타입이나 대입한다는 의미와 완전히 같지는 않고, 알 수 없는 특정 타입 하나를 뜻한다.

### Thread pool과 Future

- `ExecutorService`: worker Thread pool 관리
- `submit`: 비동기 작업 등록
- `Future`: 나중에 완료될 결과
- `get(timeout, unit)`: 제한 시간 안에 결과 대기

### `CountDownLatch`

여러 Thread가 하나의 count가 0이 될 때까지 기다리게 한다. 테스트에서는 작업을 미리 등록한 뒤 `countDown()`으로 함께 출발시켜 동시 충돌 가능성을 높인다.

### 테스트가 증명하는 범위

Mock 테스트는 대상 Java 분기를 증명하지만 실제 Redis·DB 동작을 증명하지 않는다. 통합 테스트는 실제 연동 범위를 넓히지만 외부 환경, 성능과 모든 장애를 증명하지 않는다. 테스트 이름과 준비한 경계를 보고 “무엇을 보장하지 않는가?”도 함께 판단한다.
