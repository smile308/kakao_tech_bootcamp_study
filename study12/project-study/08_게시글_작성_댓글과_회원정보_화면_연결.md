# 8장. 게시글 작성·댓글과 회원정보 화면 연결

## 8.1 학습 목표

6장까지의 백엔드 API와 7장의 목록 화면 사이에서 빠졌던 실제 사용자 기능을 연결한다. 새 개념을 반복하기보다 이미 배운 `Page → API module → request → Controller → Service → Repository → DTO → state` 구조가 기능별로 어떻게 조합되는지 확인한다.

```text
게시글 작성·수정
PostCreatePage / PostEditPage
→ PostEditor
→ file.js
→ postApi
→ PostController
→ PostService
→ Post·PostImage
→ 목록 또는 상세 페이지 이동

상세 상호작용

→ postApi
→ PostController / CommentController
→ PostService / CommentService

```

## 8.2 게시글 작성 흐름

실제 `PostCreatePage` 핵심 원문:

```jsx
<PostEditor
    mode="create"
    onSubmit={async (payload) => {
        await postApi.createPost(payload);
        navigate("/posts", { replace: true });
    }}
/>
```

라인별 주석본:

```jsx
<PostEditor // 제목·내용·이미지를 입력받는 공용 작성·수정 form component를 렌더링한다.
    mode="create" // 수정 화면이 아니라 새 게시글 작성 방식으로 표시하라고 전달한다.
    onSubmit={async (payload) => { // PostEditor 검증이 끝난 payload를 받을 비동기 callback을 전달한다.
        await postApi.createPost(payload); // POST /posts가 성공할 때까지 기다린다.
        navigate("/posts", { replace: true }); // 성공하면 목록으로 이동하고 작성 화면 history를 현재 항목으로 교체한다.
    }}
/>
```

`PostEditor`가 담당하는 실제 순서는 다음과 같다.

```text
input을 controlled state에 저장
→ submit 기본 동작 방지
→ title·content trim
→ 비어 있는 값 검사
→ 첨부 개수·type·크기 검사
→ 각 File을 Data URL 문자열로 비동기 변환
→ { title, content, imageFiles } 생성
→ 부모가 전달한 onSubmit 호출
→ 처리 중 버튼 잠금
→ 실패하면 공통 오류 메시지를 form 아래에 표시
```

실제 `handleSubmit` 원문:

```jsx
async function handleSubmit(event) {
    event.preventDefault();
    const title = form.title.trim();
    const content = form.content.trim();
    const imageError = getPostImageFilesError(files);

    if (!title || !content) {
        setError("*글 제목과 이야기 내용을 모두 작성해주세요.");
        return;
    }

    if (imageError) {
        setError(`*${imageError}`);
        return;
    }

    try {
        setIsSubmitting(true);
        setError("");
        const imageFiles = files.length
            ? await Promise.all(files.map(fileToDataUrl))
            : initialValues?.imageUrls ?? [];
        await onSubmit({ title, content, imageFiles });
    } catch (submitError) {
        setError(`*${getErrorMessage(submitError, "요청 처리에 실패했습니다.")}`);
    } finally {
        setIsSubmitting(false);
    }
}
```

라인별 주석본:

```jsx
async function handleSubmit(event) { // form submit event를 처리하고 FileReader와 API callback을 기다리는 함수다.
    event.preventDefault(); // browser의 기본 form 전송과 새로고침을 막는다.
    const title = form.title.trim(); // 제목 양끝 공백을 제거한 전송값을 만든다.
    const content = form.content.trim(); // 본문 양끝 공백을 제거한 전송값을 만든다.
    const imageError = getPostImageFilesError(files); // 현재 선택된 모든 이미지의 개수·type·크기를 다시 검사한다.

    if (!title || !content) { // 공백 제거 후 제목이나 본문이 빈 문자열인지 검사한다.
        setError("*글 제목과 이야기 내용을 모두 작성해주세요."); // form에 입력 오류를 표시한다.
        return; // API를 호출하지 않고 submit 처리를 끝낸다.
    }

    if (imageError) { // 이미지 검사 함수가 오류 문구를 반환했는지 확인한다.
        setError(`*${imageError}`); // 해당 오류를 form에 표시한다.
        return; // 잘못된 파일을 전송하지 않는다.
    }

    try { // 변환 또는 부모의 API callback 실패를 한곳에서 처리한다.
        setIsSubmitting(true); // 중복 submit을 막고 버튼에 처리 중 상태를 표시한다.
        setError(""); // 이전 오류 문구를 지운다.
        const imageFiles = files.length // 새로 선택한 파일이 있는지에 따라 전송 이미지를 결정한다.
            ? await Promise.all(files.map(fileToDataUrl)) // 모든 File을 Data URL로 동시에 변환하고 전부 끝날 때까지 기다린다.
            : initialValues?.imageUrls ?? []; // 새 파일이 없으면 수정 화면의 기존 이미지 또는 빈 배열을 유지한다.
        await onSubmit({ title, content, imageFiles }); // 페이지가 전달한 작성 또는 수정 API callback을 호출한다.
    } catch (submitError) { // File 변환이나 API 요청이 실패하면 실행한다.
        setError(`*${getErrorMessage(submitError, "요청 처리에 실패했습니다.")}`); // 서버 error code를 사용자 문구로 바꿔 표시한다.
    } finally { // 성공·실패와 관계없이 실행한다.
        setIsSubmitting(false); // 다시 submit할 수 있게 처리 중 상태를 해제한다.
    }
}
```

백엔드는 `PostController.createPost`에서 인증 사용자의 ID와 DTO를 `PostService.createPost`에 넘긴다. Service는 이미지 Data URL을 다시 검증하고, 활성 사용자를 조회하고, `Post`를 만든 뒤 `replaceImages`로 `PostImage` collection을 구성한다. 프론트 검증은 사용성을 위한 빠른 검사이고 백엔드 검증이 실제 보안 경계다.

## 8.3 게시글 수정과 version 전달

수정 화면은 먼저 `GET /posts/{postId}`로 원문을 받는다. 작성자가 아니거나 신고 차단 기준 이상이면 상세 화면으로 돌려보낸다. 정상일 때만 `PostEditor`의 `initialValues`로 값을 전달한다.

```text
PostEditPage mount
→ AbortController 생성
→ postApi.getPost(postId)
→ 작성자·신고 수 검사
→ originalPost state
→ PostEditor initialValues
→ 수정 submit
→ payload에 originalPost.version 추가
→ PATCH /posts/{postId}
→ Service가 작성자·현재 version 검사
→ Entity update
→ 상세 화면 이동
```

`version`은 화면을 열어둔 사이 다른 요청이 게시글을 바꿨는지 찾기 위한 값이다. 프론트가 읽었던 version을 다시 보내고, Service가 현재 Entity version과 다르면 `PostVersionConflictException`을 발생시킨다. 내용이 우연히 같아 JPA가 변경을 감지하지 못하는 고정 게시글 수정에는 `OPTIMISTIC_FORCE_INCREMENT`로 version 증가를 강제한다.

## 8.4 상세 화면은 서버 응답 전체를 매번 다시 받지 않는다

첫 상세 조회에서는 게시글과 댓글을 함께 받는다.

```text
postApi.getPost
→ normalizeDetailPost
→ setPost(result)
→ setComments(result.comments)
→ PostDetailCard와 CommentSection에 각각 전달
```

그 뒤 좋아요·신고·댓글 작업은 성공 응답을 이용해 관련 state만 바꾼다.

실제 좋아요 handler 원문:

```jsx
async function handleLike() {
    if (likeRequestRef.current) {
        return;
    }

    try {
        likeRequestRef.current = true;
        setIsLikeSubmitting(true);
        const result = post.isLiked
            ? await postApi.unlikePost(post.postId)
            : await postApi.likePost(post.postId);
        setPost((previous) => ({
            ...previous,
            isLiked: !previous.isLiked,
            likeCount: result?.likeCount ?? previous.likeCount + (previous.isLiked ? -1 : 1),
        }));
    } catch (likeError) {
        window.alert(getErrorMessage(likeError, "좋아요 처리에 실패했습니다."));
    } finally {
        likeRequestRef.current = false;
        setIsLikeSubmitting(false);
    }
}
```

라인별 주석본:

```jsx
async function handleLike() { // 현재 좋아요 상태에 따라 등록 또는 취소 API를 호출한다.
    if (likeRequestRef.current) { // 이미 좋아요 요청이 진행 중인지 즉시 확인한다.
        return; // 빠른 연속 클릭으로 같은 요청이 겹치지 않게 한다.
    }

    try { // API 성공 뒤 state 반영까지 한 작업으로 묶는다.
        likeRequestRef.current = true; // render를 기다리지 않고 동기적으로 요청 진행 표시를 기록한다.
        setIsLikeSubmitting(true); // 버튼 비활성화 등 화면 표시용 state도 갱신한다.
        const result = post.isLiked // 현재 게시글을 이미 좋아요 했는지 확인한다.
            ? await postApi.unlikePost(post.postId) // 좋아요 상태면 DELETE 요청을 보낸다.
            : await postApi.likePost(post.postId); // 아니면 POST 요청을 보낸다.
        setPost((previous) => ({ // 가장 최신 게시글 state를 기준으로 새 객체를 만든다.
            ...previous, // 제목·본문 등 바꾸지 않는 속성을 복사한다.
            isLiked: !previous.isLiked, // 좋아요 여부를 반대로 바꾼다.
            likeCount: result?.likeCount ?? previous.likeCount + (previous.isLiked ? -1 : 1), // 서버 count가 있으면 사용하고 없을 때만 기존 값으로 계산한다.
        }));
    } catch (likeError) { // 좋아요 등록·취소 요청이 실패하면 실행한다.
        window.alert(getErrorMessage(likeError, "좋아요 처리에 실패했습니다.")); // 공통 오류 변환 결과를 사용자에게 알린다.
    } finally { // 성공·실패 모두에서 실행한다.
        likeRequestRef.current = false; // 다음 좋아요 요청을 허용한다.
        setIsLikeSubmitting(false); // 화면의 처리 중 상태를 해제한다.
    }
}
```

`likeRequestRef`는 event가 연속해서 들어오는 바로 그 순간의 중복 요청 방지이고, 백엔드의 unique 제약과 row lock은 여러 browser·여러 server 요청까지 포함한 데이터 정합성 장치다. 둘은 같은 범위를 막지 않는다.

## 8.5 신고·삭제와 ConfirmModal

`openModal`은 실행할 함수를 바로 호출하지 않고 `{ title, description, onConfirm }` 객체로 state에 저장한다. 사용자가 확인을 누르면 `confirmModal`이 저장된 함수를 꺼내 실행한다.

```text
신고 버튼
→ requestReport가 modal state 설정
→ ConfirmModal 렌더링
→ 확인 클릭
→ confirmModal
→ postApi.reportPost
→ reportCount가 차단 기준이면 목록 이동
→ 아니면 isReported와 reportCount만 갱신
```

게시글 삭제도 같은 modal 구조를 재사용하지만 `version`을 body에 넣고 성공하면 목록으로 이동한다. `ConfirmModal`, `ActionButton`처럼 표시와 click 전달만 담당하는 공통 UI는 이 제어 흐름을 이해한 뒤 내부 JSX를 혼자 읽어도 된다.

## 8.6 댓글 작성·수정·삭제 전체 흐름

```text
CommentSection
→ CommentEditor submit
→ postApi.createComment 또는 updateComment
→ CommentController
→ CommentService
→ 사용자·게시글·댓글 소유권 검사
→ PostCounter replyCount 변경
→ Comment 저장·변경·삭제
→ CommentResponseDto
→ normalizeComment
→ PostDetailPage callback
→ comments 배열 append·map·filter
```

작성은 새 댓글을 배열 뒤에 붙이고, 수정은 같은 `commentId` 항목만 교체하며, 삭제는 같은 ID를 배열에서 제외한다. `CommentList`와 `CommentItem`은 이 배열을 `map`으로 화면에 옮기고 수정·삭제 callback을 다시 위로 전달하는 표시 계층이다.

백엔드 `CommentService`가 `postId`와 `commentId`를 모두 확인하는 이유는 URL의 게시글 A 아래에 게시글 B의 댓글 ID를 넣는 조작을 막기 위해서다. 댓글 작성·삭제가 `PostCounter.replyCount`도 함께 바꾸므로, 게시글이 동시에 삭제되는 상황을 lock을 통해 다시 확인한 뒤 transaction을 commit한다.

현재 댓글 요청은 게시글 요청과 검증 구성이 다르다. `CommentController`의 세 method는 `@RequestBody`만 사용하고 `@Valid`는 사용하지 않으며, 댓글 request DTO에도 길이·빈 문자열 검증 annotation이 없다. 따라서 프론트 form 검사를 우회한 직접 API 요청의 빈 댓글을 backend DTO 검증이 차단하는 구조는 아니다. 이 문서는 현재 코드 흐름을 그대로 설명하며, 댓글 입력 검증을 이미 구현된 것으로 간주하지 않는다.

## 8.7 응답 정규화가 API module에 있는 이유

실제 `normalizeDetailPost` 원문:

```js
export function normalizeDetailPost(post) {
    return {
        postId: post?.postId ?? null,
        version: post?.version ?? null,
        title: post?.title ?? "",
        content: post?.content ?? "",
        imageUrls: normalizeImageUrls(post?.imageUrls),
        likeCount: post?.likeCount ?? 0,
        reportCount: post?.reportCount ?? 0,
        commentCount: post?.commentCount ?? 0,
        viewCount: post?.viewCount ?? 0,
        createdAt: post?.createdAt ?? "",
        isMine: post?.isMine === true,
        isLiked: post?.isLiked === true,
        isReported: post?.isReported === true,
        comments: Array.isArray(post?.comments)
            ? post.comments.map(normalizeComment)
            : [],
    };
}
```

라인별 의미는 모든 field에 반복되는 두 규칙으로 묶는다.

- `post?.field ?? 기본값`: 응답 객체나 값이 `null`·`undefined`여도 화면이 사용할 안정적인 기본값을 만든다.
- `flag === true`: truthy 값 전체가 아니라 실제 boolean `true`만 화면의 참으로 인정한다.
- 배열은 `Array.isArray`로 확인하고, 댓글 각각에도 `normalizeComment`를 적용한다.

이 파일은 서버 DTO를 수정하는 곳이 아니다. 서버 응답을 받은 뒤 프론트 전체가 기대할 한 가지 모양으로 바꾸는 경계다. 그래서 Page와 표시 Component가 매번 null 검사를 반복하지 않는다.

## 8.8 회원정보 조회·수정·탈퇴 흐름

```text
ProfileEditPage mount
→ userApi.getMyInfo({ signal })
→ GET /users/me
→ UserService.getMyInfo
→ user·nickname·preview state 초기화

수정 submit
→ nickname frontend 검사
→ 새 File이 있으면 Data URL 변환
→ PATCH /users
→ 다른 활성 사용자의 nickname 중복 검사
→ backend image 검사
→ User.update dirty checking
→ 성공 후 현재 화면 state와 Toast 갱신

탈퇴 확인
→ DELETE /users
→ User soft delete
→ 활성 AuthSession 전체 revoke
→ Refresh Cookie 만료
→ local Access Token 삭제
→ /login 이동
```

프로필 조회 Effect의 `AbortController`는 화면을 떠난 뒤 늦은 응답이 state를 바꾸는 것뿐 아니라 진행 중인 fetch 자체를 취소한다. `toastTimerRef` cleanup은 페이지가 사라진 뒤 timer callback이 실행되는 것을 막는다. 두 cleanup은 대상 자원이 서로 다르다.

## 8.9 비밀번호 변경은 왜 다시 로그인하게 하는가?

```text
PasswordEditPage local validation
→ PATCH /users/password
→ 현재 비밀번호 PasswordEncoder.matches
→ 새 비밀번호 encode
→ User.changePassword가 authVersion 증가
→ 활성 Refresh Session 전부 revoke
→ Refresh Cookie 만료
→ 프론트 Access Token 삭제
→ 로그인 화면 이동
```

기존 Access Token 안에는 발급 당시 `authVersion`이 들어 있다. 비밀번호 변경 뒤 DB의 값이 증가하므로 `JwtAuthenticationFilter`가 예전 token을 더 이상 인증하지 않는다. Refresh Session도 모두 폐기하므로 탈취되었을 수 있는 기존 token 쌍을 함께 무효화한다.

## 8.10 이 장에서 언급만 하고 넘어가는 코드

- `PostImagePicker`, `ProfileImagePicker`: `<input type="file">`과 미리보기 표시를 담당한다. 파일 검증과 Data URL 변환은 `utils/file.js`에서 이미 설명했다.
- `PostDetailCard`, `PostMetricCard`, `ActivityBars`, `AuthorSummary`: 받은 게시글 값을 배치하는 표시 Component다.
- `CommentList`, `CommentItem`: 댓글 배열을 반복 렌더링하고 callback을 위·아래로 전달한다.
- `ProfileEditForm`, `PasswordEditForm`: Page가 소유한 state와 handler를 input에 연결한다.
- `Toast`, `InfoBanner`, `LogoMark`, `Avatar`, `AppLink`, `ActionButton`: 표시나 단일 click 전달만 담당하며 새로운 데이터 흐름은 만들지 않는다.
- CSS와 font·SVG asset: 화면 모양을 담당하고 API·state·DB 흐름에는 참여하지 않는다.

스킵한다는 것은 존재를 무시한다는 뜻이 아니다. 위 파일들은 어느 Page에서 어떤 props를 받아 표시하는지까지만 확인하고, 이미 배운 controlled input·조건부 rendering·`map` 문법을 다시 설명하지 않는다는 뜻이다.

## 8.11 기능 코드를 작성하는 순서

현재 결과물을 역으로 읽을 때는 화면부터 따라가지만, 새 기능은 보통 다음 순서로 설계하면 연결 누락을 줄일 수 있다.

```text
1. 사용자 행동과 HTTP 계약 결정
2. Request·Response DTO와 validation 결정
3. Entity 상태와 DB 제약 확인
4. Repository query·lock 결정
5. Service transaction과 업무 규칙 작성
6. Controller endpoint 연결
7. frontend API module 작성
8. Page에서 state·loading·error·cleanup 작성
9. 표시 Component로 props 전달
10. 단위·통합·동시성 테스트 작성
11. 운영 설정·migration·배포 영향 확인
```

실제 수정 작업에서는 migration을 Entity보다 먼저 작성할 수도 있고 테스트를 먼저 작성할 수도 있다. 중요한 것은 각 단계의 계약이 앞뒤 파일에서 동일한지 확인하는 것이다.
