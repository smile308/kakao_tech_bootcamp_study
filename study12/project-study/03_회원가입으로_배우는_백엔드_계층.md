# 3장. 회원가입으로 배우는 백엔드 계층

## 3.1 학습 목표

회원가입 하나를 끝까지 추적하며 DTO, Controller, Service, Repository, Entity의 작성 순서와 책임을 구분한다.

```text
프론트 입력
→ authApi.signup
→ POST /users
→ UserRequestDto
→ UserController
→ UserService
→ UserRepository로 중복·신고 이력 조회
→ User Entity 생성
→ UserRepository.save
→ JPA가 새 Entity를 persistence 처리
→ UserResponseDto
→ Service method 종료 시 transaction commit
→ JSON HTTP 응답
```

`POST /users`도 Controller 앞의 Spring Security Filter를 거친다. 현재 `SecurityConfig`가 이 요청을 `permitAll()`로 허용하므로 로그인 토큰 없이 회원가입할 수 있다. Filter와 인증 설정은 5장에서 다시 다룬다.

## 3.2 실제 코드 발췌: 요청 DTO

파일: `dto/user/UserRequestDto.java`

```java
@Getter
@NoArgsConstructor
public class UserRequestDto {
    @NotBlank
    @Email
    private String email;

    @NotBlank
    @Pattern(regexp = "^(?=.*[A-Z])(?=.*[a-z])(?=.*\\d)(?=.*[!@#$%^&*()_+\\-=\\[\\]{};':\"\\\\|,.<>\\/?~]).{8,20}$")
    private String password;
    @NotBlank
    @Pattern(regexp = "^(?=.*[A-Z])(?=.*[a-z])(?=.*\\d)(?=.*[!@#$%^&*()_+\\-=\\[\\]{};':\"\\\\|,.<>\\/?~]).{8,20}$")
    private String passwordCheck;
    @NotBlank
    @Size(max = 10)
    //공백 제거 조건
    @Pattern(regexp = "^\\S+$")
    private String nickname;
    private String profileImage;


}
```

중요한 줄:

```java
@Getter                    // JSON으로 받은 값을 Service가 getter로 읽게 한다.
@NoArgsConstructor         // JSON을 객체로 바꿀 때 사용할 기본 생성자를 제공한다.
@NotBlank                  // null, 빈 문자열, 공백 문자열을 거부한다.
@Email                     // 이메일 형식인지 검사한다.
@Pattern(...)              // 비밀번호 조합이나 닉네임 공백 규칙을 검사한다.
```

DTO는 DB 테이블이 아니다. HTTP 요청으로 받을 데이터 모양과 1차 검증 규칙을 표현한다.

## 3.3 실제 코드 발췌: Controller

파일: `controller/UserController.java`

```java
@RestController
@RequestMapping("/users")
@RequiredArgsConstructor
public class UserController {
    private final UserService userService;
    private final RefreshCookieProvider refreshCookieProvider;

    //회원가입
    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public UserResponseDto createUser(@Valid @RequestBody UserRequestDto request){
        return userService.createUser(request);
    }
```

이 블록은 실제 파일의 class 선언부터 `createUser` method까지 연속된 원문이다. class는 뒤에 다른 회원 API method가 계속되므로 이 발췌에서 마지막 class 닫는 중괄호는 보이지 않는다. `refreshCookieProvider`는 회원 탈퇴·비밀번호 수정 API에서 사용하며 회원가입 method에서는 사용하지 않는다.

중요한 줄:

```java
@RestController                       // @Controller와 @ResponseBody를 합친 어노테이션으로, Spring MVC Controller Bean으로 등록하고 method 반환값을 HTTP response body에 쓴다.
@RequestMapping("/users")             // class 안 모든 endpoint의 공통 경로를 /users로 지정한다.
@PostMapping                         // POST /users 요청과 연결된다.
@Valid @RequestBody UserRequestDto   // JSON을 DTO로 변환한 뒤 검증한다.
@ResponseStatus(HttpStatus.CREATED)  // 성공 응답 상태를 201로 지정한다.
```

Controller는 비밀번호 일치나 이메일 중복 같은 업무 규칙을 직접 검사하지 않고 Service에 위임한다.

## 3.4 실제 코드 발췌: Service

파일: `service/UserService.java`

회원가입 method에 적용되는 class 설정과 dependency 원문:

```java
@Service
@RequiredArgsConstructor
@Transactional
public class UserService {
    private final UserRepository userRepository;
    private final AuthSessionRepository authSessionRepository;
    private final PasswordEncoder passwordEncoder;
```

`authSessionRepository`는 다른 회원 기능에서 사용하며 `createUser` method에서는 사용하지 않는다. 다음은 실제 `createUser` method 원문이다.

```java
    public UserResponseDto createUser(UserRequestDto request) {
        // 비밀번호 확인
        if (!request.getPassword().equals(request.getPasswordCheck())) {
            throw new InvalidRequestException("Invalid_Password");
        }

        // 활성 이메일 중복 체크
        if (userRepository.existsByEmailAndDeletedFalse(request.getEmail())) {
            throw new InvalidRequestException("Existed_Email");
        }

        // 활성 닉네임 중복 체크
        if (userRepository.existsByNicknameAndDeletedFalse(request.getNickname())) {
            throw new InvalidRequestException("Existed_Nickname");
        }

        // 추가: 같은 이메일의 삭제 계정까지 포함해서 기존 누적 신고 수 조회
        int previousReceivedReportCount =
                userRepository.findMaxReceivedReportCountByEmailIncludingDeleted(
                        request.getEmail()
                );

        if (previousReceivedReportCount >= User.SUSPENSION_REPORT_THRESHOLD) {
            throw new InvalidRequestException("Suspended_Account");
        }

        ImageDataUrlValidator.validateProfileImage(request.getProfileImage());

        User user = new User(
                request.getEmail(),
                passwordEncoder.encode(request.getPassword()),
                request.getNickname(),
                request.getProfileImage(),
                previousReceivedReportCount
        );

        User savedUser = userRepository.save(user);

        return new UserResponseDto(savedUser);
    }
```

작업 순서는 임의가 아니다.

```text
비밀번호 확인 일치
→ 활성 이메일 중복 확인
→ 활성 닉네임 중복 확인
→ 탈퇴 계정을 포함한 누적 신고 수 확인
→ 정지 기준 확인
→ 프로필 이미지 검증
→ 비밀번호 암호화
→ Entity 생성
→ DB 저장
→ 응답 DTO 생성
```

`passwordEncoder.encode`를 통과한 값만 Entity에 넣으므로 DB에는 비밀번호 원문을 저장하지 않는다.

class에 붙은 `@Transactional`로 인해 `createUser` 전체가 하나의 transaction으로 실행된다. `save` 호출은 새 Entity를 JPA에 persistence한다. 현재 `userId`는 `IDENTITY` 생성 방식이므로 Hibernate는 생성된 ID를 얻기 위해 보통 `persist`/`save` 과정에서 `INSERT`를 실행한다. 그러나 transaction의 **commit**은 Service method가 정상 종료될 때 이루어지므로 `save = commit`으로 이해하면 안 된다.

현재 이메일·닉네임 중복 검사는 저장 전에 따로 실행하는 존재 조회다. 프로젝트의 Entity mapping과 현재 Flyway file에서는 이메일·닉네임 unique 제약을 확인할 수 없다. 따라서 **이 저장소의 코드만으로는** 동시에 같은 값으로 들어온 두 요청을 DB unique 제약이 막는다고 보장할 수 없다. 기존 RDS에 수동으로 만든 제약이 있는지는 실제 DB schema를 별도로 확인해야 한다.

## 3.5 실제 코드 발췌: Repository

파일: `repository/UserRepository.java`

```java
public interface UserRepository extends JpaRepository<User, Long> {

    Optional<User> findByUserIdAndDeletedFalse(Long userId);

    boolean existsByEmailAndDeletedFalse(String email);

    boolean existsByNicknameAndDeletedFalse(String nickname);

    boolean existsByNicknameAndDeletedFalseAndUserIdNot(String nickname, Long userId);

    Optional<User> findByEmailAndDeletedFalse(String email);

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("""
            SELECT user
            FROM User user
            WHERE user.userId = :userId
            """)
    Optional<User> findByUserIdForUpdate(@Param("userId") Long userId);

    @Query(
            value = """
                    SELECT COALESCE(MAX(received_report_count), 0)
                    FROM users
                    WHERE email = :email
                    """,
            nativeQuery = true
    )
    int findMaxReceivedReportCountByEmailIncludingDeleted(@Param("email") String email);
}
```

위 블록은 interface 본문의 실제 원문 전체다. `findByUserId...`, `findByEmail...`, `findByUserIdForUpdate`는 다른 회원·인증·신고 흐름에서 사용하는 Repository method이며, 회원가입에서는 중복 검사 두 method와 누적 신고 수 조회 method를 사용한다.

`findByUserIdForUpdate` 자체는 **회원가입 코드가 아니라 게시글 신고 코드**에서 작성자의 누적 신고 수를 안전하게 증가시키려고 사용한다. Repository의 `@Lock` 설정은 “이 조회를 DB write lock과 함께 실행하라”는 방식을 지정하고, Service의 `@Transactional` 범위가 그 lock을 commit·rollback까지 유지한다. 동시 신고에서 왜 필요한지는 6장 `6.8 신고 흐름`에서 실제 `PostService.reportPost` 순서와 함께 자세히 다룬다.

`findByUserIdForUpdate` 위의 JPQL을 한 줄씩 풀면 다음과 같다.

```text
SELECT user
→ 조회 결과로 user라는 별칭의 User Entity 객체를 반환한다.

FROM User user
→ DB table 이름이 아니라 Java Entity class인 User를 조회 대상으로 잡고, 이 쿼리 안에서 user라는 별칭으로 부른다.

WHERE user.userId = :userId
→ user Entity의 userId field가 `:userId` 인자와 같은 Entity만 남긴다.

@Param("userId") Long userId
→ Java method의 userId 값을 JPQL의 `:userId` 자리에 전달한다.
```

예를 들어 method에 `userId=10`이 전달되면 의미는 “`User` Entity 중 `userId`가 10인 객체를 조회하라”다. 여기에 `@Lock(PESSIMISTIC_WRITE)`가 함께 적용되므로, transaction이 끝날 때까지 다른 transaction이 해당 row를 동시에 수정하는 것을 제어하기 위한 write lock을 DB에 요청한다.

`findMaxReceivedReportCountByEmailIncludingDeleted` 위의 native SQL도 한 줄씩 풀면 다음과 같다.

```text
SELECT COALESCE(MAX(received_report_count), 0)
→ 조건에 맞는 row들의 received_report_count 최댓값을 구한다. row가 없어 MAX 결과가 null이면 COALESCE가 0으로 바꾼다.

FROM users
→ User Entity 이름이 아니라 실제 DB의 users table을 조회한다.

WHERE email = :email
→ users table의 email column이 `:email` 인자와 같은 row만 계산에 포함한다. deleted 조건이 없으므로 탈퇴 계정도 포함된다.

@Param("email") String email
→ Java method로 받은 email 값을 SQL의 `:email` 자리에 전달한다.
```

중요한 줄:

```java
extends JpaRepository<User, Long>
// User Entity와 Long 기본키를 대상으로 기본 CRUD 구현을 Spring Data JPA가 제공한다.

existsByEmailAndDeletedFalse(...)
// 메서드 이름을 분석해 email이 같고 deleted가 false인 행의 존재 여부를 조회한다.

nativeQuery = true
// JPQL이 아니라 실제 DB 테이블과 컬럼 이름을 사용하는 SQL이다.
```

Repository는 DB 연결 주소를 설정하지 않는다. 이미 만들어진 DataSource와 JPA 설정을 이용해 쿼리를 수행한다.

## 3.5.1 실제 코드 발췌: Entity와 응답 DTO

파일: `entity/User.java`

회원가입에서 사용하는 field와 constructor의 실제 원문:

```java
@Getter
@Entity
@Table(name = "users")
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class User {
    public static final int SUSPENSION_REPORT_THRESHOLD = 10;

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "user_id")
    private Long userId;

    @Column(nullable = false)
    private String email;

    @Column(nullable = true, unique = false, length = 255)
    private String password;

    @Column(nullable = false, length = 10)
    private String nickname;

    @Lob
    @Column(name = "profile_image", columnDefinition = "LONGTEXT")
    private String profileImage;

    @Column(name = "received_report_count", nullable = false)
    private int receivedReportCount;

    @Column(name ="deleted", nullable = false)
    private boolean deleted;

    @Column(name = "auth_version", nullable = false)
    private long authVersion;

    public User(
            String email,
            String password,
            String nickname,
            String profileImage,
            int receivedReportCount
    ) {
        this.email = email;
        this.password = password;
        this.nickname = nickname;
        this.profileImage = profileImage;
        this.receivedReportCount = receivedReportCount;
        this.deleted = false;
        this.authVersion = 0L;
    }
```

이것은 class 시작부터 회원가입이 사용하는 첫 번째 constructor까지의 연속된 원문이다. class 뒤의 다른 constructor와 수정·탈퇴·신고 method는 그 기능을 배울 때 다룬다.

파일: `dto/user/UserResponseDto.java`

```java
@Getter
@NoArgsConstructor
public class UserResponseDto {
    private Long userId;
    private String message;

    public UserResponseDto(User user){
        this.message = "signup_success";
        this.userId=user.getUserId();
    }
}
```

Entity는 `users` table에 저장할 상태와 상태 변경 규칙을 표현한다. `UserResponseDto`는 Entity 전체를 노출하지 않고 생성된 `userId`와 성공 message만 HTTP 응답으로 보낸다. 암호화된 비밀번호도 응답에 포함하지 않는다.

## 3.6.1 전체 원문 코드 라인별 주석본

아래 주석은 학습을 위해 추가한 것이며 실제 프로젝트 파일에는 없다. 줄 끝 주석을 붙인 주석본은 의미를 따라가기 위한 설명용이므로 그대로 복사해 실행하지 않는다.

### `UserRequestDto`

```java
@Getter // Service가 각 요청 필드를 getter로 읽을 수 있게 Lombok이 메서드를 생성한다.
@NoArgsConstructor // Jackson이 JSON을 DTO 객체로 만들 때 사용할 기본 생성자를 만든다.
public class UserRequestDto { // 회원가입 HTTP 요청의 데이터 모양을 선언한다.
    @NotBlank // null, 빈 문자열, 공백뿐인 이메일을 거부한다.
    @Email // 문자열이 이메일 형식인지 검사한다.
    private String email; // 요청 JSON의 email 값을 보관한다.

    @NotBlank // 비밀번호가 반드시 입력되어야 한다.
    @Pattern(regexp = "^(?=.*[A-Z])(?=.*[a-z])(?=.*\\d)(?=.*[!@#$%^&*()_+\\-=\\[\\]{};':\"\\\\|,.<>\\/?~]).{8,20}$") // 대·소문자, 숫자, 특수문자를 포함한 8~20자인지 검사한다.
    private String password; // 실제 새 비밀번호를 보관한다.

    @NotBlank // 비밀번호 확인값도 반드시 입력되어야 한다.
    @Pattern(regexp = "^(?=.*[A-Z])(?=.*[a-z])(?=.*\\d)(?=.*[!@#$%^&*()_+\\-=\\[\\]{};':\"\\\\|,.<>\\/?~]).{8,20}$") // 확인값에도 같은 형식 규칙을 적용한다.
    private String passwordCheck; // password와 일치하는지 Service에서 비교할 값을 보관한다.

    @NotBlank // 닉네임은 필수다.
    @Size(max = 10) // 닉네임 길이를 최대 10자로 제한한다.
    @Pattern(regexp = "^\\S+$") // 문자열 안의 모든 공백 문자를 금지한다.
    private String nickname; // 사용자에게 표시할 닉네임을 보관한다.

    private String profileImage; // 선택 입력인 프로필 이미지 Data URL을 보관한다.
}
```

### `UserController.createUser`

```java
@RestController // @Controller + @ResponseBody로, 이 class를 Spring MVC Controller Bean으로 등록하고 method 반환값을 HTTP response body에 쓴다.
@RequestMapping("/users") // class 안 endpoint의 공통 URL을 /users로 지정한다.
@RequiredArgsConstructor // final field를 모두 인자로 받는 constructor를 Lombok이 생성한다.
public class UserController { // 회원 HTTP 요청을 담당하는 class를 선언한다.
    private final UserService userService; // 회원 업무를 위임할 Service dependency를 보관한다.
    private final RefreshCookieProvider refreshCookieProvider; // 다른 회원 API에서 Refresh Cookie를 만들거나 만료시킬 때 사용한다.

    //회원가입 // 이 method의 용도를 적은 원문 주석이다.
@PostMapping // 클래스의 /users와 결합해 POST /users 요청을 이 메서드에 연결한다.
@ResponseStatus(HttpStatus.CREATED) // 정상 반환 시 HTTP 상태를 201 Created로 만든다.
public UserResponseDto createUser(@Valid @RequestBody UserRequestDto request){ // JSON body를 DTO로 변환·검증하고 성공 시 응답 DTO를 반환하는 method다.
    return userService.createUser(request); // 실제 회원가입 규칙은 Service에 맡기고 결과를 그대로 반환한다.
}
```

### `UserService.createUser`

```java
@Service // 이 class를 업무 로직을 담당하는 Spring Bean으로 등록한다.
@RequiredArgsConstructor // 아래 final dependency를 인자로 받는 constructor를 생성한다.
@Transactional // public method 전체를 기본적으로 DB transaction 범위에서 실행하게 한다.
public class UserService { // 회원 업무 규칙을 담는 class를 선언한다.
    private final UserRepository userRepository; // User 조회·저장을 요청할 Repository다.
    private final AuthSessionRepository authSessionRepository; // 비밀번호 변경·탈퇴 시 session을 취소할 Repository로, 회원가입에서는 사용하지 않는다.
    private final PasswordEncoder passwordEncoder; // 비밀번호 원문을 BCrypt hash로 변환할 dependency다.

public UserResponseDto createUser(UserRequestDto request) { // 검증된 요청 DTO를 받아 회원가입 Transaction을 수행한다.
    // 비밀번호 확인 // 이하 비밀번호 비교의 용도를 적은 원문 주석이다.
    if (!request.getPassword().equals(request.getPasswordCheck())) { // 비밀번호와 확인값이 서로 다른지 검사한다.
        throw new InvalidRequestException("Invalid_Password"); // 다르면 회원가입을 중단하고 400으로 변환될 예외를 던진다.
    }

    // 활성 이메일 중복 체크 // 삭제되지 않은 계정의 이메일만 중복 확인한다는 원문 주석이다.
    if (userRepository.existsByEmailAndDeletedFalse(request.getEmail())) { // 같은 이메일의 활성 계정이 있는지 DB에 묻는다.
        throw new InvalidRequestException("Existed_Email"); // 활성 이메일 중복이면 저장하지 않는다.
    }

    // 활성 닉네임 중복 체크 // 삭제되지 않은 계정의 닉네임만 중복 확인한다는 원문 주석이다.
    if (userRepository.existsByNicknameAndDeletedFalse(request.getNickname())) { // 같은 닉네임의 활성 계정을 찾는다.
        throw new InvalidRequestException("Existed_Nickname"); // 활성 닉네임 중복이면 저장하지 않는다.
    }

    // 추가: 같은 이메일의 삭제 계정까지 포함해서 기존 누적 신고 수 조회 // 재가입 정책을 위한 원문 주석이다.
    int previousReceivedReportCount = // 과거 탈퇴 계정까지 포함한 최대 누적 신고 수를 받을 변수를 선언한다.
            userRepository.findMaxReceivedReportCountByEmailIncludingDeleted( // 실제 집계 쿼리를 Repository에 요청한다.
                    request.getEmail() // 가입하려는 이메일을 쿼리 인자로 전달한다.
            );

    if (previousReceivedReportCount >= User.SUSPENSION_REPORT_THRESHOLD) { // 과거 신고 수가 정지 기준 이상인지 확인한다.
        throw new InvalidRequestException("Suspended_Account"); // 탈퇴 후 재가입으로 정지를 우회하지 못하게 막는다.
    }

    ImageDataUrlValidator.validateProfileImage(request.getProfileImage()); // 프로필 이미지의 형식, 크기와 실제 signature를 검증한다.

    User user = new User( // 검증을 모두 통과한 값으로 저장 전 Entity를 만든다.
            request.getEmail(), // 이메일을 Entity에 전달한다.
            passwordEncoder.encode(request.getPassword()), // 비밀번호 원문을 BCrypt hash로 변환해 전달한다.
            request.getNickname(), // 닉네임을 전달한다.
            request.getProfileImage(), // 선택 프로필 이미지를 전달한다.
            previousReceivedReportCount // 이전 계정의 누적 신고 수를 이어받는다.
    );

    User savedUser = userRepository.save(user); // 새 User를 JPA에 persistence하고 반환된 Entity를 받는다. 현재 IDENTITY ID를 얻기 위한 INSERT는 보통 이 과정에서 실행되지만 commit은 아직 아니다.

    return new UserResponseDto(savedUser); // DB 저장 결과에서 클라이언트 응답 DTO를 만든다.
}
```

### `UserRepository`

```java
public interface UserRepository extends JpaRepository<User, Long> { // User Entity와 Long ID에 대한 기본 CRUD를 상속한다.
    Optional<User> findByUserIdAndDeletedFalse(Long userId); // 삭제되지 않은 User를 ID로 찾고 없을 수 있으므로 Optional로 반환한다.
    boolean existsByEmailAndDeletedFalse(String email); // email 일치와 deleted=false 조건의 존재 쿼리를 메서드 이름으로 만든다.
    boolean existsByNicknameAndDeletedFalse(String nickname); // 활성 닉네임의 존재 여부를 조회한다.
    boolean existsByNicknameAndDeletedFalseAndUserIdNot(String nickname, Long userId); // 특정 User ID를 제외하고 활성 닉네임이 중복되는지 조회한다.
    Optional<User> findByEmailAndDeletedFalse(String email); // 활성 User를 email로 찾는다.

    @Lock(LockModeType.PESSIMISTIC_WRITE) // 조회한 row에 DB의 비관적 write lock을 요청한다.
    @Query(""" // Entity와 field 이름을 사용한 JPQL을 직접 선언한다.
            SELECT user
            FROM User user
            WHERE user.userId = :userId
            """)
    Optional<User> findByUserIdForUpdate(@Param("userId") Long userId); // userId를 JPQL 인자에 넣고 lock이 적용된 User를 Optional로 반환한다.

    @Query( // 메서드 이름으로 표현하기 어려운 직접 쿼리를 선언한다.
            value = """ // 아래 문자열을 실제 SQL로 사용한다.
                    SELECT COALESCE(MAX(received_report_count), 0)
                    FROM users
                    WHERE email = :email
                    """,
            nativeQuery = true // Entity 이름의 JPQL이 아니라 테이블·컬럼 이름의 SQL임을 표시한다.
    )
    int findMaxReceivedReportCountByEmailIncludingDeleted(@Param("email") String email); // Java email 인자를 SQL의 :email에 연결하고 최댓값을 int로 반환한다.
}
```

### `User` Entity의 회원가입 부분

```java
@Getter // 각 field를 읽는 getter를 Lombok이 생성한다.
@Entity // 이 class를 JPA가 관리할 Entity로 지정한다.
@Table(name = "users") // Entity를 DB의 users table과 연결한다.
@NoArgsConstructor(access = AccessLevel.PROTECTED) // JPA가 사용할 인자 없는 constructor를 protected로 생성한다.
public class User { // User의 저장 상태와 상태 변경 동작을 담는 class다.
    public static final int SUSPENSION_REPORT_THRESHOLD = 10; // 재가입을 막는 누적 신고 수 기준을 class 상수로 둔다.

    @Id // 아래 field가 Entity의 기본키임을 표시한다.
    @GeneratedValue(strategy = GenerationType.IDENTITY) // DB의 identity·auto-increment 방식으로 ID를 생성한다.
    @Column(name = "user_id") // userId field를 user_id column에 연결한다.
    private Long userId; // 저장된 User를 구분하는 기본키다.

    @Column(nullable = false) // DB column에 null을 허용하지 않는다.
    private String email; // 회원 이메일을 저장한다.

    @Column(nullable = true, unique = false, length = 255) // password column은 null을 허용하고 unique 제약은 없으며 최대 길이는 255다.
    private String password; // 원문이 아닌 PasswordEncoder의 hash를 저장한다.

    @Column(nullable = false, length = 10) // nickname column은 null을 허용하지 않고 길이는 최대 10이다.
    private String nickname; // 화면에 표시할 닉네임을 저장한다.

    @Lob // 큰 데이터로 다루는 JPA 필드임을 표시한다.
    @Column(name = "profile_image", columnDefinition = "LONGTEXT") // profileImage를 MySQL LONGTEXT column과 연결한다.
    private String profileImage; // 선택 입력인 프로필 이미지 Data URL을 저장한다.

    @Column(name = "received_report_count", nullable = false) // 누적 신고 수를 non-null column과 연결한다.
    private int receivedReportCount; // 현재와 과거 계정에서 이어받은 누적 신고 수다.

    @Column(name ="deleted", nullable = false) // soft delete 여부를 non-null column과 연결한다.
    private boolean deleted; // true면 탈퇴 처리된 계정이다.

    @Column(name = "auth_version", nullable = false) // 인증 버전을 non-null column과 연결한다.
    private long authVersion; // 비밀번호 변경 등으로 기존 Access Token을 무효화할 때 사용하는 버전이다.

    public User( // 회원가입 Service가 새 User를 만들 때 호출하는 constructor다.
            String email, // 요청에서 검증된 이메일을 받는다.
            String password, // 암호화된 비밀번호를 받는다.
            String nickname, // 검증된 닉네임을 받는다.
            String profileImage, // null일 수 있는 프로필 이미지 Data URL을 받는다.
            int receivedReportCount // 이전 계정의 누적 신고 수를 받는다.
    ) {
        this.email = email; // 인자를 Entity field에 저장한다.
        this.password = password; // 암호화된 비밀번호를 field에 저장한다.
        this.nickname = nickname; // 닉네임을 field에 저장한다.
        this.profileImage = profileImage; // 프로필 이미지를 field에 저장한다.
        this.receivedReportCount = receivedReportCount; // 누적 신고 수를 field에 저장한다.
        this.deleted = false; // 새 회원은 활성 상태로 시작한다.
        this.authVersion = 0L; // 새 회원의 인증 버전은 0으로 시작한다.
    }
```

```text

2. Entity 상태와 제약 확인
```

- `@Valid`와 `InvalidRequestException`을 HTTP 400 응답으로 변환하는 `GlobalExceptionHandler`: 4장에서 예외 흐름으로 설명한다.


## 3.9.1 이 장에서 필요한 Java·Spring 문법

### package, import와 class

```java
package kr.adapterz.springdatajpa.dto.user;
import lombok.Getter;
public class UserRequestDto { ... }
```

- `package`는 클래스의 전체 이름과 폴더 논리를 정한다.
- `import`는 다른 package의 긴 클래스 이름을 짧게 쓰게 한다.
- `public class`는 다른 package에서도 사용할 수 있는 클래스를 선언한다.

### 접근 제한자와 필드

```java
private String email;
public UserResponseDto createUser(...) { ... }
```

- `private`: 선언한 클래스 내부에서만 직접 접근한다.
- `public`: 다른 클래스에서도 호출할 수 있다.
- 필드는 객체가 보관하는 상태고, 메서드는 객체가 수행하는 동작이다.

### 어노테이션

```java
@Getter
@PostMapping
@Valid
```

`@`로 시작하는 어노테이션은 클래스·메서드·필드·인자에 추가 정보를 붙인다. Lombok은 컴파일 시 코드를 생성하고, Spring은 실행 시 요청 연결이나 검증 규칙으로 해석한다. 같은 모양이어도 누가 처리하는지를 구분해야 한다.

### Lombok 코드 생성

```java
@Getter
@NoArgsConstructor
@RequiredArgsConstructor
```

- `@Getter`: 필드 getter 생성
- `@NoArgsConstructor`: 인자 없는 생성자 생성
- `@RequiredArgsConstructor`: `final` 필드를 인자로 받는 생성자 생성

소스에는 생성자가 보이지 않아도 컴파일 결과에는 존재할 수 있다.

### Constructor injection

```java
@RequiredArgsConstructor
public class UserService {
    private final UserRepository userRepository;
}
```

Lombok이 `final` field를 받는 constructor를 만들고 Spring이 `UserRepository` Bean을 그 constructor에 넣는다. 그래서 코드에 `new UserService(...)`가 보이지 않아도 Controller가 Service를, Service가 Repository를 사용할 수 있다.

### `@RequestBody`, `@Valid`, `@RestController`

```text
JSON request body
→ @RequestBody가 UserRequestDto로 역직렬화
→ @Valid가 DTO의 검증 annotation 실행
→ method가 UserResponseDto 반환
→ @RestController의 @ResponseBody 역할이 반환값을 HTTP response body로 전달
→ Spring의 JSON converter가 UserResponseDto를 JSON으로 직렬화
```

역직렬화는 JSON에서 Java 객체로 바꾸는 것이고, 직렬화는 Java 객체를 JSON으로 바꾸는 것이다.

`@RestController`는 두 기능을 합친 Spring annotation이다.

```text
@RestController
= @Controller
+ @ResponseBody
```

- `@Controller`: Spring component scan이 class를 찾아 Spring MVC Controller Bean으로 등록한다. 그래야 `@RequestMapping`, `@PostMapping` 같은 endpoint method가 요청 처리자로 연결된다.
- `@ResponseBody`: method가 반환한 Java 값을 view 이름으로 해석하지 않고 HTTP response body에 쓰도록 한다.

현재 method는 JSON 문자열을 직접 만들어 반환하지 않고 `UserResponseDto` Java 객체를 반환한다.

```java
public UserResponseDto createUser(...) {
    return userService.createUser(request);
}
```

Spring MVC는 이 반환값을 HTTP message converter에 전달한다. JSON converter는 `UserResponseDto`의 property를 읽어 다음과 같은 JSON body를 만든다.

```json
{
  "userId": 1,
  "message": "signup_success"
}
```

전체 HTTP 응답은 개념적으로 다음과 같다.

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"userId":1,"message":"signup_success"}
```

여기서 역할을 구분해야 한다.

```text
@RequestBody
→ request JSON을 UserRequestDto로 바꾼다.

@Valid
→ 변환된 UserRequestDto를 검증한다.

@RestController
→ Controller Bean 등록 + 반환값을 response body로 전달한다.

JSON HTTP message converter
→ UserResponseDto 객체를 실제 JSON byte로 직렬화한다.

@ResponseStatus(HttpStatus.CREATED)
→ 성공 HTTP 상태 code를 201로 지정한다.
```

따라서 `@RestController`가 JSON을 혼자 직접 만든다고 외우기보다, **반환값을 HTTP body로 보내도록 지정하고 실제 JSON 변환은 HTTP message converter에 맡긴다**고 이해하는 것이 정확하다.

### `@Transactional`, persistence와 commit

```text
Service method 진입
→ transaction 시작
→ Repository 조회·save
→ method 정상 종료
→ flush와 commit
```

runtime exception이 발생해 method가 정상 종료하지 못하면 Spring은 기본적으로 transaction을 rollback한다. `save`는 Entity를 JPA에 persistence하는 호출이고, commit은 transaction 전체를 최종 확정하는 다른 시점이다.

### 생성자와 `new`

```java
User user = new User(...);
```

`new`는 메모리에 새 객체를 만들고 뒤의 생성자를 호출한다. 왼쪽 `User user`는 User 객체를 가리킬 변수 선언이다.

### `if`, `throw`와 `!`

```java
if (!condition) {
    throw new InvalidRequestException(...);
}
```

- `if`: 조건이 true일 때 블록 실행
- `!`: boolean 반전
- `throw`: 현재 메서드 정상 흐름을 즉시 중단하고 예외를 호출자 방향으로 전달

### interface와 `extends`

```java
public interface UserRepository
        extends JpaRepository<User, Long>
```

interface는 구현해야 할 동작 계약이다. `extends`로 `JpaRepository` 계약을 상속한다. Spring Data JPA가 실행 시 구현 객체를 생성하므로 개발자가 `new UserRepository()`를 작성하지 않는다.

### Generic `<User, Long>`

꺾쇠 안 Generic은 하나의 타입을 여러 구체 타입에 재사용하게 한다.

```text
JpaRepository<User, Long>
→ 관리 Entity는 User
→ 기본키 타입은 Long

Optional<User>
→ User가 있을 수도, 없을 수도 있음

List<Post>
→ Post 여러 개를 순서대로 보관
```

### 메서드 반환 타입

```java
boolean existsByEmailAndDeletedFalse(...)
UserResponseDto createUser(...)
```

메서드 이름 앞 타입은 반환값의 종류다. `void`라면 값을 반환하지 않는다.

### Spring Data 파생 query

```java
existsByEmailAndDeletedFalse
```

메서드 이름을 단어로 나눈다.

```text
exists
By
Email
And
DeletedFalse
```

Spring Data는 이를 “email이 같고 deleted가 false인 행이 존재하는가?”라는 query로 해석한다.

### Java text block

```java
@Query("""
        SELECT ...
        """)
```

큰따옴표 세 개는 여러 줄 문자열을 만드는 Java text block이다. JPQL이나 SQL을 줄바꿈 그대로 작성할 때 사용한다.

### JPQL과 native SQL

- JPQL은 테이블이 아니라 `User`, `Post` 같은 Entity와 Java 필드 이름을 사용한다.
- `nativeQuery = true`는 실제 `users`, `received_report_count` 같은 DB 이름을 사용한다.

### 정규표현식

```java
@Pattern(regexp = "^\\S+$")
```

- `^`: 문자열 시작
- `$`: 문자열 끝
- `\\S`: Java 문자열에서 정규식 `\S`를 표현하며 공백이 아닌 문자
- `+`: 앞 조건이 한 번 이상 반복

복잡한 비밀번호 정규식은 각 lookahead가 대문자·소문자·숫자·특수문자 포함을 확인한다. 정규식 전체를 암기하기보다 검증 요구사항과 테스트 경계값을 연결한다.

## 3.11 전체 모범 답안

1. Request DTO는 HTTP request body로 받을 데이터 모양과 1차 검증 규칙을 표현한다. Entity는 DB table과 mapping되는 상태와 그 상태를 변경하는 도메인 동작을 표현한다.
2. `@RequestBody`는 HTTP request body의 JSON을 `UserRequestDto` Java 객체로 역직렬화한다. `@Valid`는 그 DTO의 `@NotBlank`, `@Email`, `@Pattern` 같은 검증 annotation을 실행한다.
3. 이메일 중복은 HTTP 변환이 아니라 회원가입의 업무 규칙이다. Controller는 request·response 연결에 집중하고, Service가 transaction 안에서 Repository 조회와 다른 회원가입 규칙을 순서대로 조합한다.
4. `password` 확인값 일치 → 활성 email 중복 → 활성 nickname 중복 → 같은 email의 과거 누적 신고 수 조회 → 정지 기준 이상인지 확인 → profile image 형식·크기·signature 검증 순으로 진행된다. 모든 검증을 통과한 뒤 비밀번호 암호화, Entity 생성과 저장이 이어진다.
5. `UserService.createUser` 안의 `passwordEncoder.encode(request.getPassword())`가 비밀번호 원문을 BCrypt hash로 변환하고, 이 변환된 값을 `User` constructor에 넣는다.
6. Repository는 DB 연결 주소를 설정하지 않는다. `application*.yaml`과 Spring Boot가 만든 DataSource·JPA 설정을 사용해 query를 실행한다.
7. Spring Data JPA는 method 이름을 `exists / By / Email / And / DeletedFalse`로 분해하고 `User` Entity의 `email`, `deleted` field와 연결해 “email이 같고 deleted가 false인 row가 존재하는가?” query를 생성한다.
8. 브라우저의 frontend 검증은 수정·우회할 수 있고, client가 backend API를 직접 호출할 수도 있다. 따라서 신뢰할 수 없는 요청이 DB에 저장되지 않도록 backend가 반드시 다시 검증해야 한다.

## 3.12 오답노트

### 3-1. Request DTO와 Entity는 어떤 점이 다른가?

- 나의 답: Request DTO는 응답하는 형태의 객체이고 Entity는 한 데이터 type을 다루는 객체다.
- 틀린 점: Request DTO의 방향을 response로 반대로 이해했다. Entity의 DB mapping과 상태 변경 책임도 빠졌다.
- 정답: Request DTO는 HTTP request로 받을 데이터 모양과 검증 규칙을 표현한다. Entity는 DB table과 mapping되는 상태와 그 상태를 변경하는 도메인 동작을 표현한다.
- 상태: 재복습 필요

### 3-2. `@Valid`와 `@RequestBody`는 각각 무엇을 하는가?

- 나의 답: `@Valid`는 조건에 맞는지 검증하고 `@RequestBody`는 응답 body에 있는 데이터를 가져온다.
- 틀린 점: `@Valid`의 핵심은 맞았지만 `@RequestBody`는 response가 아니라 request body를 다룬다. 또한 단순히 가져오는 것을 넘어 JSON을 Java DTO로 역직렬화한다.
- 정답: `@RequestBody`는 HTTP request body의 JSON을 `UserRequestDto`로 역직렬화하고, `@Valid`는 변환된 DTO의 검증 annotation을 실행한다.
- 상태: 재복습 필요

### 3-3. Controller가 이메일 중복을 직접 검사하지 않는 이유는 무엇인가?

- 나의 답: Service에서 검사하기 때문이다.
- 부족한 점: 어디에서 실행하는지는 맞았지만, 왜 Service의 책임인지가 빠졌다.
- 정답: 이메일 중복은 HTTP 요청 변환이 아니라 회원가입 업무 규칙이다. Controller는 HTTP 입출력에 집중하고 Service가 transaction 안에서 중복 조회와 다른 규칙을 순서대로 조합한다.
- 상태: 재복습 필요

### 3-4. Service의 회원가입 검증은 어떤 순서로 진행되는가?

- 나의 답: 확인값과 다른지 확인 → 같은 이메일의 활성 계정 확인 → 같은 닉네임의 활성 계정 확인 → 과거 신고 수가 정지 기준 이상인지 확인
- 부족한 점: 과거 누적 신고 수를 Repository에서 먼저 조회한다는 단계와 profile image 검증이 빠졌다.
- 정답: 비밀번호 확인값 일치 → 활성 email 중복 → 활성 nickname 중복 → 과거 누적 신고 수 조회 → 정지 기준 확인 → profile image 형식·크기·signature 검증 순이다.
- 상태: 재복습 필요

### 3-6. Repository가 DB 연결 주소를 설정하는가?

- 나의 답: 한다.
- 틀린 점: Repository는 DB 연결 정보를 만드는 계층이 아니다.
- 정답: Repository는 이미 Spring이 만든 DataSource와 JPA 설정을 사용해 query를 실행한다. DB 주소는 `application*.yaml`의 `spring.datasource.url`과 외부 property가 제공한다.
- 상태: 재복습 필요

### 3-7. `existsByEmailAndDeletedFalse`에서 Spring Data JPA가 query를 만드는 근거는 무엇인가?

- 나의 답: 이름이다.
- 부족한 점: method 이름이라는 방향은 맞지만, 어떤 이름 규칙을 Entity field와 연결하는지가 빠졌다.
- 정답: Spring Data JPA는 method 이름을 `exists / By / Email / And / DeletedFalse`로 분해하고 `User.email`, `User.deleted` field와 연결해 존재 여부 query를 생성한다.
- 상태: 재복습 필요
