# 7장. 게시글 페이징과 무한 스크롤

## 7.1 학습 목표

백엔드의 페이지 번호 기반 조회가 프론트의 무한 스크롤 상태와 어떻게 연결되는지 학습한다.

```text
IntersectionObserver
→ 다음 페이지 번호
→ GET /posts?page=N&size=10
→ Page<Post>
→ posts + hasNextPage
→ 기존 배열 뒤에 추가
```

## 7.2 실제 코드 발췌: 백엔드 Controller

```java
@GetMapping
public PostPageResponseDto getPostList(
        @RequestParam(defaultValue = "0") int page,
        @RequestParam(defaultValue = "10") int size
) {
    return postService.getPostList(page, size);
}
```

중요한 줄:

```java
@RequestParam(defaultValue = "0") int page
// Query Parameter가 없으면 첫 페이지인 0을 사용한다.

@RequestParam(defaultValue = "10") int size
// 한 번에 10개를 요청한다.
```

이 프로젝트의 Spring Page 번호는 0부터 시작한다.

## 7.3 실제 코드 발췌: Service와 Repository

```java
public PostPageResponseDto getPostList(
        int page,
        int size
) {
    Pageable pageable = PageRequest.of(page, size);

    Page<Post> posts = postRepository
            .findByDeletedFalseAndReportCountLessThanOrderByPostIdDesc(
                    Post.REPORT_BLOCK_THRESHOLD,
                    pageable
            );

    List<PostListResponseDto> result = new ArrayList<>();

    for (Post post : posts.getContent()) {
        result.add(
                PostResponseFactory.createListResponse(post)
        );
    }

    return PostResponseFactory.createPageResponse(
            result,
            posts.hasNext()
    );
}
```

Repository의 정렬:

```java
@Query("""
        SELECT post
        FROM Post post
        WHERE post.deleted = false
          AND post.postCounter.reportCount < :reportCount
        ORDER BY post.postId DESC
        """)
Page<Post> findByDeletedFalseAndReportCountLessThanOrderByPostIdDesc(
        @Param("reportCount") int reportCount,
        Pageable pageable
);
```

최신 게시글부터 가져오며 삭제되었거나 신고 기준에 도달한 게시글은 제외한다.

`Page<Post>`는 현재 내용뿐 아니라 전체 개수와 다음 페이지 존재 여부를 계산할 수 있는 정보를 가진다.

## 7.4 실제 응답 모양

```java
@Getter
public class PostPageResponseDto {

    private List<PostListResponseDto> posts;
    private boolean hasNextPage;

    public PostPageResponseDto(
            List<PostListResponseDto> posts,
            boolean hasNextPage
    ) {
        this.posts = posts;
        this.hasNextPage = hasNextPage;
    }
}
```

프론트가 필요한 것은 현재 게시글 배열과 다음 페이지의 존재 여부다.

## 7.5 실제 코드 발췌: 프론트 API

```javascript
async getPosts({ page = 0, size = 10 } = {}) {
    const params = new URLSearchParams({
        page: String(page),
        size: String(size),
    });

    const result = await request(
        `/posts?${params.toString()}`
    );

    return {
        posts: Array.isArray(result?.posts)
            ? result.posts.map(normalizeListPost)
            : [],
        hasNextPage: result?.hasNextPage === true,
    };
}
```

`URLSearchParams`가 `page=0&size=10` 형식의 Query String을 만든다. 정규화는 서버 값이 누락되더라도 화면에 안전한 기본값을 제공한다.

## 7.6 실제 코드 발췌: PostsPage 상태

```javascript
const [posts, setPosts] = useState([]);
const [hasNextPage, setHasNextPage] = useState(true);
const [loadError, setLoadError] = useState(null);
const [failedPage, setFailedPage] = useState(null);
const [retryVersion, setRetryVersion] = useState(0);

const loadingRef = useRef(false);
const initialRequestRef = useRef(null);
const nextPageRef = useRef(0);
```

| 상태·ref | 역할 |
|---|---|
| `posts` | 현재 화면에 누적된 게시글 |
| `hasNextPage` | 감시 대상을 계속 둘지 결정 |
| `loadError` | 요청 실패 화면 표시 |
| `failedPage` | 어느 페이지를 재시도할지 기억 |
| `retryVersion` | 첫 요청 Effect를 다시 시작 |
| `loadingRef` | 동시에 여러 다음 페이지 요청 방지 |
| `initialRequestRef` | 최초 요청 Promise 재사용 |
| `nextPageRef` | 다음 요청 페이지 번호 |

state는 변경되면 다시 렌더링해야 하는 값에 사용한다. ref는 렌더링 사이에 값은 유지하지만 변경 자체로 다시 렌더링할 필요가 없는 제어값에 사용한다.

## 7.7 실제 코드 발췌: 다음 페이지 적재

```javascript
const loadPage = useCallback(async (page) => {
    if (loadingRef.current) {
        return;
    }

    try {
        loadingRef.current = true;
        setLoadError(null);

        const result = await postApi.getPosts({
            page,
            size: 10,
        });

        setPosts((previous) =>
            page === 0
                ? result.posts
                : [...previous, ...result.posts]
        );

        setHasNextPage(result.hasNextPage);
        nextPageRef.current = page + 1;
        setFailedPage(null);
    } catch (requestError) {
        setLoadError(requestError);
        setFailedPage(page);
    } finally {
        loadingRef.current = false;
    }
}, []);
```

중요한 줄:

```javascript
[...previous, ...result.posts]
// 기존 게시글과 새 페이지 결과를 새 배열로 합친다.

nextPageRef.current = page + 1
// 성공했을 때만 다음 페이지 번호를 증가시킨다.

finally
// 성공과 실패 모두에서 loading 잠금을 해제한다.
```

## 7.8 실제 코드 발췌: IntersectionObserver

```javascript
useEffect(() => {
    const target = observerTargetRef.current;

    if (!target || !hasNextPage) {
        return;
    }

    const observer = new IntersectionObserver((entries) => {
        if (entries[0]?.isIntersecting) {
            onLoadMore();
        }
    });

    observer.observe(target);

    return () => observer.disconnect();
}, [hasNextPage, onLoadMore]);
```

```text
목록 아래의 target이 화면에 들어옴
→ isIntersecting true
→ onLoadMore
→ nextPageRef의 페이지 요청
→ 게시글 누적
→ 다음 렌더링
```

cleanup에서 `disconnect()`하지 않으면 이전 Observer가 남아 중복 호출이나 메모리 누수가 생길 수 있다.

## 7.9 첫 요청과 StrictMode

첫 Effect는 Promise를 `initialRequestRef`에 저장한다.

```text
첫 Effect 시작
→ 요청 생성 후 ref에 보관

개발 StrictMode의 추가 Effect 시작
→ ref에 요청이 이미 있음
→ 새 네트워크 요청 대신 같은 Promise 사용
```

각 Effect 실행의 `active`는 서로 다른 지역 변수다. cleanup된 이전 Effect는 `active=false`가 되어 늦은 응답으로 state를 변경하지 않고, 현재 Effect만 응답을 반영한다.

## 7.10 이 방식의 특성

현재는 page/offset 방식이다.

장점:

- 구현과 이해가 단순하다.
- Spring Data `PageRequest`를 바로 사용할 수 있다.

주의점:

- 앞쪽에 새 게시글이 추가되면 다음 페이지에서 중복이나 누락이 생길 수 있다.
- 페이지 번호가 커지면 DB offset 비용이 커질 수 있다.

커서 페이징은 마지막으로 본 ID를 기준으로 다음 데이터를 가져오지만 현재 프로젝트에는 구현되어 있지 않다.

## 7.11 핵심 축약본

```text
백엔드:
page + size
→ PageRequest
→ Page<Post>
→ posts + hasNextPage

프론트:
Observer 감지
→ nextPage 요청
→ 기존 posts 뒤에 추가
→ hasNextPage가 false면 Observer target 제거
```

### 목록 Service

```java
public PostPageResponseDto getPostList(int page, int size) { // 페이지 번호와 크기로 목록 응답을 만든다.
    Pageable pageable = PageRequest.of(page, size); // Spring Data가 이해할 0 기반 Pageable을 만든다.

    Page<Post> posts = postRepository // 내용과 페이지 정보를 받을 변수를 선언한다.
            .findByDeletedFalseAndReportCountLessThanOrderByPostIdDesc( // 노출 가능한 최신 게시글을 조회한다.
                    Post.REPORT_BLOCK_THRESHOLD, // 이 신고 횟수 미만인 글만 허용한다.
                    pageable // DB limit과 offset 계산에 사용할 페이지 요청이다.
            );

    List<PostListResponseDto> result = new ArrayList<>(); // Entity를 화면용 DTO로 바꿔 담을 목록이다.

    for (Post post : posts.getContent()) { // 현재 페이지의 실제 게시글만 순회한다.
        result.add(PostResponseFactory.createListResponse(post)); // 각 Entity를 목록 DTO로 변환해 추가한다.
    }

    return PostResponseFactory.createPageResponse( // 프론트가 사용할 페이지 응답을 만든다.
            result, // 변환된 현재 페이지 게시글이다.
            posts.hasNext() // 현재 페이지 뒤에 데이터가 더 있는지 전달한다.
    );
}
```

### 프론트 `getPosts`

```javascript
async getPosts({ page = 0, size = 10 } = {}) { // 인자가 없을 때 첫 페이지 10개를 요청한다.
    const params = new URLSearchParams({ // query string을 안전하게 만들 객체를 생성한다.
        page: String(page), // 숫자 page를 URL 문자열 값으로 변환한다.
        size: String(size), // 숫자 size를 URL 문자열 값으로 변환한다.
    });

    const result = await request(`/posts?${params.toString()}`); // 공통 인증·오류 처리를 거쳐 목록 API를 기다린다.

    return { // Page가 사용할 정규화된 결과를 반환한다.
        posts: Array.isArray(result?.posts) // 서버 posts가 실제 배열인지 검사한다.
            ? result.posts.map(normalizeListPost) // 배열이면 게시글마다 안전한 화면 데이터로 바꾼다.
            : [], // 배열이 아니면 map 오류 대신 빈 목록을 사용한다.
        hasNextPage: result?.hasNextPage === true, // 정확히 true일 때만 다음 페이지가 있다고 판단한다.
    };
}
```

### `loadPage`

```javascript
const loadPage = useCallback(async (page) => { // Observer와 재시도가 재사용할 안정된 비동기 함수를 만든다.
    if (loadingRef.current) { // 이미 페이지 요청이 진행 중인지 확인한다.
        return; // 진행 중이면 같은 또는 다음 요청을 중복 생성하지 않는다.
    }

    try { // 요청 성공과 실패를 나눠 처리한다.
        loadingRef.current = true; // 다른 호출이 들어오지 못하게 요청 잠금을 건다.
        setLoadError(null); // 새 시도 전 이전 오류 화면을 지운다.
        const result = await postApi.getPosts({ page, size: 10 }); // 지정 페이지의 서버 응답을 기다린다.
        setPosts((previous) => // 최신 이전 state를 인자로 받아 새 목록 state를 만든다.
            page === 0 // 첫 페이지 재요청인지 확인한다.
                ? result.posts // 첫 페이지면 기존 목록을 교체한다.
                : [...previous, ...result.posts] // 다음 페이지면 기존 뒤에 새 결과를 붙인다.
        );
        setHasNextPage(result.hasNextPage); // 서버의 다음 페이지 여부를 화면 상태에 저장한다.
        nextPageRef.current = page + 1; // 성공한 페이지의 다음 번호로 이동한다.
        setFailedPage(null); // 성공했으므로 실패 페이지 기록을 지운다.
    } catch (requestError) { // 공통 request가 던진 오류를 받는다.
        setLoadError(requestError); // 오류 화면이 렌더링되게 한다.
        setFailedPage(page); // 같은 페이지를 다시 시도할 수 있게 번호를 저장한다.
    } finally { // 성공과 실패 모두에서 실행한다.
        loadingRef.current = false; // 다음 요청을 받을 수 있도록 잠금을 해제한다.
    }
}, []); // 함수 내부가 state 최신값 대신 ref와 setter를 사용하므로 최초 함수를 재사용한다.
```

### `IntersectionObserver`

```javascript
useEffect(() => { // target과 다음 페이지 여부에 맞춰 브라우저 Observer를 등록한다.
    const target = observerTargetRef.current; // 렌더링된 목록 아래 감시용 div DOM을 가져온다.
    if (!target || !hasNextPage) { // 아직 DOM이 없거나 더 가져올 페이지가 없는지 확인한다.
        return; // Observer를 만들 필요가 없으므로 종료한다.
    }

    const observer = new IntersectionObserver((entries) => { // target의 화면 진입 상태를 받을 Observer를 만든다.
        if (entries[0]?.isIntersecting) { // 첫 감시 대상이 viewport와 겹치는지 확인한다.
            onLoadMore(); // 부모가 전달한 다음 페이지 함수를 호출한다.
        }
    });

    observer.observe(target); // 실제 target DOM 감시를 시작한다.
    return () => observer.disconnect(); // 의존성 변경이나 unmount 시 이전 감시 연결을 제거한다.
}, [hasNextPage, onLoadMore]); // 다음 페이지 여부나 callback이 바뀌면 Observer를 다시 구성한다.
```

## 7.12.1 이 장에서 필요한 React Hooks·비동기 문법

### `useState`

```javascript
const [posts, setPosts] = useState([]);
```

배열 구조 분해 문법으로 두 값을 받는다.

- `posts`: 현재 state
- `setPosts`: 새 state를 예약하는 함수
- `[]`: 초기값인 빈 배열

setter를 호출하면 React가 다시 렌더링한다. 변수에 직접 대입해서는 React가 변경을 알 수 없다.

### 구조 분해

```javascript
const { page = 0, size = 10 } = options;
const [state, setter] = useState(...);
```

객체는 이름으로, 배열은 순서로 내부 값을 꺼낸다. `= 0`은 값이 undefined일 때 사용할 기본값이다.

### `useRef`

```javascript
const loadingRef = useRef(false);
loadingRef.current = true;
```

ref 객체는 렌더링 사이에 유지되며 실제 값은 `.current`에 있다. `.current`를 바꿔도 다시 렌더링하지 않는다.

### `useEffect`

```javascript
useEffect(() => {
    외부작업();

    return () => 정리작업();
}, [dependency]);
```

렌더링 결과가 화면에 반영된 뒤 외부 시스템과 동기화한다. 반환 함수는 다음 Effect 전이나 unmount 때 실행하는 cleanup이다. 대괄호는 dependency 배열이며 그 값이 바뀔 때 Effect를 다시 구성한다.

### `useCallback`

```javascript
const loadPage = useCallback(() => { ... }, []);
```

dependency가 바뀌지 않는 동안 같은 함수 객체를 재사용한다. 자식 Effect가 callback identity 변화 때문에 불필요하게 다시 등록되는 것을 줄인다.

### 함수형 state update

```javascript
setPosts(previous => [...previous, ...newPosts]);
```

현재 렌더링이 캡처한 오래된 `posts` 대신 React가 보유한 가장 최신 이전값을 인자로 받는다. 연속 비동기 업데이트에서 안전하다.

### 배열 spread

```javascript
[...previous, ...result.posts]
```

두 배열의 원소를 새 배열 안에 펼친다. 기존 배열을 직접 수정하지 않는 불변 업데이트다.

### 삼항 연산자

```javascript
page === 0 ? result.posts : [...previous, ...result.posts]
```

조건이 참이면 첫 값, 거짓이면 콜론 뒤 값을 선택한다.

### strict equality

```javascript
page === 0
```

`===`는 타입 변환 없이 값과 타입이 모두 같은지 비교한다. JavaScript에서는 예상치 못한 자동 변환을 피하기 위해 `==`보다 주로 사용한다.

### optional chaining

```javascript
entries[0]?.isIntersecting
```

첫 원소가 없으면 오류 대신 undefined가 되어 조건이 거짓으로 처리된다.

### `void` 연산자

```javascript
void loadPage(nextPageRef.current);
```

Promise 반환값을 의도적으로 사용하지 않는다는 뜻이다. 함수 실행은 그대로 발생한다.

### `URLSearchParams`

객체 값을 URL query string 규칙에 맞게 encoding한다.

```text
{ page: "0", size: "10" }
→ page=0&size=10
```

### `IntersectionObserver`

브라우저가 대상 DOM과 viewport의 교차 상태를 비동기로 알려주는 API다. scroll event를 매번 직접 계산하지 않아도 된다.

### Promise callback과 Effect의 `active`

하나의 Promise에 여러 `.then` callback을 등록할 수 있다. StrictMode에서 이전 Effect와 새 Effect가 같은 최초 Promise를 사용하더라도 각 Effect 호출은 별도의 지역 `active` 변수를 closure로 기억한다.

```text
이전 Effect cleanup → 이전 active=false
새 Effect → 새 active=true
응답 도착 → 이전 callback은 무시, 새 callback만 state 반영
```

closure는 함수가 생성될 당시 주변 지역 변수를 함수가 나중에도 기억하는 JavaScript 기능이다.
