# 7장. 게시글 페이징과 무한 스크롤

## 7.1 학습 목표

백엔드의 페이지 번호 기반 조회가 프론트의 무한 스크롤 상태와 어떻게 연결되는지 학습한다.

```text
IntersectionObserver
→ 다음 페이지 번호
→ GET /posts?page=N&size=10
→ Page<Post>
→ posts + hasNextPage
→ 기존 배열 뒤에 추가
```

### 7.1.1 이 장의 실제 코드 읽기 순서

```text
PostsPage 첫 useEffect
→ loadPage(0)
→ postApi.getPosts({ page, size, signal })
→ request() → fetch()
→ GET /posts Controller
→ PostService.getPostList()
→ Pageable Repository query
→ PostResponseFactory → PostPageResponseDto
→ postNormalizer
→ setPosts / hasNextPage / nextPageRef
→ IntersectionObserver가 다음 loadPage 호출
```

이 흐름에서 `AbortController`는 페이지 이동·재시도처럼 이전 요청의 결과가 더 이상 필요 없을 때 fetch 자체를 취소한다. `loadingRef`, `requestedPagesRef`와 `failedPageRef`는 각각 동시 호출, 같은 페이지 중복, 실패 페이지 재시도를 담당하므로 하나의 `active` boolean과 같은 역할로 뭉뚱그리면 안 된다. 화면 표시용 `PostList`와 `PostListItem`은 받은 배열을 그리는 반복 UI이므로 데이터 적재 흐름을 이해한 뒤 읽는다.

## 7.3 실제 코드 발췌: Service와 Repository

```java
public PostPageResponseDto getPostList(int page, int size) {
    validatePagination(page, size);

    Pageable pageable = PageRequest.of(page, size);
    Page<Post> posts = postRepository
            .findByDeletedFalseAndReportCountLessThanOrderByPostIdDesc(
                    Post.REPORT_BLOCK_THRESHOLD,
                    pageable
            );

    List<PostListResponseDto> result = new ArrayList<>();

    for (Post post : posts.getContent()) {
        result.add(PostResponseFactory.createListResponse(post));
    }

    return PostResponseFactory.createPageResponse(result, posts.hasNext());
}

private void validatePagination(int page, int size) {
    if (page < 0) {
        throw new InvalidRequestException("Invalid_Page");
    }
    if (size < 1) {
        throw new InvalidRequestException("Invalid_Page_Size");
    }
}
```

Repository의 정렬:

```java
@Query("""
        SELECT post
        FROM Post post
        WHERE post.deleted = false
          AND post.postCounter.reportCount < :reportCount
        ORDER BY post.postId DESC
        """)
Page<Post> findByDeletedFalseAndReportCountLessThanOrderByPostIdDesc(
        @Param("reportCount") int reportCount,
        Pageable pageable
);
```

최신 게시글부터 가져오며 삭제되었거나 신고 기준에 도달한 게시글은 제외한다.

`Page<Post>`는 현재 내용뿐 아니라 전체 개수와 다음 페이지 존재 여부를 계산할 수 있는 정보를 가진다.

`PageRequest.of()`를 만들기 전에 Service가 최소값을 검사한다.

- `page < 0`이면 `Invalid_Page`
- `size < 1`이면 `Invalid_Page_Size`

두 예외는 `InvalidRequestException`이므로 `GlobalExceptionHandler`가 HTTP 400 응답으로 바꾼다. 검사를 Service에 둔 이유는 HTTP Controller뿐 아니라 다른 코드가 Service를 직접 호출하더라도 같은 규칙을 적용하기 위해서다.

이 프로젝트는 요청한 정책에 따라 `size`의 최댓값은 제한하지 않는다. 따라서 `size=10000` 같은 값도 최소값 검사에는 통과한다. 이는 코드 오류가 아니라 현재 선택한 API 정책이며, 큰 조회가 발생할 수 있다는 성능상 특성은 남는다.

### 목록 Service

```java
public PostPageResponseDto getPostList(int page, int size) { // 페이지 번호와 크기로 목록 응답을 만든다.
    validatePagination(page, size); // PageRequest를 만들기 전에 page와 size의 최소값을 검사한다.

    Pageable pageable = PageRequest.of(page, size); // Spring Data가 이해할 0 기반 Pageable을 만든다.

    Page<Post> posts = postRepository // 내용과 페이지 정보를 받을 변수를 선언한다.
            .findByDeletedFalseAndReportCountLessThanOrderByPostIdDesc( // 노출 가능한 최신 게시글을 조회한다.
                    Post.REPORT_BLOCK_THRESHOLD, // 이 신고 횟수 미만인 글만 허용한다.
                    pageable // DB limit과 offset 계산에 사용할 페이지 요청이다.
            );

    List<PostListResponseDto> result = new ArrayList<>(); // Entity를 화면용 DTO로 바꿔 담을 목록이다.

    for (Post post : posts.getContent()) { // 현재 페이지의 실제 게시글만 순회한다.
        result.add(PostResponseFactory.createListResponse(post)); // 각 Entity를 목록 DTO로 변환해 추가한다.
    }

    return PostResponseFactory.createPageResponse( // 프론트가 사용할 페이지 응답을 만든다.
            result, // 변환된 현재 페이지 게시글이다.
            posts.hasNext() // 현재 페이지 뒤에 데이터가 더 있는지 전달한다.
    );
}

private void validatePagination(int page, int size) { // 잘못된 최소값을 프로젝트의 400 예외로 통일한다.
    if (page < 0) { // 페이지 번호가 첫 페이지 0보다 작은지 검사한다.
        throw new InvalidRequestException("Invalid_Page"); // GlobalExceptionHandler가 HTTP 400으로 바꿀 예외를 던진다.
    }
    if (size < 1) { // 한 페이지 크기가 최소 한 개보다 작은지 검사한다.
        throw new InvalidRequestException("Invalid_Page_Size"); // 잘못된 크기를 명확한 400 오류로 전달한다.
    }
} // size 최댓값 검사는 의도적으로 두지 않았다.
```

## 7.5 실제 코드 발췌: 프론트 API

```javascript
async getPosts({ page = 0, size = 10, signal } = {}) {
    const params = new URLSearchParams({
        page: String(page),
        size: String(size),
    });
    const result = await request(`/posts?${params.toString()}`, { signal });

    return {
        posts: Array.isArray(result?.posts)
            ? result.posts.map(normalizeListPost)
            : [],
        hasNextPage: result?.hasNextPage === true,
    };
}
```

`URLSearchParams`가 `page=0&size=10` 형식의 Query String을 만든다. 정규화는 서버 값이 누락되더라도 화면에 안전한 기본값을 제공한다.

`signal`은 `AbortController`가 만든 취소 신호다. `postApi`가 `{ signal }`을 공통 `request`에 넘기고, `request` 내부의 `sendRequest`가 `...options`로 이를 `fetch` 옵션에 펼치기 때문에 실제 HTTP 요청까지 연결된다.

### 페이지 응답 DTO

```java
@Getter // posts와 hasNextPage getter를 생성해 JSON 변환에 사용한다.
public class PostPageResponseDto { // 프론트 무한 스크롤이 받을 응답 모양이다.
    private List<PostListResponseDto> posts; // 현재 페이지의 게시글 목록이다.
    private boolean hasNextPage; // 다음 페이지 요청 가능 여부다.

    public PostPageResponseDto(List<PostListResponseDto> posts, boolean hasNextPage) { // 두 응답 값을 받는 생성자다.
        this.posts = posts; // 현재 페이지 목록을 필드에 저장한다.
        this.hasNextPage = hasNextPage; // 다음 페이지 여부를 필드에 저장한다.
    }
}
```

## 7.6 실제 코드 발췌: PostsPage 상태

```javascript
const [posts, setPosts] = useState([]);
const [hasNextPage, setHasNextPage] = useState(true);
const [loadError, setLoadError] = useState(null);
const [failedPage, setFailedPage] = useState(null);

const loadingRef = useRef(false);
const requestControllerRef = useRef(null);
const nextPageRef = useRef(0);
```

| 상태·ref | 역할 |
|---|---|
| `posts` | 현재 화면에 누적된 게시글 |
| `hasNextPage` | 감시 대상을 계속 둘지 결정 |
| `loadError` | 요청 실패 화면 표시 |
| `failedPage` | 어느 페이지를 재시도할지 기억 |
| `loadingRef` | 동시에 여러 다음 페이지 요청 방지 |
| `requestControllerRef` | 현재 목록 요청의 `AbortController`를 기억 |
| `nextPageRef` | 다음 요청 페이지 번호 |

state는 변경되면 다시 렌더링해야 하는 값에 사용한다. ref는 렌더링 사이에 값은 유지하지만 변경 자체로 다시 렌더링할 필요가 없는 제어값에 사용한다.

### 프론트 `getPosts`

```javascript
async getPosts({ page = 0, size = 10, signal } = {}) { // 기본 page·size와 선택적인 취소 신호를 받는다.
    const params = new URLSearchParams({ // query string을 안전하게 만들 객체를 생성한다.
        page: String(page), // 숫자 page를 URL 문자열 값으로 변환한다.
        size: String(size), // 숫자 size를 URL 문자열 값으로 변환한다.
    });

    const result = await request(`/posts?${params.toString()}`, { signal }); // query 경로와 fetch까지 전달할 AbortSignal을 넘긴다.

    return { // Page가 사용할 정규화된 결과를 반환한다.
        posts: Array.isArray(result?.posts) // 서버 posts가 실제 배열인지 검사한다.
            ? result.posts.map(normalizeListPost) // 배열이면 게시글마다 안전한 화면 데이터로 바꾼다.
            : [], // 배열이 아니면 map 오류 대신 빈 목록을 사용한다.
        hasNextPage: result?.hasNextPage === true, // 정확히 true일 때만 다음 페이지가 있다고 판단한다.
    };
}
```

## 7.7 실제 코드 발췌: 다음 페이지 적재

```javascript
const loadPage = useCallback(async (page) => {
    if (loadingRef.current) {
        return;
    }

    const controller = new AbortController();
    requestControllerRef.current = controller;
    loadingRef.current = true;

    try {
        setLoadError(null);
        const result = await postApi.getPosts({
            page,
            size: 10,
            signal: controller.signal,
        });

        if (controller.signal.aborted) {
            return;
        }

        setPosts((previous) => page === 0 ? result.posts : [...previous, ...result.posts]);
        setHasNextPage(result.hasNextPage);
        nextPageRef.current = page + 1;
        setFailedPage(null);
    } catch (requestError) {
        if (controller.signal.aborted || requestError?.name === "AbortError") {
            return;
        }
        if (requestControllerRef.current !== controller) {
            return;
        }
        setLoadError(requestError);
        setFailedPage(page);
    } finally {
        if (requestControllerRef.current === controller) {
            requestControllerRef.current = null;
            loadingRef.current = false;
        }
    }
}, []);

const cancelCurrentRequest = useCallback(() => {
    requestControllerRef.current?.abort();
    requestControllerRef.current = null;
    loadingRef.current = false;
}, []);

const loadNextPage = useCallback(() => {
    void loadPage(nextPageRef.current);
}, [loadPage]);
```

중요한 줄:

```javascript
[...previous, ...result.posts]
// 기존 게시글과 새 페이지 결과를 새 배열로 합친다.

nextPageRef.current = page + 1
// 성공했을 때만 다음 페이지 번호를 증가시킨다.

requestControllerRef.current === controller
// 종료되는 요청이 여전히 현재 요청일 때만 ref와 loading 잠금을 정리한다.
```

취소된 요청은 사용자가 다시 시도해야 하는 서버 오류가 아니다. 따라서 `AbortError`는 `loadError`에 넣지 않고 조용히 끝낸다. ref에 저장된 현재 요청의 controller와 각 요청의 지역 controller를 비교하여, 개발 StrictMode에서 먼저 취소된 요청의 `finally`가 새 요청의 잠금을 풀지 못하게 한다.

`loadNextPage`는 Observer가 호출할 때 `nextPageRef.current`에 저장된 번호를 `loadPage`에 전달한다. 첫 페이지와 다음 페이지 모두 같은 `loadPage`를 사용하므로 둘 다 동일한 중복 방지·취소·오류 처리를 거친다.

### 공통 `request`에서 `fetch`로 signal이 전달되는 줄

```javascript
const response = await fetch(`${API_BASE_URL}${endpoint}`, { // 실제 브라우저 HTTP 요청을 시작한다.
    ...options, // postApi가 전달한 signal을 포함한 모든 요청 옵션을 펼친다.
    headers, // 공통 Content-Type과 access token이 적용된 header를 사용한다.
    credentials: "include", // refresh token cookie를 함께 전송할 수 있게 한다.
});
```

`postApi.getPosts(..., signal)`에서 받은 `signal`이 `request`와 `sendRequest`의 `options`를 그대로 지나 이 `...options` 자리에 들어가므로 `fetch`가 취소 신호를 실제로 받는다.

## 7.8 실제 코드 발췌: IntersectionObserver

```javascript
useEffect(() => {
    const target = observerTargetRef.current;
    if (!target || !hasNextPage) {
        return;
    }

    const observer = new IntersectionObserver((entries) => {
        if (entries[0]?.isIntersecting) {
            onLoadMore();
        }
    });
    observer.observe(target);
    return () => observer.disconnect();
}, [hasNextPage, onLoadMore]);
```

감시용 DOM을 조건부로 만드는 실제 JSX:

```jsx
{hasNextPage && <div ref={observerTargetRef} className="scroll-observer-target" />}
```

`hasNextPage`가 false이면 `&&` 오른쪽 element를 만들지 않으므로 target이 DOM에서 제거된다. state 변경으로 Effect cleanup도 실행되어 기존 observer가 연결을 끊는다.

```text
목록 아래의 target이 화면에 들어옴
→ isIntersecting true
→ onLoadMore
→ nextPageRef의 페이지 요청
→ 게시글 누적
→ 다음 렌더링
```

cleanup에서 `disconnect()`하지 않으면 이전 Observer가 남아 중복 호출이나 메모리 누수가 생길 수 있다.

### `PostsPage` 상태와 ref

```javascript

const [failedPage, setFailedPage] = useState(null); // 재시도할 실패 페이지 번호를 기억한다.
const loadingRef = useRef(false); // 렌더링 없이 현재 요청 중인지 기억해 중복 호출을 막는다.

const nextPageRef = useRef(0); // 렌더링 없이 다음 요청 번호를 기억한다.
```

## 7.9 첫 요청, cleanup과 StrictMode

`PostsPage` 첫 요청 Effect의 실제 원문:

```javascript
useEffect(() => {
    void loadPage(0);

    return () => {
        cancelCurrentRequest();
    };
}, [cancelCurrentRequest, loadPage]);
```

화면이 처음 mount되면 `loadPage(0)`이 첫 페이지를 요청한다. 화면이 unmount되거나 Effect가 다시 구성되기 전 cleanup이 `cancelCurrentRequest()`를 호출한다.

```text
cleanup
→ 현재 AbortController의 abort() 호출
→ signal.aborted = true
→ signal이 연결된 fetch가 AbortError로 종료
→ catch는 취소를 일반 오류로 표시하지 않음
```

개발 환경에서 React StrictMode는 Effect의 setup과 cleanup이 올바른지 확인하기 위해 첫 mount 때 `setup → cleanup → setup`을 한 차례 추가로 수행할 수 있다. 이 경우 네트워크 탭에는 첫 요청이 시작된 뒤 취소되고 새 요청이 시작된 모습이 보일 수 있다.

```text
첫 setup → 요청 A 시작
개발용 cleanup → 요청 A 취소
두 번째 setup → 요청 B 시작
요청 A의 뒤늦은 정리 → B의 ref와 loading 상태를 건드리지 않음
요청 B 성공 → 화면에 반영
```

운영 빌드의 일반 mount에서는 이 개발용 추가 실행이 없다. 중요한 점은 현재 코드는 단순히 state 변경만 막는 것이 아니라, `AbortSignal`을 `fetch`에 연결해 목록 HTTP 요청 자체를 취소한다는 것이다.

### `loadPage`

```javascript
const loadPage = useCallback(async (page) => { // Observer와 재시도가 재사용할 안정된 비동기 함수를 만든다.
    if (loadingRef.current) { // 이미 페이지 요청이 진행 중인지 확인한다.
        return; // 진행 중이면 같은 또는 다음 요청을 중복 생성하지 않는다.
    }

    const controller = new AbortController(); // 이번 목록 요청만 제어할 새 controller를 만든다.
    requestControllerRef.current = controller; // cleanup이 현재 요청을 찾을 수 있게 ref에 저장한다.
    loadingRef.current = true; // 다른 페이지 요청이 겹치지 않도록 잠근다.

    try { // 요청 성공과 실패를 나눠 처리한다.
        setLoadError(null); // 새 시도 전 이전 오류 화면을 지운다.
        const result = await postApi.getPosts({ // 지정 페이지의 서버 응답을 기다린다.
            page, // 호출자가 요청한 페이지 번호다.
            size: 10, // 한 번에 게시글 열 개를 요청한다.
            signal: controller.signal, // controller의 취소 상태를 fetch까지 전달한다.
        });

        if (controller.signal.aborted) { // 응답 직후 이번 요청이 이미 취소됐는지 다시 확인한다.
            return; // 취소된 결과로 state를 변경하지 않는다.
        }

        setPosts((previous) => // 최신 이전 state를 인자로 받아 새 목록 state를 만든다.
            page === 0 // 첫 페이지 재요청인지 확인한다.
                ? result.posts // 첫 페이지면 기존 목록을 교체한다.
                : [...previous, ...result.posts] // 다음 페이지면 기존 뒤에 새 결과를 붙인다.
        );
        setHasNextPage(result.hasNextPage); // 서버의 다음 페이지 여부를 화면 상태에 저장한다.
        nextPageRef.current = page + 1; // 성공한 페이지의 다음 번호로 이동한다.
        setFailedPage(null); // 성공했으므로 실패 페이지 기록을 지운다.
    } catch (requestError) { // 공통 request가 던진 오류를 받는다.
        if (controller.signal.aborted || requestError?.name === "AbortError") { // 의도한 취소인지 확인한다.
            return; // 취소는 사용자에게 보여줄 API 실패로 저장하지 않는다.
        }
        if (requestControllerRef.current !== controller) { // 더 새로운 요청의 controller가 저장됐는지 확인한다.
            return; // 오래된 요청은 현재 화면 상태를 건드리지 않는다.
        }
        setLoadError(requestError); // 오류 화면이 렌더링되게 한다.
        setFailedPage(page); // 같은 페이지를 다시 시도할 수 있게 번호를 저장한다.
    } finally { // 성공·실패·취소 뒤에 실행한다.
        if (requestControllerRef.current === controller) { // 끝난 요청이 아직 현재 요청인지 확인한다.
            requestControllerRef.current = null; // 완료한 controller를 ref에서 제거한다.
            loadingRef.current = false; // 이 요청이 소유한 잠금만 해제한다.
        }
    }
}, []); // 함수 내부가 state 최신값 대신 ref와 setter를 사용하므로 최초 함수를 재사용한다.

const cancelCurrentRequest = useCallback(() => { // Effect cleanup이 호출할 안정된 취소 함수를 만든다.
    requestControllerRef.current?.abort(); // 현재 controller가 있으면 fetch에 취소 신호를 보낸다.
    requestControllerRef.current = null; // 취소한 controller를 현재 요청 자리에서 제거한다.
    loadingRef.current = false; // 다음 Effect setup이 새 요청을 시작할 수 있게 잠금을 푼다.
}, []); // ref만 사용하므로 같은 함수 객체를 계속 재사용한다.

const loadNextPage = useCallback(() => { // IntersectionObserver가 호출할 다음 페이지 함수를 만든다.
    void loadPage(nextPageRef.current); // 저장된 다음 페이지 번호를 읽어 취소 가능한 공통 로더에 전달한다.
}, [loadPage]); // loadPage가 같으면 같은 callback 객체를 재사용한다.
```

## 7.9.1 같은 취소 구조를 사용하는 다른 조회 화면

기존에는 다음 네 곳도 `active=false`로 늦은 state 변경만 막고 HTTP 요청은 계속 실행했다.

- `ProfileEditPage`: 내 정보 조회
- `PostDetailPage`: 게시글 상세 조회
- `PostEditPage`: 수정할 게시글 조회
- `AppHeader`: 헤더 프로필 이미지 조회

현재는 모두 Effect마다 `AbortController`를 만들고 cleanup에서 `abort()`한다. API module도 signal을 공통 `request`까지 전달한다.

```javascript
getMyInfo({ signal } = {}) { // signal을 생략해도 호출할 수 있도록 기본 빈 객체를 사용한다.
    return request("/users/me", { signal }); // 내 정보 요청과 취소 신호를 공통 request에 전달한다.
}

async getPost(postId, { signal } = {}) { // 게시글 ID와 선택적인 취소 신호를 받는다.
    return normalizeDetailPost( // 서버 상세 응답을 프론트에서 사용할 형태로 정규화한다.
        await request(`/posts/${postId}`, { signal }) // 상세 요청이 끝날 때까지 기다리며 signal을 fetch까지 전달한다.
    );
}
```

`ProfileEditPage`의 실제 Effect는 다음과 같다.

```javascript
useEffect(() => { // 첫 진입 또는 retryVersion 변경 때 내 정보를 다시 조회한다.
    const controller = new AbortController(); // 이번 Effect 조회만 취소할 controller를 만든다.
    setLoadError(null); // 새 조회를 시작하기 전에 이전 오류를 지운다.

    userApi.getMyInfo({ signal: controller.signal }) // 내 정보 요청에 취소 신호를 연결한다.
        .then((result) => { // 요청이 정상적으로 완료되면 실행한다.
            setUser(result); // 전체 사용자 정보를 state에 저장한다.
            setNickname(result.nickname ?? ""); // 닉네임이 없으면 빈 문자열을 입력값으로 사용한다.
            setPreviewUrl(result.profileImage ?? null); // 이미지가 없으면 미리보기 값을 null로 둔다.
            setLoadError(null); // 성공했으므로 오류를 비운다.
        })
        .catch((error) => { // 요청 실패 또는 취소를 받는다.
            if (controller.signal.aborted || error?.name === "AbortError") { // cleanup이 취소한 요청인지 검사한다.
                return; // 의도한 취소는 오류 화면으로 보내지 않는다.
            }
            setLoadError(error); // 실제 실패만 ErrorView에 전달한다.
        });

    return () => { // 재시도 Effect 전 또는 화면을 벗어날 때 실행한다.
        controller.abort(); // 진행 중인 내 정보 fetch를 실제로 취소한다.
        window.clearTimeout(toastTimerRef.current); // 이 화면에서 예약한 toast timer도 함께 정리한다.
    };
}, [retryVersion]); // 다시 시도 버튼이 version을 올리면 새 controller와 새 요청을 만든다.
```

나머지 세 곳의 취소 문법은 위와 같고, 화면별 차이만 다음과 같다.

| 위치 | 요청 전 처리 | 성공 후 처리 | Effect가 다시 실행되는 조건 |
|---|---|---|---|
| `PostDetailPage` | `post`, `comments`, 오류 초기화 | 상세와 댓글 저장 | `postId`, `retryVersion` 변경 |
| `PostEditPage` | 원본 게시글과 오류 초기화 | 본인 글·신고 기준 검사 후 수정 원본 저장 | `postId`, `retryVersion` 변경 |
| `AppHeader` | 프로필 표시가 필요하고 prop 이미지가 없을 때만 요청 | 헤더 이미지 저장 | `profileImage`, `showProfile` 변경 |

따라서 이제 이 네 화면도 경로나 조건이 바뀌어 Effect cleanup이 실행되면 이전 조회 결과를 단순히 무시하는 데서 끝나지 않고, 진행 중인 `fetch` 자체에 취소 신호를 보낸다. 로그인 만료로 공통 refresh 요청이 이미 시작된 경우에는 여러 API가 공유하는 refresh 작업은 계속될 수 있지만, 취소된 화면의 원래 조회와 refresh 뒤 재시도 조회에는 같은 signal이 적용된다.

### 첫 페이지 Effect와 요청 cleanup

```javascript
useEffect(() => { // mount 뒤 첫 페이지 요청을 외부 시스템인 네트워크와 연결한다.
    void loadPage(0); // 첫 페이지 Promise의 반환값을 사용하지 않고 요청을 시작한다.

    return () => { // 다음 Effect 실행 전 또는 unmount 때 실행할 cleanup을 반환한다.
        cancelCurrentRequest(); // 진행 중인 첫 페이지 또는 다음 페이지 fetch를 실제로 취소한다.
    };
}, [cancelCurrentRequest, loadPage]); // 두 함수 객체가 달라질 때 Effect를 다시 구성한다.
```

### 실패 페이지 재시도

```javascript
function retryLoadPage() { // ErrorView의 다시 시도 버튼이 호출한다.
    const page = failedPage ?? 0; // 기록된 실패 페이지가 없으면 첫 페이지 0을 사용한다.
    setLoadError(null); // 오류 화면을 지우고 목록 화면으로 돌아갈 준비를 한다.

    if (page === 0) { // 첫 페이지 실패를 다시 시도하는지 확인한다.
        nextPageRef.current = 0; // 다음 페이지 번호를 처음으로 되돌린다.
        setPosts([]); // 이전 목록을 빈 배열로 초기화한다.
        setHasNextPage(true); // 첫 응답을 받기 전까지 감시 대상을 다시 허용한다.
    }

    void loadPage(page); // 실패했던 페이지를 같은 취소 가능 함수로 다시 요청한다.
}
```

## 7.10 이 방식의 특성

현재는 page/offset 방식이다.

장점:

- 구현과 이해가 단순하다.
- Spring Data `PageRequest`를 바로 사용할 수 있다.

주의점:

- 앞쪽에 새 게시글이 추가되면 다음 페이지에서 중복이나 누락이 생길 수 있다.
- 페이지 번호가 커지면 DB offset 비용이 커질 수 있다.

커서 페이징은 마지막으로 본 ID를 기준으로 다음 데이터를 가져오지만 현재 프로젝트에는 구현되어 있지 않다.

이 절은 앞의 실제 코드 원문을 읽은 직후 확인한다. 원문과 같은 순서의 설명용 주석본이며 실제 실행 파일에는 주석이 없다.

### `IntersectionObserver`

```javascript
useEffect(() => { // target과 다음 페이지 여부에 맞춰 브라우저 Observer를 등록한다.
    const target = observerTargetRef.current; // 렌더링된 목록 아래 감시용 div DOM을 가져온다.
    if (!target || !hasNextPage) { // 아직 DOM이 없거나 더 가져올 페이지가 없는지 확인한다.
        return; // Observer를 만들 필요가 없으므로 종료한다.
    }

    const observer = new IntersectionObserver((entries) => { // target의 화면 진입 상태를 받을 Observer를 만든다.
        if (entries[0]?.isIntersecting) { // 첫 감시 대상이 viewport와 겹치는지 확인한다.
            onLoadMore(); // 부모가 전달한 다음 페이지 함수를 호출한다.
        }
    });

    observer.observe(target); // 실제 target DOM 감시를 시작한다.
    return () => observer.disconnect(); // 의존성 변경이나 unmount 시 이전 감시 연결을 제거한다.
}, [hasNextPage, onLoadMore]); // 다음 페이지 여부나 callback이 바뀌면 Observer를 다시 구성한다.
```

```jsx
{hasNextPage && <div ref={observerTargetRef} className="scroll-observer-target" />} // 다음 페이지가 있을 때만 감시용 빈 div를 DOM에 만든다.
```

## 7.12.1 이 장에서 필요한 React Hooks·비동기 문법

### `useState`

```javascript
const [posts, setPosts] = useState([]);
```

배열 구조 분해 문법으로 두 값을 받는다.

- `posts`: 현재 state
- `setPosts`: 새 state를 예약하는 함수
- `[]`: 초기값인 빈 배열

setter를 호출하면 React가 다시 렌더링한다. 변수에 직접 대입해서는 React가 변경을 알 수 없다.

### 구조 분해

```javascript
const { page = 0, size = 10 } = options;
const [state, setter] = useState(...);
```

객체는 이름으로, 배열은 순서로 내부 값을 꺼낸다. `= 0`은 값이 undefined일 때 사용할 기본값이다.

### `useRef`

```javascript
const loadingRef = useRef(false);
loadingRef.current = true;
```

ref 객체는 렌더링 사이에 유지되며 실제 값은 `.current`에 있다. `.current`를 바꿔도 다시 렌더링하지 않는다.

### `useEffect`

```javascript
useEffect(() => {
    외부작업();

    return () => 정리작업();
}, [dependency]);
```

렌더링 결과가 화면에 반영된 뒤 외부 시스템과 동기화한다. 반환 함수는 다음 Effect 전이나 unmount 때 실행하는 cleanup이다. 대괄호는 dependency 배열이며 그 값이 바뀔 때 Effect를 다시 구성한다.

### `useCallback`

```javascript
const loadPage = useCallback(() => { ... }, []);
```

dependency가 바뀌지 않는 동안 같은 함수 객체를 재사용한다. 자식 Effect가 callback identity 변화 때문에 불필요하게 다시 등록되는 것을 줄인다.

### 함수형 state update

```javascript
setPosts(previous => [...previous, ...newPosts]);
```

현재 렌더링이 캡처한 오래된 `posts` 대신 React가 보유한 가장 최신 이전값을 인자로 받는다. 연속 비동기 업데이트에서 안전하다.

### 배열 spread

```javascript
[...previous, ...result.posts]
```

두 배열의 원소를 새 배열 안에 펼친다. 기존 배열을 직접 수정하지 않는 불변 업데이트다.

### 삼항 연산자

```javascript
page === 0 ? result.posts : [...previous, ...result.posts]
```

조건이 참이면 첫 값, 거짓이면 콜론 뒤 값을 선택한다.

### strict equality

```javascript
page === 0
```

`===`는 타입 변환 없이 값과 타입이 모두 같은지 비교한다. JavaScript에서는 예상치 못한 자동 변환을 피하기 위해 `==`보다 주로 사용한다.

### optional chaining

```javascript
entries[0]?.isIntersecting
```

첫 원소가 없으면 오류 대신 undefined가 되어 조건이 거짓으로 처리된다.

### `void` 연산자

```javascript
void loadPage(nextPageRef.current);
```

Promise 반환값을 의도적으로 사용하지 않는다는 뜻이다. 함수 실행은 그대로 발생한다.

### `URLSearchParams`

객체 값을 URL query string 규칙에 맞게 encoding한다.

```text
{ page: "0", size: "10" }
→ page=0&size=10
```

### `IntersectionObserver`

브라우저가 대상 DOM과 viewport의 교차 상태를 비동기로 알려주는 API다. scroll event를 매번 직접 계산하지 않아도 된다.

### `AbortController`와 `AbortSignal`

`AbortController`는 취소를 지시하는 객체이고, 그 안의 `signal`은 취소 여부를 전달하는 객체다.

```javascript
const controller = new AbortController();
fetch(url, { signal: controller.signal });
controller.abort();
```

`abort()`가 실행되면 `signal.aborted`가 `true`가 되고, 이 signal을 받은 진행 중 `fetch`는 보통 `name`이 `"AbortError"`인 오류로 종료된다. 그래서 현재 코드는 취소 오류와 서버·네트워크 오류를 구분한다.

```javascript
requestControllerRef.current?.abort();
```

`?.`는 ref의 현재 값이 `null`이나 `undefined`가 아닐 때만 `abort()`를 호출하는 optional chaining이다. controller가 없으면 오류 없이 아무것도 하지 않는다.

### 현재 controller와 지역 controller를 비교하는 이유

```javascript
if (requestControllerRef.current === controller) {
    requestControllerRef.current = null;
    loadingRef.current = false;
}
```

각 `loadPage` 호출의 `controller`는 그 호출만의 지역 변수다. ref에는 가장 최근 요청의 controller가 들어 있다. 두 값이 같은 경우에만 정리하면, 이미 취소된 요청 A의 늦은 `finally`가 새 요청 B의 ref나 loading 잠금을 잘못 지우지 못한다.

### `&&` 조건부 rendering과 `??`

```jsx
{hasNextPage && <div ref={observerTargetRef} />}
```

왼쪽이 truthy이면 오른쪽 element를 반환하고, false이면 element를 만들지 않는다. JavaScript의 논리 연산 결과를 JSX가 조건부 UI에 사용하는 방식이다.

```javascript
const page = failedPage ?? 0;
```

`??`는 왼쪽이 `null` 또는 `undefined`일 때만 오른쪽 값을 사용한다. 실패한 페이지가 실제 숫자 `0`이면 그대로 유지한다.
