# 0장. 프로젝트를 코드가 아닌 실행 흐름으로 바라보기

## 0.1 이 프로젝트는 무엇인가?

이 프로젝트는 익명 게시판 서비스다. 사용자는 회원가입과 로그인을 한 뒤 게시글을 조회·작성·수정·삭제할 수 있고, 댓글·좋아요·신고 기능도 사용할 수 있다.

구조는 크게 네 부분으로 나뉜다.

1. React 프론트엔드
2. Spring Boot 백엔드
3. MySQL RDS와 Redis
4. Docker, Nginx, GitHub Actions를 이용한 배포 환경

각 부분은 별개의 프로그램처럼 보이지만, 실제로는 하나의 요청을 처리하기 위해 연결되어 있다.

예를 들어 사용자가 게시글 목록 화면을 열면 다음 일이 일어난다.

```text
사용자
→ 브라우저
→ React 게시글 목록 페이지
→ 프론트 API 코드
→ Nginx
→ Spring Security
→ Controller
→ Service
→ Repository
→ RDS
→ 역순으로 응답
→ React가 화면에 게시글을 그림
```

따라서 파일을 폴더 순서대로 무작정 읽으면 안 된다. 하나의 요청이 이동하는 순서를 따라가야 한다.

## 0.2 프론트엔드가 시작되는 위치

프론트엔드의 시작점은 `src/main.jsx`다.

실제 코드는 다음과 같다.

```jsx
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import { ErrorBoundary } from "react-error-boundary";
import { BrowserRouter } from "react-router-dom";
import App from "./App.jsx";

import "./styles/common.css";

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <ErrorBoundary
      fallback={(
        <main className="error-view error-view--app">
          <h1>화면을 표시하지 못했습니다.</h1>
          <p>잠시 후 다시 시도해주세요.</p>
          <button type="button" onClick={() => window.location.reload()}>
            새로고침
          </button>
        </main>
      )}
    >
      <BrowserRouter>
        <App />
      </BrowserRouter>
    </ErrorBoundary>
  </StrictMode>,
);
```


### `main.jsx` 전체 라인별 주석본

아래 주석은 학습을 위해 추가한 것이며 실제 파일에는 없다.

```jsx
import { StrictMode } from "react"; // 개발 중 컴포넌트와 Effect의 잠재적 문제를 추가 검사하는 컴포넌트를 가져온다.
import { createRoot } from "react-dom/client"; // HTML 요소 안에 React 애플리케이션을 렌더링할 함수를 가져온다.
import { ErrorBoundary } from "react-error-boundary"; // 하위 렌더링 오류를 잡고 대체 화면을 보여줄 컴포넌트를 가져온다.
import { BrowserRouter } from "react-router-dom"; // 브라우저 URL과 React 페이지를 연결할 Router를 가져온다.
import App from "./App.jsx"; // 애플리케이션의 최상위 App 컴포넌트를 가져온다.

import "./styles/common.css"; // 모든 페이지에 공통으로 적용할 CSS를 번들에 포함한다.

createRoot(document.getElementById('root')).render( // index.html에서 id가 root인 요소를 찾아 React 렌더링을 시작한다.
  <StrictMode> {/* 아래 컴포넌트 트리에 개발용 추가 검사를 적용한다. */}
    {/* 아래 트리에서 렌더링 예외가 발생하면 앱 전체 대신 fallback을 표시한다. */}
    <ErrorBoundary
      fallback={( // 오류가 발생했을 때 대신 렌더링할 JSX를 전달한다.
        <main className="error-view error-view--app"> {/* 오류 화면의 최상위 영역이며 CSS class 두 개를 적용한다. */}
          <h1>화면을 표시하지 못했습니다.</h1> {/* 오류의 핵심 제목을 표시한다. */}
          <p>잠시 후 다시 시도해주세요.</p> {/* 사용자에게 재시도를 안내한다. */}
          <button type="button" onClick={() => window.location.reload()}> {/* 클릭 시 현재 브라우저 문서를 새로고침한다. */}
            새로고침 {/* 버튼에 보이는 글자다. */}
          </button>
        </main>
      )}
    >
      <BrowserRouter> {/* 현재 URL을 읽고 AppRoutes가 라우팅할 수 있는 Context를 제공한다. */}
        <App /> {/* 실제 애플리케이션 컴포넌트 트리를 렌더링한다. */}
      </BrowserRouter>
    </ErrorBoundary>
  </StrictMode>,
);
```

`App.jsx`도 전체를 라인별로 보면 다음과 같다.

```jsx
import AppRoutes from "./routes/AppRoutes.jsx"; // URL별 페이지 정의가 있는 AppRoutes를 가져온다.

function App() { // 최상위 애플리케이션 컴포넌트를 선언한다.
    return <AppRoutes />; // 별도 화면을 직접 만들지 않고 라우팅 책임을 AppRoutes에 맡긴다.
}

export default App; // main.jsx가 App을 기본 import할 수 있도록 내보낸다.
```

이 코드를 아래에서 위가 아니라 바깥에서 안쪽으로 읽는다.

### `createRoot`

`index.html` 안의 `id="root"` 요소를 찾아서 React 애플리케이션을 그 안에 렌더링한다.

브라우저가 처음 읽는 파일은 `index.html`이고, 그 HTML이 `main.jsx`를 실행하며, `main.jsx`가 React 애플리케이션을 시작한다.

### `StrictMode`

개발 중에 위험한 코드나 부수 효과를 발견하기 위한 React 도구다.

개발 환경에서는 일부 생명주기와 Effect가 반복 실행된 것처럼 보일 수 있다. 이 때문에 게시글 목록 코드에는 최초 API 요청이 중복되지 않도록 막는 처리가 들어 있다. 그 처리는 페이징 장에서 다시 본다.

`StrictMode`가 사용자 화면을 직접 만드는 것은 아니다. 개발 중 문제를 발견하도록 돕는 바깥쪽 검사 장치라고 이해하면 된다.

### `ErrorBoundary`

하위 React 컴포넌트가 렌더링 도중 예외를 발생시키면 애플리케이션 전체가 빈 화면이 되는 대신 오류 화면을 보여준다.

중요한 점은 API의 400, 401, 500 응답을 모두 처리해 주는 장치가 아니라는 것이다. API 실패는 주로 `try/catch`, 상태값, `ErrorView`로 처리한다. `ErrorBoundary`는 렌더링 과정에서 예상하지 못한 JavaScript 예외가 발생했을 때의 마지막 방어선이다.

### `BrowserRouter`

현재 브라우저 주소에 따라 어떤 React 페이지를 보여줄지 결정할 수 있게 한다.

예를 들어 주소가 `/posts`이면 게시글 목록 페이지를 보여주고, `/login`이면 로그인 페이지를 보여준다.

### `App`

`App.jsx`는 현재 다음 역할만 한다.

```jsx
function App() {
    return <AppRoutes />;
}
```

실제 화면 선택 책임을 `AppRoutes`에 넘긴다. `App` 자체에는 별도의 업무 로직이 없다.

## 0.3 프론트엔드 라우팅 흐름

`src/routes/AppRoutes.jsx`는 URL과 페이지 컴포넌트를 연결한다.

대표적인 연결은 다음과 같다.

```text
/login             → LoginPage
/signup            → SignupPage
/posts             → PostsPage
/posts/new         → PostCreatePage
/posts/:postId     → PostDetailPage
/posts/:postId/edit → PostEditPage
```

여기서 `:postId`는 고정된 글자가 아니라 실제 게시글 ID가 들어가는 자리다.

예를 들어 `/posts/15`로 접속하면 `postId`는 `15`가 된다.

### 공개 페이지와 보호 페이지

라우트는 두 종류로 나뉜다.

```text
PublicOnlyRoute
→ 로그인, 회원가입

ProtectedRoute
→ 게시글, 프로필, 비밀번호 변경
```

`ProtectedRoute`는 `localStorage`에 Access Token이 있는지 확인한다.

- 토큰이 있으면 요청한 페이지를 보여준다.
- 토큰이 없으면 `/login`으로 이동시킨다.

반대로 `PublicOnlyRoute`는 이미 토큰이 있는 사용자가 로그인·회원가입 페이지에 접근하면 `/posts`로 이동시킨다.

여기서 주의할 점이 있다.

토큰이 존재한다는 사실과 토큰이 유효하다는 사실은 다르다. 라우트 코드는 토큰 문자열의 존재만 확인한다. 실제 서명, 만료 시간, 사용자 상태는 백엔드가 API 요청을 받을 때 검사한다.

따라서 다음과 같은 상황이 가능하다.

```text
만료된 토큰이 localStorage에 남아 있음
→ ProtectedRoute는 게시글 페이지를 보여줌
→ 게시글 API 요청은 401을 받음
→ 프론트 API 공통 코드가 Refresh Token으로 재발급 시도
```

이 과정은 보안 토큰 장에서 깊게 다룬다.


## 0.3.1 `ProtectedRoute`, `Navigate`, `Outlet`

### 실제 `ProtectedRoute.jsx` 원문

```jsx
import { Navigate, Outlet } from "react-router-dom";

import { authStorage } from "../auth/authStorage.js";

function ProtectedRoute() {
    if (!authStorage.isLoggedIn()) {
        return <Navigate to="/login" replace />;
    }

    return <Outlet />;
}

export default ProtectedRoute;
```

### 전체 라인별 주석본

```jsx
import { Navigate, Outlet } from "react-router-dom"; // Router가 제공하는 이동 컴포넌트와 자식 Route 자리 컴포넌트를 가져온다.

import { authStorage } from "../auth/authStorage.js"; // Access Token 존재 여부를 확인할 프로젝트 객체를 가져온다.

function ProtectedRoute() { // 인증이 필요한 여러 Route 앞에서 공통으로 실행할 React 함수 컴포넌트다.
    if (!authStorage.isLoggedIn()) { // localStorage에 Access Token이 존재하지 않는지 확인한다.
        return <Navigate to="/login" replace />; // 로그인하지 않았다면 현재 화면 대신 /login으로 이동한다.
    }

    return <Outlet />; // 로그인했다면 현재 URL과 일치한 자식 Route를 이 자리에 렌더링한다.
}

export default ProtectedRoute; // AppRoutes가 이름 없이 기본 import할 수 있도록 컴포넌트를 내보낸다.
```

### 실제 중첩 Route 원문

```jsx
<Route element={<ProtectedRoute />}>
    <Route path="/posts" element={page(<PostsPage />)} />
    <Route path="/posts/new" element={page(<PostCreatePage />)} />
    <Route path="/posts/:postId" element={page(<PostDetailPage />)} />
    <Route path="/posts/:postId/edit" element={page(<PostEditPage />)} />
    <Route path="/profile/edit" element={page(<ProfileEditPage />)} />
    <Route path="/password/edit" element={page(<PasswordEditPage />)} />
</Route>
```

### 전체 라인별 주석본

```jsx
<Route element={<ProtectedRoute />}> {/* path가 없는 부모 Route이며, 먼저 ProtectedRoute를 실행한다. */}
    <Route path="/posts" element={page(<PostsPage />)} /> {/*/posts가 일치하면 PostsPage가 부모의 Outlet에 들어간다. */}
    <Route path="/posts/new" element={page(<PostCreatePage />)} /> {/*/posts/new이면 생성 페이지가 Outlet에 들어간다. */}
    <Route path="/posts/:postId" element={page(<PostDetailPage />)} /> {/* :postId 자리에 실제 ID가 들어가는 상세 경로다. */}
    <Route path="/posts/:postId/edit" element={page(<PostEditPage />)} /> {/* 특정 게시글의 수정 페이지 경로다. */}
    <Route path="/profile/edit" element={page(<ProfileEditPage />)} /> {/* 사용자 프로필 수정 페이지 경로다. */}
    <Route path="/password/edit" element={page(<PasswordEditPage />)} /> {/* 비밀번호 수정 페이지 경로다. */}
</Route>
```

### `<Outlet />`의 실행 원리

`Outlet`은 `react-router-dom`이 제공하는 React 컴포넌트다. 부모 Route가 공통 처리를 끝낸 뒤, 현재 URL과 일치한 자식 Route를 표시할 위치를 뜻한다.

```text
사용자가 /posts 접근
→ path 없는 부모 Route의 ProtectedRoute 실행
→ 로그인하지 않음: Navigate 반환
→ 로그인함: Outlet 반환
→ Router가 Outlet 자리에 PostsPage 렌더링
```

`Outlet`이 없다면 로그인 검사는 통과하더라도 자식 Page를 표시할 위치가 없어 화면이 나타나지 않는다.

## 0.3.2 이 장에서 필요한 JavaScript·JSX 문법

### 이름 있는 import와 기본 import

```javascript
import { Navigate, Outlet } from "react-router-dom";
import App from "./App.jsx";
```

중괄호가 있는 import는 모듈이 이름을 붙여 내보낸 값을 정확한 이름으로 가져온다.

```text
export { Outlet }
↔ import { Outlet }
```

중괄호가 없는 import는 `export default`로 내보낸 값 하나를 가져오며, 가져오는 쪽에서 이름을 정할 수 있다.

```text
export default ProtectedRoute
↔ import ProtectedRoute from "./ProtectedRoute.jsx"
```

### 함수 컴포넌트

```jsx
function ProtectedRoute() {
    return <Outlet />;
}
```

React에서 JSX를 반환하는 JavaScript 함수는 컴포넌트로 사용할 수 있다. 컴포넌트 이름은 HTML 태그와 구분하기 위해 대문자로 시작한다.

```text
<div>          → 브라우저 기본 HTML 요소
<Outlet />     → JavaScript의 Outlet 컴포넌트
```

### JSX 자기 닫기 문법

내용이나 자식이 없는 JSX 요소는 다음 두 표현이 같은 의미다.

```jsx
<Outlet></Outlet>
<Outlet />
```

`<App />`, `<ProtectedRoute />`, `<Navigate />`도 같은 자기 닫기 문법이다.

### JSX 속성과 중괄호

```jsx
<Navigate to="/login" replace />
<Route element={<ProtectedRoute />} />
```

- `to="/login"`은 문자열 속성이다.
- `replace`는 값 없이 쓰면 `replace={true}`와 같다.
- `element={...}`의 중괄호는 JSX 안에서 JavaScript 표현식을 실행한다.
- `{<ProtectedRoute />}`는 React element 객체를 속성값으로 전달한다.

### 컴포넌트와 element의 차이

```text
ProtectedRoute
→ 함수 또는 컴포넌트 타입 그 자체

<ProtectedRoute />
→ 그 컴포넌트를 이용해 만든 React element
```

Route의 `element` 속성은 컴포넌트 함수 자체가 아니라 렌더링할 element를 받으므로 `element={ProtectedRoute}`가 아니라 `element={<ProtectedRoute />}`로 작성한다.

### 중첩 Route

부모 `<Route>`의 여는 태그와 닫는 태그 사이에 다른 `<Route>`를 쓰면 부모·자식 관계가 된다.

```jsx
<Route element={<ProtectedRoute />}>
    <Route path="/posts" element={<PostsPage />} />
</Route>
```

부모는 인증이나 공통 Layout을 담당하고, 자식은 URL별 실제 Page를 담당한다. 부모가 `<Outlet />`을 반환하면 현재 일치한 자식의 `element`가 그 위치에 표시된다.

### `if`, 논리 부정과 조기 반환

```javascript
if (!authStorage.isLoggedIn()) {
    return <Navigate to="/login" replace />;
}
```

- `authStorage.isLoggedIn()`은 함수 호출이다.
- 앞의 `!`는 true와 false를 반대로 바꾸는 논리 부정 연산자다.
- 조건이 참이면 즉시 `return`하여 아래 코드를 실행하지 않는다.
- 이런 구조를 조기 반환이라고 한다.

### 점 표기법

```javascript
authStorage.isLoggedIn()
```

`authStorage` 객체 안의 `isLoggedIn`이라는 함수를 찾아 호출한다. 점 앞은 객체이고 점 뒤는 그 객체가 가진 속성 또는 메서드 이름이다.

### `:postId`

```jsx
<Route path="/posts/:postId" ... />
```

콜론으로 시작하는 경로 부분은 고정 문자열이 아니라 URL parameter다.

```text
/posts/15
→ postId = "15"
```

이 값은 Page에서 `useParams()`를 이용해 읽는다.

## 0.3.3 `AppRoutes.jsx` 전체 코드로 라우팅 흐름 연결하기

앞에서는 `ProtectedRoute`만 떼어 보았다. 이제 실제 `AppRoutes.jsx` 전체를 보면서 `<Outlet />`에 들어갈 자식 Route가 어디에서 정해지는지 연결한다.

### 실제 `AppRoutes.jsx` 원문

```jsx
import { lazy } from "react";
import { Navigate, Route, Routes } from "react-router-dom";

import PageBoundary from "../components/layout/PageBoundary.jsx";
import ProtectedRoute from "./ProtectedRoute.jsx";
import PublicOnlyRoute from "./PublicOnlyRoute.jsx";

const LoginPage = lazy(() => import("../pages/auth/LoginPage.jsx"));
const SignupPage = lazy(() => import("../pages/auth/SignupPage.jsx"));
const PostsPage = lazy(() => import("../pages/posts/PostsPage.jsx"));
const PostDetailPage = lazy(() => import("../pages/posts/PostDetailPage.jsx"));
const PostCreatePage = lazy(() => import("../pages/posts/PostCreatePage.jsx"));
const PostEditPage = lazy(() => import("../pages/posts/PostEditPage.jsx"));
const ProfileEditPage = lazy(() => import("../pages/user/ProfileEditPage.jsx"));
const PasswordEditPage = lazy(() => import("../pages/user/PasswordEditPage.jsx"));

function page(element) {
    return <PageBoundary>{element}</PageBoundary>;
}

function AppRoutes() {
    return (
        <Routes>
            <Route path="/" element={<Navigate to="/posts" replace />} />

            <Route element={<PublicOnlyRoute />}>
                <Route path="/login" element={page(<LoginPage />)} />
                <Route path="/signup" element={page(<SignupPage />)} />
            </Route>

            <Route element={<ProtectedRoute />}>
                <Route path="/posts" element={page(<PostsPage />)} />
                <Route path="/posts/new" element={page(<PostCreatePage />)} />
                <Route path="/posts/:postId" element={page(<PostDetailPage />)} />
                <Route path="/posts/:postId/edit" element={page(<PostEditPage />)} />
                <Route path="/profile/edit" element={page(<ProfileEditPage />)} />
                <Route path="/password/edit" element={page(<PasswordEditPage />)} />
            </Route>

            <Route path="*" element={<Navigate to="/posts" replace />} />
        </Routes>
    );
}

export default AppRoutes;
```

### 전체 라인별 주석본

```jsx
import { lazy } from "react"; // 페이지 코드를 필요할 때 불러오는 React의 lazy 함수를 가져온다.
import { Navigate, Route, Routes } from "react-router-dom"; // 주소 이동, 개별 경로 선언, 경로 묶음을 담당하는 컴포넌트를 가져온다.

import PageBoundary from "../components/layout/PageBoundary.jsx"; // 각 페이지의 로딩과 렌더링 오류를 공통 처리할 컴포넌트를 가져온다.
```

### `const`, 화살표 함수, 동적 `import()`와 `lazy`

```jsx
const LoginPage = lazy(() => import("../pages/auth/LoginPage.jsx"));
```

- `const`는 변수에 다른 값을 다시 대입하지 않겠다는 선언이다.
- `() => ...`는 매개변수가 없는 화살표 함수다. 호출되면 화살표 오른쪽 표현식을 반환한다.
- 정적인 `import X from "..."`는 파일 실행 시 모듈을 바로 불러온다.
- 함수처럼 사용한 `import("...")`는 필요할 때 모듈을 비동기로 불러오며 `Promise`를 반환한다.
- `lazy`는 이 비동기 import를 React 컴포넌트처럼 사용할 수 있게 감싼다.

따라서 사용자가 `/login`에 가지 않았다면 `LoginPage.jsx` 코드 묶음은 처음 화면을 시작할 때 내려받지 않을 수 있다. 페이지별로 코드 파일을 나누어 필요할 때 받는 방식을 코드 분할이라고 한다.

### `Routes`, `Route`, `path="*"`

- `<Routes>`는 현재 주소와 일치하는 Route 조합을 고른다.
- `<Route>`는 `path`와 그때 보여줄 `element`의 관계를 선언한다.
- `path="/"`는 정확히 루트 주소를 뜻한다.
- `path="*"`의 별표는 앞에서 일치하지 않은 나머지 모든 주소를 뜻한다.

`Route`는 화면에 보이는 일반 HTML 태그가 아니다. Router가 읽는 경로 설정용 React 컴포넌트다.

### `page(element)`와 JSX의 `children`

```jsx
function page(element) {
    return <PageBoundary>{element}</PageBoundary>;
}
```

`page(<PostsPage />)`를 호출하면 `<PostsPage />` element가 `element` 매개변수에 들어간다. JSX 태그의 여는 태그와 닫는 태그 사이에 값을 쓰면 그 값은 특별한 `children` prop으로 전달된다.

```text
page(<PostsPage />)
→ <PageBoundary>{<PostsPage />}</PageBoundary>
→ PageBoundary의 children은 <PostsPage />
```

이 보조 함수 덕분에 모든 Route마다 `<PageBoundary>...</PageBoundary>`를 반복하지 않는다.

### `PublicOnlyRoute`는 `ProtectedRoute`의 반대 검사다

```jsx
function PublicOnlyRoute() {
    if (authStorage.isLoggedIn()) {
        return <Navigate to="/posts" replace />;
    }

    return <Outlet />;
}
```

로그인 상태이면 로그인·회원가입 화면을 다시 보여주지 않고 게시글 목록으로 이동한다. 로그인하지 않은 상태이면 `<Outlet />`을 반환하여 `/login` 또는 `/signup` 중 현재 주소와 일치하는 자식 페이지를 보여준다.

## 0.3.4 `PageBoundary`: 페이지 로딩과 렌더링 오류의 공통 경계

### 실제 `PageBoundary.jsx` 원문

```jsx
import { Suspense } from "react";
import { ErrorBoundary } from "react-error-boundary";
import { useLocation, useNavigate } from "react-router-dom";

import ErrorView from "../common/ErrorView.jsx";
import LoadingView from "../common/LoadingView.jsx";

function PageBoundary({ children }) {
    const location = useLocation();
    const navigate = useNavigate();

    return (
        <ErrorBoundary
            key={location.key}
            fallbackRender={({ resetErrorBoundary }) => (
                <ErrorView
                    message="페이지를 다시 열거나 게시글 목록으로 이동해주세요."
                    onRetry={() => {
                        resetErrorBoundary();
                        navigate(0);
                    }}
                />
            )}
        >
            <Suspense fallback={<LoadingView />}>
                {children}
            </Suspense>
        </ErrorBoundary>
    );
}

export default PageBoundary;
```

### 전체 라인별 주석본

```jsx
import { Suspense } from "react"; // lazy 컴포넌트 파일을 기다리는 동안 대체 화면을 보여주는 컴포넌트를 가져온다.
import { ErrorBoundary } from "react-error-boundary"; // 하위 렌더링 오류를 잡을 경계 컴포넌트를 가져온다.
import { useLocation, useNavigate } from "react-router-dom"; // 현재 위치 정보와 화면 이동 함수를 얻는 Hook을 가져온다.

import ErrorView from "../common/ErrorView.jsx"; // 오류 발생 시 보여줄 프로젝트 컴포넌트를 가져온다.
import LoadingView from "../common/LoadingView.jsx"; // 지연 로딩 중 보여줄 프로젝트 컴포넌트를 가져온다.

function PageBoundary({ children }) { // props 객체에서 children 속성만 구조 분해하여 받는다.
    const location = useLocation(); // 현재 URL 위치를 나타내는 location 객체를 얻는다.
    const navigate = useNavigate(); // 코드에서 주소 이동이나 새로고침을 실행할 navigate 함수를 얻는다.

    return ( // 여러 줄의 JSX를 반환한다.
        <ErrorBoundary // 아래 자식 트리에서 발생하는 렌더링 오류를 잡는다.
            key={location.key} // 위치 항목의 key가 바뀌면 React가 이 경계를 새 인스턴스로 취급하게 한다.
            fallbackRender={({ resetErrorBoundary }) => ( // 오류 시 받은 객체에서 초기화 함수를 꺼내 대체 JSX를 반환한다.
                <ErrorView // 공통 오류 화면 컴포넌트를 렌더링한다.
                    message="페이지를 다시 열거나 게시글 목록으로 이동해주세요." // ErrorView에 안내 문장을 문자열 prop으로 전달한다.
                    onRetry={() => { // ErrorView의 재시도 동작으로 실행할 콜백 함수를 전달한다.
                        resetErrorBoundary(); // ErrorBoundary가 기억하는 오류 상태를 초기화한다.
                        navigate(0); // 현재 주소를 다시 불러 페이지 전체 동작을 재시도한다.
                    }}
                />
            )}
        >
            <Suspense fallback={<LoadingView />}> {/* lazy 페이지 파일이 준비되지 않았을 때 LoadingView를 대신 표시한다. */}
                {children} {/* 실제 페이지 렌더링을 시도하며, lazy 파일을 기다려야 하면 그동안 fallback이 표시된다. */}
            </Suspense>
        </ErrorBoundary>
    );
}

export default PageBoundary; // 다른 파일에서 기본 import할 수 있도록 내보낸다.
```

### props 구조 분해와 `children`

React는 컴포넌트에 전달한 속성을 하나의 `props` 객체로 넘긴다.

```jsx
function PageBoundary(props) {
    const children = props.children;
}
```

위 코드를 객체 구조 분해 문법으로 줄이면 실제 코드가 된다.

```jsx
function PageBoundary({ children }) {
}
```

`children`은 `<PageBoundary>`의 여는 태그와 닫는 태그 사이에 전달된 내용이다.

### `Suspense`와 `fallback`

`lazy`로 만든 페이지는 파일을 내려받는 시간이 필요할 수 있다. 아직 준비되지 않았을 때 `Suspense`가 `fallback` element를 대신 렌더링하고, 준비가 끝나면 `children`으로 교체한다.

```text
lazy 페이지 준비 전 → LoadingView
lazy 페이지 준비 완료 → 실제 Page
```

여기서 `Suspense`는 일반적인 `fetch()` API 요청의 로딩 상태를 자동 처리하는 코드가 아니다. 이 위치에서는 주로 `lazy(() => import(...))`의 코드 로딩을 기다린다. 현재 `PostsPage`는 API 요청 중인지 `loadingRef`에 기록해 중복 요청을 막지만, 그 값을 state로 관리하거나 별도의 로딩 화면을 표시하지는 않는다. 요청에 실패하면 `loadError` state를 바꾸어 `ErrorView`를 표시한다.

### `fallbackRender`, 콜백과 매개변수 구조 분해

```jsx
fallbackRender={({ resetErrorBoundary }) => (
    <ErrorView />
)}
```

`fallbackRender`에는 JSX 결과가 아니라 함수가 전달된다. 오류가 나면 `ErrorBoundary`가 그 함수를 호출하면서 여러 값을 담은 객체를 넘긴다. `({ resetErrorBoundary })`는 그 객체 중 필요한 함수 하나만 바로 꺼내는 매개변수 구조 분해다. 소괄호로 둘러싼 화살표 함수 본문은 JSX를 즉시 반환한다.

### `key={location.key}`와 `navigate(0)`

React에서 `key`가 바뀌면 같은 위치의 컴포넌트라도 새 컴포넌트로 판단할 수 있다. 브라우저의 위치 항목이 바뀌어 `location.key`가 달라지면 오류 경계도 새로 시작할 수 있다.

`navigate("/posts")`처럼 문자열을 전달하면 해당 주소로 이동한다. `navigate(0)`처럼 숫자 `0`을 전달하면 현재 페이지를 다시 불러오는 동작으로 사용된다. 재시도 버튼은 오류 상태를 초기화한 뒤 현재 페이지를 다시 실행한다.

### 라우팅 전체 실행 순서

```text
브라우저 주소 /posts
→ BrowserRouter가 주소를 Router에 제공
→ Routes가 /posts와 일치하는 Route 조합 선택
→ 부모 ProtectedRoute 실행
→ 로그인하지 않음: Navigate로 /login 이동
→ 로그인함: Outlet 반환
→ Outlet 자리에 page(<PostsPage />) 배치
→ PageBoundary가 lazy 코드 로딩 중 LoadingView 표시
→ 로딩 완료 후 PostsPage 표시
→ 렌더링 오류가 나면 ErrorBoundary가 ErrorView 표시
```

## 0.4 페이지, 컴포넌트, API 코드의 역할

프론트엔드는 다음 세 층으로 나누어 생각하면 편하다.

### Page

URL 하나에 대응하는 화면 단위다.

예:

- `PostsPage`
- `PostDetailPage`
- `LoginPage`

Page는 주로 다음을 담당한다.

- API 요청
- 로딩·성공·실패 상태 관리
- 사용자 이벤트 처리
- 여러 하위 컴포넌트 조립

### Component

화면의 일부를 표현한다.

예:

- `PostList`
- `PostListItem`
- `LoginForm`
- `ActionButton`

컴포넌트는 가능한 한 전달받은 데이터와 함수를 이용해 화면을 그린다.

### API module

백엔드 주소와 HTTP 메서드를 알고 있는 코드다.

예:

- `api.js`: 모든 API가 공통으로 사용하는 요청 처리
- `authApi.js`: 로그인, 로그아웃, 회원가입
- `postApi.js`: 게시글, 댓글, 좋아요, 신고
- `userApi.js`: 사용자 정보 변경

게시글 목록을 예로 들면 호출 순서는 다음과 같다.

```text
PostsPage
→ postApi.getPosts()
→ 공통 request()
→ fetch()
→ 백엔드
```

응답은 반대 방향으로 돌아온다.

```text
백엔드 JSON
→ 공통 request()
→ postApi가 데이터 정규화
→ PostsPage가 state 변경
→ PostList가 다시 렌더링
```

## 0.5 백엔드가 시작되는 위치

백엔드의 시작점은 `SpringdatajpaApplication.java`다.

핵심은 다음 구조다.

```java
@SpringBootApplication
public class SpringdatajpaApplication {

    public static void main(String[] args) {
        SpringApplication.run(SpringdatajpaApplication.class, args);
    }
}
```

`SpringApplication.run`이 실행되면 Spring은 패키지 아래를 탐색하며 다음과 같은 클래스를 찾는다.

- `@Controller`, `@RestController`
- `@Service`
- `@Repository`
- `@Component`
- `@Configuration`

찾은 클래스의 객체를 Spring 컨테이너가 만들고 서로 필요한 의존성을 연결한다.

예를 들어 `PostController`는 `PostService`를 직접 `new`로 생성하지 않는다.

```java
private final PostService postService;
```

Spring이 `PostService` 객체를 찾아서 `PostController` 생성자에 넣어 준다. 이것이 이 프로젝트에서 반복해서 등장하는 생성자 주입이다.

`@RequiredArgsConstructor`는 Lombok이 `final` 필드를 받는 생성자를 자동으로 만들어 주는 역할을 한다.


### Spring Boot 진입점 라인별 주석본

```java
@SpringBootApplication // 자동 설정, Component 탐색과 설정 등록을 한 번에 활성화한다.
public class SpringdatajpaApplication { // 백엔드 애플리케이션의 최상위 시작 클래스를 선언한다.

    public static void main(String[] args) { // JVM이 프로그램 시작 시 가장 먼저 호출하는 메서드다.
        SpringApplication.run(SpringdatajpaApplication.class, args); // Spring Context를 만들고 내장 웹 서버를 시작한다.
    }
}
```

### 생성자 주입 필드 라인별 주석본

```java
private final PostService postService; // Controller가 사용할 Service 의존성이며 final이므로 생성 시 반드시 전달되어야 한다.
```

클래스의 `@RequiredArgsConstructor`가 이 `final` 필드를 받는 생성자를 만들고, Spring이 등록된 `PostService` Bean을 그 생성자에 주입한다.

### Spring Boot 진입점에서 사용된 Java 문법

```java
@SpringBootApplication
public class SpringdatajpaApplication {
    public static void main(String[] args) {
        SpringApplication.run(SpringdatajpaApplication.class, args);
    }
}
```

- `@SpringBootApplication`의 `@`는 annotation 문법이다. 클래스에 Spring Boot 시작 설정이라는 부가 정보를 붙인다.
- `public class 이름`은 어디서든 접근할 수 있는 클래스를 선언한다.
- `{ ... }`는 클래스나 메서드에 포함되는 코드 범위를 묶는다.
- `public`은 JVM이 클래스 밖에서도 `main`에 접근할 수 있게 한다.
- `static`은 객체를 먼저 `new`로 만들지 않아도 클래스에 속한 메서드로 호출할 수 있다는 뜻이다.
- `void`는 메서드가 호출자에게 결과값을 반환하지 않는다는 반환 타입이다.
- `main`은 JVM이 프로그램 시작점으로 찾기로 약속한 메서드 이름이다.
- `String[]`은 문자열 여러 개를 담는 배열 타입이고 `args`는 그 매개변수의 이름이다.
- `SpringApplication.run(...)`에서 점은 클래스가 가진 `run` 메서드에 접근한다는 뜻이다.
- `SpringdatajpaApplication.class`는 객체가 아니라 해당 클래스 자체의 메타데이터를 나타내는 `Class` 객체다. Spring은 이를 시작 설정의 기준으로 사용한다.
- 쉼표는 메서드에 전달하는 여러 argument를 구분하고, 세미콜론은 Java 문장 하나가 끝났음을 표시한다.

`public static void main(String[] args)`를 한 문장으로 읽으면 “외부에서 접근 가능하고, 객체 생성 없이 JVM이 호출하며, 반환값이 없고, 문자열 배열 하나를 받는 시작 메서드”다.

### `private final`과 의존성 필드

```java
private final PostService postService;
```

- `private`은 이 필드를 선언한 클래스 내부에서만 직접 접근할 수 있게 한다.
- `final` 필드는 한 번 초기화한 뒤 다른 객체로 다시 대입할 수 없다.
- 첫 번째 `PostService`는 필드에 담을 수 있는 객체의 타입이다.
- 두 번째 `postService`는 코드에서 그 객체를 가리키는 필드 이름이다.
- 이 줄은 객체를 생성하지 않는다. `new PostService(...)`가 없기 때문이다.

`@RequiredArgsConstructor`가 `final` 필드를 매개변수로 받는 생성자를 만들고 Spring이 그 생성자를 호출할 때 실제 `PostService` Bean을 전달한다. 따라서 Controller는 생성 책임을 갖지 않고 이미 만들어진 Service를 사용한다.

## 0.6 백엔드 요청 처리 계층

백엔드는 일반적으로 다음 순서로 요청을 처리한다.

```text
Filter
→ Interceptor
→ Controller
→ Service
→ Repository
→ Database
```

각 계층의 역할을 구분해야 한다.

### Filter

Spring MVC의 Controller에 도달하기 전 단계에서 요청을 검사한다.

이 프로젝트의 `JwtAuthenticationFilter`는 다음을 담당한다.

- Authorization 헤더 확인
- Access Token 검증
- 사용자 조회
- 인증 정보를 SecurityContext에 저장

### Interceptor

Controller 실행 전후에 공통 처리를 추가한다.

이 프로젝트에서는 다음 용도로 사용한다.

- 요청 로그
- Refresh Token 쿠키를 사용하는 API의 Origin 검사

Filter와 Interceptor는 모두 Controller 앞에 있지만, 실행되는 계층과 책임이 다르다. 지금은 Filter가 더 바깥쪽 보안 관문이고 Interceptor가 Spring MVC 안쪽의 공통 관문이라고 이해하면 충분하다.

### Controller

HTTP 요청을 Java 메서드 호출로 변환한다.

Controller는 다음 정보를 읽는다.

- URL
- HTTP 메서드
- Path Variable
- Query Parameter
- JSON Request Body
- 로그인 사용자

그리고 Service에 업무 처리를 요청한다.

Controller는 복잡한 비즈니스 규칙을 직접 처리하지 않는 것이 기본 방향이다.

### Service

실제 업무 규칙과 작업 순서를 담당한다.

예를 들면 게시글 상세 조회 Service는 다음 작업을 조합한다.

- 게시글이 존재하는지 확인
- 삭제·신고 차단된 게시글인지 확인
- 로그인 사용자 확인
- 댓글 조회
- 좋아요·신고·작성자 여부 확인
- 조회수 증가
- 응답 DTO 생성

여러 Repository 호출과 검증을 하나의 업무 흐름으로 묶는 곳이다.

### Repository

Entity를 DB에 저장하거나 DB에서 조회한다.

Spring Data JPA가 기본 CRUD 구현을 제공하며, 메서드 이름이나 `@Query`를 이용해 프로젝트에 필요한 조회를 추가한다.

### Entity

DB 테이블과 연결되는 객체이면서 해당 데이터가 지켜야 할 상태 변경 규칙을 가진다.

예를 들어 `Post`는 단순히 제목과 내용을 저장하는 것뿐 아니라 다음 행동도 가진다.

- 게시글 수정
- 이미지 교체
- 삭제 상태 전환
- 신고 처리

## 0.7 RDS와 Redis의 역할 차이

이 프로젝트는 데이터를 모두 같은 저장소에 넣지 않는다.

### RDS MySQL

영구적으로 보존해야 하는 원본 데이터를 저장한다.

예:

- 사용자
- 게시글
- 댓글
- 좋아요
- 신고
- 로그인 Refresh Session
- 영구 반영된 조회수

### Redis

빠르게 자주 변경되는 게시글 조회수를 우선 처리한다.

게시글 상세 조회 때마다 RDS의 같은 행을 수정하면 요청이 몰릴 때 DB 경합이 커질 수 있다. 그래서 조회수 증가는 먼저 Redis에서 처리하고, Scheduler가 일정 주기마다 변경된 조회수를 RDS에 반영한다.

흐름은 다음과 같다.

```text
게시글 상세 조회
→ Redis 조회수 증가
→ dirty 게시글로 표시
→ Scheduler 실행
→ 분산 락 획득
→ Redis 조회수 snapshot 읽기
→ RDS에 반영
→ 반영 중 값이 바뀌지 않았을 때만 dirty 표시 제거
```

Redis가 최종 원본 저장소가 아니라 빠른 변경을 받아 주는 중간 저장소라는 점이 중요하다.

## 0.8 배포 환경에서 요청이 이동하는 과정

운영에서는 사용자가 React 개발 서버나 Spring Boot 포트에 직접 접근하지 않는다.

프론트엔드 Nginx가 외부 요청을 먼저 받는다.

```text
GET /posts
→ 활성 프론트엔드 컨테이너
→ React index.html 반환
```

API 요청은 별도로 백엔드로 전달한다.

```text
GET /api/posts
→ 프론트 배포 Nginx
→ /api 접두사 제거
→ 백엔드 Nginx
→ 활성 Spring Boot 컨테이너
→ GET /posts
```

프론트 API 코드가 운영에서 `/api`를 기준 주소로 사용하는 이유가 여기에 있다.

블루–그린 배포에서는 같은 역할의 컨테이너를 두 개 준비한다.

```text
현재 blue가 서비스 중
→ 새 버전을 green에 실행
→ green health check
→ Nginx 대상을 green으로 변경
→ 외부 health check
→ 기존 blue 중지
```

새 컨테이너가 정상인지 확인하기 전에는 사용자 트래픽을 넘기지 않는 구조다.

## 0.9 지금 단계에서 스킵할 코드

아직 다음 코드는 자세히 읽지 않는다.

- 각각의 DTO 필드
- Entity 연관관계 세부 설정
- JWT 생성과 검증 구현
- Redis Lua 스크립트
- 페이징 상태 관리
- Dockerfile 명령

지금은 이 코드들이 각각 다음 맥락에 있다는 것만 기억한다.

```text

Entity          → DB 데이터와 상태 변경 규칙
JWT 코드        → 인증 정보 생성과 검증
Redis 코드      → 조회수의 빠른 증가와 RDS 반영

Docker/Compose  → 프로그램을 같은 방식으로 실행하기
CI/CD YAML      → 테스트, 이미지 빌드, 배포 자동화
테스트 코드     → 각 규칙이 실제로 지켜지는지 검증
```

## 0.11 전체 모범 답안

1. Spring Controller가 아니라 프론트엔드의 React 진입점인 `main.jsx`가 처음 실행된다.
2. `AppRoutes`는 현재 URL과 표시할 Page를 연결하고, 인증이 필요한 경로인지 등의 라우팅 규칙을 적용한다.
3. Page는 하나의 URL 화면과 그 화면의 상태·요청 흐름을 관리하고, Component는 화면을 구성하는 재사용 가능한 부분을 담당하며, API module은 backend로 HTTP 요청을 보내고 응답을 받는다.
4. 확정할 수 없다. 토큰이 만료되었거나 변조되었거나 현재 사용자 상태와 맞지 않을 수 있으므로 backend의 검증이 필요하다.
5. 요청은 Servlet Filter와 Spring MVC Interceptor를 거친 뒤 Controller에 도달할 수 있다.
6. Controller는 HTTP 요청을 받고 응답하며, Service는 업무 규칙과 작업 순서를 담당하고, Repository는 설정된 DB 연결을 사용해 데이터를 조회·저장·수정·삭제한다.
7. RDS는 회원·게시글 같이 영구 보존해야 하는 데이터를 담고, Redis는 조회수처럼 빠른 처리가 필요한 데이터를 먼저 처리한 뒤 RDS에 반영한다.
8. `브라우저 → 프론트 Nginx → /api 접두사 제거 → backend Nginx → 활성 Spring container → Filter → Interceptor → PostController`의 순서로 이동한다.
9. 새 container가 정상적으로 실행되는지 먼저 확인해 문제가 있는 버전으로 사용자 traffic이 전환되는 것을 막는다.
10. 현재 nested URL과 일치하는 자식 `Route`의 `element`, 즉 해당 Page component가 `<Outlet />` 자리에 표시된다.
11. `<PostsPage />`는 `PageBoundary`의 `children` prop으로 전달된다.
12. `lazy(() => import(...))`의 Page JavaScript 파일 로딩은 `PageBoundary`의 `Suspense` fallback이 처리한다. 게시글 API 응답은 `PostsPage`의 요청 코드가 기다리며, 현재 코드에는 그 대기 시간에 표시할 별도의 로딩 화면이 없다.
13. `ProtectedRoute`는 Access Token이 있으면 통과시키고 없으면 login Page로 보낸다. `PublicOnlyRoute`는 Access Token이 없으면 통과시키고 있으면 게시글 목록으로 보낸다.

다음 장에서는 백엔드 설정의 출발점인 `build.gradle`과 `application*.yaml`을 읽으며, 라이브러리·프로필·환경변수가 실제 Java 코드와 어떻게 연결되는지 학습한다.


## 0.12 오답노트

이 장의 이해 확인 문제에서 틀렸거나 핵심 설명이 부족했던 문제를 누적한다. 다시 답을 맞히더라도 어떤 부분을 혼동했는지 복습할 수 있도록 문제를 삭제하지 않고 상태를 `보완 완료`로 변경한다.

### 0-2. `AppRoutes`는 어떤 책임을 가지는가?

- 최초 답: 화면을 출력하는 책임
- 부족했던 부분: 실제 화면을 만드는 Page·Component의 책임과 URL에 맞는 페이지를 선택하는 라우터의 책임이 구분되지 않았다.
- 정답: `AppRoutes`는 현재 URL과 표시할 Page를 연결하고 어떤 페이지를 선택할지 결정한다.
- 상태: 보완 완료

### 0-5. 백엔드 요청은 Controller에 도달하기 전에 무엇을 거칠 수 있는가?

- 최초 답: Filter
- 부족했던 부분: Filter 뒤에서 Spring MVC의 Interceptor도 거칠 수 있다는 내용이 빠졌다.
- 정답: 이 프로젝트의 일반적인 순서는 `Filter → Interceptor → Controller`다. 요청 경로와 메서드에 따라 특정 Filter나 Interceptor를 건너뛸 수 있다.
- 상태: 보완 완료

### 0-6. Controller, Service, Repository의 책임은 각각 무엇인가?

- 최초 답: 모름
- 두 번째 답: Controller는 HTTP 응답을 백엔드로 보내고, Service는 실제 작업을 관리하고, Repository는 데이터베이스와의 연결을 담당한다.
- 혼동한 부분: Controller의 요청·응답 방향을 반대로 이해했고, Repository가 DB 연결 설정 자체를 담당한다고 표현했다.
- 정답:
  - Controller는 클라이언트의 HTTP 요청을 받고 HTTP 응답을 반환한다.
  - Service는 업무 규칙과 작업 순서를 담당한다.
  - Repository는 이미 설정된 DB 연결을 사용하여 데이터를 조회·저장·수정·삭제한다.
- 상태: 재복습 필요

### 0-8. `/api/posts` 요청이 운영 환경에서 백엔드의 `/posts`까지 어떻게 이동하는가?

- 최초 답: 모름
- 두 번째 답: Nginx를 거쳐 백엔드 Spring으로 간다.
- 부족했던 부분: 프론트 Nginx와 백엔드 Nginx의 역할, `/api` 접두사 제거, Spring 내부 진입 순서가 빠졌다.
- 정답: `브라우저 → 프론트 Nginx → /api 접두사 제거 → 백엔드 Nginx → 활성 Spring 컨테이너 → Filter → Interceptor → PostController` 순서로 이동한다.
- 상태: 재복습 필요

### 0-9. 블루–그린 배포에서 새 컨테이너를 먼저 검사하는 이유는 무엇인가?

- 최초 답: 배포하기 위해
- 두 번째 답: 잘못된 버전을 배포하지 않기 위해서
- 정답: 새 버전의 컨테이너가 정상적으로 실행되는지 확인하고, 문제가 있는 버전으로 사용자 트래픽이 전환되는 것을 막기 위해서다.

### 0-12. `lazy` 페이지 파일 로딩과 게시글 API 로딩은 각각 어디에서 처리하는가?

- 최초 답: `Suspense`에서 로딩 중에 다른 화면을 보여준다.
- 부족했던 부분: `Suspense`가 처리하는 페이지 JavaScript 파일 로딩만 답했고, 게시글 API 응답을 기다리는 로딩 처리가 빠졌다.
- 정답: `lazy(() => import(...))`로 불러오는 페이지 파일의 로딩 화면은 `PageBoundary` 안의 `Suspense`가 처리한다. 현재 게시글 API 요청은 `PostsPage`가 실행한 뒤 `await` 또는 Promise callback으로 기다린다. `loadingRef`는 중복 요청을 막는 용도이고 렌더링을 일으키는 state가 아니므로, API를 기다리는 동안 별도의 로딩 화면은 표시되지 않는다. 실패하면 `loadError` state를 통해 `ErrorView`를 표시한다.
- 상태: 재복습 필요

### 0-13. `PublicOnlyRoute`와 `ProtectedRoute`의 통과 조건은 어떻게 반대인가?

- 최초 답: Access Token 유무
- 부족했던 부분: 판단 기준은 맞지만 각 Route가 토큰이 있을 때와 없을 때 어떻게 행동하는지 구분하지 않았다.
- 정답: `ProtectedRoute`는 Access Token이 있으면 자식 Route를 보여주고, 없으면 로그인 페이지로 이동시킨다. `PublicOnlyRoute`는 Access Token이 없으면 자식 Route를 보여주고, 있으면 게시글 목록으로 이동시킨다.
- 상태: 재복습 필요
