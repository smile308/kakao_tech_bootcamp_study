# 14장. 전체 파일 지도와 끝에서 처음까지의 흐름

## 14.1 이 장의 목적

앞 장들은 주제별로 코드를 나눠 설명했다. 이 장은 실제 프로젝트를 처음 열었을 때 어떤 순서로 파일을 읽어야 하는지, 그리고 설명하지 않은 파일이 어느 흐름에 속하는지 정리하는 최종 지도다.

```text
프로그램 시작 흐름
사용자 HTTP 요청 흐름
백그라운드 Scheduler 흐름
테스트·빌드 흐름
배포 흐름
```

이 다섯 흐름은 같은 시점에 실행되는 하나의 긴 함수가 아니다. 서로 다른 시작 사건을 가진다. HTTP 요청이 없어도 애플리케이션 시작·Scheduler·배포 흐름은 실행될 수 있다.

## 14.2 백엔드 시작 흐름

```text
main()
→ SpringApplication.run
→ application.yaml 읽기
→ active profile의 application-local/prod.yaml 병합
→ 환경변수 placeholder 해석
→ DataSource·Redis·Security·Web 설정 Bean 생성
→ Flyway migration
→ Hibernate Entity-schema validate
→ Repository 구현체 생성
→ Controller·Service·Filter·Interceptor Bean 연결
→ embedded server가 요청 대기
→ @EnableScheduling이 Scheduler 등록
```

실제 시작 class 원문:

```java
@SpringBootApplication
@ConfigurationPropertiesScan
@EnableScheduling
public class SpringdatajpaApplication {

    public static void main(String[] args) {
        SpringApplication.run(SpringdatajpaApplication.class, args);
    }
}
```

라인별 주석본:

```java
@SpringBootApplication // 현재 package 아래를 component scan하고 Spring Boot 자동 설정을 활성화한다.
@ConfigurationPropertiesScan // ViewCountProperties처럼 설정값을 객체로 받는 class를 찾아 Bean으로 등록한다.
@EnableScheduling // @Scheduled가 붙은 method를 정해진 시간에 실행하도록 scheduling 기능을 켠다.
public class SpringdatajpaApplication { // backend application의 시작 class다.

    public static void main(String[] args) { // JVM이 가장 먼저 호출하는 Java entry point다.
        SpringApplication.run(SpringdatajpaApplication.class, args); // Spring Context와 embedded web server를 시작한다.
    }
}
```

`main`이 Controller를 직접 호출하는 것은 아니다. Spring이 시작 과정에서 각 class를 객체로 만들고 의존성을 연결해 둔 뒤, 나중에 HTTP 요청이 왔을 때 매핑된 Controller method를 호출한다.

## 14.3 모든 HTTP 요청의 공통 입구

운영 환경의 요청은 다음 순서로 이동한다.

```text
Browser
→ frontend Nginx
→ /api이면 backend Nginx
→ Spring Security FilterChain
→ JwtAuthenticationFilter
→ DispatcherServlet
→ RequestLogInterceptor.preHandle
→ session 경로면 SessionOriginInterceptor.preHandle
→ Controller
→ Service transaction
→ Repository / Redis
→ Response DTO 직렬화
→ Interceptor.afterCompletion
→ FilterChain을 거꾸로 빠져나감
→ Nginx
→ Browser request()
```

Filter와 MVC Interceptor는 위치가 다르다. Security Filter는 `DispatcherServlet` 앞에서 인증·인가를 처리하고, `HandlerInterceptor`는 DispatcherServlet이 Controller handler를 고른 뒤 실행된다. `permitAll`은 Security 인가를 통과시킨다는 뜻이지 `/sessions`에 등록된 Origin Interceptor까지 건너뛴다는 뜻이 아니다.

## 14.4 Interceptor가 Controller에 연결되는 코드

실제 원문:

```java
@Override
public void addInterceptors(InterceptorRegistry registry) {
    registry.addInterceptor(requestLogInterceptor)
            .addPathPatterns("/**");

    registry.addInterceptor(sessionOriginInterceptor)
            .addPathPatterns("/sessions", "/sessions/refresh");
}
```

라인별 주석본:

```java
@Override // WebMvcConfigurer가 정의한 interceptor 등록 method를 현재 설정으로 재정의한다.
public void addInterceptors(InterceptorRegistry registry) { // Spring MVC가 사용할 interceptor와 적용 경로를 등록한다.
    registry.addInterceptor(requestLogInterceptor) // 요청 시작·종료 log를 남기는 객체를 등록한다.
            .addPathPatterns("/**"); // 모든 MVC 경로에 적용한다.

    registry.addInterceptor(sessionOriginInterceptor) // Cookie가 관여하는 로그인·재발급·로그아웃 Origin 검사를 등록한다.
            .addPathPatterns("/sessions", "/sessions/refresh"); // POST·DELETE /sessions와 POST /sessions/refresh가 사용하는 두 URL 경로에 적용한다.
}
```

`SessionOriginInterceptor`는 경로 등록 뒤에도 method를 다시 검사하여 `POST /sessions`, `POST /sessions/refresh`, `DELETE /sessions`에서만 Origin을 검증한다. `RequestLogInterceptor.preHandle`은 시작 시각을 request attribute에 저장하고 method·URI를 기록한다. `afterCompletion`은 Controller와 예외 처리가 끝난 뒤 상태 코드와 경과 시간을 기록한다. request attribute는 해당 요청 객체 안에서만 공유되며 전역 state가 아니다.

## 14.5 API 전체 지도

| HTTP API | 프론트 시작점 | Controller | Service 핵심 | 결과 |
|---|---|---|---|---|
| `POST /users` | SignupForm → `authApi.signup` | UserController | 중복·정지 이력·이미지 검사 후 User 저장 | 회원가입 응답 |
| `GET /users/me` | AppHeader·ProfileEditPage → `userApi.getMyInfo` | UserController | 활성 사용자 조회 | 내 정보 |
| `PATCH /users` | ProfileEditPage | UserController | 다른 사용자 nickname 중복·이미지 검사 후 수정 | 수정 성공 |
| `PATCH /users/password` | PasswordEditPage | UserController | 현재 비밀번호 검사, authVersion 증가, session revoke | cookie 만료·재로그인 |
| `DELETE /users` | ProfileEditPage | UserController | soft delete와 session revoke | cookie·token 제거 |
| `POST /sessions` | LoginForm → `authApi.login` | SessionController | AuthenticationManager 인증과 token 쌍 발급 | access body·refresh cookie |
| `POST /sessions/refresh` | `request()`의 401 처리 | SessionController | session row lock과 token 회전 | 새 access·refresh |
| `DELETE /sessions` | AppHeader → `authApi.logout` | SessionController | refresh session revoke | cookie·local token 제거 |
| `GET /posts` | PostsPage | PostController | page 검사와 최신순 조회 | `posts`, `hasNextPage` |
| `POST /posts` | PostCreatePage | PostController | 사용자·이미지 검사 후 Post 저장 | 작성 성공 |
| `GET /posts/{id}` | Detail·Edit Page | PostController | 연관 데이터·사용자 상태·조회수 조합 | 상세 DTO |
| `PATCH /posts/{id}` | PostEditPage | PostController | 작성자·version 검사 후 변경 | 수정 성공 |
| `DELETE /posts/{id}` | PostDetailPage | PostController | 작성자·version·counter lock 후 soft delete | 204 |
| `POST /posts/{id}/likes` | PostDetailPage | PostController | 게시글·counter lock, Like 저장·count 증가 | 새 likeCount |
| `DELETE /posts/{id}/likes` | PostDetailPage | PostController | Like 삭제·count 감소 | 새 likeCount |
| `POST /posts/{id}/reports` | PostDetailPage | PostController | 게시글·작성자 lock, 신고 저장·count 증가 | 새 reportCount |
| `POST /posts/{id}/comments` | CommentSection | CommentController | 댓글 저장·replyCount 증가 | 정규화된 댓글 |
| `PATCH /posts/{id}/comments` | CommentSection | CommentController | 게시글·작성자 확인 후 댓글 변경 | 정규화된 댓글 |
| `DELETE /posts/{id}/comments` | PostDetailPage | CommentController | 게시글·작성자 확인 후 삭제·count 감소 | 204 |

표에서 한 행을 고른 뒤 프론트 시작점부터 결과까지 실제 method 이름을 따라가면 된다. 같은 Controller·Service 계층 개념을 API마다 다시 설명할 필요는 없지만, 검증 순서·transaction·lock·화면 state 갱신은 기능마다 다르므로 생략하면 안 된다.

## 14.6 백그라운드에서 시작되는 두 흐름

### Refresh Session 정리

실제 원문:

```java
@Scheduled(
        initialDelayString = "${jwt.refresh-session-cleanup-interval-millis}",
        fixedDelayString = "${jwt.refresh-session-cleanup-interval-millis}"
)
@Transactional
public void deleteExpiredSessions() {
    authSessionRepository.deleteAllExpiredAtOrBefore(LocalDateTime.now());
}
```

라인별 주석본:

```java
@Scheduled( // HTTP 요청이 아니라 Spring Scheduler가 method를 호출하게 한다.
        initialDelayString = "${jwt.refresh-session-cleanup-interval-millis}", // 앱 시작 뒤 첫 실행까지 설정값만큼 기다린다.
        fixedDelayString = "${jwt.refresh-session-cleanup-interval-millis}" // 직전 실행이 끝난 시점부터 다음 실행까지 같은 시간만큼 기다린다.
)
@Transactional // 만료 session 삭제 query를 하나의 DB transaction에서 실행한다.
public void deleteExpiredSessions() { // 만료된 Refresh Session row를 정리하는 scheduled method다.
    authSessionRepository.deleteAllExpiredAtOrBefore(LocalDateTime.now()); // 현재 시각 이전에 만료된 row를 bulk delete한다.
}
```

### Redis 조회수 반영

`RedisViewCountFlushScheduler`도 HTTP Controller가 호출하지 않는다. 설정된 주기마다 dirty post ID를 읽고, 분산 lock을 획득한 instance만 snapshot을 RDS에 반영한다. 두 Scheduler는 `@EnableScheduling` 하나로 함께 활성화되지만 서로 다른 설정 key·Repository·transaction을 사용한다.

## 14.7 프론트 파일을 책임별로 읽는 지도

### 반드시 흐름을 따라 읽을 파일

- 시작·route: `main.jsx`, `App.jsx`, `AppRoutes.jsx`, `ProtectedRoute.jsx`, `PublicOnlyRoute.jsx`, `PageBoundary.jsx`
- 인증 경계: `api.js`, `authApi.js`, `authStorage.js`
- 게시글 경계: `postApi.js`, `postNormalizer.js`, `PostsPage.jsx`, `PostDetailPage.jsx`, `PostCreatePage.jsx`, `PostEditPage.jsx`
- 회원 경계: `userApi.js`, `ProfileEditPage.jsx`, `PasswordEditPage.jsx`
- form 조립: `LoginForm.jsx`, `SignupForm.jsx`, `PostEditor.jsx`, `CommentSection.jsx`, `ProfileEditForm.jsx`, `PasswordEditForm.jsx`
- 공통 변환: `errorMessage.js`, `file.js`, `validation.js`, `formatter.js`

### 연결만 확인하고 넘어갈 파일

- 단일 입력 wrapper: `TextInput`, `TextArea`, `FormField`
- 단일 표시 wrapper: `Avatar`, `LogoMark`, `InfoBanner`, `Toast`
- 단일 navigation·button wrapper: `AppLink`, `ActionButton`
- 게시글 표시 조각: `ActivityBars`, `AuthorSummary`, `PostMetricCard`, `PostImageGallery`, `PostListItem`
- layout 조각: `AuthLayout`, `AuthIntroPanel`

이 파일들도 실행되지만 새로운 API 호출이나 전역 데이터 흐름을 시작하지 않는다. 부모가 전달한 props를 JSX와 event에 연결하는 동일한 개념의 반복이므로 파일명과 부모 연결만 기록하고 세부 CSS class는 스킵한다.

## 14.8 백엔드 파일을 책임별로 읽는 지도

### 시작·공통 경계

- `SpringdatajpaApplication`: application과 Scheduler 시작
- `SecurityConfig`, `JwtAuthenticationFilter`: 인증·인가 Filter 경계
- `WebConfig`, `CorsOriginProvider`: browser origin 허용 범위
- `InterceptorConfig`, `SessionOriginInterceptor`, `RequestLogInterceptor`: MVC 요청 전후 처리
- `GlobalExceptionHandler`, `ErrorResponseDto`: 예외를 HTTP JSON으로 변환
- `ViewCountProperties`: 조회수 설정값 묶음

### 기능 계층

- Controller: `UserController`, `SessionController`, `PostController`, `CommentController`
- Service: `UserService`, `SessionService`, `PostService`, `CommentService`
- 조회수 Service: `RedisViewCountStore`, `DatabaseViewCountUpdater`, `RedisViewCountFlushScheduler`, `ViewCountPersistenceService`
- 인증 객체: `JwtProvider`, `RefreshTokenProvider`, `RefreshCookieProvider`, `CustomUserDetails`, `CustomUserDetailsService`, `AccessTokenClaims`

### 저장 계층

- 주 Entity: `User`, `Post`, `Comment`, `Like`, `PostReport`, `AuthSession`
- 게시글 보조 Entity: `PostCounter`, `PostViewCount`, `PostImage`
- Repository: 각 Entity 이름의 Repository interface
- DTO: `dto/user`, `dto/post`, `dto/comment`의 request·response class

예외 class는 대부분 `RuntimeException`을 상속하고 message code를 전달하는 동일 구조다. `throw` 지점과 Handler mapping은 읽되 생성자 한 줄을 예외마다 반복 학습하지 않는다. 단순 응답 DTO도 field와 생성자 mapping을 확인하되 Lombok annotation 문법은 다시 설명하지 않는다.

### 14.8.1 파일 커버리지 판정표

앞으로 “설명했다”는 판단은 class 이름을 한 번 언급했는지가 아니라 아래 세 단계로 구분한다.

| 판정 | 의미 | 현재 프로젝트 적용 |
|---|---|---|
| 원문·라인별 | 고유한 상태 변화·보안·동시성·설정 흐름을 실제 코드로 읽는다. | `AuthSession`, `PostService`, `SessionService`, `SecurityConfig`, 조회수 Scheduler, migration, Workflow 등 |
| 핵심 흐름·축약 | 여러 파일이 같은 패턴이고 호출 관계만 다를 때 각 method의 역할과 호출 위치를 적는다. | `LikeRepository`, `PostReportRepository`, `CommentRepository`, 기능별 request/response DTO |
| 맥락 언급 | 화면 표시·Lombok getter·CSS처럼 새로운 업무 흐름을 만들지 않는 반복 코드다. | 단순 button·label·response message DTO·exception 생성자 |

백엔드의 고유 흐름 파일은 다음 장에서 확인한다.

```text
3장: User Entity와 회원가입 DTO·Controller·Service·Repository
4장: ImageDataUrlValidator·GlobalExceptionHandler·ErrorResponseDto
5장: SecurityConfig·Interceptor·JWT/Refresh provider·AuthSession·SessionService
6장: Post·PostCounter·PostImage·Like·PostReport·Comment와 관련 Repository/Service
8장: PostCreate/Edit/Detail, Comment, User profile/password 화면과 API module
9장: ViewCountUpdater 두 구현체·Redis store·flush/persistence Scheduler
10장: B3/V1/V2/V3 migration과 Flyway 설정
11장: Gradle test task와 각 실행 자원을 증명하는 테스트
12장: Dockerfile·Compose·Nginx·환경변수·volume
13장: Workflow·SSM·deploy script·blue/green Nginx 전환
```

다음 DTO들은 이름이 달라도 “입력 field를 JSON으로 받고 response message 또는 화면용 field를 반환하는 객체”라는 같은 역할이라 개별 annotation을 반복하지 않는다. 다만 어느 endpoint에서 사용되는지는 반드시 확인한다.

```text
user: UserRequestDto, UserPatchRequestDto, UserPasswordRequestDto,
      UserDeleteRequestDto, UserInfoResponseDto, UserResponseDto,
      UserPatchResponseDto, UserPasswordResponseDto, UserDeleteResponseDto
session: SessionRequestDto, SessionResponseDto, SessionRefreshResponseDto,
         SessionDeleteRequestDto, SessionDeleteResponseDto
post: PostRequestDto, PostFixRequestDto, PostDeleteRequestDto,
      PostListRequestDto, LikeRequestDto, LikeCancelRequestDto,
      ReportRequestDto와 각 성공 response DTO
comment: CommentPostRequestDto, CommentFixRequestDto, CommentDeleteRequestDto,
         CommentResponseDto, CommentDeleteResponseDto
```

이 목록에 있는 파일이 설명에서 빠졌다는 뜻이 아니다. 반복 구조를 묶어서 설명한 것이다. 반대로 목록에 없는 Entity·Service·Repository·설정 파일은 “단순 DTO와 같은 맥락”으로 자동 스킵하지 않는다.

## 14.9 한 기능을 처음부터 읽는 실전 절차

예를 들어 “댓글 삭제”를 처음 본다면 다음 순서로 읽는다.

```text
1. Route에서 어느 Page가 열리는지 확인
2. PostDetailPage의 삭제 callback 확인
3. CommentSection·CommentItem이 commentId를 어떻게 올리는지 확인
4. postApi.deleteComment의 method·URL·body 확인
5. api.request가 token·JSON·401을 어떻게 처리하는지 확인
6. SecurityConfig에서 해당 URL의 인증 조건 확인
7. CommentController parameter binding 확인
8. CommentService의 조회·소유권·counter 변경 순서 확인
9. Repository query와 Entity relation 확인
10. 성공 status가 body 없이 돌아오는지 확인
11. Page가 comments state에서 해당 ID를 filter하는지 확인
12. 관련 Service·Controller·통합 테스트 확인
```

이 절차를 그대로 게시글 수정, 좋아요, 회원 탈퇴에 적용할 수 있다. 파일을 directory 순서나 알파벳 순서로 읽지 않는 이유는 호출 관계가 그 순서와 무관하기 때문이다.

## 14.10 프로젝트를 작성한 흐름을 추론하는 법

주석 없는 코드에서 작성 의도를 찾을 때 다음 증거를 사용한다.

```text
URL·method → 사용자가 하려는 행동
Request DTO → 외부에서 필요한 입력
Service 조건문·예외 → 업무 규칙
Repository method·lock → DB에서 필요한 원자성
Entity method → 허용한 상태 변화
Response DTO → 화면에 공개하는 결과
frontend state update → 사용자가 즉시 보게 될 변화
test 이름과 assertion → 작성자가 보장하려 한 조건
YAML·Compose·Workflow → 그 코드가 어느 환경에서 실행되는지
```

method 이름만 보고 추측한 뒤 멈추지 않는다. 반드시 호출자와 피호출자, 정상 반환과 예외 경로, transaction 종료 뒤 상태를 함께 확인해야 전체 흐름이 된다.

## 14.11 전체 학습 순서

```text
0장 전체 구조
→ 2장 실행 환경
→ 3장 기본 backend 계층
→ 4장 검증·예외
→ 5장 인증·보안
→ 6장 게시글 JPA와 동시성
→ 7장 목록 paging
→ 8장 나머지 사용자 기능 연결
→ 9장 Redis 조회수
→ 10장 RDS migration
→ 11장 테스트
→ 12장 container·proxy
→ 13장 CI/CD·배포
→ 14장 전체 파일 지도로 다시 한 바퀴
```

1장은 처음부터 외울 필요가 없다. 9~11장의 library·task가 왜 필요한지 확인할 때 필요한 절만 되돌아보면 된다.

## 14.12 이해 확인
