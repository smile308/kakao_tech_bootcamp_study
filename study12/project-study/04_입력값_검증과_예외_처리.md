# 4장. 입력값 검증과 예외 처리

## 4.1 학습 목표

잘못된 요청이 어디서 발견되고 어떤 HTTP 응답으로 변환되어 프론트 화면까지 도달하는지 학습한다.

```text
잘못된 입력
→ DTO 검증 실패 또는 Service 업무 예외
→ Controller 계층으로 예외 전파
→ GlobalExceptionHandler가 예외 type에 맞는 handler 선택
→ HTTP 상태와 ErrorResponseDto
→ 프론트 request()
→ Error 객체
→ 화면 메시지
```

이 흐름은 Spring MVC Controller 계층까지 도달한 요청의 예외 처리다. Controller 앞의 Spring Security Filter에서 발생한 미인증·권한 거부는 `GlobalExceptionHandler`까지 전파되지 않고 `SecurityConfig`의 `authenticationEntryPoint`와 `accessDeniedHandler`가 응답한다. 보안 Filter 흐름은 5장에서 실제 코드로 다시 다룬다.

### 4.1.1 이 장의 실제 코드 읽기 순서

```text
프론트 form·utils/validation.js
→ api/authApi.js·postApi.js·userApi.js
→ api/api.js의 request()
→ Controller의 @RequestBody와 @Valid
→ DTO annotation 또는 Service 조건문
→ 업무 예외 throw
→ GlobalExceptionHandler
→ ErrorResponseDto JSON
→ request()가 Error 객체 생성
→ Page가 error code를 화면 문구나 field error로 배치
```

처음에는 `ImageDataUrlValidator`와 `GlobalExceptionHandler`를 읽어 “어디서 실패를 발견하는가”를 잡고, 그다음 실제 DTO 하나와 `request()`를 연결한다. 예외 class들은 대부분 이름과 생성자만 다른 동일 구조이므로 각각 다시 설명하지 않고, 어느 Service 조건에서 어떤 예외가 발생하며 Handler가 어떤 HTTP 상태로 바꾸는지만 추적한다.

## 4.2 두 종류의 검증

DTO 선언 검증:

```java
@NotBlank
@Email
private String email;
```

업무 규칙 검증:

```java
if (userRepository.existsByEmailAndDeletedFalse(request.getEmail())) {
    throw new InvalidRequestException("Existed_Email");
}
```

```text
DTO 검증
→ 값의 형식과 기본 조건
→ 이메일 형식, 필수값, 길이

Service 검증
→ DB 상태와 업무 정책
→ 이메일 중복, 정지 계정, 소유권
```

`@Valid`는 요청 JSON을 DTO로 변환하는 데 성공한 뒤 DTO field의 검증 annotation을 검사한다. 따라서 다음 두 실패는 구분해야 한다.

```text
문법적으로 정상인 JSON + DTO 조건 위반
→ MethodArgumentNotValidException
→ 현재 GlobalExceptionHandler가 400 { "message": "invalid_request" }로 변환

JSON 문법 오류 또는 DTO field type으로 변환할 수 없는 값
→ 주로 HttpMessageNotReadableException
→ 현재 GlobalExceptionHandler에는 이 예외 전용 handler가 없음
→ Spring의 기본 오류 처리가 담당
```

즉, 현재 코드에서 모든 잘못된 입력이 반드시 `ErrorResponseDto` 모양으로 반환되는 것은 아니다. `@Valid`는 JSON parser 자체를 대신하지 않는다.

### DTO 검증과 Service 검증

```java
@NotBlank // 값이 없거나 공백만 있는 이메일을 Controller 진입 전에 거부한다.
@Email // 입력 문자열이 이메일 형식인지 검사한다.
private String email; // 검증이 적용되는 DTO 필드다.
```

```java
if (userRepository.existsByEmailAndDeletedFalse(request.getEmail())) { // 현재 DB 상태를 조회해야 알 수 있는 이메일 중복 업무 규칙이다.
    throw new InvalidRequestException("Existed_Email"); // 규칙 위반을 예외로 전파하여 저장 흐름을 즉시 중단한다.
}
```

## 4.2.1 실제 코드: 이미지 입력 검증

파일: `validation/ImageDataUrlValidator.java`

`UserRequestDto.profileImage`에는 선언형 검증 annotation이 없다. Service가 다음 validator를 직접 호출해 Data URL의 형식, MIME type, 크기와 file signature를 검사한다. 다음은 package와 import를 제외한 실제 원문 전체다.

```java
public final class ImageDataUrlValidator {

    public static final int MAX_POST_IMAGE_COUNT = 3;
    public static final int MAX_IMAGE_BYTES = 3 * 1024 * 1024;

    private static final int MAX_BASE64_LENGTH =
            ((MAX_IMAGE_BYTES + 2) / 3) * 4;

    private static final Set<String> ALLOWED_IMAGE_TYPES = Set.of(
            "image/jpeg",
            "image/png",
            "image/webp",
            "image/gif"
    );

    private ImageDataUrlValidator() {
    }

    public static void validatePostImages(List<String> imageFiles) {
        if (imageFiles == null) {
            return;
        }

        if (imageFiles.size() > MAX_POST_IMAGE_COUNT) {
            throw new InvalidRequestException("Too_Many_Images");
        }

        for (String imageFile : imageFiles) {
            validateImage(imageFile);
        }
    }

    public static void validateProfileImage(String profileImage) {
        if (profileImage == null) {
            return;
        }

        validateImage(profileImage);
    }

    private static void validateImage(String dataUrl) {
        if (dataUrl == null || dataUrl.isBlank()) {
            throw new InvalidRequestException("Invalid_Image_Data");
        }

        int separatorIndex = dataUrl.indexOf(',');
        if (separatorIndex <= 5) {
            throw new InvalidRequestException("Invalid_Image_Data");
        }

        String header = dataUrl.substring(0, separatorIndex);
        String mimeType = extractMimeType(header);
        String encodedData = dataUrl.substring(separatorIndex + 1);

        if (!ALLOWED_IMAGE_TYPES.contains(mimeType)) {
            throw new InvalidRequestException("Unsupported_Image_Type");
        }

        if (encodedData.length() > MAX_BASE64_LENGTH) {
            throw new InvalidRequestException("Image_Too_Large");
        }

        byte[] imageBytes;
        try {
            imageBytes = Base64.getDecoder().decode(encodedData);
        } catch (IllegalArgumentException exception) {
            throw new InvalidRequestException("Invalid_Image_Data");
        }

        if (imageBytes.length > MAX_IMAGE_BYTES) {
            throw new InvalidRequestException("Image_Too_Large");
        }

        if (!hasMatchingSignature(mimeType, imageBytes)) {
            throw new InvalidRequestException("Invalid_Image_Data");
        }
    }

    private static String extractMimeType(String header) {
        if (!header.startsWith("data:") || !header.endsWith(";base64")) {
            throw new InvalidRequestException("Invalid_Image_Data");
        }

        return header.substring("data:".length(), header.length() - ";base64".length());
    }

    private static boolean hasMatchingSignature(String mimeType, byte[] bytes) {
        return switch (mimeType) {
            case "image/jpeg" -> startsWith(bytes, new int[]{0xFF, 0xD8, 0xFF});
            case "image/png" -> startsWith(
                    bytes,
                    new int[]{0x89, 0x50, 0x4E, 0x47, 0x0D, 0x0A, 0x1A, 0x0A}
            );
            case "image/gif" -> startsWithText(bytes, "GIF87a")
                    || startsWithText(bytes, "GIF89a");
            case "image/webp" -> startsWithText(bytes, "RIFF")
                    && hasTextAt(bytes, "WEBP", 8);
            default -> false;
        };
    }

    private static boolean startsWith(byte[] bytes, int[] signature) {
        if (bytes.length < signature.length) {
            return false;
        }

        for (int index = 0; index < signature.length; index++) {
            if ((bytes[index] & 0xFF) != signature[index]) {
                return false;
            }
        }

        return true;
    }

    private static boolean startsWithText(byte[] bytes, String text) {
        return hasTextAt(bytes, text, 0);
    }

    private static boolean hasTextAt(byte[] bytes, String text, int offset) {
        byte[] expected = text.getBytes(StandardCharsets.US_ASCII);
        if (bytes.length < offset + expected.length) {
            return false;
        }

        for (int index = 0; index < expected.length; index++) {
            if (bytes[offset + index] != expected[index]) {
                return false;
            }
        }

        return true;
    }
}
```

검증 순서는 다음과 같다.

```text
profileImage가 null
→ 선택 입력이므로 허용

null이 아닌 문자열
→ data:...;base64, 형식 분리
→ 허용 MIME type인지 검사
→ Base64 문자열 길이 사전 검사
→ Base64 decoding
→ decoded byte가 3 MiB 이하인지 검사
→ MIME type과 실제 file signature가 일치하는지 검사
```

`MAX_BASE64_LENGTH`는 decoded byte가 최대 3 MiB일 때 Base64 문자열이 가질 수 있는 최대 길이를 계산한다. decoding 전에 길이를 먼저 검사하면 지나치게 큰 문자열을 byte 배열로 만드는 작업을 피할 수 있고, decoding 뒤에는 실제 byte 길이를 다시 검사한다.

signature 검사는 JPEG·PNG·GIF·WebP file의 시작 부분에 정해진 magic byte가 있는지 확인한다. 확장자나 요청의 MIME 문자열만 믿지 않는다는 의미다. 다만 이 검사는 file 전체를 완전히 해석하거나 악성 content를 검사하는 antivirus가 아니며, 허용 형식의 기본 signature가 맞는지만 확인한다.

### `ImageDataUrlValidator`

```java
public final class ImageDataUrlValidator { // 상속해 변경할 필요가 없는 image 검증 utility class를 선언한다.

    public static final int MAX_POST_IMAGE_COUNT = 3; // 게시글 하나에 허용할 최대 image 개수다.
    public static final int MAX_IMAGE_BYTES = 3 * 1024 * 1024; // image 하나의 decoded 최대 크기를 3 MiB로 정한다.

    private static final int MAX_BASE64_LENGTH = // 허용할 Base64 문자열의 최대 길이를 저장한다.
            ((MAX_IMAGE_BYTES + 2) / 3) * 4; // byte 3개가 Base64 문자 4개가 되는 비율로 올림 계산한다.

    private static final Set<String> ALLOWED_IMAGE_TYPES = Set.of( // 중복 없는 허용 MIME type 집합을 만든다.
            "image/jpeg", // JPEG를 허용한다.
            "image/png", // PNG를 허용한다.
            "image/webp", // WebP를 허용한다.
            "image/gif" // GIF를 허용한다.
    );

    private ImageDataUrlValidator() { // 외부에서 utility 객체를 new로 만들지 못하게 private constructor를 둔다.
    }

    public static void validatePostImages(List<String> imageFiles) { // 게시글 image 목록 전체를 검증하는 static method다.
        if (imageFiles == null) { // image 목록 자체가 전달되지 않았는지 확인한다.
            return; // image는 선택 입력이므로 null이면 검증을 정상 종료한다.
        }

        if (imageFiles.size() > MAX_POST_IMAGE_COUNT) { // image 개수가 허용된 3개를 초과하는지 검사한다.
            throw new InvalidRequestException("Too_Many_Images"); // 초과하면 업무 예외를 던져 요청을 중단한다.
        }

        for (String imageFile : imageFiles) { // 목록의 각 Data URL을 하나씩 순회한다.
            validateImage(imageFile); // image 하나에 대한 공통 검증을 실행한다.
        }
    }

    public static void validateProfileImage(String profileImage) { // profile image 하나를 검증하는 public method다.
        if (profileImage == null) { // profile image가 전달되지 않았는지 확인한다.
            return; // 선택 입력이므로 null이면 허용하고 종료한다.
        }

        validateImage(profileImage); // null이 아닌 Data URL에 공통 image 검증을 실행한다.
    }

    private static void validateImage(String dataUrl) { // Data URL 하나의 형식·크기·signature를 검사하는 내부 method다.
        if (dataUrl == null || dataUrl.isBlank()) { // null이거나 빈 문자열·공백뿐인지 검사한다.
            throw new InvalidRequestException("Invalid_Image_Data"); // 유효한 image data가 아니면 요청을 중단한다.
        }

        int separatorIndex = dataUrl.indexOf(','); // Data URL header와 Base64 data를 나누는 첫 쉼표 위치를 찾는다.
        if (separatorIndex <= 5) { // data: 뒤에 MIME header가 들어갈 최소 위치보다 쉼표가 너무 앞이거나 없는지 검사한다.
            throw new InvalidRequestException("Invalid_Image_Data"); // header 구조가 잘못되면 요청을 중단한다.
        }

        String header = dataUrl.substring(0, separatorIndex); // 쉼표 앞의 data:image/...;base64 header를 잘라낸다.
        String mimeType = extractMimeType(header); // header에서 image/jpeg 같은 MIME type을 추출한다.
        String encodedData = dataUrl.substring(separatorIndex + 1); // 쉼표 뒤 Base64 문자 부분만 잘라낸다.

        if (!ALLOWED_IMAGE_TYPES.contains(mimeType)) { // 추출한 MIME type이 허용 집합에 없는지 확인한다.
            throw new InvalidRequestException("Unsupported_Image_Type"); // 허용하지 않는 image 형식이면 요청을 중단한다.
        }

        if (encodedData.length() > MAX_BASE64_LENGTH) { // decoding 전 문자열 길이가 최대 예상 길이를 넘는지 검사한다.
            throw new InvalidRequestException("Image_Too_Large"); // 지나치게 크면 byte 배열을 만들기 전에 중단한다.
        }

        byte[] imageBytes; // decoding 결과 byte 배열을 담을 변수를 선언한다.
        try { // 잘못된 Base64 문자열이 던질 예외를 처리할 범위를 시작한다.
            imageBytes = Base64.getDecoder().decode(encodedData); // Base64 문자를 실제 file byte로 decoding한다.
        } catch (IllegalArgumentException exception) { // Base64 문법이 잘못되면 decoder가 던지는 예외를 잡는다.
            throw new InvalidRequestException("Invalid_Image_Data"); // 내부 decoder 예외 대신 프로젝트의 400 오류로 변환한다.
        }

        if (imageBytes.length > MAX_IMAGE_BYTES) { // 실제 decoded byte 크기가 3 MiB를 넘는지 다시 검사한다.
            throw new InvalidRequestException("Image_Too_Large"); // 실제 file이 너무 크면 요청을 중단한다.
        }

        if (!hasMatchingSignature(mimeType, imageBytes)) { // 선언한 MIME type과 file 시작 signature가 일치하는지 검사한다.
            throw new InvalidRequestException("Invalid_Image_Data"); // header와 실제 byte 형식이 다르면 요청을 중단한다.
        }
    }

    private static String extractMimeType(String header) { // Data URL header에서 MIME type만 추출하는 내부 method다.
        if (!header.startsWith("data:") || !header.endsWith(";base64")) { // data:로 시작하고 ;base64로 끝나는지 검사한다.
            throw new InvalidRequestException("Invalid_Image_Data"); // Data URL header 형식이 아니면 요청을 중단한다.
        }

        return header.substring("data:".length(), header.length() - ";base64".length()); // 앞의 data:와 뒤의 ;base64를 제외한 MIME type을 반환한다.
    }

    private static boolean hasMatchingSignature(String mimeType, byte[] bytes) { // MIME type별 magic byte가 실제 file byte와 맞는지 반환한다.
        return switch (mimeType) { // MIME type 값에 따라 실행할 signature 검사를 선택한다.
            case "image/jpeg" -> startsWith(bytes, new int[]{0xFF, 0xD8, 0xFF}); // JPEG 시작 byte FF D8 FF를 검사한다.
            case "image/png" -> startsWith( // PNG의 8 byte signature를 검사한다.
                    bytes, // 실제 image byte 배열을 전달한다.
                    new int[]{0x89, 0x50, 0x4E, 0x47, 0x0D, 0x0A, 0x1A, 0x0A} // PNG 표준 시작 signature다.
            );
            case "image/gif" -> startsWithText(bytes, "GIF87a") // GIF87a header로 시작하는지 검사한다.
                    || startsWithText(bytes, "GIF89a"); // 또는 GIF89a header로 시작하는지 검사한다.
            case "image/webp" -> startsWithText(bytes, "RIFF") // WebP container가 RIFF로 시작하는지 검사한다.
                    && hasTextAt(bytes, "WEBP", 8); // byte offset 8에 WEBP 문자열이 있는지도 검사한다.
            default -> false; // 허용 목록 밖의 MIME type은 signature 불일치로 처리한다.
        };
    }

    private static boolean startsWith(byte[] bytes, int[] signature) { // byte 배열이 지정된 숫자 signature로 시작하는지 검사한다.
        if (bytes.length < signature.length) { // 실제 data가 signature보다 짧은지 확인한다.
            return false; // 비교할 길이조차 부족하면 일치하지 않는다.
        }

        for (int index = 0; index < signature.length; index++) { // signature의 각 위치를 처음부터 순회한다.
            if ((bytes[index] & 0xFF) != signature[index]) { // signed byte를 0~255 값으로 바꿔 예상 byte와 비교한다.
                return false; // 하나라도 다르면 signature가 일치하지 않는다.
            }
        }

        return true; // 모든 byte가 같으면 signature가 일치한다.
    }

    private static boolean startsWithText(byte[] bytes, String text) { // byte 배열이 지정 문자열로 시작하는지 검사한다.
        return hasTextAt(bytes, text, 0); // offset 0에서 문자열이 있는지 공통 method에 맡긴다.
    }

    private static boolean hasTextAt(byte[] bytes, String text, int offset) { // 지정 offset에 ASCII 문자열이 있는지 검사한다.
        byte[] expected = text.getBytes(StandardCharsets.US_ASCII); // 비교할 문자열을 ASCII byte 배열로 변환한다.
        if (bytes.length < offset + expected.length) { // 해당 위치에서 문자열 전체를 비교할 길이가 있는지 확인한다.
            return false; // data가 너무 짧으면 일치하지 않는다.
        }

        for (int index = 0; index < expected.length; index++) { // 예상 문자열 byte를 순회한다.
            if (bytes[offset + index] != expected[index]) { // 실제 offset 위치의 byte와 예상 byte를 비교한다.
                return false; // 하나라도 다르면 문자열이 일치하지 않는다.
            }
        }

        return true; // 모든 byte가 같으면 해당 위치에 문자열이 존재한다.
    }
}
```

## 4.3 실제 코드 발췌: 전역 예외 처리

파일: `controller/GlobalExceptionHandler.java`

package와 import 뒤 class 부분의 실제 원문 전체:

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(LoginFailedException.class)
    public ResponseEntity<ErrorResponseDto> handleLoginFailedException(LoginFailedException e) {
        ErrorResponseDto response = new ErrorResponseDto(e.getMessage());

        return ResponseEntity
                .status(HttpStatus.UNAUTHORIZED)
                .body(response);
    }
    @ExceptionHandler(InvalidRequestException.class)
    public ResponseEntity<ErrorResponseDto> handleInvalidRequestException(InvalidRequestException e) {
        ErrorResponseDto response = new ErrorResponseDto(e.getMessage());

        return ResponseEntity
                .status(HttpStatus.BAD_REQUEST)
                .body(response);
    }
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponseDto> handleValidationException(MethodArgumentNotValidException e) {
        ErrorResponseDto response = new ErrorResponseDto("invalid_request");

        return ResponseEntity
                .status(HttpStatus.BAD_REQUEST)
                .body(response);
    }
    @ExceptionHandler(AuthException.class)
    public ResponseEntity<ErrorResponseDto> handleAuthException(AuthException e){
        ErrorResponseDto response = new ErrorResponseDto(e.getMessage());
        return ResponseEntity
                .status(HttpStatus.UNAUTHORIZED)
                .body(response);
    }
    @ExceptionHandler(DataNullException.class)
    public ResponseEntity<ErrorResponseDto> handleDataNullException(DataNullException e){
        ErrorResponseDto response = new ErrorResponseDto((e.getMessage()));
        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(response);
    }

    @ExceptionHandler(ForbiddenException.class)
    public ResponseEntity<ErrorResponseDto> handleForbiddenException(
            ForbiddenException e
    ) {
        ErrorResponseDto response =
                new ErrorResponseDto(e.getMessage());

        return ResponseEntity
                .status(HttpStatus.FORBIDDEN)
                .body(response);
    }

    @ExceptionHandler({
            PostVersionConflictException.class,
            ObjectOptimisticLockingFailureException.class
    })
    public ResponseEntity<ErrorResponseDto> handlePostVersionConflict(
            RuntimeException e
    ) {
        ErrorResponseDto response =
                new ErrorResponseDto("Post_Version_Conflict");

        return ResponseEntity
                .status(HttpStatus.CONFLICT)
                .body(response);
    }

    @ExceptionHandler(CounterUpdateException.class)
    public ResponseEntity<ErrorResponseDto> handleCounterUpdateException(
```

## 4.4 HTTP 상태 매핑

이 프로젝트의 주요 매핑은 다음과 같다.

| 상황 | 예외 또는 처리 위치 | 상태 |
|---|---|---:|
| DTO 형식 실패 | `MethodArgumentNotValidException` | 400 |
| 잘못된 업무 요청 | `InvalidRequestException` | 400 |
| 로그인 실패·토큰 오류 | `LoginFailedException`, `AuthException` | 401 |
| 로그인했지만 권한 없음 | `ForbiddenException` | 403 |
| 데이터 없음 | `DataNullException` | 404 |
| 게시글 버전 충돌 | 낙관적 락 예외 | 409 |
| 카운터 갱신 실패 | `CounterUpdateException` | 500 |

표의 401과 403은 발생 위치에 따라 처리자가 다르다.

```text
Controller·Service에서 LoginFailedException/AuthException 발생
→ GlobalExceptionHandler가 401 ErrorResponseDto로 변환

Controller·Service에서 ForbiddenException 발생
→ GlobalExceptionHandler가 403 ErrorResponseDto로 변환

Spring Security Filter에서 미인증·접근 거부 발생
→ SecurityConfig의 authenticationEntryPoint 또는 accessDeniedHandler가 401·403 JSON을 직접 작성
```

401과 403을 구분한다.

```text
401 Unauthorized
→ 유효한 인증 정보가 없음

403 Forbidden
→ 인증은 되었지만 해당 행동 권한이 없음
```

## 4.6 실제 코드 발췌: 프론트 오류 변환

파일: `src/api/api.js`

먼저 HTTP 요청을 보내고 body를 읽는 실제 원문:

```javascript
async function sendRequest(endpoint, options = {}, includeAccessToken = true) {
    const accessToken = authStorage.getAccessToken();
    const headers = {
        "Content-Type": "application/json",
        ...options.headers,
    };

    if (includeAccessToken && accessToken) {
        headers.Authorization = `Bearer ${accessToken}`;
    }

    const response = await fetch(`${API_BASE_URL}${endpoint}`, {
        ...options,
        headers,
        credentials: "include",
    });

    return {
        response,
        data: await readResponseData(response),
    };
}

async function readResponseData(response) {
    const contentType = response.headers.get("content-type");
    const responseText = await response.text();

    if (!responseText) {
        return null;
    }

    return contentType?.includes("application/json")
        ? JSON.parse(responseText)
        : responseText;
}
```

`credentials: "include"`는 browser가 허용하는 범위에서 cross-origin 요청에도 cookie를 포함하도록 요청한다. 이 프로젝트에서는 refresh token cookie와 연결되며 자세한 보안 흐름은 5장에서 다룬다.

`readResponseData()`는 body를 먼저 text로 한 번 읽은 뒤, `content-type`에 `application/json`이 있으면 `JSON.parse()`로 JavaScript 값으로 바꾼다. body는 stream이어서 일반적으로 한 번만 읽을 수 있으므로 `text()` 결과를 기준으로 분기한다. JSON이라고 표시된 body의 문법이 잘못되면 `JSON.parse()`가 `SyntaxError`를 던지며, 이 경우에는 아직 `createRequestError()`를 거치지 않았으므로 `status`와 `data`를 추가한 프로젝트 Error가 아니다.

실패 응답을 JavaScript `Error`로 만드는 실제 원문:

```javascript
function createRequestError(response, data) {
    const errorMessage =
        typeof data === "string"
            ? data
            : data?.message ?? "요청 처리에 실패했습니다.";

    const error = new Error(errorMessage);
    error.code = errorMessage;
    error.status = response.status;
    error.data = data;
    return error;
}
```

오류를 실제로 판정하고 던지는 `request()`의 실제 원문:

```javascript
export async function request(endpoint, options = {}) {
    let result = await sendRequest(endpoint, options);

    if (
        result.response.status === 401 &&
        !isRefreshExcludedRequest(endpoint, options)
    ) {
        try {
            await refreshAccessToken();
            result = await sendRequest(endpoint, options);
        } catch (error) {
            if (error.status === 401) {
                clearAuthentication();
            }

            throw error;
        }
    }

    if (!result.response.ok) {
        if (result.response.status === 401) {
            clearAuthentication();
        }

        throw createRequestError(result.response, result.data);
    }

    return result.data;
}
```

`sendRequest()`는 `fetch`를 실행하고 응답 body까지 읽어 `{ response, data }`를 돌려준다. 첫 응답이 401이고 재발급 제외 요청이 아니면 access token 재발급을 시도한 뒤 원래 요청을 한 번 다시 보낸다. 로그인·로그아웃·token 재발급·회원가입 요청은 `NO_REFRESH_REQUESTS`에 들어 있어 이 재시도를 하지 않는다.

재시도 뒤에도 실패했거나 처음부터 다른 실패 상태라면 `response.ok`를 검사한다. `Response.ok`는 HTTP 상태가 200 이상 299 이하일 때 `true`다. 실패 응답은 `createRequestError()`가 JavaScript `Error`로 바꿔 던지고, 성공 응답만 `data`를 반환한다.

중요한 줄:

```javascript
error.status = response.status;
// 화면 코드가 400, 401, 404 같은 상태를 구분할 수 있게 한다.

error.data = data;
// 서버가 반환한 원래 데이터를 보존한다.
```

각 Page나 form의 `try/catch`는 이 오류를 받아 화면 정책에 맞게 처리한다. 예를 들어 회원가입은 field 오류 문구로 표시할 수 있고, 다른 화면은 `ErrorView`, alert 또는 Toast를 사용할 수 있다. 모든 Page가 동일한 표시 방식을 사용하는 것은 아니다.

### 프론트 `sendRequest`, `readResponseData`, `createRequestError`

`sendRequest()`와 `readResponseData()`의 라인별 주석본:

```javascript
async function sendRequest(endpoint, options = {}, includeAccessToken = true) { // 요청 경로·fetch 설정·token 포함 여부를 받는 비동기 함수다.
    const accessToken = authStorage.getAccessToken(); // browser 저장소에서 현재 access token을 읽는다.
    const headers = { // 최종 요청 header 객체를 만든다.
        "Content-Type": "application/json", // 이 client가 보내는 body를 JSON으로 해석하라고 server에 알린다.
        ...options.headers, // 호출자가 넘긴 header를 펼쳐 넣으며 같은 key라면 앞의 기본값을 덮어쓴다.
    };

    if (includeAccessToken && accessToken) { // token 포함이 허용되고 실제 token도 존재하는지 확인한다.
        headers.Authorization = `Bearer ${accessToken}`; // Authorization header에 Bearer 방식 access token을 넣는다.
    }

    const response = await fetch(`${API_BASE_URL}${endpoint}`, { // base URL과 endpoint를 합친 주소로 HTTP 요청을 보내고 Response를 기다린다.
        ...options, // method와 body 등 호출자가 넘긴 fetch 설정을 펼친다.
        headers, // 위에서 완성한 header를 사용한다.
        credentials: "include", // browser가 허용하는 범위에서 cookie도 요청에 포함하게 한다.
    });

    return { // HTTP 응답 정보와 파싱한 body를 한 객체로 반환한다.
        response, // status와 ok 등을 가진 원래 Fetch Response 객체다.
        data: await readResponseData(response), // body를 문자열 또는 JSON 값으로 읽을 때까지 기다린 결과다.
    };
}

async function readResponseData(response) { // Fetch Response의 body를 프로젝트에서 쓸 값으로 읽는다.
    const contentType = response.headers.get("content-type"); // server가 알린 응답 content type을 읽는다.
    const responseText = await response.text(); // body stream을 text로 한 번 읽는다.

    if (!responseText) { // 빈 문자열처럼 body 내용이 없는지 확인한다.
        return null; // 빈 응답은 null로 통일한다.
    }

    return contentType?.includes("application/json") // content type이 JSON을 포함하는지 안전하게 확인한다.
        ? JSON.parse(responseText) // JSON이면 text를 JavaScript 객체·배열·값으로 파싱한다.
        : responseText; // JSON이 아니면 원래 문자열을 반환한다.
}
```

`createRequestError()`의 라인별 주석본:

```javascript
function createRequestError(response, data) { // 실패한 HTTP Response와 파싱한 body를 JavaScript Error로 바꾼다.
    const errorMessage = // 최종 오류 메시지를 결정할 변수를 만든다.
        typeof data === "string" // 응답 body 자체가 문자열인지 확인한다.
            ? data // 문자열이면 그대로 오류 메시지로 사용한다.
            : data?.message ?? "요청 처리에 실패했습니다."; // JSON이면 message를 쓰고 없으면 기본 문구를 쓴다.

    const error = new Error(errorMessage); // 표준 JavaScript Error 객체를 만든다.
    error.code = errorMessage; // 프로젝트 화면 코드가 오류 종류로 사용할 code를 추가한다.
    error.status = response.status; // 400, 401 같은 HTTP 상태를 추가한다.
    error.data = data; // 서버가 반환한 원본 body도 디버깅과 추가 처리용으로 보존한다.
    return error; // Page의 catch로 전달할 완성된 Error를 반환한다.
}
```

## 4.7 ErrorBoundary와 API 오류의 차이

```text
API가 400/500 응답
→ fetch Promise는 HTTP 상태만으로 reject되지 않고 Response를 반환
→ request()가 Error로 변환
→ Page의 catch에서 처리

React 렌더링 중 JavaScript 예외
→ ErrorBoundary가 fallback 화면 표시
```

`fetch`가 reject되는 경우는 대표적으로 server에 연결할 수 없는 network 실패, browser가 차단한 CORS 실패, 요청 중단처럼 HTTP 응답 자체를 정상적으로 얻지 못한 경우다. 400·404·500 응답을 받았다는 사실만으로는 reject되지 않는다.

ErrorBoundary는 자식 component의 render와 class component lifecycle 등 React가 렌더링하는 과정에서 발생한 오류를 잡는다. click event handler 내부의 오류나 `async` 함수·Promise에서 뒤늦게 발생한 오류는 자동으로 잡지 않는다. 따라서 API 요청의 실패는 호출한 Page나 form이 `try/catch`로 처리해야 한다. 처리하지 않으면 rejected Promise로 남는 것이지, 자동으로 최상위 ErrorBoundary 화면이 되는 것은 아니다.

이 절은 앞의 실제 코드 원문을 읽은 직후 확인한다. 원문과 같은 순서의 설명용 주석본이며 실제 실행 파일에는 주석이 없다.

### 프론트 `request`

```javascript
export async function request(endpoint, options = {}) { // endpoint와 선택 요청 설정을 받아 공통 API 요청을 실행한다.
    let result = await sendRequest(endpoint, options); // 첫 HTTP 요청을 보내고 Response와 파싱한 body를 받는다.

    if ( // access token 재발급을 시도할 조건 검사를 시작한다.
        result.response.status === 401 && // 첫 응답이 유효한 인증이 없다는 401인지 확인한다.
        !isRefreshExcludedRequest(endpoint, options) // 로그인·회원가입 등 재발급 제외 요청이 아닌지도 확인한다.
    ) {
        try { // token 재발급과 원래 요청 재시도에서 발생할 오류를 처리한다.
            await refreshAccessToken(); // refresh cookie를 사용해 새 access token을 받을 때까지 기다린다.
            result = await sendRequest(endpoint, options); // 새 access token으로 원래 요청을 한 번 다시 보낸다.
        } catch (error) { // 재발급 자체가 실패하면 해당 Error를 받는다.
            if (error.status === 401) { // refresh 인증까지 실패한 경우인지 확인한다.
                clearAuthentication(); // 저장한 access token을 지우고 공개 경로가 아니면 login 화면으로 이동한다.
            }

            throw error; // 재발급 오류를 숨기지 않고 request() 호출자의 catch로 다시 전달한다.
        }
    }

    if (!result.response.ok) { // 최초 요청 또는 재시도 결과가 200~299가 아닌지 확인한다.
        if (result.response.status === 401) { // 최종 결과가 여전히 401인지 확인한다.
            clearAuthentication(); // 유효하지 않은 인증 상태를 제거하고 필요한 경우 login 화면으로 이동한다.
        }

        throw createRequestError(result.response, result.data); // HTTP 상태와 body를 넣은 JavaScript Error를 만들어 호출자에게 던진다.
    }

    return result.data; // 성공 응답이면 파싱한 body만 Page나 API module 호출자에게 반환한다.
}
```

## 4.8 실제 실행 흐름을 한 줄씩 연결하기

앞의 코드 블록을 따로 읽으면 각 class의 역할은 보이지만, 실제로는 다음 호출 stack으로 이어진다. 이 순서로 원문 파일을 다시 열어 확인한다.

### 흐름 A: 이메일 중복 회원가입

1. 프론트 `SignupForm`이 JSON body를 만든다.
2. `authApi.signup()`이 `request("/users", { method: "POST", body })`를 호출한다.
3. `request()`는 `sendRequest()`를 호출한다. 여기서 `fetch()`가 실제 네트워크 요청을 한 번 만든다.
4. `UserController`가 JSON을 `UserRequestDto`로 역직렬화한다. 역직렬화는 문자열 JSON을 Java 객체로 바꾸는 과정이다.
5. Controller parameter의 `@Valid`가 `email`, `password`, `nickname` annotation을 검사한다.
6. 형식이 통과하면 Controller가 `userService.createUser(request)`를 호출한다.
7. Service가 password 확인값을 비교하고 `UserRepository.existsByEmailAndDeletedFalse()`를 호출한다.
8. 이미 존재하면 Service는 `InvalidRequestException("Existed_Email")`을 던진다. 여기서 `throw`는 현재 메서드의 남은 줄을 중단한다.
9. 예외는 Controller가 잡지 않으므로 Spring MVC가 `GlobalExceptionHandler`를 찾는다.
10. `handleInvalidRequestException()`이 `ResponseEntity.status(400).body(ErrorResponseDto)`를 반환한다.
11. Jackson이 DTO의 getter를 읽어 `{ "message": "Existed_Email" }` JSON을 만든다.
12. `sendRequest()`가 Response와 body를 반환하고, `request()`는 `response.ok`가 false이므로 `createRequestError()`를 호출한다.
13. `createRequestError()`는 일반 `Error` 객체에 `code`, `status`, `data` property를 추가한다.
14. 호출한 Form/Page가 catch한 Error를 `getErrorMessage()`에 넘겨 사용자 문구를 선택한다.

여기서 DTO annotation 실패와 Service 중복 실패는 둘 다 최종적으로 400이지만 발생 지점이 다르다. DTO 실패는 Controller 본문 전이고, 중복 실패는 Service가 Repository를 조회한 뒤다.

### 흐름 B: 잘못된 이미지 회원가입

1. `profileImage`는 DTO에 `@Pattern`이 없으므로 DTO 검증을 통과할 수 있다.
2. `UserService`가 `ImageDataUrlValidator.validateProfileImage()`를 직접 호출한다.
3. validator는 null이면 정상 종료하고, 값이 있으면 `validateImage()`로 들어간다.
4. 쉼표 위치로 header와 Base64 본문을 분리한다. `indexOf()`는 찾지 못하면 `-1`을 반환하므로 `separatorIndex <= 5`가 구조 오류를 함께 잡는다.
5. `extractMimeType()`은 `startsWith("data:")`와 `endsWith(";base64")`로 Data URL 형태를 확인한다.
6. 허용 MIME이 아니면 `Unsupported_Image_Type`을 던진다.
7. decoding 전 문자열 길이를 검사한 뒤 `Base64.getDecoder().decode()`를 실행한다.
8. decoder의 `IllegalArgumentException`은 프로젝트 예외 code `Invalid_Image_Data`로 바뀐다.
9. decoding 후 실제 byte 길이를 다시 검사한다. 문자열 길이와 실제 byte 길이는 padding 때문에 같지 않을 수 있다.
10. `switch` expression이 MIME에 맞는 signature 검사 함수를 선택한다.
11. `startsWith()`는 byte 배열 길이를 먼저 확인하고 for 문으로 signature 각 위치를 비교한다.
12. 하나라도 다르면 false가 되고, `!hasMatchingSignature(...)` 조건이 업무 예외를 던진다.

### 흐름 C: API 401

1. `request()`가 원래 API를 호출한다.
2. 응답 status가 401이면 `isRefreshExcludedRequest()`를 먼저 확인한다.
3. 일반 API라면 `refreshAccessToken()`을 호출한다.
4. `refreshPromise`가 null일 때만 `performRefresh()`가 실행된다. 이미 Promise가 있으면 같은 Promise를 반환하므로 동시 요청이 refresh 요청을 여러 개 만들지 않는다.
5. `performRefresh()`는 세 번째 인자를 false로 넘겨 만료된 Access Token을 refresh 요청에 붙이지 않는다. Cookie는 `credentials: "include"`로 전송된다.
6. refresh 응답이 성공하고 accessToken이 있으면 storage에 저장한다.
7. 원래 API를 한 번 재요청한다.
8. refresh 자체가 실패하면 `NO_REFRESH_REQUESTS` 때문에 다시 refresh하지 않고 Error를 호출자에게 전달한다.
9. `finally`는 성공·실패 모두 실행되어 `refreshPromise = null`을 수행한다.

### 이 장에서 문법을 만난 즉시 확인할 것

- `@Valid`: JSON 변환 뒤 DTO constraint를 실행한다. JSON parser 자체가 아니다.
- `throw`: 현재 흐름을 중단하고 호출 stack 바깥으로 예외를 보낸다.
- `try/catch`: Base64 decoder처럼 예상 가능한 library 예외를 프로젝트 예외로 바꿀 때 사용한다.
- `static`: 객체를 만들지 않고 class 이름으로 호출한다. validator가 utility인 이유와 연결한다.
- `switch expression`: 값을 반환하는 switch다. statement switch와 달리 `return switch (...)` 형태로 결과를 만든다.
- `async/await`: fetch Promise가 완료될 때까지 비동기 함수의 다음 줄을 기다린다.
- optional chaining `?.`: null/undefined에서 property 접근 오류를 막는다.
- nullish coalescing `??`: null/undefined일 때만 기본값을 사용한다.
- object spread `...`: 기본 옵션과 호출자 옵션을 합치며 뒤에 나온 동일 key가 우선한다.
- `finally`: Promise 성공·실패와 무관하게 정리 코드를 실행한다.

## 4.10 스킵할 코드

예외 클래스 대부분은 `RuntimeException`을 상속하고 메시지를 전달하는 동일 구조다. 대표로 `InvalidRequestException` 하나를 이해한 뒤 다음 클래스는 사용 위치와 상태만 확인한다.

- `AuthException`
- `DataNullException`
- `ForbiddenException`
- `LoginFailedException`

`PostVersionConflictException`과 `CounterUpdateException`은 동시성 장에서 발생 이유를 다시 확인한다.


이 장의 문법 설명은 각 실행 흐름 뒤에 배치했으므로, 별도의 문법 모음 절은 두지 않는다.
