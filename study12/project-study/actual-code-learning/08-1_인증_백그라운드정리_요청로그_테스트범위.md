## 1. 애플리케이션 시작과 Scheduler 등록

### 코드 원문

~~~~java
@SpringBootApplication
@ConfigurationPropertiesScan
@EnableScheduling
public class SpringdatajpaApplication {

    public static void main(String[] args) {
        SpringApplication.run(SpringdatajpaApplication.class, args);
    }

}
~~~~

### 코드 바로 아래 설명

- @SpringBootApplication은 이 클래스를 Spring Boot 애플리케이션의 시작 설정으로 표시합니다. component scan, auto-configuration, configuration 등록을 묶어 적용합니다. 현재 코드에서 @Component가 붙은 AuthSessionCleanupScheduler와 RequestLogInterceptor 같은 Bean을 검색하는 기반입니다.
- @ConfigurationPropertiesScan은 @ConfigurationProperties가 붙은 설정 객체를 Bean으로 찾도록 합니다. 이 장의 Scheduler가 이 annotation으로 ViewCountProperties를 직접 받는 것은 아니지만 애플리케이션의 설정 객체를 등록하는 시작 설정이므로 함께 존재합니다.
- @EnableScheduling은 메서드에 @Scheduled를 붙였다고 즉시 호출하는 annotation이 아닙니다. Spring의 scheduling 기능과 예약 메서드 탐색을 활성화합니다. 실제 실행 대상은 다음에 읽을 AuthSessionCleanupScheduler.deleteExpiredSessions()입니다.
- public static void main(String[] args)는 Java 프로그램의 시작 메서드입니다. static이라 객체를 먼저 생성하지 않아도 JVM이 호출할 수 있고, String[] args는 명령행 인자를 받지만 현재 코드에서는 직접 사용하지 않습니다.
- SpringApplication.run(SpringdatajpaApplication.class, args)는 Spring ApplicationContext를 만들고 설정 파일을 읽고 Bean을 생성한 뒤 내장 서버를 시작합니다. 반환값은 현재 main에서 별도 변수에 저장하지 않습니다.
- @EnableScheduling이 활성화되는 시점은 애플리케이션 시작이고 deleteExpiredSessions()의 첫 실제 호출은 YAML의 interval만큼 기다린 뒤입니다. 따라서 main이 cleanup method를 직접 호출한다는 해석은 현재 코드와 다릅니다.

### 호출과 반환

- 호출자: JVM이 main을 호출하고 Spring이 이 클래스를 시작 설정으로 사용합니다.
- 직접 호출 대상: SpringApplication.run
- 간접 등록 대상: @Component Bean, @Scheduled method, Web MVC와 Security 설정
- 반환값 사용 위치: SpringApplication.run의 반환값은 사용하지 않습니다.
- 예외 지점: context 생성, 설정 누락, Bean 생성 실패 시 정상 시작되지 않을 수 있고 현재 main에는 별도 catch가 없습니다.

## 2. Scheduler 주기를 YAML이 공급한다

### 실제 파일

/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/resources/application.yaml:24-27

### 코드 원문

~~~~yaml
jwt:
  access-expiration-millis: ${JWT_ACCESS_EXPIRATION_MILLIS:600000}
  refresh-expiration-millis: ${JWT_REFRESH_EXPIRATION_MILLIS:10800000}
  refresh-session-cleanup-interval-millis: ${JWT_REFRESH_SESSION_CLEANUP_INTERVAL_MILLIS:3600000}
~~~~

### 코드 바로 아래 설명

- jwt는 JWT 관련 설정을 묶는 YAML mapping key입니다.
- access-expiration-millis의 기본값 600000은 Access Token 유효기간 10분입니다. Scheduler 실행 간격과 다른 값입니다.
- refresh-expiration-millis의 기본값 10800000은 새 Refresh Token의 만료 시각 계산에 사용되는 3시간입니다. cleanup 실행 주기가 아닙니다.
- refresh-session-cleanup-interval-millis가 Scheduler 실행 간격입니다. 기본값 3600000은 3,600,000ms, 즉 1시간입니다.
- ${ENV_NAME:default}는 Spring property placeholder 문법입니다. 외부 ENV_NAME을 먼저 찾고 값이 없으면 콜론 뒤의 default를 사용합니다. 예를 들어 JWT_REFRESH_SESSION_CLEANUP_INTERVAL_MILLIS=60000을 주입하면 60,000ms를 사용합니다.
- 이 값은 Refresh Token 자체의 생존 시간을 바꾸지 않습니다. token의 refreshExpiresAt 계산과 DB cleanup 실행 간격은 서로 다른 key입니다.
- 현재 YAML만으로 환경변수가 shell, Compose .env, 배포 환경 중 어디에서 실제 주입되는지는 확정할 수 없습니다.

### 같은 property가 연결되는 곳

~~~~text
application.yaml
└─ jwt.refresh-session-cleanup-interval-millis
   ├─ @Scheduled(initialDelayString = cleanup property)
   └─ @Scheduled(fixedDelayString = cleanup property)
~~~~

- initialDelayString은 첫 실행 전에 기다리는 시간입니다.
- fixedDelayString은 이전 method가 끝난 뒤 다음 실행까지 기다리는 시간입니다.
- 현재 기본값은 숫자 문자열이므로 3,600,000ms로 해석됩니다. Duration 표현식을 별도 테스트한 코드는 현재 없습니다.

## 3. AuthSessionCleanupScheduler가 HTTP 밖에서 정리 작업을 실행한다

### 실제 파일

/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/service/AuthSessionCleanupScheduler.java:11-25

### 코드 원문

~~~~java
@Component
@RequiredArgsConstructor
public class AuthSessionCleanupScheduler {

    private final AuthSessionRepository authSessionRepository;

    @Scheduled(
            initialDelayString = "${jwt.refresh-session-cleanup-interval-millis}",
            fixedDelayString = "${jwt.refresh-session-cleanup-interval-millis}"
    )
    @Transactional
    public void deleteExpiredSessions() {
        authSessionRepository.deleteAllExpiredAtOrBefore(LocalDateTime.now());
    }
}
~~~~

### 코드 바로 아래 설명

- @Component는 이 클래스를 Spring Bean 후보로 등록합니다. Controller가 new AuthSessionCleanupScheduler를 하지 않아도 Spring이 객체를 만들고 예약 method를 발견할 수 있습니다.
- @RequiredArgsConstructor는 Lombok이 final field를 받는 생성자를 컴파일 시 생성합니다. 소스에 생성자가 직접 보이지 않지만 AuthSessionRepository를 받는 생성자가 생깁니다.
- private final AuthSessionRepository는 만료 session 삭제를 실제로 수행하는 Repository입니다. Scheduler가 SQL을 직접 작성하지 않고 Repository method를 호출합니다.
- @Scheduled는 Spring scheduling infrastructure가 이 method를 예약 실행 대상으로 등록하게 합니다. Controller, Filter, 다른 service가 이 method를 호출하는 위치는 source 검색에서 확인되지 않았습니다.
- initialDelayString은 애플리케이션 시작 직후 즉시 실행하지 않고 property 값만큼 기다린 뒤 첫 실행하게 합니다.
- fixedDelayString은 이 method가 끝난 시점부터 같은 시간만큼 기다린 뒤 다음 호출을 예약합니다. fixed rate처럼 시작 시각 기준으로 고정 간격을 유지하는 설정이 아닙니다.
- @Transactional은 modifying query가 transaction 경계 안에서 수행되도록 합니다. 성공하면 commit되고, 실패 시 현재 method는 예외를 직접 catch하거나 재시도하지 않습니다.
- public void deleteExpiredSessions()는 삭제 건수를 호출자에게 반환하지 않습니다. Repository는 int를 반환하지만 Scheduler가 받지 않아 현재 코드에는 삭제 건수 log가 없습니다.
- LocalDateTime.now()는 method 실행 시점의 날짜·시간을 만들고 Repository의 now parameter로 전달됩니다.

### 실행 흐름

~~~~text
Spring context 생성
→ @Component로 Bean 생성
→ @Scheduled method 등록
→ initialDelay 경과
→ deleteExpiredSessions() 진입
→ LocalDateTime.now() 생성
→ Repository bulk DELETE
→ transaction 종료/commit
→ fixedDelay 경과
→ 반복
~~~~

### 확인되는 범위

- DB에서 만료 AuthSession row를 삭제합니다.
- 실행 주기는 하나의 YAML property가 정합니다.
- 현재 코드에는 Redisson RLock, tryLock, 분산 lock key가 없습니다.
- 현재 코드에는 삭제 건수 로그나 실패 재시도가 없습니다.
- 다중 backend instance에서 executor가 어떻게 동작하는지, 중복 DELETE의 실제 부하가 얼마인지는 source만으로 확인할 수 없습니다.

blue/green backend가 동시에 실행되는 운영 구조라면 각 instance가 이 Bean을 갖고 예약 method를 실행할 수 있습니다. 이는 source에 분산 lock 호출이 없다는 관찰이며, 실제 운영에서 어떤 instance 수와 DB lock 정책이 적용되는지는 배포 실행을 별도로 확인해야 합니다.

## 4. Repository bulk DELETE가 만료 row를 판정한다

### 실제 파일

/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/repository/AuthSessionRepository.java:15-37

### 코드 원문

~~~~java
public interface AuthSessionRepository extends JpaRepository<AuthSession, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    Optional<AuthSession> findByRefreshTokenHash(String refreshTokenHash);

    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query("""
            UPDATE AuthSession authSession
            SET authSession.revokedAt = :revokedAt
            WHERE authSession.user = :user
              AND authSession.revokedAt IS NULL
            """)
    int revokeAllActiveByUser(
            @Param("user") User user,
            @Param("revokedAt") LocalDateTime revokedAt
    );

    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query("""
            DELETE FROM AuthSession authSession
            WHERE authSession.refreshExpiresAt <= :now
            """)
    int deleteAllExpiredAtOrBefore(@Param("now") LocalDateTime now);
}
~~~~

### 코드 바로 아래 설명

- interface AuthSessionRepository extends JpaRepository<AuthSession, Long>은 Spring Data JPA가 구현체를 만들어 주도록 하는 선언입니다. AuthSession은 Entity type이고 Long은 ID type입니다.
- findByRefreshTokenHash의 PESSIMISTIC_WRITE는 07장의 Refresh rotation에서 row write lock을 요청합니다. cleanup method가 이 lock을 호출하는 것은 아닙니다.
- revokeAllActiveByUser는 비밀번호 변경·탈퇴 때 active session의 revokedAt을 일괄 UPDATE합니다. Scheduler가 호출하지 않고 UserService가 호출합니다.
- @Modifying은 SELECT가 아닌 UPDATE/DELETE query임을 알려 줍니다. clearAutomatically는 bulk query 후 persistence context를 비우고, flushAutomatically는 query 전 pending 변경을 flush하도록 하는 옵션입니다.
- @Query annotation 안의 Java text block은 여러 줄 JPQL을 문자열로 선언하는 문법입니다.
- DELETE FROM AuthSession에서 AuthSession은 DB table명이 아니라 JPA Entity 이름입니다. authSession은 query alias입니다.
- WHERE authSession.refreshExpiresAt <= :now는 만료 시각이 now보다 과거이거나 정확히 같은 row를 모두 대상에 넣습니다.
- @Param("now")는 Java parameter와 JPQL의 :now를 연결합니다. Scheduler의 LocalDateTime.now()가 이 값으로 들어옵니다.
- int 반환값은 영향을 받은 row count입니다. Scheduler가 이 값을 저장하지 않아 현재 운영 response나 log에 노출되지 않습니다.
- 이 query는 browser Cookie를 삭제하지 않습니다. DB row 삭제와 Cookie 만료는 별도의 동작이며 Cookie는 08장의 Controller와 RefreshCookieProvider가 처리합니다.

### 실행 경계

~~~~text
AuthSessionCleanupScheduler.deleteExpiredSessions()
→ deleteAllExpiredAtOrBefore(LocalDateTime.now())
→ JPQL DELETE
→ refreshExpiresAt <= now인 AuthSession row 제거
→ int row count는 Scheduler에서 버림
→ transaction 종료
~~~~

### 예외 지점

- Entity 이름이나 field 이름이 query mapping과 다르면 query parsing·실행 오류가 날 수 있습니다.
- modifying query는 transaction 경계가 필요하지만 현재 Scheduler method에 @Transactional이 있습니다.
- DB 연결·권한·lock 문제는 발생할 수 있으나 Scheduler에는 별도 error response나 retry 코드가 없습니다.

## 5. RequestLogInterceptor가 MVC 요청의 시작과 완료를 기록한다

### 실제 파일

/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/config/RequestLogInterceptor.java:9-46

### 코드 원문

~~~~java
@Slf4j
@Component
public class RequestLogInterceptor implements HandlerInterceptor {

    private static final String START_TIME = "startTime";

    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler
    ) {
        request.setAttribute(START_TIME, System.currentTimeMillis());

        log.info("[REQUEST] {} {}", request.getMethod(), request.getRequestURI());

        return true;
    }

    @Override
    public void afterCompletion(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler,
            Exception ex
    ) {
        Long startTime = (Long) request.getAttribute(START_TIME);
        long elapsedTime = System.currentTimeMillis() - startTime;

        log.info(
                "[RESPONSE] {} {} status={} time={}ms",
                request.getMethod(),
                request.getRequestURI(),
                response.getStatus(),
                elapsedTime
        );
    }
}
~~~~

### preHandle 코드 바로 아래 설명

- @Slf4j는 Lombok이 log logger field를 생성하게 합니다. 소스에 Logger 선언이 없어도 log.info를 호출할 수 있는 이유입니다.
- @Component는 Interceptor를 Bean으로 등록합니다. 모든 URL에 자동 적용되는 것이 아니라 InterceptorConfig가 path pattern을 연결해야 합니다.
- implements HandlerInterceptor는 Spring MVC handler lifecycle에 참여한다는 뜻입니다. Servlet Filter와 다른 계층이며 Controller handler 선택 전·후에 동작합니다.
- private static final String START_TIME은 request attribute key입니다. static은 instance 간 공유, final은 재할당 금지입니다.
- preHandle의 request는 HTTP method·URI와 attribute를 제공하고 response는 현재 응답 객체이며 handler는 선택된 Controller 정보입니다. 현재 response와 handler는 받기만 하고 사용하지 않습니다.
- request.setAttribute(START_TIME, System.currentTimeMillis())는 시작 시각을 해당 request에 저장합니다. static 변수에 저장하지 않아 여러 요청의 값이 섞이지 않습니다.
- log.info의 {}는 SLF4J parameterized logging placeholder입니다. method와 URI가 차례로 들어갑니다.
- return true는 다음 MVC Interceptor와 Controller를 계속 실행하라는 의미입니다. 인증 성공이나 JWT 검증을 뜻하지 않습니다.

### afterCompletion 코드 바로 아래 설명

- afterCompletion은 MVC 요청 처리가 끝난 뒤 호출되는 callback입니다. 정상 응답과 Controller 예외 경로에서 response status를 기록할 위치입니다.
- handler는 받지만 사용하지 않습니다.
- Exception ex는 예외 정보를 받을 수 있는 parameter지만 현재 구현은 log에 포함하지 않습니다. 현재 response log만으로 예외 class/message까지 확인할 수 있다고 말하면 안 됩니다.
- request.getAttribute는 Object를 반환하므로 (Long) cast로 시작 시각을 꺼냅니다.
- elapsedTime은 완료 시각 - 시작 시각의 millisecond입니다.
- response.getStatus는 Controller 또는 exception handler가 설정한 현재 status를 읽습니다.
- 이 method는 response body, Cookie, 예외 응답을 만들지 않고 관측용 log만 남깁니다.

### Filter와의 경계

~~~~text
Servlet Filter
→ JwtAuthenticationFilter가 Authorization header 검사
→ 오류면 response를 직접 끝낼 수 있음
→ 또는 filterChain.doFilter로 MVC에 전달

MVC Interceptor
→ RequestLogInterceptor.preHandle
→ Controller
→ RequestLogInterceptor.afterCompletion
~~~~

JwtAuthenticationFilter가 Controller 도달 전에 직접 401 JSON을 작성한 요청까지 RequestLogInterceptor가 항상 기록한다고 현재 코드만으로 단정할 수 없습니다. RequestLogInterceptor는 MVC HandlerInterceptor이고 그 Filter 단계 응답 경로를 직접 다루지 않으며, 이를 검증하는 test도 없습니다.

## 6. InterceptorConfig가 적용 범위와 등록 순서를 정한다

### 실제 파일

/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/config/InterceptorConfig.java:8-23

### 코드 원문

~~~~java
@Configuration
@RequiredArgsConstructor
public class InterceptorConfig implements WebMvcConfigurer {

    private final RequestLogInterceptor requestLogInterceptor;
    private final SessionOriginInterceptor sessionOriginInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(requestLogInterceptor)
                .addPathPatterns("/**");

        registry.addInterceptor(sessionOriginInterceptor)
                .addPathPatterns("/sessions", "/sessions/refresh");
    }
}
~~~~

### 코드 바로 아래 설명

- @Configuration은 이 class를 Spring 설정 Bean으로 등록합니다.
- @RequiredArgsConstructor는 두 final Interceptor를 받는 constructor를 Lombok으로 생성하고 Spring이 Bean을 주입하게 합니다.
- implements WebMvcConfigurer는 MVC 설정 callback을 override할 수 있게 합니다.
- addInterceptors는 매 HTTP 요청에서 Controller가 호출하는 method가 아니라 애플리케이션 초기화 시 MVC chain을 구성하는 callback입니다.
- registry.addInterceptor(requestLogInterceptor).addPathPatterns("/**")는 모든 MVC path에 RequestLogInterceptor를 등록합니다.
- sessionOriginInterceptor의 두 pattern은 /sessions와 /sessions/refresh뿐입니다. Origin 검사가 모든 API에 적용된다는 뜻이 아닙니다.
- source의 등록 순서상 RequestLogInterceptor가 먼저, SessionOriginInterceptor가 나중에 추가됩니다. 두 interceptor가 모두 match하는 sessions path를 이해할 때 이 순서를 기준으로 읽습니다.
- /sessions에는 POST 로그인과 DELETE 로그아웃이 모두 포함될 수 있고, 실제 HTTP method 조건은 SessionOriginInterceptor 내부에서 처리됩니다.
- 이 registration order를 직접 assertion하는 test는 현재 없습니다.

### path별 지도

~~~~text
GET /posts
→ RequestLogInterceptor만 match
→ Filter/Controller/Service
→ RequestLogInterceptor.afterCompletion

POST /sessions
→ RequestLogInterceptor
→ SessionOriginInterceptor
→ Origin 검사
→ SessionController 또는 Origin 거부

POST /sessions/refresh
→ RequestLogInterceptor
→ SessionOriginInterceptor
→ SessionController.refreshSession 또는 Origin 거부

DELETE /sessions
→ RequestLogInterceptor
→ SessionOriginInterceptor
→ SessionController.deleteSession 또는 Origin 거부
~~~~

DELETE /sessions의 모든 Origin 조합을 직접 확인하는 SecurityConfigTest는 현재 없습니다. 위 지도는 path pattern과 source 연결을 보여 주는 것이며 method별 결과 전부가 test로 증명됐다는 뜻은 아닙니다.

### 모든 Test task 공통 설정

~~~~groovy
tasks.withType(Test).configureEach {
    useJUnitPlatform()
    jvmArgs(
~~~~

- tasks.withType(Test)는 Gradle Test type인 task 전체를 선택합니다. 기본 test, redisTest, mysqlTest가 모두 대상입니다.
- configureEach는 각 task에 같은 설정을 적용합니다.
- useJUnitPlatform은 JUnit 5 engine으로 test를 검색·실행하게 합니다.
- -javaagent 옵션은 Mockito agent jar를 테스트 JVM에 붙입니다. application Bean이나 환경변수가 아닙니다.
- -Xshare:off는 agent와 JVM class data sharing 충돌을 피하는 JVM option입니다.
- testLogging은 passed, skipped, failed와 전체 exception stack trace를 로그에 표시합니다.

### 기본 test task

~~~~groovy
tasks.named('test') {
    systemProperty 'spring.profiles.active', 'test'
    useJUnitPlatform {
        excludeTags 'redis-integration', 'mysql-integration'
    }
    finalizedBy jacocoTestReport
}
~~~~

### 코드 바로 아래 설명

- systemProperty는 test JVM에 spring.profiles.active=test를 전달합니다.
- excludeTags는 해당 tag test를 삭제하는 것이 아니라 이번 test task의 선택 대상에서 제외합니다.
- finalizedBy는 test 종료 후 JaCoCo report task를 연결합니다. report가 Redis/MySQL test를 대신 실행하지는 않습니다.
- 따라서 ./gradlew test는 일반 단위, Spring context, H2, MockMvc test를 실행하지만 Redis·MySQL tagged test는 제외합니다.

### Redis와 MySQL task

~~~~groovy
tasks.register('redisTest', Test) {
    description = 'Runs integration tests against a Testcontainers Redis server.'
    group = 'verification'
    testClassesDirs = sourceSets.test.output.classesDirs
    classpath = sourceSets.test.runtimeClasspath
    useJUnitPlatform {
        includeTags 'redis-integration'
    }
    shouldRunAfter test
}

tasks.register('mysqlTest', Test) {
    description = 'Runs schema and locking integration tests against a Testcontainers MySQL server.'
    group = 'verification'
    testClassesDirs = sourceSets.test.output.classesDirs
    classpath = sourceSets.test.runtimeClasspath
    useJUnitPlatform {
        includeTags 'mysql-integration'
    }
    shouldRunAfter test
}
~~~~

- 두 task는 기본 test와 별개입니다.
- testClassesDirs와 classpath는 컴파일된 test class와 runtime dependency를 연결합니다.
- includeTags는 지정된 tag만 선택합니다.
- shouldRunAfter는 두 task가 같은 invocation에 포함될 때 순서를 권장하는 관계입니다. task를 자동 실행하는 연결은 아닙니다.
- check.dependsOn이 실제 연결을 추가합니다.

~~~~groovy
check.dependsOn jacocoTestCoverageVerification
check.dependsOn tasks.named('redisTest')
check.dependsOn tasks.named('mysqlTest')
~~~~

- ./gradlew check에는 coverage verification, redisTest, mysqlTest가 포함됩니다.
- 현재 build.gradle만으로 최종 세부 실행 순서를 단정하지 않고 shouldRunAfter를 ordering hint로 읽습니다.
- 이 문서 작성 중 Gradle task는 실행하지 않았으므로 Docker 가용성·컨테이너 실행 결과·전체 소요 시간은 확인하지 않았습니다.

### JaCoCo 범위

~~~~groovy
def coverageIncludes = [
    'kr/adapterz/springdatajpa/entity/**',
    'kr/adapterz/springdatajpa/auth/**',
    'kr/adapterz/springdatajpa/config/**',
    'kr/adapterz/springdatajpa/service/**',
    'kr/adapterz/springdatajpa/controller/**'
]

tasks.named('jacocoTestCoverageVerification') {
    dependsOn test
    classDirectories.setFrom(files(sourceSets.main.output.classesDirs.collect {
        fileTree(dir: it, include: coverageIncludes)
    }))
    violationRules {
        rule {
            limit {
                counter = 'LINE'
                value = 'COVEREDRATIO'

            }
        }
    }
}
~~~~

- coverageIncludes는 report와 verification에 넣을 운영 class package pattern입니다.

- verification의 dependsOn test는 일반 test 결과를 필요로 한다는 뜻입니다. redisTest와 mysqlTest 결과가 JaCoCo execution data에 자동 합쳐진다고 현재 설정만으로 말할 수 없습니다.

이 통합 test는 H2/Spring context에서 soft-delete 조회와 탈퇴 작성자 게시글 정책을 확인합니다. 비밀번호 변경 시 모든 AuthSession을 실제 DB에서 revoke하는 repository integration assertion은 별도 method로 찾지 못했습니다.

## 10. 테스트 종류별 확인 범위

### 순수 단위 테스트

Mockito 또는 Java 객체만 사용해 한 class의 계산·분기·상태를 확인합니다.

예: JwtProviderTest, RefreshTokenProviderTest, AuthSessionTest, UserTest, SessionServiceTest, JwtAuthenticationFilterTest, ControllerDelegationTest.

이 test만으로 Spring Bean 등록, JPA query, DB transaction, browser Cookie 전송을 증명하지 않습니다.

### Spring context와 MockMvc

SecurityConfigTest는 @SpringBootTest와 MockMvc로 실제 Spring Security chain과 MVC endpoint를 거칩니다. 401/403 status와 JSON response boundary를 확인할 수 있습니다.

MockMvc는 browser가 아니므로 실제 browser의 CORS policy, HttpOnly Cookie 자동 전송, preflight credentials, blue/green network behavior를 그대로 증명하지 않습니다.

### H2 repository 통합

UserSoftDeleteIntegrationTest와 repository integration test는 Spring context와 H2를 사용합니다. SQL·JPA mapping·조회 filter를 확인하지만 운영 MySQL의 isolation, index plan, lock behavior와 동일하다고 말할 수 없습니다.

### Redis와 MySQL Testcontainers

현재 tag가 확인되는 파일은 RedisViewCountStoreIntegrationTest, RedisAofRestartIntegrationTest, MySqlSchemaIntegrationTest입니다.

Redis tag는 조회수 Redis, MySQL tag는 schema·좋아요 동시성을 다룹니다. AuthSession cleanup Scheduler가 실제 MySQL에서 주기적으로 실행되는 test는 현재 없습니다.

### JaCoCo

test 종료 후 report가 연결되고, verification minimum은 line coverage 0.80입니다. coverage include는 entity/auth/config/service/controller입니다. Repository와 DTO는 test가 있어도 현재 include 목록에서 제외됩니다. redisTest와 mysqlTest 결과가 coverage verification에 자동 합쳐진다고 현재 build.gradle만으로는 말할 수 없습니다.

## 11. 현재 코드에 없는 검증

실제 src/test 검색에서 다음 전용 test가 확인되지 않았습니다.

- AuthSessionCleanupSchedulerTest
- RequestLogInterceptorTest
- InterceptorConfig 등록 순서 test
- Refresh Token 실제 다중 transaction 동시성 integration test
- browser CORS preflight/credentials test
- 실제 Cookie jar 로그인→refresh→logout browser E2E
- AuthSession 만료 DELETE를 실제 MySQL Testcontainers에서 scheduler 주기로 실행하는 test
- blue/green 두 backend에서 scheduler 중복 실행을 확인하는 test

따라서 문서에서는 다음처럼 써야 정확합니다.

- Scheduler가 설정된 주기로 만료 row를 삭제하도록 구현되어 있다: source로 확인 가능
- Scheduler가 운영 DB에서 매시간 성공적으로 삭제한다: 운영 실행 로그와 DB가 없어 확인 불가
- RequestLogInterceptor가 모든 401을 기록한다: Filter가 MVC 전에 끝내는 경로를 별도 검증하지 않아 확정 불가
- Refresh 동시 요청이 test로 완전히 보장된다: 현재 test 목록으로 확인 불가
- CORS가 실제 browser에서 정상 동작한다: MockMvc만으로 확정 불가

## 결론

현재 인증 관련 백엔드에는 세 실행 축이 있습니다.

- 요청 중 인증: Filter → MVC Interceptor → Controller/Service
- 요청과 독립된 정리: Scheduler → Repository bulk DELETE
- 코드 검증: Gradle task → JUnit 선택 → 단위/MockMvc/H2/Testcontainers

AuthSessionCleanupScheduler는 Refresh Session 사용 여부를 판단하거나 Cookie를 삭제하지 않습니다. 만료 시각이 지난 DB row를 주기적으로 삭제할 뿐입니다. RequestLogInterceptor는 요청을 허용하거나 인증하는 코드가 아니라 MVC 요청의 시작 시각과 응답 status·소요 시간을 기록합니다. Gradle 설정은 모든 테스트를 운영 환경처럼 실행하는 것이 아니라 task와 tag에 따라 범위를 나눕니다.

이번 문서 작성에서 실행한 검증은 source path, method, Gradle 설정, test tag를 정적으로 대조하는 작업입니다. backend/frontend test, Docker, 실제 DB·Redis, browser E2E는 실행하지 않았습니다.
