# 21. 전체 코드의 설계 의도와 실행 흐름

이 문서는 01~20장에서 파일별로 확인한 내용을 한 단계 위에서 다시 연결한다. 목표는
“각 클래스가 무엇을 한다”를 나열하는 것이 아니라, 왜 현재와 같은 경계·상태·저장소·설정·테스트
구조가 만들어졌는지를 실제 코드에 근거해 이해하는 것이다.

## 0. 근거와 표현 규칙

### 확인 범위

- 백엔드: backend의 src/main/java, src/main/resources, src/test, build.gradle
- 프론트엔드: frontend의 src, package.json, Dockerfile, nginx/default.conf
- 배포: 두 저장소의 deploy/와 .github/workflows/
- 기존 교안: actual-code-learning/00~20

### 문장의 신뢰도 표시

- **[확정]** 현재 소스·설정·테스트에서 직접 확인되는 동작이다.
- **[테스트 근거]** 특정 테스트가 그 동작을 확인하지만, 테스트가 확인하지 않는 범위까지 확대하지 않는다.
- **[설계 의도 해석]** 코드 구조를 보고 합리적으로 해석한 이유다. 작성자가 직접 남긴 결정 기록은 아니다.
- **[확인 불가]** 운영 문서·커밋 메시지·실제 인프라 상태가 없어서 이 저장소만으로는 확정할 수 없다.

예를 들어 PESSIMISTIC_WRITE가 있다는 사실은 확정할 수 있지만, “트래픽이 많아서 이 락을
선택했다”는 작성자의 동기까지 코드가 증명하지는 않는다.

### 21번의 위치

00장의 공식 학습 대상은 현재도 214/214 파일이다. 이 21번은 새 소스 파일을 추가한 장이

## 1. 프로젝트를 한 문장으로 요약하면

**React SPA가 인증이 필요한 게시글·댓글 기능을 호출하고, Spring 애플리케이션이
검증·업무 규칙·동시성 제어를 담당하며, MySQL을 영구 저장소로 사용하고 Redis를
조회수의 빠른 증가 버퍼로 사용하는 구조**다.

실행 경계는 다음과 같다.

```text
브라우저
  → React Router / 페이지 컴포넌트
  → src/api/api.js (Authorization, Cookie, 401 재시도)
  → 프론트 Nginx (/api/는 백엔드로 전달)
  → 백엔드 Nginx (blue 또는 green backend로 전달)
  → Session/CORS Origin Interceptor
  → Spring Security JWT Filter
  → Controller
  → DTO 역직렬화·Bean Validation
  → Service 트랜잭션
  → Repository/Entity
  → MySQL 또는 Redis
  → Response DTO/JSON
  → React state 갱신 또는 오류·재시도 화면
```

GET /posts/{postId}처럼 읽기 요청도 단순 조회로 끝나지 않는다. 게시글을 읽을 수 있는지
확인하고, 댓글·좋아요·신고 여부를 응답에 넣고, 조회수를 증가시키기 때문이다.

## 2. 전체 설계를 관통하는 기준

| 코드에서 보이는 기준 | 현재 구현 | 설계 의도 해석 |
|---|---|---|
| 요청 계층 분리 | Controller → Service → Repository | HTTP·업무 규칙·DB 접근을 분리해 각 계층의 변경 범위를 줄이려는 구조로 해석할 수 있다. |
| 상태의 단일 책임 | 사용자·게시글·카운터·세션·조회수 테이블 분리 | 서로 다른 변경 빈도와 동시성 조건을 한 row에 몰아 넣지 않으려는 의도로 해석할 수 있다. |
| 방어적 검증 | 프론트 유효성 검사 + DTO Bean Validation + Service 검사 + DB 제약 | 클라이언트 우회나 경쟁 요청에도 서버와 DB가 최종 방어하도록 한 구조다. [확정] |
| 영구 상태와 임시 상태 분리 | MySQL은 원본, Redis는 조회수 증가·dirty set | 빠른 쓰기와 재시작 후 복구를 함께 고려한 구조로 해석할 수 있다. |
| 명시적 실패 응답 | ApiErrorCode, GlobalExceptionHandler, ErrorResponseWriter | 클라이언트가 상태 코드만 보지 않고 안정된 오류 코드를 사용하게 하려는 구조다. |
| 인증 수명 분리 | 짧은 Access Token, DB hash Refresh Session | 매 요청 DB 세션 조회 없이 빠르게 인증하면서 장기 로그인과 강제 무효화를 함께 처리하려는 구조로 해석할 수 있다. |
| 환경 분리 | local H2/create, prod MySQL/validate+Flyway, test Redis 비활성 | 개발 편의성과 운영 스키마 안정성을 분리하려는 목적이 명확하다. [확정] |
| 실패 격리 | 페이지·댓글·목록 단위 ErrorBoundary, 요청 AbortController | 한 화면의 작은 실패가 전체 앱을 무너뜨리지 않게 하려는 구조로 해석할 수 있다. |

“의도 해석”은 사실과 섞어 읽으면 안 된다. 실제 보장은 옆 열의 구현 범위다.

## 3. 애플리케이션 시작과 환경 설정의 의도

### 3.1 SpringdatajpaApplication의 세 annotation

파일: backend/src/main/java/kr/adapterz/springdatajpa/SpringdatajpaApplication.java

- @SpringBootApplication은 컴포넌트 스캔, 자동 설정, 설정 클래스 역할을 묶는다. [확정]
- @ConfigurationPropertiesScan은 ViewCountProperties처럼 YAML을 타입 있는 객체로 받는 클래스를 찾는다. [확정]
- @EnableScheduling은 @Scheduled가 붙은 세션 정리·조회수 flush 메서드를 등록한다. [확정]
- SpringApplication.run(...)이 내장 서버와 Spring Bean 생성을 시작한다. [확정]

**설계 의도 해석:** 시작 클래스는 업무 로직을 두지 않고 “어떤 기능을 켜고 어떤 설정 객체를
스캔하는가”만 선언한다. 애플리케이션 시작 책임과 게시글 업무를 분리한 것이다.

### 3.2 profile 병합

파일:

- backend/src/main/resources/application.yaml
- application-local.yaml
- application-prod.yaml
- src/test/resources/application-test.yaml

현재 흐름은 다음과 같다.

```text
application.yaml 기본값
  + 활성 profile(local/prod/test)의 같은 key
  → Spring Environment
  → @Value 또는 @ConfigurationProperties Bean
  → Service/Config Bean
```

- 기본 profile은 local이다. test profile group은 local 설정을 함께 가져오되 test에서 일부 값을 덮어쓴다. [확정]
- local은 H2 메모리 DB, ddl-auto:create, SQL 초기화, Flyway 비활성이다. [확정]
- prod는 외부 DB URL·계정·비밀번호를 받고, ddl-auto:validate, Flyway 활성이다. [확정]
- test는 Redisson 자동 설정을 제외하고 app.view-count.enabled=false로 DB 조회수 구현체를 선택한다. [확정]

**왜 local에서 자동 생성하는가?** [설계 의도 해석]

개발자가 임시 H2를 쉽게 재생성하려는 편의가 목적이라고 해석할 수 있다. 반대로 운영 RDS에서
create가 실행되면 기존 구조를 재생성하거나 손상시킬 위험이 있으므로 validate로 Entity 매핑과
실제 schema가 맞는지만 확인하고 변경은 Flyway 이력으로 통제한다.

### 3.3 placeholder는 제한 시간 자체가 아니다

예를 들어 application.yaml의 REDIS_CONNECT_TIMEOUT 기본값 2s는 “환경변수가 없을 때 사용할 값”이다.
환경변수가 있으면 그 값이 우선한다. 실제 연결 수립 최대 시간은 Redis 클라이언트가 이 값을
해석한 뒤 결정한다. 같은 placeholder를 “항상 최대 2초”라고 주석 처리하면 의미가 달라진다.

같은 원리가 다음에 적용된다.

- JWT_SECRET: 운영에서는 외부 secret을 주입하고 local에서만 개발용 기본값을 둔다.
- DB_URL, DB_USERNAME, DB_PASSWORD: prod Compose가 값을 요구한다.
- VIEW_COUNT_REDIS_ENABLED: 구현체 선택의 입력값이다.

### 3.4 Actuator health와 인증의 분리

application.yaml의 management.endpoints.web.exposure.include=health와
management.endpoint.health.show-details=never는 health endpoint를 HTTP로 노출하고 내부 세부
정보를 숨기는 설정이다. 이것만으로 “누구나 접근 가능”이 결정되지는 않는다. SecurityConfig가
GET /actuator/health를 permitAll로 허용하고, Nginx와 배포 스크립트가 이 URL을 health check로 호출한다.

```text
배포 스크립트
  → http://backend-port/actuator/health
  → backend Nginx의 /health
  → 현재 backend의 actuator health
```

프론트 Nginx는 정적 Nginx의 /health를 200 ok로 응답한다. 두 health는 서로 다른 프로세스를 검사한다. [확정]

### 3.5 CORS와 Origin 검사의 두 층

- WebConfig: 브라우저 CORS 응답을 구성한다.
- SessionOriginInterceptor: 로그인·refresh·logout의 세션 변경 요청에 허용 Origin을 검사한다.
- SecurityConfig: OPTIONS와 public endpoint를 허용하고 나머지를 인증한다.

따라서 CORS 설정은 브라우저의 cross-origin 동작을 위한 것이고, Origin interceptor는 세션
변경 요청을 별도로 방어하는 것이다. 두 설정은 서로 대체하지 않는다.

현재 interceptor의 isAllowed(null)은 허용하지 않으므로 세션 경로에서 Origin 없는 요청도
거부한다. curl·서버 간 호출에도 Origin을 명시해야 한다는 것이 현재 구현의 결과다. [확정]

### 3.6 설정 key의 소유자

| 설정 key | 읽는 코드 | 설계상 역할 |
|---|---|---|
| app.view-count.enabled | DatabaseViewCountUpdater, RedisViewCountStore, RedisViewCountFlushScheduler | Redis 경로와 DB 경로 중 어느 Bean을 생성할지 결정 |
| app.view-count.count-key-prefix | ViewCountProperties | 게시글별 Redis count key namespace를 통일 |
| app.view-count.dirty-set-key | ViewCountProperties, RedisViewCountStore | flush 대상 postId를 모으는 Set 이름을 통일 |
| app.view-count.flush-lock-key | ViewCountProperties, RedisViewCountFlushScheduler | 여러 backend가 공유할 Redisson lock 이름 |
| app.view-count.flush-interval | ViewCountProperties, RedisViewCountFlushScheduler | dirty set을 DB로 반영하는 주기 |
| jwt.secret | JwtProvider | Access Token 서명·검증에 같은 HMAC secret 사용 |
| jwt.access-expiration-millis | JwtProvider | Access Token exp 계산 |
| jwt.refresh-expiration-millis | RefreshTokenProvider | Refresh Session 만료 시각 계산 |
| jwt.refresh-cookie-secure | RefreshCookieProvider | HTTPS에서 Cookie를 전송할지 결정 |
| jwt.refresh-cookie-path | RefreshCookieProvider | Cookie가 전송될 URL path 범위를 결정 |
| cors.allowed-origins | CorsOriginProvider, WebConfig | 브라우저 CORS와 session Origin 검사에 같은 허용 목록 사용 |

설정 key를 Service 메서드 안에서 직접 문자열로 읽지 않고 Properties·Provider·Config Bean으로
모으는 이유는 [설계 의도 해석]이다. 환경값의 형식 검증과 Bean 선택을 애플리케이션 시작 시점에
끝내고, 업무 메서드는 이미 준비된 객체를 사용하게 하려는 구조다.

local의 refresh-cookie-path는 /sessions이고 prod는 /api/sessions다. 외부 브라우저 URL에는
프론트 Nginx의 /api prefix가 존재하지만, Nginx가 backend로 전달할 때는 그 prefix를 제거한다.
따라서 Cookie가 브라우저에서 전송되는 공개 경로와 Spring Controller의 내부 경로가 다를 수
있다. 이 설정을 바꾸면 refresh 요청이 Cookie를 받지 못할 수 있으므로 frontend Nginx의
proxy 경로와 함께 읽어야 한다.

## 4. 데이터 모델을 이렇게 나눈 이유

### 4.1 User: soft delete와 authVersion

파일: entity/User.java, UserRepository.java, UserService.java

User에는 deleted, receivedReportCount, authVersion이 있다.

```text
deleted = true
  → 활성 사용자 조회 메서드에서 제외
  → CustomUserDetails.isEnabled() = false
  → 기존 Access Token도 Filter에서 통과하지 못함
```

계정을 물리적으로 지우지 않고 deleted를 바꾸는 이유는 [설계 의도 해석]이다. 게시글·댓글·신고의
작성자 FK를 유지하고 탈퇴 계정의 흔적을 보존하면서 로그인만 막기 위한 방식으로 해석할 수 있다.
실제 코드가 보장하는 것은 “삭제 flag를 조회 조건과 인증 상태에 반영한다”는 점이다.

비밀번호 변경은 authVersion++을 수행한다.

```text
Access Token 생성 시 authVersion claim 포함
→ 비밀번호 변경 시 User.authVersion 증가
→ 이후 JWT Filter가 token claim과 현재 User 값 비교
→ 예전 token 거부
```

이 방식은 모든 Access Token을 DB에서 일괄 삭제하지 않고도 특정 사용자 토큰을 무효화한다.

### 4.2 Post를 집계 루트로 두되 카운터 row는 분리

파일: entity/Post.java, PostCounter.java, PostViewCount.java, PostImage.java

Post 생성자는 Post와 함께 PostCounter, PostViewCount를 만든다. @MapsId로 두 보조 엔티티가
Post의 ID를 공유한다.

```text
Post 1 ── 1 PostCounter
     └─ 1 PostViewCount
     └─ * PostImage
```

- Post 본문·삭제 flag·version은 게시글 자체의 상태다.
- PostCounter는 좋아요·댓글·신고 같은 작은 정수 집계다.
- PostViewCount는 조회수만 별도 보관한다.
- PostImage는 게시글 생명주기와 함께 생성·교체·삭제된다.

**왜 Post 안에 모든 count를 넣지 않았는가?** [설계 의도 해석]

좋아요·댓글·신고·조회수는 변경 빈도와 동시성 방식이 다르다. 하나의 Post row를 모든 요청이
수정하면 본문 수정과 count 증가가 같은 row에서 충돌한다. 현재 코드는 카운터를 별도 row로
분리하고 조회수는 다시 PostViewCount로 분리해 서로 다른 저장·락 전략을 적용한다.

PostCounter의 현재 production 메서드는 report()만 남아 있다. 좋아요·댓글 수는 Entity의 ++
메서드가 아니라 Repository bulk update를 사용한다. 따라서 PostCounterTest가 생성과 초기값을
확인한다고 해서 좋아요·댓글 증가 API가 Entity 메서드를 호출한다는 뜻은 아니다.

### 4.3 Post의 @Version은 본문 수정 충돌용

PostService.fixPost와 삭제는 요청의 version을 확인하고 JPA @Version으로 낙관적 충돌을
검출한다. 이미지 collection만 바뀌는 경우에는 OPTIMISTIC_FORCE_INCREMENT를 요청해 본문
변경이 없더라도 게시글 version을 올린다.

```text
화면 A가 version 3을 읽음
화면 B가 먼저 수정 → DB version 4
화면 A가 version 3으로 수정 시도
→ PostVersionConflictException/OptimisticLock 예외
→ 409 응답
```

이 락은 좋아요 수나 조회수 증가용 락이 아니다. 게시글 편집의 “내가 읽은 버전이 아직 같은가”를
확인하는 용도다.

### 4.4 Like와 Report의 unique 제약

- Like: (post_id, user_id) unique
- PostReport: (post_id, user_id) unique

Service에서 먼저 exists를 확인해 사용자에게 친절한 오류를 제공하고, DB unique 제약이
최종 방어선이다. 경쟁 요청에서는 두 요청이 모두 exists=false를 읽을 수 있으므로 DB 제약
위반을 별도 예외로 변환한다. [확정]

Like ID는 현재 모든 독립 ID와 같은 IDENTITY 전략이다. 과거 baseline의 post_likes_seq를
V6에서 제거한 것은 현재 Entity 전략과 운영 schema를 맞추기 위한 migration이다.

### 4.5 AuthSession: refresh token 자체가 아니라 hash 저장

RefreshTokenProvider가 만든 원문은 Cookie로 브라우저에 가고, DB에는 SHA-256 hash만 저장된다.

```text
원문 refresh token
  → SHA-256 hex hash
  → AuthSession.refreshTokenHash (unique)
```

DB 유출만으로 Cookie 원문을 바로 재사용하기 어렵게 하려는 구조로 해석할 수 있다. 만료·revoke
상태는 AuthSession row가 관리하고 hash 조회에는 PESSIMISTIC_WRITE가 걸린다.

## 5. 요청 처리 계층을 나눈 이유

### 5.1 Controller는 HTTP 어댑터

Controller는 path/query/body/cookie/principal을 받고, @Valid가 붙은 DTO는 Spring에 검증을
요청하고, Service를 호출하고, 상태 코드와 Cookie header를 조립한다. 현재 CommentController의
일부 request parameter처럼 @Valid가 없는 입력도 있으므로 모든 DTO가 자동 검증된다고 말할 수는
없다. 반환 DTO는 Spring이 JSON body로 직렬화한다.

예를 들어 SessionController.createSession은 SessionService.createSession을 호출한 뒤
HttpServletResponse.addHeader("Set-Cookie", ...)로 Cookie를 response header에 넣고 DTO를
return한다. header와 body는 별개의 response 구성 요소이므로 body에 Cookie 값을 넣지 않는다.

### 5.2 Service는 업무 순서와 transaction 경계

Service에서 담당하는 것은 “누가 무엇을 할 수 있는가”와 “여러 repository 호출을 어떤 순서로
묶는가”다.

예: 신고.

```text
게시글을 update lock으로 조회
→ 신고자 active 여부 확인
→ 자기 글인지 확인
→ 중복 신고 여부 확인
→ PostReport 저장
→ PostCounter.report()
→ 작성자 User.receiveReport()
→ Response DTO 생성
```

이 흐름이 하나의 @Transactional 안에 있으므로 정상 완료 전 중간 변경은 commit되지 않는다.
구체적인 rollback 정책은 예외 타입·Spring 설정에 따라 달라질 수 있으므로 “모든 예외가 항상
같은 방식으로 rollback된다”고 확대해서 말할 수는 없다.

### 5.3 Repository는 SQL과 lock의 경계

Repository에는 derived query, JPQL @Query, native SQL, @Lock, @EntityGraph가 모여 있다.

락을 Repository에 두는 이유는 [설계 의도 해석]이다. SQL을 생성하는 조회 경계에서
“이 row를 어떤 잠금으로 읽을 것인가”를 선언하면 Service는 업무 순서를 읽고 동일 조회를
다른 호출자가 사용할 때 lock 여부가 숨겨지지 않는다.

### 5.4 예외 응답의 두 경로

```text
Controller 호출 중 예외
  → GlobalExceptionHandler
  → ResponseEntity<ErrorResponseDto>

Security Filter/Origin Interceptor에서 먼저 거절
  → Controller까지 도달하지 않음
  → ErrorResponseWriter가 servlet response에 JSON 직접 작성
```

두 경로가 같은 ErrorResponseDto/ApiErrorCode 계열을 사용하도록 맞춘 이유는 프론트가 오류
응답 형태를 한 가지로 처리하게 하려는 구조로 해석할 수 있다. GlobalExceptionHandler가
Filter보다 먼저 실행되는 것은 아니다. Filter가 response를 끝내면 Handler는 호출되지 않는다.

## 6. 인증 설계의 의도

### 6.1 로그인: Access Token과 Refresh Session을 동시에 만든다

```text
LoginPage
→ authApi.login
→ api.request("/sessions", POST)
→ SessionController.createSession
→ SessionService.createSession
→ AuthenticationManager
→ CustomUserDetailsService / password encoder
→ JwtProvider.createAccessToken(userId, authVersion)
→ RefreshTokenProvider.createRefreshToken()
→ hashRefreshToken()
→ AuthSession 저장
→ accessToken JSON + refresh Cookie header
```

- Access Token은 프론트 authStorage(localStorage)에 저장된다.
- Refresh Token은 HttpOnly Cookie로 보낸다.
- DB에는 Refresh Token 원문이 아닌 hash를 저장한다.

**설계 의도 해석:** Access Token을 매 요청 DB에 저장·조회하지 않고 빠르게 인증하고,
Access Token이 만료되면 HttpOnly Cookie로 새 Access Token을 얻도록 역할을 나눈 것이다.
localStorage 사용의 보안 트레이드오프 자체는 현재 코드에서 해결되지 않으므로, “토큰 탈취가
불가능하다”고 말할 수 없다.

### 6.2 Access Token: 서명과 사용자 상태를 둘 다 확인

JwtProvider는 sub(사용자 ID 문자열), authVersion, iat, exp claim을 만든다. Filter는 다음 순서다.

```text
Authorization: Bearer ... 확인
→ 같은 secretKey로 서명·exp 검증
→ payload의 sub/authVersion 파싱
→ CustomUserDetailsService로 active User 조회
→ User.authVersion == token.authVersion 확인
→ enabled/suspended 여부 확인
→ UsernamePasswordAuthenticationToken 생성
→ SecurityContextHolder에 저장
→ filterChain.doFilter
```

서명 검증은 “토큰이 서버 secret으로 만들어졌는가”를 보고, authVersion·isEnabled 검사는
“서명이 맞더라도 현재 사용자 상태상 사용할 수 있는가”를 본다. 두 검사는 서로 다른 문제다.

Bearer header가 없거나 Bearer로 시작하지 않는 요청은 Filter에서 JWT 검증하지 않고 chain을
계속 보낸다. 보호 endpoint라면 뒤의 SecurityConfig가 인증 부족을 판단한다. Filter 안의
return은 현재 Filter 메서드만 끝내며, 이미 호출한 filterChain 내부 작업을 취소하는 명령은 아니다.

### 6.3 Refresh Token rotation과 row lock

SessionService.refreshSession의 핵심은 다음과 같다.

```text
Cookie 원문 수신
→ hash 계산
→ refreshTokenHash로 AuthSession 조회(PESSIMISTIC_WRITE)
→ active·만료·User 상태 확인
→ 새 원문 refresh token 생성
→ 기존 hash를 새 hash로 교체(rotate)
→ 새 Access Token/Cookie 반환
```

같은 Cookie로 두 refresh 요청이 동시에 오면 AuthSession row lock이 한 요청만 먼저 rotation을
수행하게 한다. 두 번째 요청은 lock을 기다린 뒤 이미 바뀐 hash를 기준으로 실패한다.

- 백엔드 lock: 같은 refresh session row의 DB 경쟁 방지
- 프론트 refreshPromise: 한 브라우저에서 여러 API가 동시에 401일 때 refresh HTTP 요청 중복 방지

### 6.4 로그아웃·비밀번호 변경·탈퇴

- 로그아웃: Cookie hash로 session을 찾아 revokedAt 기록 후 만료 Cookie를 보낸다.
- 비밀번호 변경: 현재 비밀번호 검증 후 password 변경과 authVersion++, refresh Cookie 만료를 수행한다.
- 회원 탈퇴: User deleted=true, refresh Cookie 만료. 관련 기록은 FK와 soft-delete 조건에 의해 보존·차단된다.

이 세 동작이 모두 “Access Token 문자열을 찾아 삭제”하지 않는 이유는 Access Token이 서버에
저장된 세션 목록이 아니기 때문이다. 현재 Access Token Filter는 User의 enabled 상태와
authVersion을 확인하고, Refresh 흐름은 AuthSession의 revokedAt·만료 상태를 확인한다.
즉 AuthSession을 revoke했다고 이미 발급된 Access Token이 즉시 사라지는 것은 아니다.

## 7. 게시글·댓글 기능의 설계 의도

### 7.1 목록과 상세의 역할 차이

목록 조회:

```text
GET /posts?page=0&size=10
→ 활성·차단되지 않은 Post만 Page로 조회
→ PostCounter/PostViewCount의 DB 값으로 List DTO 생성
→ Redis 직접 조회 없음
```

상세 조회:

```text
GET /posts/{postId}
→ 게시글 visibility 확인
→ 댓글·작성자 조회
→ viewer의 like/report/mine 계산
→ DB baseline 조회수 + ViewCountUpdater.increment
→ 상세 DTO 반환
```

목록에서 Redis를 직접 읽지 않는 것은 [확정]이다. [설계 의도 해석]으로는 목록을 매우 자주
읽을 때 각 row마다 Redis round trip을 발생시키지 않고 DB에 flush된 snapshot을 사용하는
선택으로 볼 수 있다. 상세 응답은 증가된 값을 반환할 수 있다.

### 7.2 신고 수와 차단 기준

- 게시글 신고 수가 REPORT_BLOCK_THRESHOLD=5 이상이면 목록·상세 조회 대상에서 제외된다.
- 신고를 받은 작성자의 receivedReportCount가 10 이상이면 User가 suspended로 간주된다.
- 프론트도 5 기준으로 수정·신고 버튼을 비활성화하거나 목록으로 이동하지만 최종 판단은 Service가 한다.

프론트 상수와 백엔드 조건이 둘 다 존재하는 이유는 UX와 보안을 분리하기 위해서라고 해석할
수 있다. 프론트 조건은 화면 제어이고, 서버 조건은 API 직접 호출을 막는 업무 규칙이다.

### 7.3 게시글 수정과 이미지 collection

PostEditor는 제목·내용과 이미지 Data URL 목록을 만들고 PostService.fixPost에 보낸다.

- orphanRemoval=true인 image collection에서 제거된 PostImage는 부모 관계에서 끊어진다.
- 새 image는 Post.addImage를 통해 Post collection에 들어간다.
- 기존 이미지와 새 이미지가 같은지에 따라 OPTIMISTIC_FORCE_INCREMENT 여부가 달라진다.

이미지의 실제 바이트는 Data URL 문자열로 LONGTEXT에 저장된다. @Lob은 큰 문자열을 대용량
컬럼으로 매핑하기 위한 JPA 힌트이고, columnDefinition="LONGTEXT"는 MySQL 컬럼 타입을
구체화한다. Java 타입이 String인 것은 같아도 DB 저장 용량·타입은 달라질 수 있다.

### 7.4 Like와 Report의 unique 제약

- Like: (post_id, user_id) unique
- PostReport: (post_id, user_id) unique

Service에서 먼저 exists를 확인해 사용자에게 친절한 오류를 제공하고 DB unique 제약이 최종
방어선이다. 경쟁 요청에서는 두 요청이 모두 exists=false를 읽을 수 있으므로 DB 제약 위반을
별도 예외로 변환한다. [확정]

Like ID는 현재 모든 독립 ID와 같은 IDENTITY 전략이다. 과거 baseline의 post_likes_seq를
V6에서 제거한 것은 현재 Entity 전략과 운영 schema를 맞추기 위한 migration이다.

### 7.5 댓글: 댓글 row와 reply count의 별도 제어

댓글 등록·삭제는 댓글 row를 저장/삭제하는 것과 Post의 reply_count bulk update를 분리한다.
증가 후 Post를 PESSIMISTIC_READ로 다시 확인하는 것은 게시글이 활성인지 확인하면서 삭제와의
경쟁을 조정하기 위한 현재 코드 흐름이다. [확정]

댓글 Entity의 changeComment는 댓글 본문 수정에 사용되고, 댓글 수 증감은 Entity의 addReply
같은 메서드가 아니라 Repository query에서 수행된다. 사용되지 않는 API와 테스트를 현재
production 흐름으로 설명해서는 안 된다.

## 8. 동시성 제어를 기능별로 다르게 둔 이유

| 기능 | 경쟁하는 상태 | 현재 제어 | 이 선택의 의미 |
|---|---|---|---|
| Access Token 인증 | 사용자 상태와 token claim | JWT 서명 + authVersion/enabled 비교 | DB row를 매 요청 수정하지 않고 폐기 상태 반영 |
| Refresh rotation | 같은 AuthSession hash | PESSIMISTIC_WRITE | 한 row의 rotation을 직렬화 |
| 게시글 본문 수정/삭제 | Post version | @Version, OPTIMISTIC_FORCE_INCREMENT | 오래 잡는 DB lock 대신 충돌을 감지해 409 |
| 좋아요 | Like 존재와 like count | unique 제약 + counter PESSIMISTIC_WRITE + bulk update | 중복 row와 숫자 lost update를 각각 방지 |
| 댓글 수 | 댓글 row·게시글 활성 상태 | bulk count update + Post PESSIMISTIC_READ 재확인 | count 증가와 게시글 삭제 경쟁을 조정 |
| 신고 | 신고 중복, 게시글 count, 작성자 report count | Post/User PESSIMISTIC_WRITE + unique 제약 + dirty checking | 한 신고 transaction에서 여러 aggregate를 순서대로 변경 |
| 조회수 증가 | 같은 post의 빠른 증가 | Redis Lua 원자 script 또는 DB 원자 update | 요청마다 row lock을 잡지 않고 증가 연산을 원자화 |
| 조회수 flush | 여러 backend scheduler | Redisson RLock | backend 인스턴스 중 하나만 flush 수행 |

이 표에서 “안전하다”는 표현은 범위를 제한해 읽어야 한다. Redis Lua가 해당 script의 명령을
원자적으로 실행한다는 것과, 장애·네트워크·운영 재시작을 포함한 전체 시스템의 정확성이
완전히 증명됐다는 것은 같은 말이 아니다. 현재 저장소는 관련 단위·통합·동시성 테스트로
주요 경우를 확인하지만 모든 운영 interleaving을 증명하지는 않는다.

## 9. 조회수에서 Redis를 선택한 이유와 현재 한계

### 9.1 구현체 교체를 인터페이스로 숨김

파일: ViewCountUpdater.java, DatabaseViewCountUpdater.java, RedisViewCountStore.java

Service는 ViewCountUpdater.increment(postId, baseline)만 호출한다.

```text
app.view-count.enabled=false
  → DatabaseViewCountUpdater Bean

app.view-count.enabled=true
  → RedisViewCountStore Bean
  → RedisViewCountFlushScheduler도 활성
```

ConditionalOnProperty로 Bean을 선택하므로 PostService는 RedisTemplate이나 DB update 구문을
직접 알 필요가 없다. [확정] 이 구조는 테스트에서 Redis를 끄고 H2/DB 구현체를 사용할 수
있게 한다는 점에서 경계가 분명하다.

### 9.2 Redis key 구조

- count:{postId} 계열 key: 게시글의 Redis 현재 조회수
- dirty set: DB에 아직 반영해야 할 postId 목록
- flush lock key: Redisson이 분산 lock을 식별하는 이름

ViewCountProperties가 prefix·set key·lock key·flush interval을 한곳에서 검증한다. key 문자열을
Service 곳곳에 흩어 쓰지 않는 이유는 [설계 의도 해석]이다. 운영 namespace를 바꾸거나 테스트
key를 분리할 때 설정 한 곳만 바꾸기 위해서다.

### 9.3 Lua script의 실행 순서

RedisViewCountStore는 한 번의 redisTemplate.execute(...)로 다음을 묶는다.

```text
count key / dirty set 타입 확인
→ Redis 현재 count 확인
→ baseline보다 작으면 baseline으로 복구
→ INCR
→ SADD dirty set
→ 증가된 값 반환
```

이렇게 하는 이유는 count 증가와 dirty 등록 사이에 다른 요청이 끼어 dirty 정보가 사라지는
틈을 줄이기 위해서다. redis.call, INCR, SADD, KEYS, ARGV는 Lua/Redis 문법이며 Java의
일반 메서드 호출과 같은 것이 아니다.

### 9.4 Redis 장애와 Redis 비활성화는 다르다

- 설정 비활성화: DatabaseViewCountUpdater를 Bean으로 사용한다.
- 통신 중 오류: RedisViewCountStore가 catch 경로에서 baseline을 반환한다.

현재 코드에는 Redis 오류가 발생한 뒤 실행 중에 DB 구현체로 Bean을 교체하는 동적 전환은
없다. 따라서 예전 교안의 “Redis 장애 시 DB fallback”이라는 표현은 “오류 시 baseline 반환”으로
정정해야 한다. baseline 반환은 조회수 증가를 DB에 즉시 기록한다는 뜻이 아니다.

### 9.5 flush와 snapshot 안전성

Scheduler는 다음 순서로 동작한다.

```text
@Scheduled 실행
→ RLock.tryLock
→ dirty postId 목록 스냅샷
→ Redis count snapshot 읽기
→ ViewCountPersistenceService.persistMaxViewCount
→ 현재 Redis 값과 snapshot 비교
→ 같을 때만 dirty 제거
→ 현재 thread가 보유한 lock일 때만 unlock
```

예를 들어 snapshot이 150일 때 flush 중 새 요청이 151을 만들면 현재 Redis 값이 snapshot과
달라진다. 이 경우 dirty를 지우지 않아 다음 flush가 151을 처리한다. dirty 제거 조건이 없는
단순 flush는 새 증가분을 지울 수 있기 때문에 현재 비교가 필요하다.

DB 반영 SQL은 GREATEST(현재 DB 값, snapshot)을 사용한다. Redis나 재시작·재시도 과정에서
낮은 값이 들어와도 영구 조회수가 감소하지 않게 하려는 의도가 SQL에 직접 드러난다. [확정]

### 9.6 AOF와 eventual consistency

Compose의 Redis는 appendonly yes, appendfsync everysec, redis-data volume을 사용한다.
이는 Redis 프로세스 재시작 뒤에도 일정 수준의 명령 로그 복구를 기대하는 운영 설정이다.
그러나 everysec의 정확한 내구성·장애 시점 손실량은 Redis 운영 환경에 의존하므로 “절대
유실되지 않는다”고 말할 수 없다.

조회수는 요청 시 Redis와 DB가 잠시 다를 수 있다. DB는 최종 영구 snapshot, Redis는 flush 전
최신 증가분이라는 역할이기 때문이다. 목록이 DB 값만 읽는 것도 이 eventual consistency
경계를 사용자 화면에 드러내는 선택이다.

## 10. Flyway와 RDS schema 진화의 의도

### 10.1 baseline과 이후 migration

migration의 의미상 순서는 다음과 같지만, 모든 DB에서 모든 파일이 한 번에 실행되는 것은 아니다.

```text
B3__current_schema.sql  (기존 운영 구조를 baseline으로 표현)
→ V1 post_counters 이동/보정
→ V2 users.auth_version
→ V3 post_view_counts 분리·backfill
→ V4 post_counters.view_count 제거
→ V5 posts.is_fixed 제거
→ V6 Like IDENTITY 통일·post_likes_seq 제거
```

빈 DB에서는 B3가 schema 출발점을 만들고, Flyway baseline migration version보다 높은 V4·V5·V6가
뒤처리를 수행한다. 이 경로에서는 이미 B3보다 낮은 V1·V2·V3이 다시 실행되지 않는다. 실제
FlywayBaselineMigrationTest도 빈 DB에서 B3·V4·V5·V6의 history를 확인한다. 반대로 V1·V2·V3은
과거 schema를 이미 사용하는 DB에서 legacy data를 새 구조로 옮기는 역사적 migration이다.

따라서 “새 RDS에서 B3와 V1~V6를 모두 순서대로 실행한다”고 이해하면 안 된다. 중요한 것은
각 DB의 현재 Flyway history와 schema 상태에 맞는 경로를 선택해 같은 최종 구조를 재현하는 것이다.
파일을 나중에 수정해 “현재 모습만 맞추는” 것이 아니라, 새 변경은 다음 버전 파일로 추가해야 한다.

### 10.2 왜 Hibernate 자동 생성만 사용하지 않는가

현재 prod는 ddl-auto:validate라 Hibernate가 schema를 만들지 않는다. Flyway가 migration을
적용하고 Hibernate는 Entity와 schema가 맞는지 검사한다. [확정]

**설계 의도 해석:** 운영 데이터가 있는 RDS에서 자동 생성은 “현재 Entity가 무엇인가”만 알고
“기존 데이터가 어떤 과정을 거쳐 이동해야 하는가”를 표현하기 어렵다. V1·V3처럼 legacy
column에서 새 table로 값을 복사하는 작업은 migration 이력에 SQL로 남아야 재현 가능하다.

local의 ddl-auto:create는 개발 편의용이고 prod의 Flyway는 데이터 보존·재현용이다. 같은
프로젝트에서 둘을 함께 쓰는 것은 환경별 목적이 다르기 때문이다.

### 10.3 현재 schema의 중요한 결과

- 최종 table은 9개이며 post_likes_seq는 V6 이후 없다. [테스트 근거]
- posts.is_fixed는 V5 이후 없다.
- 조회수는 post_view_counts로 분리됐다.
- post_likes.post_like_id는 AUTO_INCREMENT가 됐다.

FlywayBaselineMigrationTest와 MySqlSchemaIntegrationTest가 이 결과를 검사하지만, 실제 사용
중인 개인 AWS RDS가 이 파일을 성공적으로 적용했다는 증거는 이 저장소 테스트만으로 확인할 수 없다.

## 11. 프론트엔드 구조의 설계 의도

### 11.1 시작·라우팅·페이지 경계

```text
main.jsx
→ StrictMode + app ErrorBoundary + BrowserRouter
→ App
→ AppRoutes
→ PublicOnlyRoute / ProtectedRoute
→ lazy page
→ PageBoundary(Suspense + ErrorBoundary)
```

- StrictMode는 개발 중 부작용을 점검하기 위해 React가 일부 lifecycle을 다시 실행할 수 있게 한다.
- lazy(() => import(...))는 페이지 코드를 필요할 때 불러온다.
- Suspense는 lazy module이 준비될 때 LoadingView를 보인다.
- PageBoundary의 key=location.key는 위치가 바뀔 때 ErrorBoundary 인스턴스를 새로 취급하게 한다.
- Outlet은 부모 route element가 허용한 자식 route element가 렌더링될 자리다.

이 경계들은 같은 실패를 중복 처리하는 것이 아니다.

| 경계 | 담당 실패 |
|---|---|
| app ErrorBoundary | 앱 전체 render 오류 |
| PageBoundary | 페이지 lazy/render 오류 + lazy 로딩 |
| PostBoard/PostList/CommentSection | 목록·댓글 같은 화면 조각 오류 |
| API request | HTTP status·JSON 오류 |
| 각 페이지 state | 요청 중 loading/error/retry |

### 11.2 api.js를 단일 요청 관문으로 둔 이유

모든 authApi, postApi, userApi는 request를 호출한다. request는 API base URL 결합,
JSON header, Authorization, credentials include, 응답 JSON/text 파싱, non-2xx Error 변환,
401 refresh 후 원래 요청 1회 재시도를 공통 처리한다.

refreshPromise는 module-level 공유 변수다.

```text
요청 A 401 → refreshPromise 생성
요청 B 401 → 이미 존재하는 같은 Promise를 await
→ refresh HTTP 요청 1개
→ 두 요청이 새 token으로 원래 요청 재시도
```

이는 브라우저 탭 내부의 중복 refresh를 줄이는 장치다. 여러 backend 인스턴스 사이의 DB
동시성 문제를 해결하는 장치는 아니다.

### 11.3 목록 pagination과 무한 스크롤

파일: PostsPage.jsx, postApi.js, PostList.jsx

```text
PostsPage mount
→ loadPage(0)
→ GET /posts?page=0&size=10
→ posts state 교체
→ nextPageRef=1
→ IntersectionObserver가 sentinel 감지
→ loadPage(1)
→ posts에 append
```

- loadingRef는 같은 순간 중복 page 요청을 막는다.
- requestControllerRef와 AbortController는 unmount·재시도 시 이전 요청을 취소한다.
- nextPageRef는 render를 유발하지 않고 다음 page 번호를 저장한다.
- hasNextPage=false가 되면 observer target을 만들지 않는다.
- page 0 재시도는 posts를 비우고 처음부터 다시 시작한다.

PostList의 IntersectionObserver callback이 여러 번 실행되어도 PostsPage.loadingRef가 최종
중복 방어를 한다. [확정]

### 11.4 상세 화면의 상태 설계

PostDetailPage는 post, comments, loadError, retryVersion, isLikeSubmitting, modal을 별도로 가진다.

- postId/retryVersion이 바뀌면 상세 요청을 새로 시작한다.
- 이전 요청은 cleanup에서 abort한다.
- 좋아요는 likeRequestRef로 중복 click을 차단한다.
- 신고·삭제·댓글 삭제는 modal에서 확인한 뒤 API를 호출한다.
- 댓글 생성·수정·삭제 후 전체 상세를 재조회하지 않고 comments state를 국소 갱신한다.

이 구조는 작은 변화마다 전체 새로고침하지 않게 하려는 선택으로 해석할 수 있다. 단, 화면
state 갱신이 서버의 모든 상태를 자동 동기화한다는 뜻은 아니다. 다른 사용자의 변경은 다시 조회해야 한다.

### 11.5 normalizer의 경계

postNormalizer.js는 목록·상세·댓글 응답의 null/누락 field를 기본값으로 바꾼다. 컴포넌트가
매번 null 분기를 반복하지 않고 API 응답 변화가 UI 전체로 퍼지는 것을 줄이려는 선택으로
해석할 수 있다. Normalizer는 서버의 업무 검증을 대신하지 않는다.

### 11.6 프론트와 백엔드의 이중 입력 검증

```text
PostImagePicker/File 유틸
→ 파일 수·크기·타입을 빠르게 확인
→ FileReader로 Data URL 생성
→ PostEditor payload
→ ImageDataUrlValidator가 header/Base64/signature/크기를 다시 확인
→ DB LONGTEXT 저장
```

브라우저 검사는 사용자 경험을 개선하고 백엔드 검사는 악의적인 직접 API 호출을 막는 최종
경계다. 프론트 검사만 통과했다고 서버가 신뢰하면 안 된다.

## 12. 테스트 설계가 증명하는 것과 증명하지 않는 것

### 12.1 Gradle 실행 층

build.gradle의 의도는 테스트 비용과 외부 의존성을 분리하는 것이다.

```text
./gradlew test
  → redis-integration/mysql-integration tag 제외
  → 일반 단위·H2 중심 테스트

./gradlew redisTest
  → Redis 통합 테스트

./gradlew mysqlTest
  → MySQL Testcontainers 테스트

./gradlew check
  → 일반 test + Jacoco verification + redisTest + mysqlTest
```

Jacoco는 entity/auth/config/service/controller를 coverage class directory에 넣고 DTO·Repository·
validation은 제외한다. 이는 “DTO와 Repository가 중요하지 않다”는 뜻이 아니라 현재 coverage
정책의 자동 산정 범위가 그렇게 정해졌다는 뜻이다. [확정]

### 12.2 테스트 그룹별 의도

| 그룹 | 대표 파일 | 확인하는 것 |
|---|---|---|
| context | SpringdatajpaApplicationTests | Spring context가 뜨는가 |
| pure auth | JwtProviderTest, RefreshTokenProviderTest | claim·만료·hash·토큰 형식 |
| filter/security | JwtAuthenticationFilterTest, SecurityConfigTest | public/보호 경로, 401, context 처리 |
| entity | PostTest, UserTest, AuthSessionTest 등 | 생성·상태 변경·불변식 |
| service mock | PostServiceTest, CommentServiceTest, SessionServiceTest, UserServiceTest | 업무 분기와 dependency 호출 순서 |
| controller | ControllerDelegationTest | HTTP adapter가 Service에 위임하는가 |
| H2 repository | PostRepositoryIntegrationTest, PostViewCountRepositoryIntegrationTest, UserSoftDeleteIntegrationTest | JPQL/native query와 DB 결과 |
| schema | FlywayBaselineMigrationTest, MySqlSchemaIntegrationTest | migration 최종 구조와 validate |
| Redis unit | RedisViewCountStoreTest, RedisViewCountFlushSchedulerTest | key/script 오류·lock·snapshot 분기 |
| Redis integration | RedisViewCountStoreIntegrationTest, RedisAofRestartIntegrationTest | 실제 Redis/Testcontainers/AOF 재시작 |
| concurrency | PostConcurrencyIntegrationTest | 동시 신고·좋아요·댓글 등 주요 interleaving |

### 12.3 테스트를 과대해석하지 않기

- Mockito service test는 실제 DB lock을 실행하지 않는다.
- H2 test의 lock·격리 동작이 MySQL과 완전히 같다고 가정할 수 없다.
- MySQL Testcontainers test는 개인 AWS RDS 네트워크·파라미터·백업 정책을 검사하지 않는다.
- Redis Testcontainers test는 실제 다중 backend 운영망과 같지 않다.
- check가 통과해도 Docker image pull·Nginx blue/green 전환·AWS SSM 권한을 증명하지 않는다.

현재 테스트가 잘 보여주는 것은 코드가 의도한 대표적인 분기와 migration 결과다. 모든 장애
상황을 보장하는 계약서는 아니다.

## 13. Docker·Compose·Nginx의 설계 의도

### 13.1 백엔드 Dockerfile

```text
eclipse-temurin:26-jdk build stage
→ Gradle dependencies cache layer
→ bootJar
→ eclipse-temurin:26-jre runtime stage
→ spring 시스템 사용자
→ app.jar 실행
```

- build에는 JDK, runtime에는 JRE만 사용해 실행 이미지에 build 도구를 남기지 않는다.
- USER spring:spring으로 root 실행을 피한다. [확정]
- EXPOSE 8080은 컨테이너 내부 포트이고 외부 공개는 Compose/Nginx가 결정한다.

### 13.2 프론트 Dockerfile

frontend/Dockerfile와 frontend/nginx/default.conf는 Node 24에서 npm ci로 lockfile 의존성을
설치하고 Vite build를 한 뒤 Nginx가 dist를 정적으로 제공한다.

- VITE_API_BASE_URL을 build arg로 받아 정적 bundle에 주입한다.
- try_files ... /index.html로 React client-side route 새로고침을 fallback한다.
- /assets/에는 immutable cache header, /health에는 text ok를 사용한다.

VITE_API_BASE_URL은 runtime container 환경변수가 아니라 build-time 값이다. 배포 후 Compose
환경변수만 바꾸어도 이미 만들어진 JS bundle 안의 값은 바뀌지 않는다. [확정]

### 13.3 Backend Compose

backend/deploy/compose.yaml의 서비스는 Redis, backend-blue, backend-green, Nginx다.

- 두 backend가 같은 MySQL·Redis 환경변수를 공유한다.
- backend는 127.0.0.1:8081/8082에만 bind되고 외부는 Nginx가 받는다.
- Redis는 redis-data volume을 공유하고 redis-cli ping healthcheck를 사용한다.
- Nginx는 BACKEND_ACTIVE_COLOR에 따라 blue/green 설정 파일을 복사해 시작한다.

Blue와 green이 Redis를 공유하는 것은 중요하다. backend 교체 후에도 조회수 count/dirty set과
refresh session의 DB 상태가 인스턴스별 local memory에 남지 않는다.

### 13.4 Frontend Compose와 Nginx

프론트 Nginx는 다음을 한다.

```text
/health → frontend active container /health
/api/   → BACKEND_UPSTREAM
/       → frontend active container
```

프론트 template의 proxy_pass는 BACKEND_UPSTREAM 뒤에 경로 구분자를 두어 /api/ prefix를
제거한 경로를 backend로 전달한다. backend Controller가 /posts, /sessions 등 root path를
사용하는 현재 코드와 맞물린다. [확정]

### 13.5 Blue/Green deploy script

두 script 모두 다음 설계를 공유한다.

1. .env, Compose, 필수 명령 존재 확인
2. flock으로 같은 서버의 중복 배포 차단
3. 현재 active color의 반대 색을 target으로 선택
4. target image pull·container 시작
5. target health 확인
6. Nginx active color 전환
7. public health 확인
8. 실패 시 proxy rollback

백엔드는 Redis health도 먼저 확인한다. 프론트는 backend health를 직접 확인하지 않고 자신의
target /health를 확인한다. “무중단”은 실제 트래픽·connection draining·세션 상태까지 포함하므로
script만으로 완전히 보장된다고 말할 수 없다.

### 13.6 운영 환경에서 먼저 확인할 설정

다음은 버그라고 단정하는 목록이 아니라 배포 전에 의도를 확인해야 하는 지점이다.

- .env.example와 Compose 기본값의 JWT_REFRESH_COOKIE_SECURE=false가 HTTPS 운영 값과 맞는지
- CORS_ALLOWED_ORIGINS가 실제 프론트 주소와 정확히 일치하는지
- BACKEND_UPSTREAM이 프론트 Nginx가 접근할 backend Nginx 주소·포트인지
- JWT_SECRET에 local 기본값을 prod에서 사용하지 않는지
- Nginx 20m와 애플리케이션 이미지 검증 3MB의 업로드 범위를 의도했는지
- RDS 보안 그룹·Redis 네트워크·SSM IAM 권한은 이 저장소만으로 확인할 수 없음

## 14. GitHub Actions의 설계 의도

### Backend workflow

backend/.github/workflows/backend-ci.yml의 흐름은 다음과 같다.

```text
push/PR main
→ Java 26 + Gradle cache
→ chmod gradlew
→ ./gradlew clean check
→ PR이 아니면 Docker build/push GHCR
→ DEPLOY_ENABLED=true이면 AWS OIDC
→ SSM RunShellScript
→ 서버가 raw GitHub deploy 파일을 내려받고 script 실행
```

- PR에서는 test job으로 검증하지만 image push/deploy는 하지 않는다.
- GITHUB_TOKEN으로 GHCR에 push한다.
- Deploy job은 OIDC 임시 AWS credential을 사용하며 장기 access key를 workflow에 적지 않는다.
- concurrency로 production backend deploy를 직렬화한다.

frontend workflow도 같은 단계이며 validate job에서 npm ci, npm run lint, npm run build를 수행한다.
image build 시 VITE_API_BASE_URL=/api를 build arg로 명시해 배포 Nginx의 /api proxy와 맞춘다.

**[확인 불가]** 실제 GitHub repository variable, AWS role policy, SSM instance 상태는 이 저장소만으로
확인할 수 없다. 따라서 workflow YAML이 그 값을 “올바르게 운영한다”고 확정할 수는 없다.

## 15. 기능별 end-to-end 설계 지도

### 회원가입

```text
SignupPage
→ authApi.signup
→ api.request POST /users
→ UserController @Valid DTO
→ UserService email/nickname/password/image 검증
→ UserRepository 중복 확인
→ password encode
→ User 저장
→ UserResponseDto
→ JSON
→ 로그인 페이지 이동
```

프론트 errors 객체는 email, password, passwordCheck, nickname field를 가진다. 이 객체는
서버 DTO가 아니라 화면 입력별 오류를 저장하는 UI state다.

### 로그인과 보호 요청

```text
LoginPage
→ POST /sessions
→ access token localStorage
→ refresh Cookie browser
→ 이후 api.request Authorization header
→ JwtAuthenticationFilter
→ SecurityContext
→ Controller @AuthenticationPrincipal
```

### Refresh

```text
API 401
→ api.js shared refreshPromise
→ POST /sessions/refresh with Cookie
→ SessionService row lock + rotate
→ Set-Cookie + accessToken
→ 원래 요청 재시도
```

### 게시글 상세·조회수

```text
PostDetailPage useEffect
→ postApi.getPost
→ PostController.getPostView
→ PostService.getPostView
→ PostRepository visibility/detail
→ comments/like/report 상태
→ ViewCountUpdater.increment
→ Redis count/dirty 또는 DB update
→ PostViewResponseDto
→ post/comments state
```

### 게시글 작성·수정

```text
PostEditor
→ title/content/image Data URL
→ POST/PATCH /posts
→ DTO validation + ImageDataUrlValidator
→ PostService transaction
→ Post/PostImage 저장 또는 교체
→ version 충돌 검사
→ 응답/상세 페이지 이동
```

### 좋아요·댓글·신고

각 기능은 같은 Controller→Service→Repository 구조를 공유하지만 저장 상태와 lock이 다르다.
좋아요는 unique Like+counter bulk, 댓글은 Comment row+reply counter bulk, 신고는 PostReport
unique+Post/User lock+dirty checking이다. 같은 화면의 숫자를 바꾼다는 UI 결과만 같고,
백엔드 동시성 계약은 서로 다르다.

## 16. 세세한 설정을 읽을 때의 해석표

| 설정/문법 | 실제 의미 | 흔히 생기는 오해 |
|---|---|---|
| ENV 값과 기본값 placeholder | 환경값이 없을 때 기본값 | 항상 기본값으로 강제된다고 해석 |
| @Value와 jwt.secret key | YAML key 값 주입 | 이름만 같으면 아무 파일에서나 자동 공유된다고 해석 |
| @ConfigurationProperties | prefix 아래 값을 타입 객체로 binding | Bean을 Controller가 직접 호출한다고 해석 |
| @ConditionalOnProperty | 조건에 맞는 Bean만 생성 | 실행 중 구현체가 자동 failover한다고 해석 |
| @Scheduled | Bean 메서드를 scheduler가 주기 호출 | 요청이 들어올 때만 실행된다고 해석 |
| @Transactional | transaction proxy 경계 | 메서드 내부 모든 호출이 별도 transaction이라고 해석 |
| @Modifying | SELECT가 아닌 DML query | row lock을 자동으로 건다고 해석 |
| @Lock | 해당 Repository 조회의 lock mode | 모든 Service 조회가 자동 lock된다고 해석 |
| @Version | optimistic version 검사 | pessimistic row lock이라고 해석 |
| @Lob | 대용량 매핑 힌트 | Java String 자체가 자동 LONGTEXT라는 뜻이라고 해석 |
| @MapsId | 부모 ID를 공유하는 mapping | 별도 ID를 새로 생성한다는 뜻으로 해석 |
| React useEffect | render 후 side effect 실행 | 컴포넌트가 영원히 두 번 실행된다고 해석 |
| React useRef | render를 유발하지 않는 mutable reference | state와 동일하게 화면을 다시 그린다고 해석 |
| AbortController | fetch 취소 신호 | 서버가 이미 처리한 요청까지 되돌린다고 해석 |
| Filter 안의 return | 현재 Filter 메서드 반환 | 이미 전달한 FilterChain까지 취소한다고 해석 |
| lazy + Suspense | module 지연 로드와 fallback | lazy가 없으면 컴포넌트를 만들 수 없다고 해석 |

## 17. 현재 코드에서 확인되는 설계상의 경계와 주의점

다음은 “문제다”라고 단정하는 목록이 아니라 코드 읽을 때 경계를 놓치지 않기 위한 확인 목록이다.

1. Redis 오류 경로: DB 구현체로 동적 전환하지 않고 baseline을 반환한다.
2. 목록 조회수: Redis 최신값이 아니라 DB flush 값이다.
3. Origin: 현재 session 경로에서 null Origin을 허용하지 않는다.
4. Access Token 저장: 프론트 localStorage 사용의 보안 위험은 별도 운영 정책이 필요하다.
5. 운영 Cookie: secure 기본값이 실제 HTTPS 운영 값과 맞는지 배포 환경에서 확인해야 한다.
6. 테스트 환경 차이: H2·Testcontainers 결과를 실제 RDS/Redis 운영 결과와 동일시하지 않는다.
7. Flyway baseline: B3은 current schema 표현이지 개인 RDS에 이미 적용됐다는 증거가 아니다.
8. 배포 health: backend와 frontend의 /health는 서로 다른 프로세스를 검사한다.
9. 프론트 API URL: Vite 값은 build time에 고정된다.
10. 공식 진행률: 21번은 종합 문서이므로 214/214 파일 계산에 새 파일로 포함하지 않는다.

## 19. 파일 묶음별 설계 의도 커버리지

다음 표는 00장의 214개 공식 대상 파일을 기능 묶음으로 다시 매핑한 것이다. 같은 문법과
같은 역할이 반복되는 파일은 최초 파일에서 원리를 설명하고, 이 표에서는 각 파일 묶음이
전체 흐름에서 왜 필요한지만 확인한다.

### 반복 파일을 한 번만 자세히 설명한 이유

- DTO는 field·validation·factory 구조가 반복되므로 최초 User/Post DTO에서 역직렬화·직렬화를 설명하고, 나머지는 실제 field와 사용 Controller만 확인한다.
- 예외 class는 대부분 RuntimeException과 message 생성자 구조가 같으므로 ApiErrorCode와 GlobalExceptionHandler에서 HTTP 변환을 설명하고, 각 예외는 발생 Service만 확인한다.
- 공통 React 버튼·입력·배너·modal은 props와 callback을 받아 렌더링하는 동일한 패턴이므로 첫 컴포넌트에서 controlled component와 callback을 설명하고, 화면별 차이만 확인한다.
- backend/frontend의 blue/green 설정은 색상·포트·proxy 대상만 다르므로 backend blue 설정에서 Compose·Nginx 문법을 설명하고 green은 차이만 확인한다.

반복을 스킵한 것은 파일이 사용되지 않는다는 뜻이 아니다. 같은 설계 원리를 다시 증명하지
않고 실제 호출 위치·field·환경값 차이를 확인한다는 뜻이다.
