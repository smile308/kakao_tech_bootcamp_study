# 2단계. 회원가입: 프론트에서 DB 저장까지

## 이 문서에서 확인하는 전체 호출 흐름

~~~text
SignupPage
→ SignupForm의 onSubmit
→ authApi.signup
→ api.js의 request
→ fetch POST /users
→ UserController.createUser
→ UserRequestDto 역직렬화와 @Valid
→ UserService.createUser
→ UserRepository 조회
→ User Entity 생성과 save
→ UserResponseDto
→ 201 JSON
→ SignupPage navigate("/login")
~~~

이 흐름을 읽을 때 화면 component부터 무작정 읽지 않는다. 먼저 DB에 저장되는 User와 요청/응답 DTO를 이해한 뒤 Repository, Service, Controller를 읽고 프론트로 돌아온다.

## 1. User Entity

파일: `src/main/java/kr/adapterz/springdatajpa/entity/User.java`

### 이 파일을 먼저 읽는 이유

Service가 생성하는 객체가 어떤 상태를 가지며, 어떤 값이 DB column이 되는지 결정한다. DTO는 요청/응답 모양이고 User는 영속화되는 상태다.

~~~java
@Getter
@Entity
@Table(name = "users")
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class User {
    public static final int SUSPENSION_REPORT_THRESHOLD = 10;

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "user_id")
    private Long userId;

    @Column(nullable = false)
    private String email;

    @Column(nullable = true, unique = false, length = 255)
    private String password;

    @Column(nullable = false, length = 10)
    private String nickname;

    @Lob
    @Column(name = "profile_image", columnDefinition = "LONGTEXT")
    private String profileImage;

    @Column(name = "received_report_count", nullable = false)
    private int receivedReportCount;

    @Column(name = "deleted", nullable = false)
    private boolean deleted;

    @Column(name = "auth_version", nullable = false)
    private long authVersion;

    public User(String email, String password, String nickname,
                String profileImage, int receivedReportCount) {
        this.email = email;
        this.password = password;
        this.nickname = nickname;
        this.profileImage = profileImage;
        this.receivedReportCount = receivedReportCount;
        this.deleted = false;
        this.authVersion = 0L;
    }
}
~~~

### 줄의 역할과 다음 호출 위치

- `@Entity`: JPA가 이 class를 DB table과 매핑할 Entity로 관리한다.
- `@Table(name = "users")`: class 이름이 아니라 users table을 사용한다.
- protected 기본 생성자: JPA가 조회한 row를 Entity로 만들 때 필요하다. Service가 회원가입할 때는 public 생성자를 사용한다.
- `SUSPENSION_REPORT_THRESHOLD`: 신고 수를 기준으로 정지 여부를 판단할 때 UserService/PostService가 사용한다.
- `@Id`와 `@GeneratedValue(IDENTITY)`: userId를 DB identity auto-increment로 생성한다. 회원가입 전에는 null이고 save 후 DB가 채운다.
- `email`, `password`, `nickname`, `profileImage`, `receivedReportCount`, `deleted`, `authVersion`: DB에 저장되는 상태다.
- `password`는 평문이 아니라 Service가 PasswordEncoder로 encode한 값을 받는다.
- `deleted=false`, `authVersion=0L`: 새 User의 초기 상태다.

`@Entity`, `@Id`, `@Column`은 Java 실행 순서의 method 호출이 아니라 JPA metadata다. 실제 insert는 Service가 `userRepository.save(user)`를 호출하고 transaction이 commit될 때 발생한다.

회원가입 흐름에서 사용하는 것은 public constructor와 field 초기값이다. `update`, `delete`, `receiveReport`, `changePassword`는 이후 회원정보/보안 흐름에서 다시 읽으므로 여기서는 선언만 확인한다.

## 2. UserRequestDto

파일: `dto/user/UserRequestDto.java`

~~~java
@Getter
@NoArgsConstructor
public class UserRequestDto {
    @NotBlank
    @Email
    private String email;
    @NotBlank
    @Pattern(regexp = "...")
    private String password;
    @NotBlank
    @Pattern(regexp = "...")
    private String passwordCheck;
    @NotBlank
    @Size(max = 10)
    @Pattern(regexp = "^\\S+$")
    private String nickname;
    private String profileImage;
}
~~~

실제 정규표현식 전체는 원문 파일에서 확인한다. 이 DTO는 DB Entity가 아니라 HTTP request body의 임시 객체다.

- 외부 입력: JSON의 email/password/passwordCheck/nickname/profileImage
- 생성 위치: Jackson이 Controller parameter를 만들 때
- 사용 위치: UserController가 UserService로 전달
- 변경 여부: Service가 이 DTO를 수정하지 않고 읽기만 한다.
- 예외: JSON 변환 실패 또는 `@Valid` constraint 실패

## 3. UserResponseDto

파일: `dto/user/UserResponseDto.java`

~~~java
public class UserResponseDto {
    private Long userId;
    private String message;

    public UserResponseDto(User user) {
        this.message = "signup_success";
        this.userId = user.getUserId();
    }
}
~~~

Service가 저장된 User를 이 DTO로 변환한다. password나 deleted 같은 내부 상태는 응답에 포함하지 않는다. `userId`는 save 전 Entity에는 없을 수 있으므로 `savedUser`를 전달해야 한다.

## 4. UserRepository

파일: `repository/UserRepository.java`

회원가입에서 실제로 사용하는 메서드는 다음 세 개다.

~~~java
boolean existsByEmailAndDeletedFalse(String email);

boolean existsByNicknameAndDeletedFalse(String nickname);

int findMaxReceivedReportCountByEmailIncludingDeleted(@Param("email") String email);
~~~

- 첫 메서드: 활성 사용자의 email 중복 여부를 반환한다.
- 둘째 메서드: 활성 사용자의 nickname 중복 여부를 반환한다.
- 셋째 메서드: 삭제된 사용자까지 포함해 같은 email의 과거 신고 수 최대값을 native SQL로 조회한다.

`existsBy...`는 method name의 `Email`, `Nickname`, `DeletedFalse`를 Spring Data가 query 조건으로 해석한다. `findMax...`는 `@Query(nativeQuery = true)`이므로 method 이름이 SQL을 만들지 않고 SQL text가 직접 실행된다.

Repository는 DB 연결 주소를 결정하지 않는다. 주소는 application profile의 datasource 설정이고 Repository는 이미 구성된 EntityManager를 통해 query를 실행한다.

## 5. UserService.createUser

파일: `service/UserService.java`

~~~java
public UserResponseDto createUser(UserRequestDto request) {
    if (!request.getPassword().equals(request.getPasswordCheck())) {
        throw new InvalidRequestException("Invalid_Password");
    }
    if (userRepository.existsByEmailAndDeletedFalse(request.getEmail())) {
        throw new InvalidRequestException("Existed_Email");
    }
    if (userRepository.existsByNicknameAndDeletedFalse(request.getNickname())) {
        throw new InvalidRequestException("Existed_Nickname");
    }

    int previousReceivedReportCount =
            userRepository.findMaxReceivedReportCountByEmailIncludingDeleted(
                    request.getEmail());

    if (previousReceivedReportCount >= User.SUSPENSION_REPORT_THRESHOLD) {
        throw new InvalidRequestException("Suspended_Account");
    }

    ImageDataUrlValidator.validateProfileImage(request.getProfileImage());

    User user = new User(
            request.getEmail(),
            passwordEncoder.encode(request.getPassword()),
            request.getNickname(),
            request.getProfileImage(),
            previousReceivedReportCount
    );

    User savedUser = userRepository.save(user);
    return new UserResponseDto(savedUser);
}
~~~

### 실행 순서

1. password와 passwordCheck를 값 비교한다.
2. 활성 email 중복을 query한다.
3. 활성 nickname 중복을 query한다.
4. 삭제된 과거 계정의 최대 신고 수를 query한다.
5. 정지 기준 이상이면 가입을 중단한다.
6. profile image를 검증한다.
7. password를 encoder로 hash한 뒤 User를 만든다.
8. Repository save를 호출한다.
9. 저장 결과를 UserResponseDto로 변환한다.

### 변수의 출처와 이동

- `request`: Controller가 받은 DTO에서 온다. Service 전체 검증의 입력이다.
- `previousReceivedReportCount`: Repository query 결과다. 정지 조건과 새 User의 초기 신고 수에 모두 사용된다.
- `user`: 아직 DB insert 전인 새 Entity다.
- `savedUser`: save 결과다. ID가 DB에서 생성된 뒤 response 변환에 사용된다.

`@Transactional`은 Service class에 붙어 있으므로 method 실행이 하나의 transaction 범위에서 진행된다. Repository query와 save가 같은 transaction에 속한다. 실제 commit 시점과 rollback은 Spring transaction 설정에 의해 결정된다.

## 6. UserController.createUser

파일: `controller/UserController.java`

~~~java
@PostMapping
@ResponseStatus(HttpStatus.CREATED)
public UserResponseDto createUser(
        @Valid @RequestBody UserRequestDto request
) {
    return userService.createUser(request);
}
~~~

- `@PostMapping`: `/users`에 대한 HTTP POST와 method를 연결한다. class의 `@RequestMapping("/users")`와 합쳐진다.
- `@RequestBody`: HTTP JSON body를 UserRequestDto로 변환한다.
- `@Valid`: 변환된 DTO의 validation annotation을 실행한다.
- `userService.createUser`: Controller가 업무 규칙을 직접 처리하지 않고 Service로 위임한다.
- 반환 DTO: Spring/Jackson이 JSON response body로 직렬화한다.
- `@ResponseStatus(CREATED)`: 정상 저장 시 HTTP 201을 지정한다.

Controller에서 예외를 catch하지 않는 것이 중요하다. DTO validation 실패는 Controller method body 전에 발생하고, Service exception은 GlobalExceptionHandler로 전파된다.

## 7. 프론트가 이 endpoint를 호출하는 위치

### SignupPage

파일: `src/pages/auth/SignupPage.jsx`

실제 state 선언부터 확인한다.

~~~javascript
const initialForm = {
    email: "",
    password: "",
    passwordCheck: "",
    nickname: "",
};

function SignupPage() {
    const navigate = useNavigate();
    const [form, setForm] = useState(initialForm);
    const [errors, setErrors] = useState({});
    const [profileImage, setProfileImage] = useState(null);
    const [previewUrl, setPreviewUrl] = useState(null);
    const [isSubmitting, setIsSubmitting] = useState(false);
~~~

여기서 `errors`는 `form` 내부 field가 아니다. `form`과 완전히 별도의 React state다.

- `initialForm`: 입력 field의 최초값만 가진 일반 JavaScript object다.
- `form`: 현재 사용자가 입력한 email/password/passwordCheck/nickname을 보관한다.
- `setForm`: input 변경 시 form state를 교체한다.
- `errors`: field 이름을 key로 갖는 오류 문구 object다. 최초값은 빈 object다.
- `setErrors`: blur 검증이나 서버 응답 뒤 오류 object를 교체한다.
- `profileImage`: form object에 포함되지 않은 File 객체 state다.
- `previewUrl`: 선택한 이미지 미리보기 URL state다.
- `isSubmitting`: 제출 중 중복 submit을 막고 버튼 문구를 바꾸는 state다.

즉 실제 state 구조는 다음과 같다.

~~~text
form
├─ email
├─ password
├─ passwordCheck
└─ nickname

errors
├─ email        (오류가 없으면 없거나 빈 문자열)
├─ password
├─ passwordCheck
└─ nickname
~~~

`SignupPage`는 이 두 state를 `SignupForm`에 각각 다른 prop으로 전달한다.

~~~jsx
<SignupForm
    form={form}
    errors={errors}
    previewUrl={previewUrl}
    isSubmitting={isSubmitting}
    isValid={isValid}
    onChange={handleChange}
    onBlur={handleBlur}
    onImageChange={handleImageChange}
    onSubmit={handleSubmit}
    loginTo="/login"
/>
~~~

`SignupForm.jsx`는 이 prop을 함수 매개변수 구조 분해로 받는다.

~~~jsx
function SignupForm({
    form,
    errors,
    previewUrl,
    isSubmitting,
    isValid,
    onChange,
    onBlur,
    onImageChange,
    onSubmit,
    loginTo,
}) {
~~~

따라서 `errors.email`은 SignupForm 내부에서 새로 만들어진 field가 아니다. SignupPage의 `errors` state가 prop으로 전달되어 들어온 값이다.

중요한 상태와 메서드:

- `form`: email/password/passwordCheck/nickname의 현재 입력값
- `errors`: `form`과 별도로 존재하는 field별 검증/서버 오류 문구 state
- `profileImage`: 선택한 File 객체
- `isValid`: 현재 form이 프론트 기본 검증을 통과했는지 계산
- `handleChange`: input event에서 name/value를 읽고 form state를 함수형 update한다.
- `handleBlur`: field별 검증을 실행한다.
- `handleImageChange`: File을 선택하고 Data URL preview를 만든다.
- `handleSubmit`: local 검증 → authApi.signup → 성공 시 login 이동 → 오류 문구 배치 순서로 실행한다.

`FormField`에는 다음처럼 전달된다.

~~~jsx
<FormField
    error={errors.email}
>
    <TextInput
        name="email"
        value={form.email}
        onChange={onChange}
        onBlur={onBlur}
    />
</FormField>
~~~

`value={form.email}`은 입력값을 표시하고, `error={errors.email}`은 같은 field의 오류 문구를 표시한다. 두 값은 이름이 비슷해 보이지만 서로 다른 state에서 온다.

`handleSubmit`의 핵심 흐름:

~~~javascript
event.preventDefault();
const nextErrors = Object.fromEntries(
    Object.keys(form).map((name) => [name, validateField(name)]),
);
setErrors(nextErrors);

if (!isValid) return;

try {
    setIsSubmitting(true);
    await authApi.signup({
        ...form,
        email: form.email.trim(),
        nickname: form.nickname.trim(),
        profileImage: profileImage ? await fileToDataUrl(profileImage) : null,
    });
    navigate("/login", { replace: true });
} catch (error) {
    // error code에 따라 email 또는 nickname field에 문구를 배치한다.
} finally {
    setIsSubmitting(false);
}
~~~

- `preventDefault`: browser의 기본 form submit/reload를 막는다.
- `Object.keys(form).map(...)`: 모든 field를 순회해 검증 결과 배열을 만든다.
- `Object.fromEntries`: `[key, value]` 배열을 errors object로 변환한다.
- `...form`: 기존 입력값을 payload에 복사한다.
- `trim()`: 서버로 보내기 전에 email/nickname 양끝 공백을 제거한다.
- `await fileToDataUrl`: File을 서버 DTO의 profileImage 문자열로 변환한다.
- `try/catch/finally`: 성공 이동, 오류 field 배치, submit 상태 정리를 분리한다.

### authApi와 공통 request

~~~javascript
signup(payload) {
    return request("/users", {
        method: "POST",
        body: JSON.stringify(payload),
    });
}
~~~

`authApi.signup`은 실제 fetch를 직접 하지 않는다. `api.js`의 `request`가 base URL, JSON header, Cookie, HTTP 오류 변환을 담당한다. `JSON.stringify`가 JavaScript object를 HTTP JSON 문자열로 바꾼다.

## 8. 실패 시 실제 이동

```text
DTO annotation 실패
→ MethodArgumentNotValidException
→ GlobalExceptionHandler
→ 400 { message: "invalid_request" }

email 중복
→ UserService가 InvalidRequestException("Existed_Email")
→ Handler
→ 400 { message: "Existed_Email" }
→ api.js Error.code
→ SignupPage가 email field에 문구 표시
```

프론트의 `isValid`는 사용자 경험을 위한 사전 검사이고, 서버의 `@Valid`와 Service 검사는 보안/업무 규칙을 위한 최종 검사다. 프론트가 통과해도 서버 검증은 반드시 실행된다.

## 스킵하는 코드

- `UserPatch*`, `UserPassword*`, `UserInfoResponseDto`: DTO 선언 구조는 UserRequest/Response에서 이해한 뒤, 해당 endpoint의 field와 사용 위치만 확인한다.
- `User`의 `delete`, `changePassword`: 회원가입 흐름에는 사용되지 않는다. 이후 회원정보/인증 흐름에서 다시 읽는다.
- `UserRepository`의 lock/query 메서드: 회원가입에는 호출되지 않는다. 메서드가 어느 Service에서 참조되는지 검색한 뒤 해당 기능에서 읽는다.
