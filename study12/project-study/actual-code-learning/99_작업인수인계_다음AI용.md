## 2. 사용자의 최종 학습 목표

사용자는 AI가 작성한 코드가 많아 주석 없는 실제 코드를 처음부터 끝까지 이해하고 싶어 합니다. 목표는 모든 파일을 기계적으로 읽는 것이 아니라, 다음 조건을 만족하는 것입니다.

1. 애플리케이션이 시작되는 시점부터 HTTP 요청이 Controller, Service, Repository, Entity, DB·Redis를 거쳐 응답으로 돌아오는 전체 흐름을 이해한다.
2. 프론트엔드에서 사용자의 동작이 화면 state, API module, 공통 request, 백엔드 endpoint와 어떻게 연결되는지 이해한다.
3. 새로운 문법·annotation·라이브러리 API가 처음 등장하면 반드시 그 코드 위치에서 설명한다.
4. 완전히 중복되는 코드만 실제 사용 위치와 역할을 확인한 뒤 스킵한다.
5. 각 메서드와 변수의 선언 파일, 호출 위치, 매개변수 출처, 반환값 사용 위치, 예외 이동 경로를 추적한다.
6. 코드를 작성하는 순서와 프로그램이 실행되는 순서를 구분한다.
7. 설명은 실제 현재 저장소 코드와 검색 결과에 근거한다. 확인하지 못한 내용은 추측하지 않고 `현재 코드만으로 확인할 수 없음`이라고 표시한다.

## 3. 반드시 지켜야 하는 정확성 규칙

다음 AI는 설명을 빨리 완성하는 것보다 실제 코드와의 일치를 우선해야 합니다.

- 실제 파일을 열고 원문을 확인한 뒤 설명한다.
- `rg` 등으로 import, route, 문자열 참조, 메서드 호출, workflow 참조를 검색한다.
- Spring annotation 때문에 연결되는 관계는 단순 import 검색만으로 결론내리지 않는다.
- 문서의 문장을 현재 구현, 과거 코드·장애, 테스트로 증명된 내용, 사용자의 의도, 설정 설명으로 구분한다.
- 과거 코드 설명은 현재 코드와 섞지 않는다. 기존 내용이 남아 있다면 `변경 전 참고`와 `현재 코드`를 분리한다.
- 실제로 실행하지 않은 테스트를 실행했다고 쓰지 않는다.
- 파일을 수정하기 전에는 변경 범위·방법·검증 방법을 먼저 설명하고, 사용자의 명시적 승인을 받은 뒤 수정한다.
- 문서만 수정할 때도 실제 코드와 문서를 다시 대조한다.
- 기존 설명이 틀렸다면 방어하지 말고 `무엇이 틀렸는지 → 왜 틀렸는지 → 현재 결론` 순서로 바로잡는다.

## 4. 문서 작성 형식: 현재 최종 규칙

대화 중 형식 요구가 여러 번 바뀌었으므로, 아래 규칙을 최종 규칙으로 사용합니다.

### 4.1 연관된 파일은 한 문서에 묶는다

호출 흐름상 함께 읽어야 하는 파일은 파일별로 분리하지 말고 하나의 Markdown 문서 안에서 실제 실행 순서대로 이어 붙입니다.

예시:

`JwtAuthenticationFilter.java → CustomUserDetailsService.java → CustomUserDetails.java`

인증 문서는 실행 흐름별 5개 Markdown으로 나누며, 각 문서 내부에서도 파일별 코드 블록을 따로 둡니다. 현재 구조에서 인증 파일을 다시 하나의 Markdown으로 합치지 않습니다. 다섯 문서가 각각 로그인, Access Token 요청 인증, Refresh Token rotation, 로그아웃·Origin/CORS, 세션 정리·테스트를 담당합니다. 실행 기반·회원가입·이미지 검증·예외 응답은 인증 문서와 섞지 않고 각각 `01`, `02`, `03` 문서에 둡니다.

인증 문서의 이전 내용은 별도 `auth-legacy-backup` 디렉터리로 보관하지 않습니다. 현재
`04~08`과 `04-08` 파일이 인증 문서의 최신 기준이며, 복구가 필요하면 Git diff/history와
실제 코드 저장소를 대조합니다.

### 4.2 코드 블록은 파일별로 하나씩 둔다

과거에는 `전체 주석본`과 `목차 주석본`을 따로 만들거나 여러 파일을 하나의 거대한 코드 블록에 섞는 문제가 있었습니다. 현재 인증 문서의 최종 규칙은 **실제 코드 블록과 설명을 대응시키고, 별도 목차 주석본을 만들지 않는 것**입니다.

연관된 여러 파일을 하나의 Markdown에 묶을 수는 있지만, 코드 블록까지 하나로 합치지 않습니다.

각 파일은 반드시 다음 순서입니다.

해당 파일의 전체 코드
→ 설명할 코드 일부
→ 그 코드 일부에 대한 설명
→ 다음 코드 일부
→ 그 코드 일부에 대한 설명
→ 해당 파일의 설명이 끝난 뒤 다음 파일의 전체 코드

한 파일의 코드와 설명이 끝나기 전에 다음 파일의 코드나 설명을 넣지 않습니다. 설명 앞에는 반드시 설명 대상 코드 일부를 다시 보여주며, 번호로만 위치를 표시하지 않습니다.

하나의 파일 설명 단위에는 다음을 함께 넣습니다.

- 실제 코드의 원문 또는 현재 흐름에 필요한 정확한 코드 구간
- 코드 바로 아래의 실행 주체·매개변수 출처·반환값 사용처·예외·상태 변경 설명
- 새로운 문법이 처음 등장한 위치의 문법·현재 코드에서의 역할 설명
- 같은 파일의 다른 method를 발췌한 경우에도 파일 경로와 호출 관계 표시
- 호출 위치·값의 출처·반환값의 도착 위치·예외 이동 경로
- 처음 등장하는 문법과 현재 코드에서 사용하는 이유

`package`와 `import` 줄에는 주석을 달지 않습니다.

### 4.3 실제 코드 생략 금지

사용자는 코드 일부만 보면 흐름이 끊긴다고 여러 번 지적했습니다. 따라서 전체 파일을 설명하는 문서에서는 원문을 생략하지 않습니다.

정말로 연결 확인만 필요한 파일에서 발췌할 때만 다음 정보를 적습니다.

- `발췌`라는 표시
- 실제 절대 경로
- 발췌한 메서드명과 줄 범위
- 전체 파일을 넣지 않은 이유
- 생략된 나머지 코드가 흐름 이해에 필요 없는 근거

### 4.4 번호 주석 배치

번호는 설명 위치를 찾기 위한 목차 역할입니다. 번호만 멀리 떨어진 곳에 모아두면 안 됩니다.

- `/* 1. 클래스의 책임과 호출 위치 */`처럼 코드 묶음 바로 위에 둔다.
- 메서드 내부의 세부 줄은 `// 1` 또는 `//1,3`처럼 해당 줄 가까이에 표시한다.
- 여러 설명이 같은 코드 구간에 적용되면 병합 번호를 유지한다.
- 코드 한 줄에서 시작한 설명을 문서 아래 먼 위치로 보내지 않는다.
- 한 코드에 번호가 너무 많이 걸리면 메서드·생성자·조건문·반복문 단위로 코드 구간을 나눈다.

### 4.5 모든 설명은 “무엇”과 “왜”를 함께 적는다

결과만 적지 않습니다. 최소한 다음 질문에 답해야 합니다.

- 이 코드의 책임은 무엇인가?
- 누가 이 코드를 호출하는가?
- 언제 실행되는가? 애플리케이션 시작 시인가, 요청이 들어왔을 때인가?
- 매개변수는 어디에서 왔는가?
- 내부에서 어떤 순서로 값이 변하는가?
- 반환값은 어느 파일의 어느 메서드에서 사용하는가?
- 예외가 발생하면 어느 Handler·Filter·호출자에게 이동하는가?
- DB·Redis·HTTP response·SecurityContext 중 무엇을 변경하는가?
- 이 구현을 사용한 이유와 사용하지 않았을 때의 차이는 무엇인가?

Spring이 내부에서 이어서 처리하는 경우에는 반드시 처리 주체를 적습니다. 예를 들면 `DispatcherServlet`, `Jackson`, `HttpServletResponse`, `SecurityFilterChain`, `SecurityContextHolder` 등이 있습니다.

### 4.6 새로운 문법은 처음 나오는 위치에서 설명한다

문법 설명을 문서 마지막에 모으지 않습니다.

처음 등장하는 코드 바로 아래에 다음을 적습니다.

- 문법의 의미
- 이 프로젝트 코드에서 왜 사용했는지
- 현재 입력과 반환값으로 실행 결과가 무엇인지
- 짧은 일반 예시

같은 문법이 반복되면 `앞의 파일에서 설명한 문법`이라고 표시하고, 현재 코드에서 달라지는 점만 설명합니다. 단, 사용자가 다시 질문한 개념은 이미 설명했다는 이유로 스킵하지 않고 해당 코드 위치에서 다시 설명합니다.

## 5. 지금까지 확정된 주요 요구사항

다음은 대화에서 사용자가 반복해서 확정한 요구입니다.

- 실제 코드 원문을 먼저 보여주고 설명한다.
- 축약 코드만 보여주지 않는다.
- 프론트 코드도 주석을 생략하지 않는다.
- `errors`처럼 코드에 실제로 존재하는 state·field는 빠뜨리지 않는다.
- 코드의 모든 줄이 어느 설명을 가리키는지 코드 가까이에 표시한다.
- 새로운 문법과 개념은 설명용 주석 코드 안에 넣는다.
- 다른 코드와 연결되어 있으면 이해에 필요한 관련 코드도 함께 발췌한다.
- 관련 파일의 호출 관계, 값 전달, 반환값 사용 위치, 예외 경로를 반드시 연결한다.
- 지금 당장 호출되지 않는 상수나 Bean도 어디에서 쓰이는지, 현재 흐름에서 안 쓰이면 그 사실을 적는다.
- 같은 개념이 다른 화면이나 기능에서 다시 나오면 그 위치에서도 흐름상 필요한 설명을 반복한다.
- 완전히 중복된 파일만 역할과 차이를 확인한 뒤 스킵한다.
- 파일 하나를 완성할 때마다 파일 개수 기준 진행률을 표시한다.
- 사용자가 질문한 내용은 기존 설명이 부족했다는 뜻으로 보고, 이후 해당 코드 문서에 더 자세히 반영한다.
- 설명을 추가할 때 기존의 유효한 설명을 삭제하지 않는다.

## 8. 현재 문서별 진행 상태와 포함 파일

진행률은 장 수가 아니라 **중복 제거한 실제 파일 확인 수**로 계산합니다. 현재 기준표는
00번 문서의 파일별 누적 진행률표이며, 0번부터 18번까지의 문서 작성 당시 도달 지점은
199/213개 = 93.4%입니다. 이 숫자는 문서가 늘어났다는 이유만으로 올리지 않고,
실제 원문·호출자·호출 대상·입력·반환·예외 확인이 끝난 파일만 한 번 집계합니다.
이전 문장에 남아 있던 `116/213 (54.5%)`는 과거 계산 기록이므로 현재 진행률로 사용하지 않습니다.

파일별 최종 순서는 00번의 표를 기준으로 합니다. 위 숫자는 19번 배포 문서 작성 전의
기록이며, 현재 최신 진행률은 이 파일의 마지막 완료 기록을 기준으로 합니다.

## 9. 현재 확인된 핵심 실행 흐름

아래는 시작 지도입니다. 다음 AI는 각 장에서 실제 코드와 검색 결과를 다시 연결해 설명해야 합니다.

### 9.1 애플리케이션 시작

```text
SpringdatajpaApplication.main
→ SpringApplication.run
→ @SpringBootApplication component scan
→ YAML profile 병합
→ ConfigurationProperties Bean 생성
→ SecurityConfig·WebConfig·InterceptorConfig Bean 생성
→ Repository/Service/Controller Bean 생성
→ @EnableScheduling으로 Scheduler 등록
```

`@Bean` 메서드가 애플리케이션 시작 중 호출되어 객체를 준비한다는 사실과, 그 객체의 업무 메서드가 요청 시 실행된다는 사실을 구분해야 합니다.

### 9.2 회원가입

```text
SignupPage.handleSubmit
→ authApi.signup
→ api.js request
→ fetch POST /users
→ UserController.createUser
→ @RequestBody 역직렬화·@Valid 검증
→ UserService.createUser
→ 중복·업무 규칙 검사
→ ImageDataUrlValidator 호출
→ PasswordEncoder.encode
→ User Entity 생성·저장
→ UserResponseDto
→ Jackson JSON body
→ 프론트 성공 또는 errorMessage 처리
```

프론트 validation은 사용자 경험을 위한 사전 검사이고, 백엔드 `@Valid`와 Service 검사는 최종 검증입니다. 프론트가 통과해도 서버 검증은 반드시 별도로 실행됩니다.

### 9.3 로그인


#### AuthenticationManager의 정확한 실행 시점

현재 코드에는 다음 두 시점을 반드시 구분해야 합니다.

1. `SecurityConfig.authenticationManager(...)`의 `@Bean` 메서드: Spring이 애플리케이션 Context를 만들 때 `AuthenticationManager` 객체를 준비하고 `SessionService`에 주입합니다. 이때 사용자의 이메일·비밀번호 검증은 실행되지 않습니다.
2. `SessionService.createSession()` 안의 `authenticationManager.authenticate(...)`: 실제 `POST /sessions` 로그인 요청이 들어왔을 때 명시적으로 실행됩니다. 이때 사용자 조회와 비밀번호 검증이 일어나고, 성공한 `Authentication`이 다음 코드로 반환됩니다.

따라서 `AuthenticationManager` 객체는 요청 전에 준비되어 있지만, `authenticate()` 업무 실행은 로그인 요청 시점입니다. “Bean이 자동 실행된다”라고 설명하면 안 됩니다.

### 9.4 Access Token 인증

```text
보호된 프론트 API request
→ api.js가 Authorization: Bearer <token> 추가
→ SecurityFilterChain
→ JwtAuthenticationFilter
→ shouldNotFilter 대상인지 확인
→ JwtProvider.getAccessTokenClaims
→ 서명·claim 검증
→ CustomUserDetailsService.loadUserByUserId
→ UserRepository에서 활성 User 조회
→ deleted·suspended·authVersion 확인
→ UsernamePasswordAuthenticationToken 생성
→ SecurityContextHolder에 Authentication 저장
→ 다음 Filter와 Controller로 진행
```

로그인 시 `AuthenticationManager`가 이메일·비밀번호를 검증하는 흐름과, 이후 요청에서 `JwtAuthenticationFilter`가 JWT를 검증하는 흐름은 서로 다릅니다.

### 9.5 Refresh Token 재발급

```text

→ api.js의 refreshPromise 공유 로직
→ POST /sessions/refresh
→ Cookie에서 refresh token 추출
→ SessionController.refreshSession
→ SessionService.refreshSession
→ 원문 token hash 계산
→ AuthSessionRepository.findByRefreshTokenHash
→ PESSIMISTIC_WRITE row lock
→ isActive·User 상태 확인
→ 새 원문 token·hash 생성
→ 같은 AuthSession.rotate
→ 새 Access Token 생성
→ 새 Set-Cookie header와 body 반환
→ 원래 API 요청 재시도
```

동시 Refresh 요청의 정확한 결과는 실제 lock·transaction·DB 제약과 테스트를 함께 확인해야 합니다. 근거 없이 “항상 특정 예외가 된다”고 단정하지 않습니다.

```text
게시글 상세 진입
→ PostService 또는 조회수 호출 위치
→ ViewCountUpdater
→ RedisViewCountStore key 증가·dirty 기록
→ RedisViewCountFlushScheduler
→ ViewCountPersistenceService
→ DatabaseViewCountUpdater
→ PostViewCountRepository
```

Redis 장애 시 실제 fallback과 실패 처리 범위는 해당 Service·테스트를 정독한 뒤 확정해야 합니다.

### 9.8 배포

```text

→ build/test
→ Docker image build·push
→ AWS/OIDC·SSM 단계
→ deploy script
→ Compose service 실행
→ health 확인
```

배포 파일은 아직 정독하지 않았으므로 포트·환경변수·health 명령·전환 방식은 실제 파일을 확인하기 전까지 확정하지 않습니다.

## 11. 지금까지 사용자가 지적한 오류와 반드시 반영할 교훈

### 11.1 코드 일부 생략

문제: `SignupPage.jsx`에서 실제 코드에 있는 `errors` state를 설명에서 빠뜨린 적이 있습니다.

교훈: state·field·상수·함수 호출을 임의로 줄이지 않습니다. 생략하면 실제 코드와 설명의 흐름이 달라져 학습을 방해합니다.

### 11.2 주석 위치가 멀리 떨어짐

문제: 코드 앞의 번호가 코드 한참 아래의 설명을 가리키거나, `1` 코드 아래에 `2,3,4` 설명이 멀리 떨어진 적이 있습니다.

교훈: 설명 대상 코드 바로 위·아래에 둡니다. 관련 번호를 병합할 수는 있지만 멀리 보내지 않습니다.

### 11.3 두 주석본의 중복

문제: 전체 주석본과 목차 주석본을 따로 만들면서 실행 코드가 반복되고 순서가 어긋났습니다.

교훈: 현재는 하나의 코드 블록에 실제 코드와 line comment, block comment, 상세 설명을 함께 넣습니다.

### 11.4 결과만 적고 원리를 생략

문제: `response.addHeader(...)`가 왜 반환 body에 포함되지 않아도 응답에 들어가는지, `HttpHeaders.SET_COOKIE`가 어디서 온 값인지 등을 단순히 “Cookie를 추가한다”로만 설명한 적이 있습니다.

교훈: `HttpServletResponse`가 Controller 메서드에 전달되는 이유, header mutation, DispatcherServlet이 반환 객체를 Jackson으로 직렬화하는 시점까지 설명해야 합니다.

### 11.5 Spring Bean의 실행 시점 혼동

문제: `AuthenticationManager` Bean이 로그인 검증을 자동 실행하는 것처럼 설명한 적이 있습니다.

현재 정정:

- `@Bean authenticationManager(...)` 메서드는 애플리케이션 시작 시 객체를 준비한다.
- 실제 인증 검증은 `SessionService.createSession()` 내부의 `authenticationManager.authenticate(...)`가 로그인 요청 중 호출될 때 실행된다.
- `deleteSession()`과 `refreshSession()`은 현재 코드에서 `AuthenticationManager.authenticate()`를 호출하지 않고, Refresh Token hash와 `AuthSession`을 사용한다.

### 11.6 YAML placeholder 의미

문제: `${NAME:default}` 문법을 입력값이 없을 때 기본값을 쓰는 기능과, 연결 timeout 자체의 의미를 혼동한 적이 있습니다.

교훈: placeholder 해석과 실제 설정값의 동작 의미를 분리해 설명합니다. 예를 들어 `${REDIS_CONNECT_TIMEOUT:2s}`는 환경변수 값이 있으면 그 값을 사용하고 없으면 `2s`를 사용한다는 뜻입니다. `2s`가 timeout 설정이므로 결과적으로 연결 시도 제한 시간이 2초가 될 수 있지만, 두 문장은 같은 설명이 아닙니다.

### 11.7 Actuator health·보안·배포 경계

`management.endpoints.web.exposure.include=health`는 health endpoint를 HTTP endpoint로 노출하는 설정입니다. 로그인 없이 접근 가능한지는 `SecurityConfig`의 `requestMatchers(HttpMethod.GET, "/actuator/health").permitAll()`에서 별도로 결정합니다. YAML의 배포 환경변수 주입, Compose, Nginx, health 확인 과정은 배포 장에서 실제 연결을 추적해야 합니다.

### 11.8 Origin 없는 요청

Origin이 없는 요청을 허용한다고 해서 모든 CSRF 상황을 차단하는 것은 아닙니다. 반대로 Origin 없는 요청을 일괄 차단하면 curl, 서버 간 요청, 기존 MockMvc 테스트에 영향을 줄 수 있습니다. 현재 정책을 설명할 때는 실제 `SessionOriginInterceptor`, `InterceptorConfig`, 테스트 요청 header를 대조하고 “일부러 열어둔 것인지”와 “현재 도메인·HTTPS 조건”을 구분해야 합니다.

### 11.9 동시성·DB 제약

동시 중복 신고나 Refresh 동시 요청에 대해 DB unique 제약이 발생한다고 해서 항상 업무 예외 `Already_Reported`로 변환된다고 단정하면 안 됩니다. 실제 catch, exception translator, constraint 이름, 테스트 결과를 확인해야 합니다.

### 11.10 Front React 개념

다음 개념은 사용자가 실제 코드 위치에서 다시 설명받기를 원합니다.

- `Outlet`: 부모 route가 자식 route element를 렌더링할 자리로 제공하는 React Router 컴포넌트
- `lazy`: 동적 import의 Promise를 React가 렌더링할 수 있는 lazy component로 감싸는 함수
- `Suspense`: lazy component 등이 준비될 때 fallback을 표시하는 경계
- `key={location.key}`: 위치 key가 바뀔 때 React가 경계를 다른 인스턴스로 취급하게 하는 식별자
- `useEffect`: 컴포넌트 렌더링 외부의 작업을 실행하는 Hook; cleanup과 비동기 응답의 stale 상태 방지 흐름을 실제 코드와 함께 설명
- `AbortController`, `IntersectionObserver`: 게시글 목록 요청 취소·다음 페이지 감지에 사용되는지 실제 코드로 확인

사용자가 이미 질문한 개념이라도 그 개념이 다른 실제 코드에 다시 나오면 해당 코드 위치에서 흐름을 다시 설명합니다.

## 12. 아직 정독하지 않은 영역

현재 문서가 완료된 것은 전체 프로젝트가 아닙니다. 다음 영역은 아직 실제 원문·호출 관계·테스트를 모두 정독하지 않았습니다.

- 게시글 상세·작성·수정·댓글·회원정보 화면은 15번 문서에서 원문 확인을 완료했으며, 이후 Redis·Flyway·테스트·배포가 남아 있다.
- Redis 조회수 전체 구현과 fallback
- Flyway V1~V5와 RDS 연결 설정
- H2·MySQL·Redis·Testcontainers·AOF·동시성 테스트
- backend/frontend Dockerfile, Compose, `.env.example`, Nginx, deploy script, GitHub Actions

참조되지 않는 파일이라고 표시하려면 import뿐 아니라 route, 문자열, annotation, reflection, workflow 참조를 먼저 검색해야 합니다.

## 13. 다음 AI가 이어서 할 권장 순서

### 전체 재배치 원칙

실행 시점과 학습 시점을 분리한다. Filter가 요청 중 먼저 실행된다는 이유로 Filter가
사용하는 wrapper·service보다 먼저 설명하지 않는다. 반대로 실제 사용처가 없는 파일을
단순히 폴더가 같다는 이유로 먼저 설명하지 않는다. 아래 순서는 현재 저장소의 import,
메서드 호출, route, 설정 key를 확인해 정한 학습 순서다.

### 1. 기반 실행

`settings.gradle` → `build.gradle` → `application.yaml` → `application-local.yaml` →
`application-prod.yaml` → `src/test/resources/application-test.yaml` →
`SpringdatajpaApplication.java` → 프론트 `package.json` → `vite.config.js` → `index.html` →
`src/main.jsx` → `src/App.jsx`.

Gradle wrapper 내부 구현은 버전 고정 역할만 확인하고 스킵한다. `data.sql`은 local의
`spring.sql.init.mode: always`와 연결되는지 확인한 뒤 Flyway 장에서 schema와 함께 다시 본다.

### 2. 프론트 라우팅 기반

`AppRoutes.jsx` → `ProtectedRoute.jsx` → `PublicOnlyRoute.jsx` → `PageBoundary.jsx` →
`PageLayout.jsx` → `AuthLayout.jsx` → `AppHeader.jsx`.

이 단계에서 `Outlet`, `lazy`, `Suspense`, `ErrorBoundary`, `useLocation`, route guard의
문법을 처음 등장한 코드 바로 아래에 설명한다.

### 3. 공통 응답·검증·예외

`ErrorResponseDto.java` → `ApiErrorCode.java` → `GlobalExceptionHandler.java` →
`ErrorResponseWriter.java` → 첫 예외 class → 나머지 `exception/*` →
`ImageDataUrlValidator.java`.

Controller가 던지는 예외와 Filter/Interceptor가 직접 response를 쓰는 경로를 먼저
분리해 둬야 이후 인증·게시글 오류 흐름을 혼동하지 않는다.

### 4. 회원가입

`User.java` → 회원가입 Request/Response DTO → `UserRepository.java` → `UserService.java` →
`UserController.java`.

이 단계에서 Entity, DTO 역직렬화·검증, Repository method-name query, Service 업무 순서,
Controller JSON 응답을 처음부터 끝까지 연결한다.

### 5. 인증 모델·Provider·세션 저장

인증은 `actual-code-learning/04-08_인증_통합_실행흐름.md`를 주 학습 문서로 확인한다.
기존 04~08 문서는 전체 원문과 세부 설명을 대조하는 참고 자료로 유지한다. 통합 문서는
로그인·보호 요청·Refresh·로그아웃·Origin/CORS·인증 무효화·세션 정리를 하나의 실행
흐름으로 연결한다.

### 6. 로그인·보안 요청 흐름

`AuthenticationManager` Bean 생성과 `authenticate()` 호출 시점을 분리하고, Filter의
`filterChain.doFilter`와 Controller 진입을 실제 코드로 연결한다.

### 7. 게시글·댓글 Entity

`Post.java` → `PostImage.java` → `PostCounter.java` → `PostViewCount.java` → `Like.java` →
`PostReport.java` → `Comment.java`.

호출 Service를 확인한다.

### 8. 게시글·댓글 DTO·Repository

게시글 DTO 전체 → 댓글 DTO 전체 → `PostResponseFactory.java` → `PostRepository.java` →

## 14. 파일별 문서 작성 전 체크리스트

다음 AI는 파일 하나 또는 관련 파일 묶음을 문서에 추가하기 전에 아래를 모두 확인합니다.

- [ ] 실제 절대 경로를 적었는가?
- [ ] 현재 원문을 다시 읽었는가?
- [ ] import와 annotation을 확인했는가?
- [ ] public 메서드와 흐름상 중요한 private 메서드의 호출 위치를 검색했는가?
- [ ] 호출자·호출 대상·매개변수 출처·반환값 도착 위치를 적었는가?
- [ ] DB·Redis·HTTP response·SecurityContext 변경 여부를 적었는가?
- [ ] 정상 흐름과 예외 흐름을 둘 다 적었는가?
- [ ] 다른 파일에서 이해에 필요한 연결 코드가 있으면 발췌했는가?
- [ ] 새 문법·annotation·라이브러리 API를 코드 바로 아래에 설명했는가?
- [ ] `package`와 `import`에 주석을 달지 않았는가?
- [ ] 코드 원문을 임의로 생략하지 않았는가?
- [ ] 생략했다면 발췌 이유와 확인 범위를 적었는가?
- [ ] 주석 번호가 실제 코드 가까이에 있는가?
- [ ] 결과뿐 아니라 작동 이유를 설명했는가?
- [ ] 문서의 문장이 실제 코드보다 강한 주장을 하지 않는가?
- [ ] 문서 추가 후 `git diff --check` 등 문서 형식 검사를 실행했는가?
- [ ] 진행률을 실제 확인 파일 수에 맞게 갱신했는가?

7. Type variable = methodCall(argument) 형태의 대입문은 결과만 쓰지 않습니다. 왼쪽 타입·변수의 의미, 오른쪽 호출 객체, 매개변수의 출처, 메서드 내부의 조회·변환, 반환값이 왼쪽 변수에 저장된 뒤 어디에서 사용되는지까지 그 코드 일부 아래에 적습니다.
8. 7번은 특정 대입문 하나에만 적용하는 규칙이 아닙니다. 문서에 포함하는 모든 코드에 적용합니다. 모든 중요한 줄과 코드 구간에 대해 실행 주체, 실행 시점, 문법 구조, 값의 출처, 내부에서 호출되는 메서드, 생성·변경되는 상태, 반환값의 전달 위치, 예외 이동 경로, 왜 필요한지를 사용자 질문 전에 설명합니다.
9. 메서드 호출은 메서드가 선언된 파일·class·호출자·매개변수 출처·반환값 사용처를 적습니다. field와 상수는 선언 위치·초기화 방법·주입 주체·사용 위치를 적습니다. framework 객체는 누가 생성·전달·호출하는지 적습니다. 조건문·반복문·형변환·람다·체이닝도 현재 코드에서 실제로 어떤 값과 흐름을 만드는지 적습니다.
10. “호출한다”, “저장한다”, “응답한다”처럼 결과만 적는 주석으로 끝내지 않습니다. 그 결과가 생기는 원리와 다음 코드에서 사용되는 이유까지 해당 코드 일부 바로 아래에 둡니다. 사용자가 먼저 질문해야 설명을 추가하는 방식은 금지합니다.
11. Spring·Servlet·React 등 외부 framework가 제공하는 class·interface·Hook·객체는 framework가 제공한다는 사실과 현재 코드에서의 역할을 해당 코드 일부 바로 위 주석과 아래 설명에 적습니다. import 줄에는 주석을 달지 않습니다.
12. Filter·middleware·router처럼 다음 처리 단계로 넘기는 코드는 단순히 “다음으로 전달한다”고 쓰지 않습니다. 누가 다음 객체를 호출하는지, 그 호출이 Controller까지 어떻게 이어지는지, 현재 method의 return이 downstream 호출을 취소하지 않고 현재 method만 종료하는 이유를 실행 순서로 설명합니다. 인증하지 않는 것과 공개 endpoint로 허용하는 것도 구분합니다.
13. `throw`, `throws`, `orElseThrow`처럼 실행과 선언이 비슷해 보이는 문법은 구분해서 설명합니다. 실제로 예외를 발생시키는 코드, 예외 가능성을 메서드 선언에 적는 문법, 호출자에게 전파되는 경로를 각각 코드 일부 바로 아래에 적습니다.

### 18.4 사용자·게시글·댓글·조회수 흐름

회원가입은 `UserController → UserService → UserRepository` 흐름이며, Service에서 중복·재가입 제한·이미지 검증·비밀번호 hash 처리를 수행한 뒤 User Entity를 저장합니다. 비밀번호 변경은 `User.authVersion`을 증가시키고 active AuthSession을 revoke하여 기존 Access Token과 Refresh Session을 무효화합니다.

게시글 목록은 다음 흐름입니다.

```text
GET /posts
→ PostController
→ PostService.getPostList
→ PostRepository Page query
→ 삭제되지 않고 reportCount가 5 미만인 Post 조회
→ PostResponseFactory
→ PostPage DTO
```

게시글 상세에서는 Post·User·Image·Counter·Like·Report·Comment를 조합하고, 로그인 사용자 기준 `isMine`, `isLiked`, `isReported`를 계산합니다. 조회수는 현재 `PostCounter`가 아니라 별도 `PostViewCount`가 기준입니다.

좋아요·신고·댓글은 Service에서 Repository bulk update, DB lock, unique 제약, Entity 상태 변경을 조합합니다. 게시글과 User는 soft delete이고, Comment는 현재 물리 삭제입니다. 게시글 reportCount가 5 이상이면 목록·상세·수정 제한이 발생하고, User가 받은 reportCount가 10 이상이면 suspended 상태가 됩니다.

조회수 구현은 `ViewCountUpdater` 인터페이스를 기준으로 두 경로가 선택됩니다.

```text
PostService
→ ViewCountUpdater
├─ app.view-count.enabled=true
│  → RedisViewCountStore
│  → Redis count·dirty set
│  → RedisViewCountFlushScheduler
│  → ViewCountPersistenceService
│  → PostViewCountRepository
└─ app.view-count.enabled=false
   → DatabaseViewCountUpdater
   → PostViewCountRepository
```

Redis 장애 시 `RedisViewCountStore`는 현재 DB baseline을 반환하지만, Redis 구현을 실행 중에 Database 구현으로 교체하는 동적 fallback은 아닙니다. Redis flush는 Redisson 분산 lock, snapshot, `GREATEST` 저장, 변경 여부 확인 후 dirty marker 삭제 순서로 동작합니다.


프론트는 전역 상태 저장소나 React Query/Redux를 사용하지 않고, 페이지·컴포넌트의 `useState`, `useRef`, `useEffect`, `useCallback`으로 상태와 비동기 흐름을 관리합니다.

`authStorage`는 Access Token을 localStorage에 저장하고, Refresh Token은 저장하지 않습니다. `api.js`는 모든 요청에 `credentials: "include"`를 사용하고, Access Token을 Authorization header에 추가합니다. 401이 발생하면 모듈 수준 `refreshPromise`를 공유하여 동시 요청이 하나의 refresh 요청을 기다리게 하고, 성공 시 원래 요청을 재시도합니다. refresh 또는 재시도도 401이면 localStorage를 지우고 `/login`으로 이동합니다.

주요 화면 연결은 다음과 같습니다.

```text
LoginPage/SignupPage
→ authApi
→ api.js
→ SessionController/UserController

PostsPage
→ postApi.getPosts
→ PostController
→ PostService
→ PostBoard → PostList → PostListItem

PostDetailPage
→ postApi.getPost
→ PostController
→ PostService
→ PostDetailCard·CommentSection
→ like/report/comment API

ProfileEditPage/PasswordEditPage
→ userApi
→ UserController
→ UserService
```

운영 환경에서는 프론트 `VITE_API_BASE_URL=/api`와 frontend Nginx의 `/api/` proxy가 `/api/sessions` 등을 `/sessions`로 변환해 backend Nginx와 Spring Controller에 전달합니다. 개발 환경의 API base URL은 `http://localhost:8080` fallback입니다.

게시글 목록은 `PostsPage`가 page 0을 교체하고 이후 page를 append하며, `PostList`의 `IntersectionObserver`가 다음 페이지를 요청합니다. `AbortController`는 목록·상세·수정·프로필 조회의 unmount 또는 대상 변경 시 요청을 취소합니다. Mutation에는 공통 취소 흐름이 없습니다.

### 18.6 migration·테스트·배포 지도

Profile별 기준은 다음과 같습니다.

- local: H2, `ddl-auto=create`, `data.sql` 실행, Flyway 비활성화
- test: local profile 기반, Redis view count 비활성화, `DatabaseViewCountUpdater` 사용
- prod: MySQL/RDS, `ddl-auto=validate`, Flyway 활성화, 환경변수 기반 설정

Migration은 `B3__current_schema.sql`이 새 DB의 baseline이고, V1에서 legacy counter를 정리할 기반을 만들고, V2에서 `users.auth_version`, V3에서 `post_view_counts`, V4에서 `post_counters.view_count`, V5에서 `posts.is_fixed` 제거를 담당합니다. 따라서 B3 파일만 읽어 최종 schema라고 설명하지 않고, 현재 최종 구조는 B3와 V1~V5의 적용 결과로 설명합니다.

백엔드 검증 명령은 `./gradlew test`, `./gradlew redisTest`, `./gradlew mysqlTest`, `./gradlew check`이며 Redis/MySQL 통합 테스트는 Docker가 필요합니다. `check`는 일반 테스트·JaCoCo 검증·Redis/MySQL task를 포함합니다. 프론트는 `npm run lint`와 `npm run build`가 CI 검증 범위이며, Jest/Vitest/Playwright/Cypress 등 자동화된 프론트 테스트는 현재 없습니다.

배포는 backend/frontend 각각 Docker image를 만들고, blue·green container와 Nginx upstream을 전환하는 방식입니다. GitHub Actions는 backend에서 `./gradlew clean check --no-daemon`, frontend에서 `npm ci`, `npm run lint`, `npm run build`를 수행하고, 선택적으로 AWS OIDC·SSM을 통해 deploy script를 실행합니다. 실제 RDS, Docker host, SSM, GHCR, TLS와 현재 production `.env`는 저장소만으로 확인할 수 없습니다.

## 19. 2026-08-06 이후 학습 문서 구조 변경

사용자는 기존 문서를 파일별·전체 코드 중심으로 읽으면서 각 코드의 문법, 선언 위치,
호출자, 인자 출처, 반환값 사용처를 기억하기 어려웠습니다. 기존 문서는 인수인계와 코드
추적에는 유용하지만, 초보자가 처음부터 실행 흐름을 학습하는 주교재로는 정보가 한 번에
너무 많다는 점을 확인했습니다.

따라서 **현재 1~7번 문서는 우선 기존 내용을 유지하고, 다음에 새로 작성하는 학습 문서부터
요청 하나·실행 흐름 하나 중심의 학습 구조를 사용합니다.** 이 절의 규칙은 이전의
파일별 전체 코드 배치 규칙보다 이후 문서의 학습 본문 구성에 우선합니다. 기존 전체 원문과
정확성 규칙은 삭제하지 않으며, 학습자가 한 번에 모두 읽어야 하는 본문과 나중에 대조하는
원문 보관 영역을 분리합니다.

### 19.1 새 문서의 기본 단위

문서 하나는 가능한 한 하나의 사용자 동작 또는 하나의 backend 실행 흐름을 완성합니다.
파일을 먼저 나열하지 않고 HTTP 요청·scheduler 작업·애플리케이션 시작 중 하나를 진입점으로
정합니다.

예시:

```text
사용자 로그아웃
→ frontend AppHeader
→ authApi.logout
→ api.request
→ DELETE /sessions
→ Spring Security 공개 endpoint 확인
→ SessionOriginInterceptor
→ SessionController.deleteSession
→ SessionService.deleteSession
→ AuthSession revoke
→ 만료 Cookie response
```

한 문서에서 위 흐름을 끝까지 연결한 뒤 다음 흐름으로 이동합니다. `RequestLogInterceptor`
같이 같은 요청에 함께 실행되는 구성요소는 흐름 안에서 필요한 시점에 설명하고, 단순히
package가 같다는 이유로 먼저 설명하지 않습니다.

### 19.2 학습 문서의 고정 순서

새 문서는 다음 순서를 사용합니다.

1. **이번 문서의 목표**: 어떤 사용자 동작 또는 요청을 이해하는지 한 문장으로 적습니다.
2. **시작 전 최소 개념**: 이번 흐름에 꼭 필요한 Java·Spring·React 개념만 짧게 설명합니다.
3. **전체 실행 지도**: frontend 입력부터 backend response 또는 scheduler 종료까지 먼저 보여줍니다.
4. **현재까지 본 개념 목록**: 이전 문서의 개념을 한 줄로 복습하고, 새 개념을 표시합니다.
5. **실제 코드 구간**: 한 번에 method 하나 또는 이해 가능한 짧은 코드 구간만 보여줍니다.
6. **구간 바로 아래 설명**: 문법, 선언 위치, 생성·주입 주체, 호출자, 실행 시점, 인자 출처, 내부 호출, 반환값 도착 위치, 상태 변경, 예외 이동, 사용 이유를 설명합니다.
7. **중간 흐름 확인**: 방금 코드가 전체 지도에서 어느 단계인지 한 줄로 다시 연결합니다.
8. **다음 코드 구간**: 앞 구간의 반환값·등록 결과·변경된 상태가 다음 파일에서 어떻게 사용되는지 이어갑니다.
9. **흐름 종료 요약**: 정상·실패 흐름과 핵심 객체의 최종 상태를 정리합니다.
10. **이해 checkpoint**: 선언 위치, 호출자, 인자, 반환값 사용처를 짧게 확인하고 이해한 흐름을 기록합니다.
11. **원문 대조 영역**: 학습 본문에서 설명한 파일의 전체 현재 원문을 파일당 한 블록으로 별도 보관합니다. 전체 원문은 누락하지 않지만, 학습자는 처음부터 모든 줄을 한 번에 암기하려고 하지 않습니다.

### 19.3 모든 코드 구간에서 반드시 추적할 항목

코드 한 줄을 설명할 때 결과만 적지 않습니다. 다음 정보를 같은 구간 아래에 둡니다.

- 선언 파일·package·class·method 또는 field
- `private`, `final`, `static`, `implements`, generic, lambda, 형변환 등 Java 문법의 현재 역할
- 객체의 생성·주입 주체와 Bean lifecycle
- 호출자와 호출되는 실제 위치
- 매개변수의 출처와 호출 전 변환 과정
- 메서드 내부의 Repository·Provider·framework 호출 순서
- 반환값의 타입, 저장되는 변수, 다음 사용 위치
- DB·Redis·Cookie·HTTP response·SecurityContext에 생기는 변화
- `throw`, `throws`, `orElseThrow`, Handler·Filter·Interceptor를 통한 예외 경로
- 이 구현이 필요한 이유와 코드가 없을 때의 실행 차이

framework가 호출하는 callback은 프로젝트 source의 직접 호출 위치만 찾지 않고,
`@Configuration`·`@Bean`·`@Component`·`implements`·registry 등록·Spring lifecycle을
연결해 “누가 언제 호출하는가”를 설명합니다. 직접 호출 코드가 없는 경우에는 그 사실과
framework 내부의 호출 주체를 명확히 표시합니다.

### 19.4 반복 기억을 위한 개념 기록

문서마다 새로 등장한 class·method·field·상수는 다음 형식으로 기록합니다.

```text
이름: SessionOriginInterceptor
선언: backend/config/SessionOriginInterceptor.java
생성·주입: @Component Bean, InterceptorConfig 생성자에 주입
호출: Spring MVC HandlerExecutionChain이 preHandle 호출
입력: HttpServletRequest, HttpServletResponse, handler
반환값 사용: Spring MVC가 true/false로 Controller 진행 여부 결정
역할: Cookie session endpoint의 Origin 검사
다시 사용되는 위치: InterceptorConfig, 세션 요청 흐름
```

이미 본 개념은 “앞에서 봤다”로 끝내지 않고 현재 흐름에서 어떤 값과 역할로 다시 쓰이는지
한 줄 복습합니다. 사용자가 “이게 뭐였지?”라고 질문한 개념은 학습 문서의 해당 위치에
설명을 보강하고, 같은 질문이 반복되지 않도록 이 개념 기록과 인수인계 문서에도 반영합니다.

### 20.1 통합 문서의 학습 순서

```text
로그인
→ 보호 요청과 Access Token
```

각 흐름은 목표 → 최소 선행 개념 → 전체 실행 지도 → 짧은 코드 구간 → 선언 위치·호출자·

파일을 한 번에 암기하지 않고, 앞 흐름의 checkpoint를 확인한 뒤 다음 흐름으로 이동합니다.

### 20.2 인증 파일 진행 상태

- 통합 문서 작성은 기존 파일을 다시 연결한 작업이므로 새로운 source 파일 완료로 계산하지 않습니다.

- 인증 통합 흐름의 이해 상태는 별도 checkpoint로 기록합니다.
- 다음 AI는 기존 04~08 문서를 주 학습 순서로 다시 제시하지 않고 통합 문서를 먼저 안내합니다.

### 20.3 현재 확인하지 않은 실행 결과

통합 문서는 backend/frontend source와 기존 테스트 목록을 정적으로 대조해 작성했습니다.
애플리케이션 실행, frontend browser 흐름, backend test, Redis/MySQL lock, 실제 운영 Cookie
path와 proxy 동작은 이 문서 작성 중 실행하지 않았습니다. 코드로 확인한 사실과 실행이
필요한 사항을 답변에서 구분합니다.

## 21. 2026-08-06 9번 문서 이후 적용할 형식

인증 통합 문서는 사용자가 전체 인증 흐름을 다시 잡기 위한 예외적인 요약·지도 문서였습니다.
사용자는 9번 문서부터는 실행 흐름은 새로 구성하되, 기존 파일별 코드 설명 양식은 유지해
달라고 결정했습니다. 따라서 이후 문서에는 다음 두 기준을 동시에 적용합니다.

### 21.1 새로 설계하는 부분: 실행 흐름과 파일 순서

- 문서의 시작점은 파일 목록이 아니라 사용자 동작·HTTP 요청·scheduler 작업 중 하나로 정합니다.
- 어떤 파일을 먼저 읽을지는 실제 실행 순서와 값의 의존 관계를 기준으로 정합니다.
- 하나의 문서 안에서 관련 파일을 실행 흐름 순서대로 묶습니다.
- 각 파일을 독립적으로 설명하되, 앞 파일의 반환값·변경 상태가 다음 파일의 어떤 입력이 되는지 연결합니다.
- 문서 처음에는 목표·선행 개념·전체 실행 지도를 짧게 제시합니다.
- 문서 마지막에는 정상 흐름·실패 흐름·checkpoint와 다음 파일을 기록합니다.

### 21.2 유지하는 부분: 기존 파일별 코드 설명 양식

9번 문서부터 각 파일은 다음 순서를 유지합니다.

```text
[현재 파일의 실제 절대 경로와 책임]
→ [현재 파일의 전체 원문 코드 블록 1개]
→ [설명할 코드 일부를 원문 순서대로 다시 제시]
→ [그 코드 일부 바로 아래 상세 설명]
→ [다음 코드 일부]
→ [그 코드 일부 바로 아래 상세 설명]
→ [파일의 호출자·반환값·예외·다음 흐름 정리]
→ [다음 파일의 전체 원문 코드 블록 1개]
```

각 파일의 전체 원문은 한 문서 안에서 한 번만 보여줍니다. 서로 다른 파일의 전체 원문을
하나의 코드 블록에 섞지 않습니다. 전체 원문 뒤의 코드 일부는 설명 대상 위치를 다시
확인하기 위한 것이며, 설명은 반드시 그 코드 일부 바로 아래에 둡니다.

### 21.3 기존 양식에서 반드시 유지할 세부 규칙

- 실제 현재 소스의 원문을 임의로 생략하지 않습니다.
- `package`와 `import` 줄에는 학습 주석을 달지 않습니다.
- 코드 일부마다 선언 파일·class·method·field와 접근 제한자를 적습니다.
- 메서드의 호출자·호출 위치·실행 시점·매개변수 출처를 적습니다.
- 반환값의 타입·저장 변수·다음 사용 위치를 적습니다.
- `private final` field의 생성·주입 주체와 사용 위치를 적습니다.
- `implements`, annotation, generic, lambda, 형변환, method reference와 같은 새 문법을 처음 등장한 위치에서 설명합니다.
- Spring·Servlet·React framework가 호출하는 callback은 직접 호출 코드가 없다는 사실과 framework 호출 주체를 적습니다.
- DB·Redis·Cookie·HTTP response·SecurityContext가 변경되는지 적습니다.
- 정상 흐름·실패 흐름·예외 Handler/Filter/Interceptor 이동을 모두 적습니다.
- 문서 형식만 바꾼 것은 파일 진행도에 포함하지 않습니다.

따라서 **9번 이후 문서는 “흐름 중심으로 파일 순서를 새로 구성하되, 파일 안의 전체 코드 →
코드 일부 → 바로 아래 설명 양식은 유지”**합니다. 04-08 인증 통합 문서의 짧은 코드만
사용한 형식을 9번 이후 문서의 기본 양식으로 삼지 않습니다.

## 22. 2026-08-06 9번 문서의 최우선 기준: 사용자 이해

9번 문서부터는 학습 대상 파일 수나 문서 분량보다 사용자가 실제 실행 흐름을 이해하는지를
우선합니다. 코드를 많이 포함하는 것이 목표가 아니며, 사용자가 각 단계에서 다음 질문에
답할 수 있어야 다음 단계로 이동합니다.

- 이 코드의 선언 위치와 타입은 무엇인가?
- 이 객체나 값은 어디에서 생성·주입·전달되었는가?
- 누가 이 method를 호출하는가?
- 매개변수의 실제 값은 앞 단계에서 어떻게 만들어졌는가?
- 반환값이나 변경된 상태는 다음 어느 코드에서 사용하는가?
- 이 코드가 실행되는 시점은 시작·HTTP 요청·Scheduler 중 언제인가?
- 정상 흐름과 실패 흐름에서 DB·Redis·response가 어떻게 달라지는가?
- 이 코드를 사용하지 않으면 다음 단계가 어떻게 달라지는가?

### 22.1 이해 중심 작성 원칙

- 한 번에 새 핵심 개념을 너무 많이 도입하지 않고, 필요한 개념부터 순서대로 설명합니다.
- 이전 문서에서 본 class·method·field도 현재 흐름에서 어떤 역할로 다시 사용되는지 짧게 복습합니다.
- 코드 일부 바로 아래에 문법 설명과 실행 흐름 설명을 함께 둡니다.
- framework가 호출하는 코드는 직접 호출자가 없다는 사실, 실제 호출 주체, 호출 시점을 반드시 적습니다.
- 코드 한 줄의 결과만 설명하지 않고 값의 출처와 다음 전달 위치까지 연결합니다.
- 한 파일 설명이 끝날 때 `선언 위치·호출자·입력·반환값·다음 사용처` checkpoint를 둡니다.
- 사용자가 checkpoint를 이해하지 못하면 다음 파일로 넘어가지 않고 해당 흐름을 현재 문서 안에서 다시 설명합니다.
- 문서의 실제 진행 상태는 파일 확인 진행도와 사용자 흐름 이해 checkpoint를 분리합니다.

### 22.2 9번 조회수 문서의 이해 순서

9번 문서는 다음 순서로 작성하되, 각 단계의 checkpoint를 확인한 뒤 이동합니다.

```text
게시글 상세 화면이 왜 조회수 method를 호출하는가
→ PostService의 baseline 값은 어디에서 오는가
→ ViewCountUpdater interface가 필요한 이유는 무엇인가
→ Redis 구현이 실제로 어떤 key와 값을 받는가
→ Lua가 한 번의 요청에서 어떤 순서로 값을 바꾸는가
→ 증가 결과가 응답으로 어떻게 돌아가는가
→ Scheduler는 왜 별도 흐름인가
→ snapshot과 dirty를 왜 함께 사용하는가
→ RDS 저장 후 dirty를 언제 제거하는가
→ Redis가 꺼졌거나 실패했을 때 무엇이 달라지는가
```

각 단계 안에서는 기존 형식인 `파일 전체 코드 1회 → 코드 일부 → 바로 아래 설명`을
유지하지만, 전체 코드를 먼저 읽고 암기하도록 요구하지 않습니다. 먼저 해당 파일을
읽는 이유와 앞뒤 연결을 설명한 뒤 원문을 대조합니다.

## 27. 2026-08-06 이해 확인 문제의 모범 답안 규칙

사용자가 문서의 이해 확인·checkpoint 문제 답을 요청했습니다. 앞으로 새 문서에는 질문만
두지 않고 같은 문서에 `모범 답안` 절을 함께 작성합니다.

- 답안은 실제 현재 source의 선언·호출·반환·예외 흐름에 근거합니다.
- 질문 바로 아래 또는 해당 checkpoint 바로 다음에 답안을 둡니다.

## 34. 2026-08-07 Refresh Token 07장 작성 완료

### 문서에 연결한 실제 흐름
