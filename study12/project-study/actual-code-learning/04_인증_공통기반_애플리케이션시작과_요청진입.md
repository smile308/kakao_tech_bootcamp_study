# 04장. 인증 공통 기반: 애플리케이션 시작과 HTTP 요청 진입

이 장은 로그인·Access Token·Refresh Token·로그아웃의 업무 로직을 반복해서 설명하는 장이 아닙니다. 네 기능이 실행되기 전에 Spring이 어떤 객체를 만들고, HTTP 요청이 어떤 순서로 Filter·Security·MVC Interceptor를 통과하는지 먼저 확정합니다.

이 공통 기반을 이해하면 다음 장에서 `SessionController`나 `JwtAuthenticationFilter`를 볼 때 “누가 이 method를 호출하는가”, “이 코드가 Controller보다 먼저 실행되는가”, “이 오류가 어느 응답 경계에서 끝나는가”를 추측하지 않아도 됩니다.

> 이 파일이 재구성된 새 04장의 기준 문서입니다. 계획에는 기존 `04_인증_로그인_자격증명과_세션생성.md`를 임시 보존한다고 적었지만, 현재 작업 트리에서는 그 파일이 이미 삭제 상태입니다. 로그인 전체 흐름은 새 05장에 작성하고, 기존 Access Token 05장과 06~08은 새 문서가 완성될 때까지 보존합니다.

## 이 장의 실행 지도

~~~~text
애플리케이션 시작
→ SpringdatajpaApplication.main
→ SpringApplication.run
→ profile YAML 병합
→ @Component/@Configuration/@Bean 객체 생성
→ SecurityFilterChain 등록
→ MVC Interceptor 등록
→ @EnableScheduling scheduler 등록

HTTP 요청
→ Servlet request/response 생성
→ Spring Security Filter chain
→ Security 인가 규칙
→ DispatcherServlet
→ MVC Interceptor preHandle
→ Controller
→ Service/Repository
→ Controller 반환값·response header
→ MVC Interceptor afterCompletion
~~~~

실제 Spring MVC에서는 HandlerInterceptor가 DispatcherServlet의 Controller 호출 전후에 실행됩니다. Security Filter는 그보다 앞선 Servlet filter 단계에 있으므로, Filter가 직접 응답을 끝내면 MVC Interceptor와 Controller까지 도달하지 않을 수 있습니다.

## 실행 순서와 코드 읽기 순서

### 실제 실행 순서

사용자가 보낸 요청은 대략 다음 경계를 지나갑니다.

1. Servlet container가 `HttpServletRequest`, `HttpServletResponse`를 만듭니다.
2. Spring Security Filter chain이 먼저 실행됩니다.
3. Filter가 요청을 계속 넘기면 Security의 인증·인가 규칙이 적용됩니다.
4. DispatcherServlet이 Controller를 찾기 전후에 MVC Interceptor가 실행됩니다.
5. Controller가 Service를 호출합니다.
6. Service가 Entity·Repository를 통해 업무를 처리합니다.
7. Controller 반환값은 JSON body가 되고, `HttpServletResponse`에 추가한 header와 함께 전송됩니다.
8. MVC 요청이 끝나면 `afterCompletion`이 실행됩니다.

### 코드를 읽는 순서

실행 시점과 선언된 파일의 순서는 다르므로, 이 장에서는 다음 순서로 읽습니다.

1. 애플리케이션 시작 class와 profile property
2. SecurityFilterChain을 만드는 설정
3. MVC Interceptor를 등록하는 설정
4. 등록된 RequestLogInterceptor
5. CORS property를 읽는 Provider와 MVC CORS 설정
6. Cookie session의 Origin을 실제로 차단하는 Interceptor
7. Filter·Interceptor가 직접 응답을 만드는 ErrorResponseWriter
8. Controller까지 도달한 예외를 처리하는 GlobalExceptionHandler의 위치

## 1. 애플리케이션 시작이 Bean과 scheduler를 등록한다

### 실제 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/SpringdatajpaApplication.java`

### 코드 원문

~~~~java
package kr.adapterz.springdatajpa;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.context.properties.ConfigurationPropertiesScan;
import org.springframework.scheduling.annotation.EnableScheduling;

@SpringBootApplication
@ConfigurationPropertiesScan
@EnableScheduling
public class SpringdatajpaApplication {

    public static void main(String[] args) {
        SpringApplication.run(SpringdatajpaApplication.class, args);
    }

}
~~~~

### 코드 바로 아래 설명

- `public class SpringdatajpaApplication`은 애플리케이션의 시작 class입니다. 사용자가 HTTP 요청을 보낼 때마다 이 class가 다시 만들어지는 것이 아닙니다.
- `main`은 Java 프로그램의 시작 method입니다. `SpringApplication.run(...)`이 Spring ApplicationContext를 만들고, classpath의 `@Component`, `@Service`, `@Configuration`, `@Bean`을 찾아 객체를 등록합니다.
- `@SpringBootApplication`은 Spring Boot 설정, 자동 설정, component scan을 묶은 annotation입니다. 이 class의 package인 `kr.adapterz.springdatajpa` 하위가 기본 scan 범위가 됩니다.
- `@ConfigurationPropertiesScan`은 `@ConfigurationProperties`가 붙은 설정 class를 scan합니다. 현재 조회수 설정의 `ViewCountProperties`가 이 경로로 Bean이 됩니다. `@Value` property는 이 annotation이 아니라 각 생성자·field의 `@Value`가 직접 주입합니다.
- `@EnableScheduling`은 `@Scheduled`가 붙은 method를 scheduler가 주기적으로 호출할 수 있게 합니다. `AuthSessionCleanupScheduler`를 main이 직접 호출하는 것은 아닙니다.

### 이 파일이 호출·등록하는 것

`SpringApplication.run` 내부에서 다음 Bean과 설정이 만들어집니다.

- `SecurityConfig.securityFilterChain`
- `InterceptorConfig.addInterceptors`
- `WebConfig.corsConfigurer`
- `JwtAuthenticationFilter`, `SessionOriginInterceptor`, `RequestLogInterceptor` 등 `@Component`
- `AuthSessionCleanupScheduler`의 `@Scheduled` 작업

이 method들의 반환값은 main으로 돌아와 사용되는 것이 아니라 Spring ApplicationContext에 등록되어 이후 요청·scheduler 실행에 사용됩니다.

## 2. YAML profile이 인증 설정값을 채운다

### 확인할 파일

- `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/resources/application.yaml`
- `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/resources/application-local.yaml`
- `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/resources/application-prod.yaml`
- `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/test/resources/application-test.yaml`

전체 YAML과 DB·Redis 설정은 01장에서 설명했으므로, 여기서는 인증 공통 진입에 직접 연결되는 key만 실제 값과 함께 확인합니다.

### 기본 profile과 test profile 연결

~~~~yaml
# application.yaml
spring:
  profiles:
    default: local
    group:
      test:
        - local
~~~~

- 실행 profile을 따로 지정하지 않으면 `local`을 기본 profile로 사용합니다.
- 테스트가 `test` profile을 활성화하면 profile group에 의해 `local`도 함께 활성화됩니다. 따라서 `application-test.yaml`의 설정과 local 설정이 함께 적용됩니다.
- YAML의 profile 파일은 Java class를 호출하지 않습니다. Spring Boot가 시작할 때 property source를 병합하고, 그 결과를 `@Value`나 `@ConfigurationProperties`에 주입합니다.

### JWT·Cookie·Origin·scheduler 설정

~~~~yaml
# application.yaml
jwt:
  access-expiration-millis: ${JWT_ACCESS_EXPIRATION_MILLIS:600000}
  refresh-expiration-millis: ${JWT_REFRESH_EXPIRATION_MILLIS:10800000}
  refresh-session-cleanup-interval-millis: ${JWT_REFRESH_SESSION_CLEANUP_INTERVAL_MILLIS:3600000}

# application-local.yaml
jwt:
  secret: ${JWT_SECRET:default-development-jwt-secret-key-must-be-at-least-32-chars-change-me}
  refresh-cookie-secure: false
  refresh-cookie-path: /sessions

cors:
  allowed-origins: http://localhost:5500,http://127.0.0.1:5500,http://localhost:5173,http://127.0.0.1:5173

# application-prod.yaml
jwt:
  secret: ${JWT_SECRET}
  refresh-cookie-secure: ${JWT_REFRESH_COOKIE_SECURE:true}
  refresh-cookie-path: /api/sessions

cors:
  allowed-origins: ${CORS_ALLOWED_ORIGINS}
~~~~

### 코드 바로 아래 설명

- `${KEY:default}`는 환경변수나 외부 property `KEY`가 있으면 그 값을 사용하고, 없으면 colon 뒤 기본값을 사용합니다. 예를 들어 `JWT_ACCESS_EXPIRATION_MILLIS`가 없으면 `600000` milliseconds를 사용합니다.
- `${JWT_SECRET}`처럼 기본값이 없는 placeholder는 운영 환경에서 반드시 값을 제공해야 합니다. 값이 없으면 Bean 생성 또는 property 해석 단계에서 애플리케이션 시작이 실패할 수 있습니다.
- `jwt.secret`는 `JwtProvider` 생성자에 들어가 `SecretKey`로 바뀝니다. `jwt.refresh-expiration-millis`는 `RefreshTokenProvider`와 `RefreshCookieProvider`가 각각 주입받아 DB session 만료와 Cookie max-age의 기준으로 사용합니다.
- local의 `refresh-cookie-secure: false`는 HTTP 개발 환경에서 Cookie를 전송할 수 있게 하고, prod의 기본값 `true`는 HTTPS Cookie를 의도합니다. `refresh-cookie-path`는 browser가 Cookie를 보낼 URL path이며 발급·만료 Cookie에 같은 path가 필요합니다.
- `cors.allowed-origins`는 comma-separated 문자열입니다. `CorsOriginProvider`가 시작 시 comma로 나누고 trim한 뒤 Set으로 바꿉니다.
- `refresh-session-cleanup-interval-millis`는 `AuthSessionCleanupScheduler`가 첫 작업과 다음 작업 사이에 사용할 시간입니다. 이 scheduler의 실제 query는 08-1장에서 읽습니다.

### 현재 코드에서 확인되는 profile 주의점

- 운영 Cookie path는 `/api/sessions`이지만 backend Controller mapping은 `/sessions`입니다. reverse proxy가 `/api` prefix를 어떻게 전달하는지는 배포 설정에서 별도로 확인해야 하며, YAML만으로 proxy rewrite를 보장하지 않습니다.
- `application-test.yaml`은 Redisson 자동 설정을 제외하고 view count를 비활성화합니다. 인증 공통 설정을 바꾸는 파일은 아니지만, 테스트 ApplicationContext가 Redis 없이 시작되는 이유와 연결됩니다.

## 3. `SecurityConfig`가 Security Filter chain과 공개 범위를 만든다

### 실제 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/config/SecurityConfig.java`

### 코드 원문

~~~~java
package kr.adapterz.springdatajpa.config;

import kr.adapterz.springdatajpa.auth.JwtAuthenticationFilter;
import kr.adapterz.springdatajpa.exception.ApiErrorCode;
import lombok.RequiredArgsConstructor;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.authentication.AuthenticationManager;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.authentication.configuration.AuthenticationConfiguration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.config.annotation.web.configurers.AbstractHttpConfigurer;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.authentication.UsernamePasswordAuthenticationFilter;

@Configuration
@EnableWebSecurity
@RequiredArgsConstructor
public class SecurityConfig {

    private final JwtAuthenticationFilter jwtAuthenticationFilter;
    private final ErrorResponseWriter errorResponseWriter;

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
                .cors(Customizer.withDefaults())

                .csrf(AbstractHttpConfigurer::disable)

                .sessionManagement(session -> session
                        .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
                )

                .exceptionHandling(exception -> exception
                        .authenticationEntryPoint((request, response, authException) -> {
                            errorResponseWriter.write(response, org.springframework.http.HttpStatus.UNAUTHORIZED, ApiErrorCode.UNAUTHORIZED);
                        })
                        .accessDeniedHandler((request, response, accessDeniedException) -> {
                            errorResponseWriter.write(response, org.springframework.http.HttpStatus.FORBIDDEN, ApiErrorCode.FORBIDDEN);
                        })
                )

                .authorizeHttpRequests(auth -> auth
                        .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()

                        .requestMatchers(HttpMethod.GET, "/actuator/health").permitAll()

                        .requestMatchers(HttpMethod.POST, "/users").permitAll()

                        .requestMatchers(
                                HttpMethod.POST,
                                "/sessions",
                                "/sessions/refresh"
                        ).permitAll()

                        .requestMatchers(HttpMethod.DELETE, "/sessions").permitAll()

                        .anyRequest().authenticated()
                )

                .addFilterBefore(
                        jwtAuthenticationFilter,
                        UsernamePasswordAuthenticationFilter.class
                );

        return http.build();
    }

    @Bean
    public AuthenticationManager authenticationManager(AuthenticationConfiguration configuration) throws Exception {
        return configuration.getAuthenticationManager();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}
~~~~

### 코드 바로 아래 설명: class와 Bean

- `@Configuration`은 이 class가 Spring 설정을 제공한다는 뜻입니다. `@EnableWebSecurity`는 Spring Security web 설정을 활성화합니다.
- `@RequiredArgsConstructor`는 두 `final` field를 받는 생성자를 Lombok으로 생성합니다. `JwtAuthenticationFilter`와 `ErrorResponseWriter` Bean은 Spring이 생성자에 주입합니다.
- `@Bean` method가 반환한 `SecurityFilterChain`, `AuthenticationManager`, `PasswordEncoder`는 ApplicationContext에 등록됩니다. Controller나 Service가 요청마다 이 method를 다시 호출하지 않습니다.
- `throws Exception`은 `HttpSecurity` build나 `AuthenticationConfiguration` 조회 과정에서 checked exception이 발생할 수 있음을 method 선언에 적은 것입니다. 실제 exception 처리 방식은 Spring이 Bean 생성 단계에서 담당합니다.

### 코드 바로 아래 설명: CORS·CSRF·stateless

- `.cors(Customizer.withDefaults())`는 Spring Security Filter 단계에서 CORS 처리를 활성화합니다. 실제 허용 Origin·method·header는 뒤에서 보는 `WebConfig`의 MVC CORS 설정과 연결됩니다.
- `.csrf(AbstractHttpConfigurer::disable)`는 Spring Security 기본 CSRF token 검사를 끕니다. 현재 프로젝트는 Cookie session endpoint에 `SessionOriginInterceptor`의 Origin 검사를 별도로 두었지만, 이것이 모든 CSRF 상황을 자동으로 해결한다고 볼 수는 없습니다.
- `SessionCreationPolicy.STATELESS`는 Spring Security가 server HTTP session에 인증 결과를 저장하지 않도록 합니다. 보호 요청마다 JWT Filter가 token을 검증해 현재 요청의 `SecurityContext`를 만듭니다.

### 코드 바로 아래 설명: 오류 handler

- `authenticationEntryPoint`는 보호 endpoint에 인증 정보가 없을 때 Spring Security가 호출합니다. 401 `UNAUTHORIZED`를 `ErrorResponseWriter`에 전달합니다.
- `accessDeniedHandler`는 인증은 통과했지만 권한이 부족할 때 호출되어 403 `FORBIDDEN`을 기록합니다.
- 두 lambda는 Controller를 호출하는 일반 업무 callback이 아니라 Security filter chain 내부에서 response를 끝내는 callback입니다. 따라서 이 경로의 오류는 `GlobalExceptionHandler`까지 가지 않습니다.

### 코드 바로 아래 설명: 공개 endpoint와 Filter 위치

- `requestMatchers(HttpMethod, path)`는 HTTP method와 path가 모두 일치해야 합니다. `POST /sessions`와 `POST /sessions/refresh`는 Access Token 없이 시작해야 하므로 공개로 허용됩니다.
- `DELETE /sessions`도 Refresh Cookie를 이용한 logout endpoint이므로 Security 인증 요구를 면제합니다. Cookie Origin 검사는 별도로 적용됩니다.
- `OPTIONS /**`는 browser CORS preflight가 인증 없이 통과하기 위한 공개 규칙입니다.
- `anyRequest().authenticated()`는 위 목록에 없는 모든 요청에 인증이 필요하다는 기본 규칙입니다.
- `addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)`는 사용자 정의 `JwtAuthenticationFilter`를 Spring Security가 제공하는 기준 Filter class 앞에 등록합니다. 두 번째 class는 프로젝트가 선언한 class가 아닙니다.

### 코드 바로 아래 설명: 인증 Bean의 실제 사용처

- `authenticationManager` Bean은 로그인 시 `SessionService.createSession`이 `authenticate(...)`를 호출할 때 사용합니다. 내부에서 `CustomUserDetailsService`와 password 검증이 연결됩니다.
- `passwordEncoder` Bean은 회원가입 password hash와 비밀번호 변경 hash 생성, Spring Security password 비교에 사용됩니다.
- 두 Bean의 업무 흐름은 새 05장 로그인 문서에서 호출 위치와 함께 읽습니다.

## 4. MVC Interceptor를 등록하고 요청 로그를 남긴다

### 4.1 등록 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/config/InterceptorConfig.java`

~~~~java
package kr.adapterz.springdatajpa.config;

import lombok.RequiredArgsConstructor;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.InterceptorRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
@RequiredArgsConstructor
public class InterceptorConfig implements WebMvcConfigurer {

    private final RequestLogInterceptor requestLogInterceptor;
    private final SessionOriginInterceptor sessionOriginInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(requestLogInterceptor)
                .addPathPatterns("/**");

        registry.addInterceptor(sessionOriginInterceptor)
                .addPathPatterns("/sessions", "/sessions/refresh");
    }
}
~~~~

### 코드 바로 아래 설명

- `WebMvcConfigurer`는 Spring MVC 설정 callback을 제공하는 interface입니다. `addInterceptors`는 요청마다 호출되지 않고 MVC 설정 초기화 때 호출됩니다.
- `registry.addInterceptor(requestLogInterceptor).addPathPatterns("/**")`는 모든 MVC path에 RequestLogInterceptor를 등록합니다.
- `sessionOriginInterceptor`는 `/sessions`, `/sessions/refresh` path에 등록됩니다. `DELETE /sessions`도 path가 `/sessions`이므로 registry 대상입니다. 실제 HTTP method 조합을 다시 확인하는 것은 Interceptor의 `isCookieSessionRequest`입니다.
- 등록 순서가 request log → Origin interceptor이므로, session endpoint가 Origin에서 거부되어 Controller에 도달하지 않아도 request log의 시작과 completion callback이 연결될 수 있습니다.

### 4.2 요청 로그 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/config/RequestLogInterceptor.java`

~~~~java
package kr.adapterz.springdatajpa.config;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Component;
import org.springframework.web.servlet.HandlerInterceptor;

@Slf4j
@Component
public class RequestLogInterceptor implements HandlerInterceptor {

    private static final String START_TIME = "startTime";

    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler
    ) {
        request.setAttribute(START_TIME, System.currentTimeMillis());

        log.info("[REQUEST] {} {}", request.getMethod(), request.getRequestURI());

        return true;
    }

    @Override
    public void afterCompletion(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler,
            Exception ex
    ) {
        Long startTime = (Long) request.getAttribute(START_TIME);
        long elapsedTime = System.currentTimeMillis() - startTime;

        log.info(
                "[RESPONSE] {} {} status={} time={}ms",
                request.getMethod(),
                request.getRequestURI(),
                response.getStatus(),
                elapsedTime
        );
    }
}
~~~~

### 코드 바로 아래 설명

- `@Slf4j`는 Lombok이 `log` logger field를 생성합니다. source에 logger를 직접 선언하지 않아도 `log.info`를 호출할 수 있는 이유입니다.
- `HandlerInterceptor.preHandle`은 Controller 호출 전, `afterCompletion`은 요청 처리가 끝난 뒤 Spring MVC가 호출하는 callback입니다.
- `request.setAttribute(START_TIME, ...)`는 현재 request 객체에 시작 시각을 저장합니다. `afterCompletion`이 같은 request에서 값을 꺼내므로 요청별 시간이 섞이지 않습니다.
- `getAttribute`의 반환 타입은 `Object`이므로 앞에서 저장한 `Long`으로 `(Long)` 형변환합니다.
- `log.info`의 `{}`는 SLF4J placeholder이고 뒤의 argument가 왼쪽부터 삽입됩니다.
- `return true`는 이 Interceptor가 요청을 막지 않고 다음 MVC 단계로 진행시키라는 뜻입니다. 인증 성공이나 권한 통과를 의미하지 않습니다.
- `Exception ex`는 completion callback에 전달되지만 현재 source에서는 사용하지 않습니다. 따라서 현재 response log는 예외 종류가 아니라 method·URI·status·elapsed time을 기록합니다.
- 현재 `afterCompletion`은 `START_TIME` attribute가 없을 때를 별도로 처리하지 않습니다. 정상적으로 `preHandle`이 먼저 실행된 같은 MVC 요청이라는 전제에서 `Long`을 꺼내 elapsed time을 계산합니다.

### 이 Interceptor가 호출되는 위치

~~~~text
RequestLogInterceptor.preHandle
→ startTime 저장
→ [REQUEST] 로그
→ 다음 Interceptor/Controller/Service/응답
→ RequestLogInterceptor.afterCompletion
→ status·elapsed time 로그
~~~~

Security Filter가 MVC 진입 전에 직접 401을 끝내면 이 Interceptor까지 도달하지 않을 수 있습니다. 반대로 RequestLogInterceptor가 먼저 실행된 뒤 SessionOriginInterceptor가 `false`를 반환하면 Controller는 실행되지 않아도 completion log가 남을 수 있습니다.

## 5. CORS Origin 목록을 만들고 MVC 규칙에 연결한다

### 5.1 Origin property를 Set으로 바꾸는 Provider

실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/config/CorsOriginProvider.java`

~~~~java
package kr.adapterz.springdatajpa.config;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

import java.util.Arrays;
import java.util.Set;
import java.util.stream.Collectors;

@Component
public class CorsOriginProvider {

    private final Set<String> allowedOrigins;

    public CorsOriginProvider(
            @Value("${cors.allowed-origins}") String allowedOrigins
    ) {
        this.allowedOrigins = Arrays.stream(allowedOrigins.split(","))
                .map(String::trim)
                .filter(origin -> !origin.isEmpty())
                .collect(Collectors.toUnmodifiableSet());
    }

    public String[] getAllowedOrigins() {
        return allowedOrigins.toArray(String[]::new);
    }

    public boolean isAllowed(String origin) {
        return origin != null && allowedOrigins.contains(origin);
    }
}
~~~~

### 코드 바로 아래 설명

- `@Component`가 이 class를 Bean으로 등록하므로 constructor는 애플리케이션 시작 때 한 번 호출됩니다. HTTP 요청마다 YAML을 다시 읽지 않습니다.
- `@Value("${cors.allowed-origins}")`는 Java parameter 이름이 아니라 placeholder key를 기준으로 property를 주입합니다.
- `split(",")`가 comma-separated 문자열을 배열로 나눕니다. `String::trim`은 각 문자열의 앞뒤 공백을 제거하는 method reference입니다.
- `filter(origin -> !origin.isEmpty())`는 빈 항목을 제거하는 lambda입니다. `Collectors.toUnmodifiableSet()`은 중복을 제거하고 내부 Set을 수정할 수 없게 만듭니다.
- `getAllowedOrigins()`는 내부 Set을 그대로 반환하지 않고 String 배열로 변환합니다. WebConfig의 `allowedOrigins`가 배열을 받기 때문입니다.
- `isAllowed`는 `Origin`이 null이 아니면서 Set에 정확히 포함되는 경우만 true입니다. scheme·host·port가 다르면 다른 Origin입니다. path는 Origin의 비교 대상이 아닙니다.

### 5.2 Web MVC CORS 규칙

실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/config/WebConfig.java`

~~~~java
package kr.adapterz.springdatajpa.config;

import lombok.RequiredArgsConstructor;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.CorsRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
@RequiredArgsConstructor
public class WebConfig {

    private final CorsOriginProvider corsOriginProvider;

    @Bean
    public WebMvcConfigurer corsConfigurer() {
        return new WebMvcConfigurer() {
            @Override
            public void addCorsMappings(CorsRegistry registry) {
                registry.addMapping("/**")
                        .allowedOrigins(corsOriginProvider.getAllowedOrigins())
                        .allowedMethods("GET", "POST", "PATCH", "DELETE", "OPTIONS")
                        .allowedHeaders("*")
                        .allowCredentials(true);
            }
        };
    }
}
~~~~

### 코드 바로 아래 설명

- `@Bean corsConfigurer`가 반환하는 익명 `WebMvcConfigurer` 객체를 Spring MVC가 설정 Bean으로 등록합니다. Controller가 이 method를 직접 호출하지 않습니다.
- `new WebMvcConfigurer() { ... }`는 interface를 익명 class로 구현하는 Java 문법입니다. `addCorsMappings` callback은 MVC 초기화 과정에서 호출됩니다.
- `addMapping("/**")`는 모든 MVC path에 규칙을 적용합니다.
- `allowedOrigins(...)`는 Provider가 만든 명시적 Origin 배열만 허용합니다. `allowedMethods`와 `allowedHeaders`는 browser가 허용받을 HTTP method와 header를 정합니다.
- `allowCredentials(true)`는 cross-origin fetch가 Cookie를 포함할 수 있게 하는 설정입니다. 이 때문에 `allowedOrigins("*")` 대신 실제 Origin 목록이 필요합니다.

### CORS 설정과 Origin 차단의 차이

- WebConfig는 browser가 cross-origin 요청을 처리할 수 있도록 CORS response 규칙을 등록합니다.
- 다음 `SessionOriginInterceptor`는 Cookie가 자동으로 전송되는 session endpoint가 서버의 Controller까지 진행할지 직접 판단합니다.
- 두 코드가 같은 `CorsOriginProvider`를 사용하지만 하나는 browser/CORS 규칙이고 다른 하나는 server-side 요청 차단입니다. `allowedOrigins`가 등록되었다고 해서 Interceptor의 403 판단이 자동으로 사라지는 것은 아닙니다.

## 6. Cookie session의 Origin을 MVC 단계에서 차단한다

### 실제 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/config/SessionOriginInterceptor.java`

### 코드 원문

~~~~java
package kr.adapterz.springdatajpa.config;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import lombok.RequiredArgsConstructor;
import kr.adapterz.springdatajpa.exception.ApiErrorCode;
import org.springframework.stereotype.Component;
import org.springframework.web.servlet.HandlerInterceptor;

import java.io.IOException;

@Component
@RequiredArgsConstructor
public class SessionOriginInterceptor implements HandlerInterceptor {

    private final CorsOriginProvider corsOriginProvider;
    private final ErrorResponseWriter errorResponseWriter;

    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler
    ) throws IOException {
        if (!isCookieSessionRequest(request)) {
            return true;
        }

        String origin = request.getHeader("Origin");

        if (corsOriginProvider.isAllowed(origin)) {
            return true;
        }

        errorResponseWriter.write(response, org.springframework.http.HttpStatus.FORBIDDEN, ApiErrorCode.FORBIDDEN_ORIGIN);
        return false;
    }

    private boolean isCookieSessionRequest(HttpServletRequest request) {
        String method = request.getMethod();
        String path = request.getRequestURI();

        return method.equals("POST") && path.equals("/sessions")
                || method.equals("POST") && path.equals("/sessions/refresh")
                || method.equals("DELETE") && path.equals("/sessions");
    }
}
~~~~

### 코드 바로 아래 설명

- `HandlerInterceptor`는 MVC 요청 전후 callback을 제공하는 Spring interface입니다. 이 class를 `@Component`로 등록하는 것만으로는 실행되지 않고, 4장의 `InterceptorConfig`가 path와 함께 registry에 등록해야 합니다.
- `preHandle`의 `request`, `response`, `handler`는 Spring MVC가 현재 요청에 맞춰 전달합니다. 이 method가 객체를 직접 생성하지 않습니다.
- `isCookieSessionRequest`는 `(POST && /sessions) || (POST && /sessions/refresh) || (DELETE && /sessions)`를 계산합니다. Java에서 `&&`가 `||`보다 우선이므로 각 줄은 method와 path가 함께 일치해야 합니다.
- 대상이 아니면 `true`를 반환하여 이 Interceptor가 요청을 막지 않습니다. 이 true는 JWT 인증 성공을 의미하지 않습니다.
- 대상이면 `request.getHeader("Origin")`을 읽습니다. Header가 없으면 `null`이고 Provider의 `origin != null` 조건 때문에 허용되지 않습니다.
- 허용 Origin이면 `true`를 반환해 Controller로 진행합니다. 불일치하면 `ErrorResponseWriter.write`가 403 JSON을 직접 기록하고, `false`가 Controller 호출을 중단합니다.
- `return false`만으로 JSON이 만들어지는 것이 아닙니다. JSON을 만드는 작업은 바로 앞의 `errorResponseWriter.write(...)`가 수행합니다.
- `preHandle`에 `throws IOException`이 있는 이유는 `ErrorResponseWriter.write`가 response writer에 쓰는 과정에서 I/O 예외를 전달할 수 있기 때문입니다. Origin이 허용된 정상 경로에서는 이 writer 호출이 실행되지 않습니다.

### 이 Interceptor가 적용되는 요청

~~~~text
POST /sessions             → login Cookie 생성
POST /sessions/refresh     → Refresh Cookie 교체
DELETE /sessions           → logout Cookie 만료
~~~~

회원가입 `POST /users`나 일반 게시글 요청은 이 method의 세 조합에 포함되지 않습니다. CORS 규칙 자체는 WebConfig의 `/**`에 적용되지만, 이 server-side Origin 차단은 세 Cookie session 요청에만 적용됩니다.

## 7. Filter·Security·Interceptor의 응답 경계를 구분한다

### 7.1 Filter 단계의 직접 응답

실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/config/ErrorResponseWriter.java`

~~~~java
package kr.adapterz.springdatajpa.config;

import com.fasterxml.jackson.databind.ObjectMapper;
import jakarta.servlet.http.HttpServletResponse;
import kr.adapterz.springdatajpa.dto.ErrorResponseDto;
import kr.adapterz.springdatajpa.exception.ApiErrorCode;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Component;

import java.io.IOException;

@Component
public class ErrorResponseWriter {

    private final ObjectMapper objectMapper = new ObjectMapper();

    public void write(
            HttpServletResponse response,
            HttpStatus status,
            ApiErrorCode errorCode
    ) throws IOException {
        response.setStatus(status.value());
        response.setContentType("application/json;charset=UTF-8");
        objectMapper.writeValue(
                response.getWriter(),
                new ErrorResponseDto(errorCode.getCode(), errorCode.getMessage(), status.value())
        );
    }
}
~~~~

### 코드 바로 아래 설명

- 이 Bean은 `SecurityConfig`, `JwtAuthenticationFilter`, `SessionOriginInterceptor`가 공유합니다. Controller가 Service를 호출할 때 사용하는 오류 handler가 아닙니다.
- `setStatus`가 HTTP status 숫자를 기록하고, `setContentType`이 response body의 형식을 기록합니다.
- `response.getWriter()`는 현재 HTTP body에 쓰는 writer입니다.
- `new ErrorResponseDto(...)`는 code·message·status를 가진 Java 객체이고, `ObjectMapper.writeValue`가 JSON으로 직렬화해 writer에 씁니다.
- 이 method를 호출한 Filter·Interceptor가 chain을 더 진행하지 않으면 Controller와 `GlobalExceptionHandler`가 실행되지 않습니다.

### 7.2 Controller 이후의 예외

전체 `GlobalExceptionHandler.java`, `ErrorResponseDto.java`, `ApiErrorCode.java`는 03장에서 정독합니다. 인증 공통 흐름에서 연결되는 실제 handler는 다음과 같습니다.

실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/controller/GlobalExceptionHandler.java`

~~~~java
@ExceptionHandler(LoginFailedException.class)
public ResponseEntity<ErrorResponseDto> handleLoginFailedException(LoginFailedException e) {
    return error(HttpStatus.UNAUTHORIZED, e.getMessage());
}

@ExceptionHandler(AuthException.class)
public ResponseEntity<ErrorResponseDto> handleAuthException(AuthException e){
    return error(HttpStatus.UNAUTHORIZED, e.getMessage());
}

private ResponseEntity<ErrorResponseDto> error(HttpStatus status, String rawCode) {
    ApiErrorCode errorCode = ApiErrorCode.from(rawCode);
    ErrorResponseDto response = new ErrorResponseDto(
            errorCode.getCode(),
            errorCode.getMessage(),
            status.value()
    );
    return ResponseEntity.status(status).body(response);
}
~~~~

### 코드 바로 아래 설명

- `@RestControllerAdvice`가 붙은 GlobalExceptionHandler는 Controller 호출 중 전파된 예외를 받습니다.
- `LoginFailedException`은 로그인 Service에서 발생하고, `AuthException`은 Refresh Service 등 Controller까지 도달한 인증 업무에서 발생합니다.
- `error`가 raw code를 `ApiErrorCode.from`에 넘겨 enum code·message로 바꾸고, `ResponseEntity.status(status).body(response)`가 HTTP status와 JSON body를 함께 구성합니다.
- 반대로 JWT parser 실패나 Origin 불일치처럼 Controller에 도달하기 전에 끝난 오류는 이 handler가 아니라 `ErrorResponseWriter`가 직접 응답합니다.

### 오류 경계 한눈에 보기

~~~~text
JwtAuthenticationFilter / SecurityConfig / SessionOriginInterceptor
→ ErrorResponseWriter.write
→ response 직접 기록
→ Controller로 진행하지 않음

Controller → Service
→ RuntimeException 전파
→ GlobalExceptionHandler
→ ResponseEntity<ErrorResponseDto>
~~~~

## 8. 실제 요청 유형별 공통 진입 경로

### 로그인·Refresh·logout

~~~~text
POST /sessions
POST /sessions/refresh
DELETE /sessions
→ JwtAuthenticationFilter의 shouldNotFilter 대상
→ SecurityConfig permitAll 대상
→ RequestLogInterceptor
→ SessionOriginInterceptor
→ 허용 Origin이면 Controller
~~~~

`shouldNotFilter`와 `permitAll`은 같은 설정이 아닙니다. 첫 번째는 JWT Filter 내부 method를 건너뛰는 조건이고, 두 번째는 Security 인가 규칙입니다. 둘 다 통과해야 요청이 다음 단계로 진행합니다. Origin Interceptor는 그 뒤 MVC 단계에서 별도로 실행됩니다.

### 보호 API

~~~~text
GET/PATCH/DELETE protected endpoint
→ JwtAuthenticationFilter가 Authorization header 확인
→ 유효하면 SecurityContext에 Authentication 저장
→ filterChain.doFilter
→ anyRequest().authenticated
→ Controller
~~~~

보호 요청의 Bearer 검증과 `SecurityContext` 생성은 새 06장 Access Token 문서에서 전체 method body를 읽습니다. 이 장에서는 공통 진입 경계만 확정합니다.

### scheduler

~~~~text
@Scheduled tick
→ AuthSessionCleanupScheduler
→ AuthSessionRepository.deleteAllExpiredAtOrBefore
→ DB 만료 row 삭제
~~~~

scheduler는 HTTP Filter·Interceptor·Controller를 통과하지 않습니다. 따라서 요청 log나 Origin 검사가 scheduler에 적용된다고 해석하면 안 됩니다. 전체 scheduler 흐름은 새 08-1장에서 읽습니다.

## 10. 현재 장에서 스킵하는 코드와 이유

- `JwtAuthenticationFilter.java` 전체: 보호 요청의 핵심이므로 새 06장에서 실제 body를 읽습니다. 이 장에서는 `SecurityConfig`에 등록되고 공개 endpoint가 `shouldNotFilter` 대상이라는 연결만 확인합니다.
- `SessionController.java`, `SessionService.java`: 로그인·Refresh·logout method가 각각의 실행 흐름에 속하므로 새 05·07·08에서 실제 body를 읽습니다. 이 장은 Controller가 호출되기 전 공통 경계만 다룹니다.
- `GlobalExceptionHandler.java` 전체: 03장에서 전체 class를 읽었으므로 인증에 연결되는 handler와 오류 경계만 발췌합니다.
- `AuthSessionCleanupScheduler.java`: HTTP 요청과 독립된 scheduler 흐름이므로 새 08-1장에서 실제 body를 읽습니다.
- `PostController`·`UserController`의 일반 업무 method: 보호 Controller에 도달한다는 연결만 표시하고, 게시글·회원 기능 문서에서 각 method를 읽습니다.

스킵은 “현재 프로젝트에서 사용되지 않는다”는 뜻이 아닙니다. 이 장의 책임 범위와 중복 설명을 줄이기 위한 배치입니다. 호출 위치와 다음에 읽을 파일은 위에서 모두 표시했습니다.
