# 18장. 테스트 실행 범위와 테스트 코드 실제 흐름

## 18.0 이 장에서 먼저 구분할 것

테스트는 한 종류가 아닙니다. 현재 프로젝트는 같은 `@Test` 어노테이션을 사용하더라도 실행 비용과 확인 범위가 서로 다른 테스트를 분리해 두었습니다.

| 종류 | 실제 확인 대상 | 외부 시스템 | 현재 실행 명령 |
|---|---|---|---|
| 순수 단위 테스트 | 한 클래스의 계산·분기·상태 변경 | 없음 또는 Mockito mock | `./gradlew test` |
| Spring context 테스트 | Spring Bean 생성과 설정 로딩 | H2·Spring context | `./gradlew test` |
| H2 통합 테스트 | Repository SQL, JPA 매핑, Service와 DB 연결 | H2 메모리 DB | `./gradlew test` |
| Redis 단위 테스트 | Redis 호출 인자와 오류 분기 | 실제 Redis 없음, `StringRedisTemplate` mock | `./gradlew test` |
| Redis 통합 테스트 | Lua script, Redis key, 원자 증가, 분산 lock | Testcontainers Redis | `./gradlew redisTest` |
| Flyway baseline 테스트 | 빈 H2에 migration 전체 적용 | H2를 MySQL mode로 실행 | `./gradlew test` |
| MySQL 통합 테스트 | 실제 MySQL schema와 동시성 | Testcontainers MySQL 8.4 | `./gradlew mysqlTest` |

따라서 “테스트가 있다”와 “커버리지에 포함된다”, “실제 Redis/MySQL을 사용한다”는 각각 다른 질문입니다. 이 장은 세 가지를 분리해서 읽습니다.

1. Gradle이 어떤 테스트를 선택하는가
2. 선택된 테스트가 무엇을 실제로 실행하는가
3. JaCoCo가 어떤 운영 코드를 커버리지 계산에 넣는가

## 18.2 Gradle이 테스트를 선택하는 구조

확인 파일: `backend/build.gradle`

### 18.2.1 모든 Test task에 공통으로 적용되는 설정

실제 코드:

```groovy
tasks.withType(Test).configureEach {
	useJUnitPlatform()
	jvmArgs(
			"-javaagent:${configurations.mockitoAgent.asPath}",
			"-Xshare:off"
	)
	testLogging {
		events "passed", "skipped", "failed"
		exceptionFormat "full"
	}
}
```

줄별 의미:

- `tasks.withType(Test)`: Gradle의 `Test` 타입인 task 전체를 선택합니다. 기본 `test`뿐 아니라 아래에서 직접 등록한 `redisTest`, `mysqlTest`에도 적용됩니다.
- `configureEach { ... }`: 선택된 task마다 같은 설정을 적용합니다. 특정 테스트 클래스가 이 블록을 호출하는 것이 아니라 Gradle이 task를 실행하기 전에 설정합니다.
- `useJUnitPlatform()`: JUnit 5 엔진으로 테스트를 검색·실행합니다. 테스트 클래스의 `org.junit.jupiter.api.Test`가 이 플랫폼에서 실행됩니다.
- `configurations.mockitoAgent.asPath`: `mockitoAgent` configuration에 둔 Mockito jar의 실제 경로를 얻습니다.
- `-javaagent:...`: Mockito가 필요로 하는 JVM agent를 테스트 JVM에 붙입니다. 애플리케이션 코드의 Bean이 아니며, 테스트 task 프로세스 시작 옵션입니다.
- `-Xshare:off`: JVM class data sharing을 끕니다. Mockito agent와 함께 실행할 때 생기는 JVM 충돌을 피하기 위한 옵션입니다.
- `testLogging.events`: 통과·건너뜀·실패한 테스트 이벤트를 Gradle 로그에 표시합니다.
- `exceptionFormat "full"`: 실패 시 축약된 예외가 아니라 전체 stack trace를 표시합니다.

### 18.2.2 기본 `test` task

실제 코드:

```groovy
tasks.named('test') {
	systemProperty 'spring.profiles.active', 'test'
	useJUnitPlatform {
		excludeTags 'redis-integration', 'mysql-integration'
	}
	finalizedBy jacocoTestReport
}
```

실행 흐름:

```text
./gradlew test
→ Test task에 spring.profiles.active=test 전달
→ JUnit Platform에서 redis-integration, mysql-integration 태그를 제외
→ 나머지 테스트 실행
→ test가 끝난 뒤 jacocoTestReport 실행
```

- `systemProperty`: 테스트 JVM의 system property입니다. `@ActiveProfiles`를 직접 쓰지 않은 테스트도 이 task로 실행되면 `test` profile을 기본 활성화합니다.
- `excludeTags`: `@Tag("redis-integration")`, `@Tag("mysql-integration")`가 붙은 테스트를 이 task에서 제외합니다. “클래스가 컴파일되지 않는다”가 아니라 “이번 실행에서 선택하지 않는다”는 뜻입니다.
- `finalizedBy jacocoTestReport`: `test` task의 후처리 task로 JaCoCo report를 연결합니다. JaCoCo report 자체가 Redis/MySQL 테스트를 자동으로 다시 실행한다는 뜻은 아닙니다. report task의 `dependsOn test`와 합쳐져 기본 test 결과를 바탕으로 보고서를 만듭니다.

### 18.2.3 Redis 전용 task

```groovy
tasks.register('redisTest', Test) {
	description = 'Runs integration tests against a Testcontainers Redis server.'
	group = 'verification'
	testClassesDirs = sourceSets.test.output.classesDirs
	classpath = sourceSets.test.runtimeClasspath
	useJUnitPlatform {
		includeTags 'redis-integration'
	}
	shouldRunAfter test
}
```

- `tasks.register('redisTest', Test)`: 기본 `test`와 별개의 Test task를 새로 만듭니다.
- `testClassesDirs`, `classpath`: 이미 컴파일된 테스트 클래스와 실행 classpath를 이 task에 연결합니다.
- `includeTags`: Redis 통합 태그가 있는 테스트만 선택합니다.
- `shouldRunAfter test`: 두 task가 같은 Gradle 실행에 포함될 때 순서를 권장합니다. 이것만으로 `redisTest`가 항상 실행되는 것은 아닙니다. `check.dependsOn redisTest`가 실제 연결을 만듭니다.

따라서 `./gradlew redisTest`는 `test`의 제외 규칙을 이어받는 것이 아니라, `redis-integration`만 포함하는 별도 task입니다. 이 task 정의에는 `spring.profiles.active=test` system property가 직접 적혀 있지 않습니다. Redis integration 테스트는 Testcontainers와 직접 만든 Redis client를 사용하므로, 이 문서에서 “항상 test profile로 실행된다”고 확대해석하면 안 됩니다.

### 18.2.4 MySQL 전용 task

```groovy
tasks.register('mysqlTest', Test) {
	description = 'Runs schema and locking integration tests against a Testcontainers MySQL server.'
	group = 'verification'
	testClassesDirs = sourceSets.test.output.classesDirs
	classpath = sourceSets.test.runtimeClasspath
	useJUnitPlatform {
		includeTags 'mysql-integration'
	}
	shouldRunAfter test
}
```

구조는 Redis task와 같지만 `mysql-integration` 태그만 선택합니다. 실제 MySQL 주소·계정은 `MySqlSchemaIntegrationTest`의 `@DynamicPropertySource`가 컨테이너 매핑 포트로 주입합니다.

## 18.3 JaCoCo 커버리지 범위는 테스트 파일 목록과 다르다

확인 파일: `backend/build.gradle`

실제 운영 코드 포함 목록:

```groovy
def coverageIncludes = [
	'kr/adapterz/springdatajpa/entity/**',
	'kr/adapterz/springdatajpa/auth/**',
	'kr/adapterz/springdatajpa/config/**',
	'kr/adapterz/springdatajpa/service/**',
	'kr/adapterz/springdatajpa/controller/**'
]
```

이 목록은 `src/test/java`의 테스트 파일을 고르는 목록이 아닙니다. `sourceSets.main.output.classesDirs`에서 어떤 운영 class 파일을 커버리지 계산 대상으로 남길지 정하는 필터입니다.

실제 report 설정:

```groovy
tasks.named('jacocoTestReport') {
	dependsOn test

	reports {
		html.required = true
		xml.required = true
		csv.required = false
	}

	classDirectories.setFrom(files(sourceSets.main.output.classesDirs.collect {
		fileTree(dir: it, include: coverageIncludes)
	}))
}
```

- `dependsOn test`: report를 만들기 전에 기본 `test` task가 먼저 완료되어야 합니다.
- `html.required = true`: 사람이 브라우저로 읽는 HTML report를 만듭니다.
- `xml.required = true`: CI나 다른 도구가 읽을 XML report를 만듭니다.
- `csv.required = false`: CSV report는 만들지 않습니다.
- `classDirectories.setFrom(...)`: JaCoCo가 분석할 운영 class 디렉터리를 위의 5개 패키지로 제한합니다.

검증 규칙:

```groovy
tasks.named('jacocoTestCoverageVerification') {
	dependsOn test

	classDirectories.setFrom(files(sourceSets.main.output.classesDirs.collect {
		fileTree(dir: it, include: coverageIncludes)
	}))

	violationRules {
		rule {
			limit {
				counter = 'LINE'
				value = 'COVEREDRATIO'
				minimum = 0.80
			}
		}
	}
}
```

- `counter = 'LINE'`: 메서드 개수가 아니라 소스 line 단위로 계산합니다.
- `value = 'COVEREDRATIO'`: 실행된 line 수 / 대상 line 수 비율을 계산합니다.
- `minimum = 0.80`: 포함된 운영 class 전체의 line coverage가 80% 미만이면 verification이 실패할 수 있습니다.

중요한 현재 코드 결과:

- DTO, Repository, exception, validation 패키지는 `coverageIncludes`에 없습니다.
- 이 클래스들에 테스트가 있어도 JaCoCo의 대상 class에는 포함되지 않습니다.
- 반대로 `service`, `controller`, `auth`, `config`, `entity`는 테스트가 충분한지 커버리지에 영향을 줍니다.
- “테스트 코드가 있다”와 “JaCoCo가 그 운영 코드를 세고 있다”는 같은 뜻이 아닙니다.

최종 `check` 연결:

```groovy
check.dependsOn jacocoTestCoverageVerification
check.dependsOn tasks.named('redisTest')
check.dependsOn tasks.named('mysqlTest')
```

따라서 `./gradlew check`는 다음 의존성을 갖습니다.

```text
check
├─ jacocoTestCoverageVerification
│  └─ test
│     └─ jacocoTestReport (test의 finalized task)
├─ redisTest
└─ mysqlTest
```

정확히 말하면 `check`가 `test`, Redis, MySQL을 하나의 Test task로 합치는 것이 아닙니다. 서로 다른 task를 의존성 그래프에 연결하고, `test` 결과로 coverage verification을 수행합니다.

## 18.4 test profile과 H2가 일반 테스트에서 선택되는 이유

### 18.4.1 `application-test.yaml`

실제 코드:

```yaml
spring:
  autoconfigure:
    exclude:
      - org.redisson.spring.starter.RedissonAutoConfigurationV4

app:
  view-count:
    enabled: false
```

이 파일은 단독으로 모든 설정을 가지고 있지 않습니다. `application.yaml`의 profile group에 다음이 있습니다.

```yaml
spring:
  profiles:
    default: local
    group:
      test:
        - local
```

`test`가 활성화되면 `local` profile도 함께 활성화됩니다. 그래서 일반 `test` task에서는 다음 설정이 함께 적용됩니다.

```text
application.yaml
 + application-local.yaml
 + application-test.yaml
```

실제 결과:

- `application-local.yaml`의 H2 메모리 datasource 사용
- `ddl-auto: create`로 Hibernate가 테스트 schema 생성
- `flyway.enabled: false`
- `application-test.yaml`이 Redisson Spring Boot 자동설정을 제외
- `app.view-count.enabled: false`로 Redis 조회수 구현체 대신 DB 구현체 선택

`spring.autoconfigure.exclude`는 Redisson library 자체를 dependency에서 제거하는 설정이 아닙니다. Spring Boot가 Redisson 관련 자동 구성 Bean을 만들지 않게 하는 설정입니다. Redis 단위 테스트는 mock을 사용하고, Redis 통합 테스트는 자신이 직접 컨테이너와 client를 만들기 때문에 일반 Spring context가 Redis 연결을 요구하지 않도록 분리합니다.

### 18.4.2 profile 설정이 모든 custom task에 동일하게 적용되는 것은 아니다

`tasks.named('test')`에는 `systemProperty 'spring.profiles.active', 'test'`가 있지만 `redisTest`, `mysqlTest`에는 그 줄이 없습니다. 따라서 실행 방식은 실제 어노테이션과 task를 함께 봐야 합니다.

- `SpringdatajpaApplicationTests`, H2 repository 테스트, `PostConcurrencyIntegrationTest`, `SecurityConfigTest`, `ViewCountPropertiesTest`: 클래스에 `@ActiveProfiles("test")`가 있거나 기본 `test` task의 system property를 사용합니다.
- `MySqlSchemaIntegrationTest`: `@ActiveProfiles("test")`가 있고, `@SpringBootTest(properties = {...})`로 Flyway·JPA·view-count 설정을 다시 덮습니다.
- `RedisViewCountStoreIntegrationTest`, `RedisAofRestartIntegrationTest`: `@Tag("redis-integration")`, `@Testcontainers`로 실제 Redis를 직접 준비합니다. 일반 Spring context 기반 테스트가 아닙니다.
## 18.5 Spring context 시작 테스트

파일: backend/src/test/java/kr/adapterz/springdatajpa/SpringdatajpaApplicationTests.java

실제 코드:

```java
package kr.adapterz.springdatajpa;

import org.junit.jupiter.api.Test;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.context.ActiveProfiles;

@ActiveProfiles("test")
@SpringBootTest
class SpringdatajpaApplicationTests {

}
```

이 클래스에는 Test 메서드가 없습니다. 현재 파일만 보면 Test import도 사용되지 않습니다. 따라서 이 파일은 “메서드가 실행되어 결과를 assert한다”기보다 SpringBootTest가 테스트 context를 만들 수 있는지 확인하는 시작점입니다.

- ActiveProfiles("test"): test profile을 활성화합니다.
- SpringBootTest: SpringBootApplication을 찾고 애플리케이션 context를 구성합니다.
- 빈 생성, 설정 바인딩, JPA·Web·Security 등 context 구성 중 예외가 나면 context 로딩 단계에서 실패합니다.

이 테스트가 통과해도 다음을 증명하지는 않습니다.

- 회원가입 API의 모든 분기
- 실제 Redis 연결
- 실제 AWS RDS 연결
- 모든 Controller HTTP 응답

즉, 애플리케이션이 “기본적으로 조립되는가”를 확인하는 smoke test입니다.

## 18.6 Entity·DTO 테스트: DB 없이 도메인 규칙 확인

### 18.6.1 대표 Entity 테스트

파일: backend/src/test/java/kr/adapterz/springdatajpa/entity/PostViewCountTest.java

실제 코드:

```java
class PostViewCountTest {

    @Test
    void 조회수_카운터는_게시글과_함께_생성되고_0으로_초기화된다() {
        User user = new User(
                "view-counter@test.com",
                "Password1!",
                "view-counter",
                "profile.png",
                0
        );

        Post post = new Post(user, "title", "content");
        PostViewCount viewCount = post.getPostViewCount();

        assertAll(
                () -> assertThat(viewCount.getPost()).isEqualTo(post),
                () -> assertThat(viewCount.getViewCount()).isZero()
        );
    }
}
```

실행 흐름:

```text
User 생성
→ Post 생성자 호출
→ Post 내부에서 PostViewCount 생성

→ post 관계가 같은 객체인지 확인

```

- Test는 JUnit이 호출하는 테스트 메서드입니다.
- assertAll은 여러 assertion을 묶습니다. 하나가 실패해도 나머지 assertion 결과를 함께 수집할 수 있습니다.
- assertThat(...).isEqualTo(...)는 AssertJ assertion입니다.
- 이 테스트에는 repository, transaction, DB가 없습니다. 생성자와 getter의 Java 객체 동작만 확인합니다.

### 18.7.1 JWT Provider는 순수 단위 테스트

파일: backend/src/test/java/kr/adapterz/springdatajpa/auth/JwtProviderTest.java

실제 코드의 핵심:


데이터 흐름:

```text

→ JwtProvider 생성
→ createAccessToken(userId=42, authVersion=3)
→ JWT 문자열 생성

→ 서명 검증·claim 파싱
→ AccessTokenClaims 반환
```

같은 파일의 나머지 테스트는 다른 비밀키 서명과 만료 토큰이 AuthException("Invalid_Token")으로 변환되는지 확인합니다. 실제 Spring Security filter나 HTTP 요청은 사용하지 않습니다.

### 18.7.2 Filter 테스트는 Servlet mock과 SecurityContext를 사용

파일: backend/src/test/java/kr/adapterz/springdatajpa/auth/JwtAuthenticationFilterTest.java

준비 부분:

```java
@ExtendWith(MockitoExtension.class)
class JwtAuthenticationFilterTest {

    @Mock
    private JwtProvider jwtProvider;

    @Mock
    private CustomUserDetailsService customUserDetailsService;

    @BeforeEach
    void setUp() {
        jwtAuthenticationFilter = new JwtAuthenticationFilter(
                jwtProvider,
                customUserDetailsService,
                new kr.adapterz.springdatajpa.config.ErrorResponseWriter()
        );
    }

    @AfterEach
    void clearSecurityContext() {
        SecurityContextHolder.clearContext();
    }
}
```

- ExtendWith(MockitoExtension.class): Mockito mock 초기화와 검증 기능을 JUnit lifecycle에 연결합니다.
- Mock: 실제 JwtProvider, CustomUserDetailsService 대신 mock 객체를 주입합니다.
- BeforeEach: 각 테스트 전에 Filter를 새로 만듭니다.
- AfterEach: 한 테스트에서 만든 SecurityContext 인증 정보가 다음 테스트로 새지 않게 비웁니다.

정상 요청 테스트의 흐름:

```text
MockHttpServletRequest 생성
→ Authorization: Bearer valid-access-token 추가
→ jwtProvider.getAccessTokenClaims(...)가 (42, 0)을 반환하도록 stubbing
→ customUserDetailsService.loadUserByUserId(42)가 userDetails를 반환하도록 stubbing
→ jwtAuthenticationFilter.doFilter(request, response, filterChain)
→ SecurityContext에 Authentication 저장
→ 응답 상태 200·principal 확인
```

실패 테스트는 두 가지를 분리합니다.

- token claim의 authVersion과 현재 User의 버전이 다르면 401·INVALID_TOKEN, SecurityContext 비어 있음
- JwtProvider가 위조·만료를 AuthException으로 던지면 401·JSON error, 사용자 조회 service는 호출되지 않음

verifyNoInteractions(customUserDetailsService)는 예외가 발생한 앞 단계에서 뒤의 사용자 조회가 실행되지 않았다는 호출 검증입니다. 단순 반환값 검증만으로는 이 순서 정보를 알 수 없습니다.

### 18.7.3 SecurityConfig는 MockMvc로 Filter chain과 응답을 확인

파일: backend/src/test/java/kr/adapterz/springdatajpa/config/SecurityConfigTest.java

실제 준비 흐름:

```java
@ActiveProfiles("test")
@SpringBootTest
class SecurityConfigTest {

    @Autowired
    private WebApplicationContext webApplicationContext;

    @Autowired
    @Qualifier("springSecurityFilterChain")
    private Filter springSecurityFilterChain;

    @BeforeEach
    void setUp() {
        mockMvc = MockMvcBuilders
                .webAppContextSetup(webApplicationContext)
                .addFilters(springSecurityFilterChain)
                .build();

}
```

- SpringBootTest가 실제 Spring context와 Security 설정 Bean을 만듭니다.
- Qualifier("springSecurityFilterChain")는 여러 Filter 타입 중 Security filter chain Bean을 지정합니다.
- MockMvcBuilders.webAppContextSetup(...)은 실제 서버 socket을 열지 않고 MVC context에 요청을 보냅니다.
- addFilters(...)를 통해 요청이 Spring Security filter chain을 지나가게 합니다.

검증하는 요청:

```text
GET /posts, 인증 없음
→ Security filter chain
→ 401 JSON { code: UNAUTHORIZED, status: 401 }

POST /sessions, 허용 Origin
→ 인증 없이 endpoint 진입 가능
→ body가 {}라 controller/service 검증 단계에서 400

POST /sessions, Origin 없음 또는 허용되지 않은 Origin
→ SessionOriginInterceptor 경로
→ 403 FORBIDDEN_ORIGIN
```

이 테스트는 “로그인 성공”을 검증하는 테스트가 아닙니다. 인증이 없는 보호 API, public session API의 접근 조건, Origin 차단을 확인합니다.

### 18.7.4 SessionService는 협력 객체 호출을 검증

파일: backend/src/test/java/kr/adapterz/springdatajpa/service/SessionServiceTest.java

로그인 성공 테스트의 연결은 다음과 같습니다.

```text
SessionRequestDto

→ Authentication.getPrincipal()
→ CustomUserDetails
```

### 18.9.2 조회수 Repository의 세 가지 확인

첫 번째 테스트:

```text
User save
→ Post save
→ entityManager.flush()
→ entityManager.clear()
→ postViewCountRepository.findById(postId)
→ 별도 PostViewCount row가 같은 postId와 0으로 저장됐는지 확인
```

flush()는 영속성 context의 INSERT를 DB에 보내는 시점입니다. clear()는 현재 영속성 context에서 Entity를 떼어냅니다. 그래서 이후 findById가 이미 메모리에 있던 객체가 아니라 DB에서 다시 읽는지 확인할 수 있습니다.

두 번째 테스트는 incrementViewCount(postId, baseline)을 두 번 호출합니다.

```java
int firstUpdatedRows =
        postViewCountRepository.incrementViewCount(post.getPostId(), 100L);
int secondUpdatedRows =
        postViewCountRepository.incrementViewCount(post.getPostId(), 50L);

PostViewCount savedViewCount = postViewCountRepository
        .findById(post.getPostId())
        .orElseThrow();

assertThat(firstUpdatedRows).isEqualTo(1);
assertThat(secondUpdatedRows).isEqualTo(1);
assertThat(savedViewCount.getViewCount()).isEqualTo(102L);
```

실행 의미:

```text
초기 DB 값 0, baseline 100
→ GREATEST(0, 100) + 1 = 101
→ baseline 50으로 다시 증가
→ GREATEST(101, 50) + 1 = 102
```

세 번째 테스트는 persistMaxViewCount(postId, 150) 뒤 120을 저장하고 최종 값이 150인지 확인합니다. Redis snapshot이 오래된 값으로 돌아가도 DB 조회수가 감소하지 않는다는 Repository query 계약을 H2에서 검증합니다.

## 18.10 Redis 단위 테스트: 실제 Redis 없이 분기와 인자 확인

### 18.10.1 RedisViewCountStoreTest

파일: backend/src/test/java/kr/adapterz/springdatajpa/service/RedisViewCountStoreTest.java

준비:

```java
@ExtendWith(MockitoExtension.class)
class RedisViewCountStoreTest {

    @Mock
    private StringRedisTemplate redisTemplate;

    private RedisViewCountStore store;

    @BeforeEach
    void setUp() {
        ViewCountProperties properties = new ViewCountProperties(
                true,
                "bamboo:{post-view}:count:",
                "bamboo:{post-view}:dirty",
                "bamboo:{post-view}:flush-lock",
                Duration.ofSeconds(5)
        );
        store = new RedisViewCountStore(redisTemplate, properties);
    }
}
```

실제 Redis server는 없습니다. redisTemplate.execute(...)에 어떤 RedisScript, key list, argument가 전달되는지 Mockito로 지정하고 검증합니다.

대표 정상 테스트:

```java
when(redisTemplate.execute(
        ArgumentMatchers.<RedisScript<Long>>any(),
        eq(List.of(
                "bamboo:{post-view}:count:42",
                "bamboo:{post-view}:dirty"
        )),
        eq("100"),
        eq("42")
)).thenReturn(101L);

long updatedViewCount = store.increment(42L, 100L);

assertThat(updatedViewCount).isEqualTo(101L);
verify(redisTemplate).execute(
        ArgumentMatchers.<RedisScript<Long>>any(),
        eq(List.of(
                "bamboo:{post-view}:count:42",
                "bamboo:{post-view}:dirty"
        )),
        eq("100"),
        eq("42")
);
```

이 코드는 Redis가 실제로 101을 계산했다는 증거가 아닙니다. store가 Lua script 실행을 위해 정확한 key·argument를 전달하고, Redis가 101을 반환했다고 가정했을 때 반환값을 전달하는지 확인합니다. 실제 script 동작과 동시성은 다음의 Redis integration test가 담당합니다.

나머지 단위 테스트가 고정하는 분기:

- 음수 DB baseline: IllegalArgumentException, Redis와 상호작용하지 않음
- execute가 null: baseline 반환
- RedisConnectionFailureException: baseline 반환
- count key가 없을 때: dirty 제거 script 결과가 true

현재 코드 기준으로 Redis 오류 시 DatabaseViewCountUpdater로 동적 전환하지 않습니다. 이 단위 테스트가 확인하는 것은 RedisViewCountStore.increment()가 baseline을 반환하는 현재 fallback입니다. 실제 DB 구현체로 교체되는 동작으로 설명하면 안 됩니다.

### 18.10.2 RedisViewCountFlushSchedulerTest

파일: backend/src/test/java/kr/adapterz/springdatajpa/service/RedisViewCountFlushSchedulerTest.java

이 테스트도 실제 Redis와 DB가 없습니다. RedisViewCountStore, ViewCountPersistenceService, RedissonClient, RLock을 모두 mock으로 만들고 호출 순서를 확인합니다.

정상 순서:

```text
redissonClient.getLock
→ lock.tryLock() == true
→ dirty postId 조회
→ Redis snapshot 조회
→ persistenceService.persist(postId, snapshot)
→ redisViewCountStore.acknowledgeIfUnchanged(postId, snapshot)
→ 현재 thread가 가진 lock이면 unlock
```

InOrder 검증은 DB 저장 전에 dirty를 지우지 않았는지 확인합니다. DB 저장이 실패하면 acknowledgeIfUnchanged를 호출하지 않아 dirty가 남습니다. lock을 얻지 못하면 Redis store와 persistence service에 상호작용하지 않습니다.

이 테스트는 분산 lock의 실제 상호 배제를 증명하지 않습니다. lock 호출 순서와 실패 시 cleanup은 다음 integration test와 별도로 읽어야 합니다.

## 18.11 Redis Testcontainers·AOF·동시성 통합 테스트

### 18.11.1 Redis container 준비

파일: backend/src/test/java/kr/adapterz/springdatajpa/service/RedisViewCountStoreIntegrationTest.java

실제 코드 일부:

```java
@Tag("redis-integration")
@Testcontainers
class RedisViewCountStoreIntegrationTest {

    @Container
    private static final GenericContainer<?> REDIS =
            new GenericContainer<>(
                    DockerImageName.parse("redis:7.4-alpine")
            )
                    .withExposedPorts(6379)
                    .waitingFor(Wait.forListeningPort());

```

- Tag: Gradle의 redisTest가 선택하는 JUnit tag입니다.
- Testcontainers: Testcontainers lifecycle 연동을 활성화합니다.
- Container: 테스트 전후 container lifecycle을 관리할 대상입니다.
- GenericContainer: Redis 전용 Spring test slice가 아니라 Docker image를 일반 container로 실행합니다.
- withExposedPorts(6379): container port를 host에 동적으로 매핑합니다. 테스트는 getMappedPort로 실제 host port를 얻습니다.
- waitingFor: 포트가 열릴 때까지 테스트 연결을 기다립니다.

@BeforeAll connectToRedis()는 mapped port로 두 개의 Redisson client를 만들고, 첫 번째 client를 RedissonConnectionFactory와 StringRedisTemplate에 연결합니다. 두 client가 같은 Redis에 연결되므로 분산 lock 테스트가 가능합니다.

### 18.11.2 실제 Redis에서 검증하는 것

| 테스트 | 확인하는 실제 동작 |
|---|---|
| Redis_키가_없으면_DB_기준값에서_조회수를_증가시킨다 | count key가 없을 때 100→101, dirty set에 postId 저장 |
| Redis와_DB_중_더_큰_조회수를_기준으로_증가시킨다 | Redis 150, DB baseline 100이면 151 |
| Redis_조회수가_DB보다_작으면_DB_값으로_복구한_뒤_증가시킨다 | Redis 90, baseline 100이면 101 |
| 동시에_200번_증가해도_조회수가_유실되지_않는다 | 20 thread가 200회 호출해 최종 300, dirty member 1개 |
| 저장한_스냅샷보다_조회수가_증가하면_dirty_표시를_유지한다 | snapshot이 stale이면 acknowledge false, 최신 snapshot이면 dirty 제거 |
| 조회수_키가_없을_때만_고아_dirty_표시를_제거한다 | count key 없는 dirty만 제거, count가 생기면 유지 |
| 두_백엔드_중_한_백엔드만_분산_락을_획득한다 | 같은 lock name에서 첫 client true, 두 번째 false, unlock 후 두 번째 true |

200회 테스트에서 CountDownLatch는 모든 작업을 동시에 시작시키는 장벽입니다. ExecutorService는 20개 worker thread를 만들고, 각 Future의 결과와 timeout을 확인합니다. 최종 count가 300인 것은 Redis Lua script의 원자적인 기준값 복구·INCR·dirty 추가 흐름이 실제 Redis에서 동작했다는 의미입니다.

## 18.12 Flyway baseline과 실제 MySQL schema 테스트

### 18.12.1 FlywayBaselineMigrationTest

파일: backend/src/test/java/kr/adapterz/springdatajpa/config/FlywayBaselineMigrationTest.java

핵심 실행:

```java
String jdbcUrl =
        "jdbc:h2:mem:flyway-baseline;MODE=MySQL;DATABASE_TO_LOWER=TRUE;DB_CLOSE_DELAY=-1";
```

실행 주체는 Spring Boot의 자동 Flyway Bean이 아니라 테스트가 직접 만든 Flyway 객체입니다. 빈 H2 schema에 migration location의 B3와 V1~V6를 적용하고, JDBC information_schema를 조회해 table·legacy column·history row를 확인합니다.

현재 테스트가 확인하는 것:

- 현재 migration 최종 version이 6인지
- users, posts, comments, post_counters, post_images, post_likes, post_reports, post_view_counts, auth_sessions가 존재하는지

- B3, V4, V5, V6가 flyway_schema_history에서 성공으로 기록됐는지

파일: backend/src/test/java/kr/adapterz/springdatajpa/config/MySqlSchemaIntegrationTest.java

일반 test profile의 H2/Flyway off 설정을 그대로 쓰지 않고, 이 테스트의 SpringBootTest(properties = ...)가 MySQL migration 경로를 켭니다.

DynamicPropertySource:

```java
@DynamicPropertySource
static void configureMySql(DynamicPropertyRegistry registry) {
    registry.add(
            "spring.datasource.url",
            () -> "jdbc:mysql://%s:%d/%s?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=UTC"
                    .formatted(
                            MYSQL.getHost(),
                            MYSQL.getMappedPort(3306),
                            DATABASE_NAME
                    )
    );
    registry.add("spring.datasource.username", () -> "root");
    registry.add("spring.datasource.password", () -> ROOT_PASSWORD);
}
```

registry.add(key, Supplier)의 Supplier는 container가 시작되어 mapped port를 가진 뒤 값을 계산하게 합니다. 그래서 정적인 localhost:3306을 쓰지 않고 Testcontainers가 만든 실제 host port를 Spring datasource에 전달합니다.

테스트 메서드는 다음을 한 번에 확인합니다.

```text
MySQL container 시작
→ Spring datasource URL 동적 주입
→ Flyway B3~V6 적용
→ Hibernate ddl-auto=validate
→ 최종 table 9개·post_likes_seq 없음·legacy column 없음 확인
→ 5명의 사용자 동시 좋아요 요청
→ post counter like_count == 5
→ like row count == 5
```

이 테스트는 실제 RDS에 연결했다는 테스트가 아닙니다. MySQL 8.4 container가 운영 MySQL과 같은 모든 데이터·네트워크·권한 조건을 재현한다고도 말할 수 없습니다. 현재 코드가 자동으로 보장하는 것은 이 container와 설정에서 schema migration과 좋아요 동시성 계약이 통과한다는 범위입니다.

## 18.13 PostConcurrencyIntegrationTest: H2에서 Service의 동시성 계약 확인

파일: backend/src/test/java/kr/adapterz/springdatajpa/service/PostConcurrencyIntegrationTest.java

상단:

```java
@ActiveProfiles("test")
@SpringBootTest
class PostConcurrencyIntegrationTest {
```

test profile에서는 app.view-count.enabled=false이므로 게시글 상세 조회가 Redis 구현체가 아니라 DatabaseViewCountUpdater를 사용합니다. 따라서 이 파일의 조회수 테스트와 RedisViewCountStoreIntegrationTest는 서로 다른 구현체를 검증합니다.

### 18.13.1 조회수 30회

```text
writer·viewer·post 저장
→ entityManager.clear()
→ requestCount=30개 작업 준비
→ readyLatch가 모두 도착하면 startLatch 해제
→ 각 작업이 postService.getPostView(postId, viewerId) 호출
→ PostViewCountRepository의 DB 증가
→ 최종 viewCount == 30
```

runConcurrently의 두 latch를 구분해야 합니다.

- readyLatch: 모든 worker가 실행 준비를 마쳤는지 기다립니다.
- startLatch: 준비가 끝난 뒤 모든 worker가 거의 동시에 업무를 시작하도록 합니다.

### 18.13.2 좋아요·신고

- 서로 다른 사용자 10명이 동시에 좋아요를 누르면 PostCounter.likeCount와 Like row가 각각 10인지 확인합니다.
- 한 작성자의 서로 다른 게시글 5개가 동시에 신고되면 작성자의 receivedReportCount가 5이고, 각 게시글 report count가 1이며, report row가 5인지 확인합니다.

이 테스트는 단순히 Java list에 값을 더하는 것이 아니라 Service→Repository→DB counter update의 동시 실행 결과를 확인합니다.

### 18.13.3 게시글 수정과 optimistic lock

같은 제목·내용을 두 요청이 동시에 보내면 현재 Entity의 내용 비교 로직이 실제 변경이 없다고 판단하여 version이 증가하지 않는지 확인합니다.

서로 다른 내용을 두 transaction이 같은 version에서 읽으면:

```text
두 transaction이 같은 version 읽음
→ 각각 update 시도
→ 먼저 반영한 transaction 성공
→ 다른 transaction의 version 조건 update 행 수 0
→ optimistic lock 예외
→ successCount=1, failures=1
→ 최종 version=기존 version+1
```

테스트는 containsOptimisticLockFailure에서 exception cause chain을 따라가며 class name에 Optimistic이 들어가는지 확인합니다. 이 검사는 정확한 Spring 예외 class 하나만 고정하지 않고 wrapping된 원인까지 검사하는 현재 구현입니다.

```java
@ActiveProfiles("test")
@SpringBootTest
class ViewCountPropertiesTest {

    private ViewCountProperties boundProperties;

    void application_YAML의_조회수_설정을_객체로_변환한다() {
        assertThat(boundProperties.enabled()).isFalse();
        assertThat(boundProperties.countKey(42L))
                .isEqualTo("bamboo:{post-view}:count:42");
        assertThat(boundProperties.flushInterval())
                .isEqualTo(Duration.ofSeconds(5));
    }

    @Test
    void 게시글_ID는_양수여야_한다() {
        ViewCountProperties properties = properties();

        assertThatIllegalArgumentException()
                .isThrownBy(() -> properties.countKey(0L))
                .withMessage("postId must be positive");
    }
}
```
