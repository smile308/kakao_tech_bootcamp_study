# 부록. 동시성 제어와 잠금 전략 실제 코드 정리

이 부록은 00~19장의 기능 흐름을 읽은 뒤, 여러 기능에 흩어진 동시성 제어 방식을
한곳에서 비교하기 위한 자료입니다. 공식 학습 파일 목록에 추가하는 소스 파일이
아니므로 공식 파일 진행률에는 포함하지 않습니다. 현재 공식 대상은 8월 10일 커밋의
새 source·test 파일을 반영한 `217/217` 기준입니다.

이 문서에서는 다음을 구분합니다.

- **코드로 확인된 사실**: 실제 annotation, query, 메서드 호출, 테스트 assertion으로 확인되는 내용
- **설계 의도 해석**: 코드에 주석이나 ADR로 직접 적혀 있지는 않지만 현재 구조로 볼 때 가능한 이유
- **확인할 수 없는 내용**: 운영 환경이나 작성자의 의사결정 기록이 없어 단정할 수 없는 내용

## 1. 먼저 바로잡을 표현

“조회수·좋아요·댓글 수·신고가 각각 서로 다른 락을 사용한다”는 표현은 절반만
맞습니다. 네 기능 모두가 별도의 락 객체를 하나씩 갖는 구조는 아닙니다.

| 기능 | 실제 동시성 제어 | 락인가? | 코드상 목적 |
|---|---|---:|---|
| 조회수 요청 증가 | Redis Lua script 또는 DB `UPDATE ... GREATEST(...) + 1` | 명시적 락 없음 | 증가와 dirty 표시를 원자적으로 처리 |
| 조회수 flush | Redisson `RLock` | 예, 분산 락 | 여러 backend가 같은 dirty 목록을 동시에 DB에 반영하지 않게 함 |
| 좋아요 | `PostCounter`의 `PESSIMISTIC_WRITE` + bulk `+ 1` + unique constraint | 예 | 카운터 변경 구간 직렬화와 중복 좋아요 방지 |
| 댓글 수 | bulk `+ 1/- 1` + `Post` `PESSIMISTIC_READ` 재확인 | 부분적으로 예 | DB 원자 증가와 게시글 active 상태 재확인 |
| 신고 | interaction 확인 → `PostCounter`·`Post`·작성자 `User`의 `PESSIMISTIC_WRITE` + Entity dirty checking + unique constraint | 예 | 신고와 게시글·작성자 누적 수 변경을 정해진 순서로 보호 |

따라서 조회수의 일반 요청은 “Redis 락을 잡고 1 증가”가 아니라, Redis의 단일
명령 실행 특성과 Lua script의 원자성을 이용합니다. 반면 flush 단계에는 backend
인스턴스 사이의 Redisson 분산 락이 있습니다.

### 1.1 8월 10일 신고 lock 순서 변경

현재 `PostService.reportPost()`의 확인된 호출 순서는 다음과 같다.

```text
findActivePostForInteraction(postId)
→ findByPostIdForUpdate(postId)로 PostCounter lock
→ findActivePostForUpdate(postId)로 Post lock
→ 신고자 User 조회
→ findByUserIdForUpdate(writerId)로 작성자 User lock
→ 중복·자기 신고 검사
→ PostReport 저장 + Post.report() + User.receiveReport()
```

이 순서는 좋아요·댓글이 먼저 `PostCounter`를 잠그는 구조와 순서를 맞추려는 설계 의도로
해석할 수 있다. 다만 커밋 메시지와 코드만으로 모든 DB 격리 수준에서 deadlock이 절대
발생하지 않는다고 단정할 수는 없다. 락 획득 실패는 `GlobalExceptionHandler`에서 503
`COUNTER_UPDATE_FAILED`로 변환되고, `GlobalExceptionHandlerTest`는 그 응답 매핑만 검사한다.

## 2. 잠금과 원자 연산의 차이

### 2.1 비관적 쓰기 잠금

`@Lock(LockModeType.PESSIMISTIC_WRITE)`가 붙은 SELECT입니다. DB가 조회한 row에
쓰기 잠금을 걸어 다른 트랜잭션의 충돌하는 변경을 기다리게 합니다.

현재 코드에서는 다음과 같이 사용됩니다.

- 같은 게시글의 카운터를 변경할 때
- 신고 대상 게시글을 처리할 때
- 신고를 받은 작성자 User를 변경할 때
- 같은 refresh token session을 회전할 때

### 2.2 비관적 읽기 잠금

`PESSIMISTIC_READ`는 읽기 중인 row가 쓰기 중에 변경되지 않도록 공유 읽기 잠금을
요청합니다. 이 프로젝트에서는 좋아요·댓글 등의 카운터 변경 직후 게시글이 아직
활성인지 다시 확인하는 데 사용됩니다.

### 2.3 낙관적 잠금

`@Version` column을 이용해 “읽은 뒤 다른 요청이 먼저 수정했는지”를 commit 시점에
검사합니다. 충돌하면 `ObjectOptimisticLockingFailureException`이 발생합니다.

### 2.4 분산 락

JVM 안의 `synchronized`가 아니라 Redis에 저장된 잠금 상태를 여러 backend가
공유하는 방식입니다. 이 프로젝트에서는 조회수 flush Scheduler가 사용합니다.

### 2.5 원자 연산

잠금 객체를 별도로 만들지 않고 DB 한 문장, Redis 한 script가 중간 상태를 다른
요청에게 노출하지 않도록 실행하는 방식입니다.

예를 들어 다음 SQL은 애플리케이션에서 값을 읽고 더한 뒤 저장하는 것이 아니라,
DB 안에서 현재 값에 1을 더합니다.

```sql
SET like_count = like_count + 1
```

원자 연산과 잠금은 서로 대체어가 아닙니다. 현재 코드는 두 방식을 함께 사용합니다.

## 3. 조회수: 일반 요청은 Redis 원자 script, flush는 분산 락

### 3.1 상세 조회에서 조회수를 증가시키는 위치

호출 흐름:

```text
PostService.getPostView()
→ PostViewReadService.read()의 read-only DB transaction에서 baseline 확인
→ ViewCountUpdater.increment(postId, baseline)
→ RedisViewCountStore 또는 DatabaseViewCountUpdater
```

`ViewCountUpdater`는 Redis 구현과 DB 구현의 공통 계약입니다. 설정에 따라
Redis 구현체 또는 DB 구현체가 선택되며, 일반 요청마다 Java `Lock`을 생성하지는
않습니다.

### 3.2 Redis 증가 script

파일: `backend/src/main/java/kr/adapterz/springdatajpa/service/RedisViewCountStore.java`

핵심 script의 순서:

```lua
local current = redis.call('GET', KEYS[1])
local baseline = tonumber(ARGV[1])

if not current or tonumber(current) < baseline then
    redis.call('SET', KEYS[1], ARGV[1])
end

local updated = redis.call('INCR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[2])
return updated
```

이 script는 다음 작업을 하나의 Redis script 실행으로 묶습니다.

1. Redis count key와 dirty set의 타입을 확인합니다.
2. Redis 값이 DB baseline보다 작으면 baseline으로 복구합니다.
3. count key를 1 증가시킵니다.
4. 해당 postId를 dirty set에 추가합니다.
5. 증가된 값을 반환합니다.

Redis script는 실행 중 다른 Redis 명령이 중간에 끼어들지 않는 원자 실행 단위입니다.
따라서 여기서 사용하는 것은 `RLock`이 아니라 **Redis script 원자성**입니다.

### 3.3 DB fallback의 증가 query

파일: `backend/src/main/java/kr/adapterz/springdatajpa/repository/PostViewCountRepository.java`

```sql
UPDATE post_view_counts
SET view_count = GREATEST(view_count, :baselineViewCount) + 1
WHERE post_id = :postId
```

Redis가 비활성화된 경우 `DatabaseViewCountUpdater`가 이 query를 호출합니다.
이 역시 row를 Entity로 읽고 `count++`한 뒤 저장하는 방식이 아니라 DB가 현재 값과
baseline 중 큰 값을 선택하고 1을 더하는 방식입니다.

### 3.4 flush Scheduler의 Redis 분산 락

파일: `backend/src/main/java/kr/adapterz/springdatajpa/service/RedisViewCountFlushScheduler.java`

```java
RLock lock = redissonClient.getLock(properties.flushLockKey());
boolean acquired = lock.tryLock();

if (!acquired) {
    return;
}

try {
    flushWhileHoldingLock();
} finally {
    releaseIfOwned(lock, acquired);
}
```

설계 의도는 여러 backend 인스턴스에 Scheduler가 각각 실행되어도 같은 dirty set을
동시에 순회하고 DB에 중복 반영하지 않도록 하는 것입니다. `flush-lock-key`가
공유되므로 JVM별 `synchronized`보다 여러 서버에 적합합니다.

### 3.5 snapshot 이후 새 조회를 보존하는 조건부 제거

flush가 `snapshot = 150`을 읽은 뒤 새로운 조회가 발생해 Redis 값이 151이 되면,
`acknowledgeIfUnchanged()` script는 dirty set을 삭제하지 않습니다.

```text
snapshot 150 저장
→ flush 중 새 요청으로 Redis 151
→ 현재 값 151 != snapshot 150
→ dirty 유지
→ 다음 flush에서 151 처리
```

이 비교·삭제도 Lua script 안에서 원자적으로 실행됩니다. 이것은 분산 락과 별개의
보호 장치입니다. 분산 락은 flush 실행자 하나를 고르고, 조건부 script는 flush 중
새로 들어온 증가를 잃지 않게 합니다.

## 4. 좋아요와 댓글 수: bulk update를 공유하지만 잠금 범위는 다름

### 4.1 공통 counter row 잠금

파일: `backend/src/main/java/kr/adapterz/springdatajpa/repository/PostCounterRepository.java`

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("""
        SELECT counter
        FROM PostCounter counter
        WHERE counter.postId = :postId
        """)
Optional<PostCounter> findByPostIdForUpdate(Long postId);
```

좋아요, 좋아요 취소, 게시글 삭제에서는 `PostCounter` row를 먼저 잠급니다.
반면 댓글 작성·삭제는 현재 `findByPostIdForUpdate()`를 호출하지 않습니다. 댓글은
같은 Repository의 counter update query를 실행한 뒤, 게시글 상태를
`PESSIMISTIC_READ`로 다시 확인합니다.

### 4.2 좋아요

```text
PostService.likePost()
→ PostCounter row PESSIMISTIC_WRITE
→ 게시글 active 상태 재확인
→ Like row 저장·flush
→ postCounterRepository.incrementLikeCount()
→ 결과 row 수가 1인지 확인
→ Counter 다시 조회해 응답
```

`incrementLikeCount()`는 다음처럼 DB에서 직접 계산합니다.

```sql
UPDATE PostCounter counter
SET counter.likeCount = counter.likeCount + 1
WHERE counter.postId = :postId
```

여기에는 Entity의 `like()` 메서드가 없습니다. 이전에 있던 unused Entity method가
삭제되었고, 현재 production 흐름은 Repository query입니다.

좋아요 중복은 잠금만으로 처리하지 않습니다. `post_likes`의 `(post_id, user_id)`
unique constraint가 최종 방어선이고, `saveAndFlush()`에서 발생할 수 있는
`DataIntegrityViolationException`을 `Already_Liked`로 변환합니다.

### 4.3 댓글 수

댓글 작성·삭제는 좋아요와 bulk counter query는 공유하지만, `PostCounter`의
`PESSIMISTIC_WRITE` 잠금은 공유하지 않습니다.

```sql
UPDATE PostCounter counter
SET counter.replyCount = counter.replyCount + 1
WHERE counter.postId = :postId
```

삭제 시에는 `replyCount > 0` 조건으로 0 아래로 내려가지 않게 합니다.

현재 확인되는 댓글 흐름:

```text
CommentService.commentPost/commentDelete
→ PostCounter bulk UPDATE replyCount
→ PostRepository.findActivePostForInteractionCheck()
   → Post PESSIMISTIC_READ
→ 댓글 row 저장 또는 삭제
```

설계 의도 해석:

- 좋아요와 댓글 수는 요청 빈도가 높고 숫자만 증가·감소하는 값입니다.
- DB의 `count = count + 1` 표현식으로 read-modify-write를 줄입니다.
- 좋아요에서는 `PostCounter` row lock이 카운터 변경 구간과 삭제 흐름의 충돌을
  조정하려는 역할로 보입니다.
- 댓글에서는 DB의 `replyCount = replyCount +/- 1` 원자 query와 `Post` active 상태
  재확인을 조합한 것으로 보입니다. 댓글 흐름에 counter row `PESSIMISTIC_WRITE`가
  없는 이유는 현재 코드만으로 확정할 수 없습니다.

“빈도가 높기 때문에 반드시 bulk query를 써야 한다”는 규칙이 코드에 적혀 있는
것은 아닙니다. 빈도·동시성·성능을 고려한 설계로 해석할 수 있지만, 작성자의
의사결정 기록은 현재 저장소에서 확인할 수 없습니다.

## 5. 신고: 게시글과 작성자 두 row를 잠그고 Entity dirty checking

### 5.1 실제 잠금

게시글 조회:

파일: `backend/src/main/java/kr/adapterz/springdatajpa/repository/PostRepository.java`

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@EntityGraph(attributePaths = "postCounter")
Optional<Post> findActivePostForUpdate(Long postId);
```

작성자 조회:

파일: `backend/src/main/java/kr/adapterz/springdatajpa/repository/UserRepository.java`

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<User> findByUserIdForUpdate(Long userId);
```

### 5.2 Entity 변경

```text
PostReport 저장
→ post.report()
   → postCounter.report()
      → reportCount++
→ writer.receiveReport()
   → receivedReportCount++
→ transaction commit
→ JPA dirty checking으로 PostCounter와 User UPDATE
```

신고 메서드는 현재 단순히 `++`만 수행합니다. 따라서 신고가 Entity method를
사용하는 데 기술적인 필수 조건이 있는 것은 아닙니다.

설계 의도 해석:

- `PostService`가 `reportCount`나 `receivedReportCount` field에 직접 접근하지 않고
  `report()`·`receiveReport()`라는 도메인 행위로 표현합니다.
- 신고 기록, 게시글 신고 수, 작성자 신고 수를 하나의 transaction에서 함께
  처리하기 때문에 Entity dirty checking으로 구현하기가 단순합니다.
- 좋아요·댓글보다 발생 빈도가 낮으므로 bulk query의 성능 이점이 상대적으로 작다고
  판단했을 가능성은 있습니다.

마지막 항목은 코드에 직접 적힌 사실이 아니라 합리적인 추측입니다. 확정된 사실은
Entity method 호출, `@Transactional`, 두 개의 `PESSIMISTIC_WRITE`입니다.

### 5.3 신고 중복 방지

신고도 `(post_id, user_id)` unique constraint를 사용합니다. `existsByPostAndUser`
사전 확인만으로는 두 요청이 동시에 통과할 수 있으므로, DB unique constraint가
최종 중복 방지 역할을 합니다. unique constraint는 락 annotation이 아니라 DB의
무결성 제약입니다.

## 6. 게시글 수정·삭제: 카운터와 다른 낙관적 잠금

### 6.1 `Post.version`

파일: `backend/src/main/java/kr/adapterz/springdatajpa/entity/Post.java`

```java
@Version
@Column(name = "version", nullable = false)
private Long version;
```

`@Version`은 수정 시 version 조건을 UPDATE에 포함해 다른 요청이 먼저 수정했는지
확인합니다. `PostService.validatePostVersion()`은 요청 DTO의 version과 현재
Entity의 version을 먼저 비교하고, JPA의 `@Version`은 commit 시점의 충돌도
검사합니다.

### 6.2 이미지 변경 시 `OPTIMISTIC_FORCE_INCREMENT`

파일: `backend/src/main/java/kr/adapterz/springdatajpa/service/PostService.java`

```java
if (sameTitleAndContent) {
    entityManager.lock(post, LockModeType.OPTIMISTIC_FORCE_INCREMENT);
}
```

제목·본문은 그대로이고 이미지만 바뀌는 경우, 부모 `Post` row 자체의 일반 field가
변경되지 않을 수 있습니다. 이때도 게시글 수정 version을 올려 동시 수정 충돌을
감지하려는 의도로 해석됩니다. 테스트에는 이 잠금 호출을 확인하는 assertion이
있습니다.

### 6.3 삭제와 active 재확인

`findActivePostForInteractionCheck()`는 다음과 같이 `PESSIMISTIC_READ`를 사용합니다.

```java
@Lock(LockModeType.PESSIMISTIC_READ)
Optional<Post> findActivePostForInteractionCheck(Long postId);
```

좋아요·댓글 수 변경 뒤 게시글이 여전히 `deleted = false`인지 재확인하려는 위치입니다.
카운터 변경과 soft delete가 엇갈리는 순간에 잘못된 상호작용을 허용하지 않으려는
의도로 보입니다. 다만 delete path 전체가 Post row에 같은 PESSIMISTIC_WRITE를
사용하는 것은 아니므로, 이 잠금만으로 모든 삭제·상호작용 순서를 보장한다고
확정해서는 안 됩니다. 실제 보장 범위는 transaction과 counter lock, version check를
함께 읽어야 합니다.

## 7. Refresh Token: 같은 session row의 회전 직렬화

파일: `backend/src/main/java/kr/adapterz/springdatajpa/repository/AuthSessionRepository.java`

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<AuthSession> findByRefreshTokenHash(String refreshTokenHash);
```

`SessionService.refreshSession()`은 이 query로 session row를 잠근 뒤 다음을 실행합니다.

```text
refresh token hash 조회 + row lock
→ active·만료·사용자 상태 확인
→ 새 refresh token hash 생성
→ AuthSession.rotate()
→ 새 access token 응답
→ transaction commit
```

같은 refresh token으로 두 요청이 동시에 들어오면 한 요청이 row를 잠근 동안 다른
요청은 대기합니다. 첫 요청이 hash를 새 값으로 바꾼 뒤 commit하면 두 번째 요청은
기존 hash를 정상 세션으로 사용할 수 없게 됩니다. 이것이 refresh rotation의
동시 사용을 막는 현재 설계 의도입니다.

로그아웃도 같은 조회 method를 사용하고, 만료 session 정리 Scheduler는 조건부
bulk DELETE를 사용합니다. 만료 정리에는 특정 session을 회전시키는 read-modify-write
가 없으므로 별도 row lock method가 없습니다.

## 8. 고유 제약과 `@Modifying`은 락과 다르다

다음 요소들은 동시성에 기여하지만 `@Lock`과 같은 잠금은 아닙니다.

| 요소 | 역할 |
|---|---|
| `post_likes(post_id, user_id)` unique | 같은 사용자의 중복 좋아요 차단 |
| `post_reports(post_id, user_id)` unique | 같은 사용자의 중복 신고 차단 |
| `refresh_token_hash` unique | 같은 refresh token hash 중복 저장 방지 |
| `UPDATE count = count + 1` | DB 내부 원자 증가 |
| Redis Lua script | count 증가와 dirty 표시의 원자 처리 |
| `@Modifying(clearAutomatically = true, flushAutomatically = true)` | bulk query 전후 Persistence Context 정리·flush; 잠금 자체는 아님 |
| `@Transactional` | 여러 상태 변경의 commit·rollback 경계; 잠금 annotation 자체는 아님 |

## 9. 테스트에서만 보이는 동기화

`PostConcurrencyIntegrationTest`의 `synchronized (successCount)`는 애플리케이션
동시성 제어가 아닙니다. 여러 테스트 thread가 성공 횟수를 세는 과정에서 테스트용
변수 자체가 경쟁하지 않게 보호하는 코드입니다.

반대로 다음 테스트는 애플리케이션의 동시성 계약을 확인합니다.

- `MySqlSchemaIntegrationTest`: 30개 동시 조회수, 여러 게시글 신고의 작성자 누적 수,
  신고·좋아요·댓글 혼합 흐름이 MySQL에 반영되는지 확인
- `PostConcurrencyIntegrationTest`: H2의 좋아요·댓글·게시글 수정·삭제 동시 흐름 확인
- `RedisViewCountStoreIntegrationTest`: 여러 thread의 Redis 증가와 flush lock 확인
- `RedisViewCountFlushSchedulerTest`: `tryLock()` 실패, unlock, snapshot 이후 dirty
  유지 같은 분기 확인
- `PostServiceTest`: Entity method 호출 결과와 Service의 정상·예외 흐름을 Mockito로 확인

Mockito 테스트는 실제 DB row lock의 대기 순서나 MySQL isolation level을 증명하지
않습니다. 실제 interleaving 보장은 통합 테스트와 운영 DB 설정까지 확인해야 합니다.

## 10. 기능별 최종 요약

### 조회수

```text
일반 요청
→ Redis Lua 원자 script
→ count key INCR + dirty set SADD

flush
→ Redisson global RLock
→ snapshot DB 반영
→ snapshot과 현재 Redis 값이 같을 때만 dirty 제거
```

### 좋아요·댓글 수

```text
좋아요:
  PostCounter row PESSIMISTIC_WRITE
  → Like row 저장/삭제
  → PostCounter bulk UPDATE likeCount = likeCount +/- 1

댓글:
  PostCounter bulk UPDATE replyCount = replyCount +/- 1
  → Post PESSIMISTIC_READ로 active 상태 재확인
  → Comment row 저장/삭제
```

### 신고

```text
Post row PESSIMISTIC_WRITE
→ 작성자 User row PESSIMISTIC_WRITE
→ PostReport unique 확인·저장
→ Entity method로 두 counter 변경
→ dirty checking UPDATE
```

### 게시글 수정

```text
요청 version 비교
→ Post @Version 충돌 검사
→ 이미지-only 변경이면 OPTIMISTIC_FORCE_INCREMENT
```

### Refresh Token

```text
refresh token hash에 해당하는 AuthSession PESSIMISTIC_WRITE
→ active 확인
→ rotate
→ commit 후 기존 hash 무효화
```

## 11. 설계 의도에 대한 결론

현재 코드만으로 확정할 수 있는 결론:

1. 조회수 일반 요청은 명시적인 DB/JVM 락보다 Redis Lua와 DB 원자 query를 사용합니다.
2. 조회수 flush는 여러 backend 사이의 Redisson 분산 락을 사용합니다.
3. 좋아요·댓글 수는 공통 `PostCounter` row의 비관적 쓰기 잠금과 bulk update를 사용합니다.
4. 신고는 게시글·작성자 row를 비관적 쓰기 잠금으로 보호하고 Entity dirty checking을 사용합니다.
5. 게시글 수정은 `@Version`과 필요한 경우 `OPTIMISTIC_FORCE_INCREMENT`를 사용합니다.
6. Refresh Token 회전은 `AuthSession` row의 비관적 쓰기 잠금을 사용합니다.

합리적인 설계 의도 해석:

- 고빈도 단순 카운터는 DB/Redis 원자 연산으로 처리하고,
- 신고처럼 여러 Entity의 업무 상태를 함께 변경하는 흐름은 Entity 메서드와
  dirty checking으로 표현하며,
- refresh rotation처럼 같은 token row를 한 번만 소비해야 하는 흐름은 비관적 쓰기
  잠금으로 직렬화했을 가능성이 큽니다.

다만 “신고가 적게 발생해서 dirty checking을 선택했다”는 문장이나 “모든 동시성
문제를 완전히 해결한다”는 문장은 현재 코드와 작성자 기록만으로 확정할 수 없습니다.
교안에서는 반드시 “가능한 설계 의도”라고 표시해야 합니다.
