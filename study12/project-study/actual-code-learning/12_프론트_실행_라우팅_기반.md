# 12. 프론트 실행 기반과 라우팅
## 12.1 이 문서의 범위와 실제 시작점

이 문서는 백엔드 응답을 화면에서 사용하는 단계로 들어가기 전에, 브라우저가 React
애플리케이션을 어떻게 시작하고 현재 URL에 맞는 페이지를 어떻게 선택하는지 설명합니다.
실제 학습 순서는 다음과 같습니다.

```text
package.json
→ vite.config.js
→ index.html
→ src/main.jsx
→ src/App.jsx
→ src/routes/AppRoutes.jsx
→ route guard
→ PageBoundary
→ layout
```

각 파일은 `실제 경로와 책임 → 전체 원문 → 코드 일부와 학습용 주석 → 바로 아래 상세
설명` 순서입니다. 전체 원문은 실제 프로젝트와 대조하기 위한 것이며, 학습용 주석은
문서 안의 발췌 코드에만 추가했습니다. 실제 프론트 소스는 수정하지 않았습니다.

이 문서에서 전체 원문을 확인한 파일은 17개입니다. `package-lock.json`은 소스 실행 로직이
아니지만 설치 버전 고정과 재현 가능한 실행을 확인하기 위해 파일 기준에 포함합니다.

- `package.json`
- `package-lock.json`
- `vite.config.js`
- `index.html`
- `src/main.jsx`
- `src/App.jsx`
- `src/routes/AppRoutes.jsx`
- `src/routes/ProtectedRoute.jsx`
- `src/routes/PublicOnlyRoute.jsx`
- `src/components/layout/PageBoundary.jsx`
- `src/components/layout/PageLayout.jsx`
- `src/components/layout/AuthLayout.jsx`
- `src/components/layout/AppHeader.jsx`
- `src/components/layout/AuthIntroPanel.jsx`

- `src/auth/authStorage.js`

`authApi.js`와 `userApi.js`는 `AppHeader`의 로그아웃·프로필 조회 연결에 필요한 부분만
이 문서에서 발췌하고, 전체 API module은 13번 문서에서 정독합니다.

## 12.2 `package.json`: 프론트 실행 명령과 의존성

### 파일을 지금 읽는 이유

브라우저 코드보다 먼저 이 프로젝트가 어떤 도구로 실행되고 어떤 라이브러리를 제공받는지
확인해야 `createRoot`, `lazy`, `Routes`, `ErrorBoundary`가 어디에서 온 것인지 추측하지
않게 됩니다.

### 파일 책임과 연결

- 실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/package.json`
- 호출하는 파일: npm이 이 파일의 script를 읽어 Vite를 실행합니다.
- 호출되는 파일: `vite`, React, React Router, `react-error-boundary`가 이후 source에서 import됩니다.
- 외부 입력: `npm run dev`, `npm run build`, `npm run lint`, `npm run preview` 명령
- 생성·변경 값: 실행 중인 개발 서버 또는 production build 결과
- 반환값: JavaScript 함수처럼 반환하지 않고 npm script를 정의합니다.
- 예외 지점: dependency가 설치되지 않았거나 script 명령이 실패하면 실행이 중단됩니다.
- 다음 파일: `vite.config.js`

### 전체 실제 코드

```json
{
  "name": "bamboo-board-react",
  "private": true,
  "version": "0.0.0",
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "lint": "oxlint",
    "preview": "vite preview"
  },
  "dependencies": {
    "react": "^19.2.7",
    "react-dom": "^19.2.7",
    "react-error-boundary": "^6.1.2",
    "react-router-dom": "^7.18.1"
  },
  "devDependencies": {
    "@types/react": "^19.2.17",
    "@types/react-dom": "^19.2.3",
    "@vitejs/plugin-react": "^6.0.3",
    "oxlint": "^1.71.0",
    "vite": "^8.1.1"
  }
}
```

### 코드 일부와 바로 아래 설명

```json
"type": "module", // JavaScript 파일에서 ES module import/export 문법을 사용한다.
"scripts": {
  "dev": "vite", // 개발 서버를 실행해 브라우저가 source를 불러오게 한다.
  "build": "vite build", // 배포 가능한 정적 결과물을 만든다.
  "lint": "oxlint", // 현재 JavaScript/JSX 문법과 규칙을 검사한다.
  "preview": "vite preview" // build 결과를 로컬에서 미리 제공한다.
}
```

`type: module` 때문에 `src/main.jsx`의 `import ... from ...`와 `export default`를 사용할
수 있습니다. `dev`는 source를 개발 서버로 제공하고, `build`는 배포 폴더에 넣을 정적
파일을 생성합니다. 이 파일 자체가 React 화면을 렌더링하지 않고, 아래 source가 어떤
실행 환경에서 해석되는지를 정합니다.

```json
"dependencies": {
  "react": "^19.2.7", // 컴포넌트와 Hook을 제공한다.
  "react-dom": "^19.2.7", // React tree를 브라우저 DOM에 연결한다.
  "react-error-boundary": "^6.1.2", // 렌더링 오류를 경계별로 처리한다.
  "react-router-dom": "^7.18.1" // URL과 route element를 연결한다.
}
```

`react`만으로는 브라우저 DOM에 화면을 붙일 수 없으므로 `react-dom`이 필요합니다.
`react-router-dom`은 `BrowserRouter`, `Routes`, `Route`, `Navigate`, `Outlet`을 제공하고,
`react-error-boundary`는 `ErrorBoundary`를 제공합니다. 이 이름들은 사용자가 직접 선언한
문법이 아니라 dependency가 export한 값입니다.

### `package-lock.json`의 위치

`package-lock.json`은 위 dependency의 실제 설치 버전을 고정하는 lock 파일입니다. 현재
실행 흐름에서 새로운 React 문법을 제공하지 않으므로 전체 JSON을 반복해서 정독하지 않고,
배포·CI에서 `npm ci`가 lock 내용을 사용한다는 역할만 확인합니다.

## 12.3 `vite.config.js`: Vite가 React source를 해석하는 설정

### 파일을 지금 읽는 이유

`index.html`에서 `/src/main.jsx`를 브라우저 진입점으로 지정하지만, JSX를 어떤 방식으로
변환하고 개발 서버가 source를 어떻게 제공하는지는 Vite 설정과 React plugin이 담당합니다.

### 파일 책임과 연결

- 실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/vite.config.js`
- 호출하는 파일: Vite CLI(`npm run dev`, `npm run build`)
- 호출되는 값: `defineConfig`, `react` plugin
- 외부 입력: Vite가 이 설정 파일을 읽는 실행 시점
- 생성·변경 값: Vite configuration object와 JSX transform plugin 등록
- 반환값: `defineConfig`로 감싼 설정 객체를 default export합니다.
- 예외 지점: plugin import 또는 설정 해석 실패 시 Vite가 시작되지 않습니다.
- 다음 파일: `index.html`

### 전체 실제 코드

```javascript
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [react()],
})
```

### 코드 일부와 바로 아래 설명

```javascript
import { defineConfig } from 'vite' // Vite가 설정 객체를 해석할 수 있게 도와주는 함수다.
import react from '@vitejs/plugin-react' // JSX와 React Fast Refresh 처리를 제공하는 plugin factory다.

export default defineConfig({ // 이 객체를 Vite가 설정으로 읽도록 default export한다.
  plugins: [react()], // react()가 반환한 plugin을 배열에 등록한다.
})
```

`import { defineConfig }`의 중괄호는 `vite` module이 named export한 값만 가져오는 문법입니다.
`react`는 React 컴포넌트가 아니라 Vite plugin을 만드는 함수입니다. `react()`를 호출한
결과를 `plugins` 배열에 넣으면 Vite가 `.jsx` 파일을 브라우저가 이해할 JavaScript로 변환합니다.
이 파일의 `default export`는 애플리케이션 화면에 표시되는 값이 아니라 Vite 실행기가 읽는
설정 객체입니다.

## 12.4 `index.html`: 브라우저가 React를 꽂을 DOM 자리

### 파일을 지금 읽는 이유

React는 빈 HTML에 스스로 실행되는 것이 아니라, 브라우저가 읽은 `index.html`의 특정 DOM
요소를 root로 삼아 tree를 렌더링합니다. 이 연결을 알아야 `document.getElementById('root')`가
어디에서 온 값인지 이해할 수 있습니다.

### 파일 책임과 연결

- 실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/index.html`
- 호출하는 파일: Vite 개발 서버 또는 build 결과를 제공하는 웹 서버
- 호출되는 파일: `/src/main.jsx` module script
- 외부 입력: 브라우저의 최초 GET 요청
- 생성·변경 값: `id="root"`를 가진 빈 DOM element
- 반환값: HTML 문서이며 JavaScript 함수 반환값은 아닙니다.
- 예외 지점: script 경로가 잘못되면 React 진입점이 실행되지 않습니다.
- 다음 파일: `src/main.jsx`

### 전체 실제 코드

```html
<!doctype html>
<html lang="ko">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>대나무숲</title>
  </head>
  <body>
    <div id="root"></div>
    <script type="module" src="/src/main.jsx"></script>
  </body>
</html>
```

### 코드 일부와 바로 아래 설명

```html
<div id="root"></div> <!-- React가 전체 App tree를 삽입할 실제 DOM container다. -->
<script type="module" src="/src/main.jsx"></script> <!-- 브라우저가 main.jsx module을 실행한다. -->
```

`id="root"`는 React 문법이 아니라 HTML element의 식별자입니다. `main.jsx`가
`document.getElementById('root')`로 같은 element를 찾고, `createRoot(...).render(...)`가
그 안에 React tree를 생성합니다. `type="module"`은 `main.jsx`에서 import/export를
사용할 수 있게 합니다. 아직 화면 컴포넌트가 실행된 것은 아니고, 이 script가 다음 파일을
실행시키는 진입 연결만 만들어 둔 상태입니다.

## 12.5 `src/main.jsx`: React tree의 최초 생성

### 파일을 지금 읽는 이유

이 파일에서 HTML의 `root` element가 React root로 바뀌고, 전역 오류 경계·라우터·개발용
Strict Mode가 어떤 바깥쪽 순서로 감싸는지 결정됩니다. 이후 모든 route와 page는 이 tree
안에서 렌더링됩니다.

### 파일 책임과 연결

- 실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/src/main.jsx`
- 호출하는 파일: `index.html`의 module script
- 호출하는 파일: `App.jsx`, `common.css`, React·Router·ErrorBoundary dependency
- 외부 입력: 브라우저 DOM의 `#root`
- 생성·변경 값: React root와 최상위 component tree
- 반환값: module 실행 자체는 화면을 반환하지 않고 DOM을 갱신합니다.
- 예외 지점: root element가 없거나 초기 render 중 오류가 발생하면 ErrorBoundary 경로가 사용됩니다.
- 다음 파일: `src/App.jsx`

### 전체 실제 코드

```jsx
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import { ErrorBoundary } from "react-error-boundary";
import { BrowserRouter } from "react-router-dom";
import App from "./App.jsx";

import "./styles/common.css";

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <ErrorBoundary
      fallback={(
        <main className="error-view error-view--app">
          <h1>화면을 표시하지 못했습니다.</h1>
          <p>잠시 후 다시 시도해주세요.</p>
          <button type="button" onClick={() => window.location.reload()}>
            새로고침
          </button>
        </main>
      )}
    >
      <BrowserRouter>
        <App />
      </BrowserRouter>
    </ErrorBoundary>
  </StrictMode>,
);
```

### 코드 일부와 바로 아래 설명

```jsx
createRoot(document.getElementById('root')).render( // root DOM에 React root를 만들고 tree를 렌더링한다.
  <StrictMode> // 개발 중 잠재적인 문제를 찾기 위해 React 검사를 활성화한다.
    <ErrorBoundary fallback={( // 하위 렌더링 오류가 나면 이 JSX를 대신 표시한다.
      <main className="error-view error-view--app">
        <h1>화면을 표시하지 못했습니다.</h1>
        <p>잠시 후 다시 시도해주세요.</p>
        <button type="button" onClick={() => window.location.reload()}>
          새로고침
        </button>
      </main>
    )}>
      <BrowserRouter> // 현재 browser URL을 React Router location으로 연결한다.
        <App /> // 실제 route tree를 가진 최상위 사용자 component다.
      </BrowserRouter>
    </ErrorBoundary>
  </StrictMode>,
);
```

`createRoot`는 `react-dom/client`가 제공하는 함수입니다. 먼저 `getElementById('root')`가
HTML container를 반환하고, 그 값을 `createRoot`에 전달해 React 전용 root 객체를 만듭니다.
이후 `.render(...)`의 인자에 들어간 JSX가 실제 화면 tree입니다.

`BrowserRouter`는 URL의 pathname·history를 React Router가 읽게 하는 provider입니다. 이
wrapper가 없으면 아래 `Routes`, `Navigate`, `useLocation`, `useNavigate`가 browser URL과
연결되지 않습니다.

`ErrorBoundary`의 `fallback`은 오류가 발생했을 때 표시할 React element입니다. 버튼의
`onClick={() => window.location.reload()}`는 클릭 시 현재 브라우저 문서를 다시 요청하는
inline arrow function입니다. 이 경계는 route별 `PageBoundary`보다 바깥에 있으므로 route
구성 자체나 초기 App 렌더링 오류까지 처리하는 최상위 안전망입니다.

`StrictMode`는 production에서 화면을 두 번 보여준다는 설정이 아닙니다. React development
검사를 위해 일부 render·Effect setup/cleanup을 추가로 실행해 부작용을 찾을 수 있습니다.
따라서 개발자 도구에서 Effect나 요청이 반복되는 것처럼 보여도, 실제 production 실행 횟수와
동일하다고 단정하면 안 됩니다. 각 Effect가 cleanup을 제공해야 하는 이유가 여기서 나옵니다.

## 12.6 `src/App.jsx`: 최상위 사용자 component

### 파일을 지금 읽는 이유

`main.jsx`가 외부 runtime wrapper를 모두 만든 다음 실제 application component로 넘기는
지점을 확인합니다. 이 파일은 업무 로직을 하지 않고 route component를 한 단계 감쌉니다.

### 파일 책임과 연결

- 생성·변경 값: `AppRoutes` React element
- 반환값 사용 위치: `main.jsx`의 BrowserRouter 하위에 렌더링됩니다.
- 예외 지점: AppRoutes 렌더링 오류는 main의 ErrorBoundary로 전파됩니다.
- 다음 파일: `src/routes/AppRoutes.jsx`

### 전체 실제 코드

```jsx
import AppRoutes from "./routes/AppRoutes.jsx";

function App() {
    return <AppRoutes />;
}

export default App;
```

### 코드 일부와 바로 아래 설명

```jsx
function App() { // 사용자가 만든 React function component를 선언한다.
    return <AppRoutes />; // route 선언 component를 React element로 만들어 반환한다.
}

export default App; // main.jsx가 default import App로 가져올 수 있게 export한다.
```

함수 component는 호출자가 일반 함수처럼 직접 부르는 대신 JSX `<App />`로 사용합니다.
React가 render 과정에서 함수를 호출하고 반환된 element tree를 화면에 반영합니다.
`App`이 `AppRoutes`를 직접 import하는 이유는 애플리케이션의 실제 URL 선택 책임을 route
파일에 모으기 위해서입니다.

- 반환값 사용 위치: `App`가 반환하고 `main.jsx`의 React tree에 표시됩니다.
- 예외 지점: lazy module import 실패는 `PageBoundary`의 ErrorBoundary로 전파됩니다.
- 다음 파일: `ProtectedRoute.jsx`, `PublicOnlyRoute.jsx`, `PageBoundary.jsx`

### 전체 실제 코드

```jsx
import { lazy } from "react";
import { Navigate, Route, Routes } from "react-router-dom";

import PageBoundary from "../components/layout/PageBoundary.jsx";
import ProtectedRoute from "./ProtectedRoute.jsx";
import PublicOnlyRoute from "./PublicOnlyRoute.jsx";

const LoginPage = lazy(() => import("../pages/auth/LoginPage.jsx"));
const SignupPage = lazy(() => import("../pages/auth/SignupPage.jsx"));
const PostsPage = lazy(() => import("../pages/posts/PostsPage.jsx"));
const PostDetailPage = lazy(() => import("../pages/posts/PostDetailPage.jsx"));
const PostCreatePage = lazy(() => import("../pages/posts/PostCreatePage.jsx"));
const PostEditPage = lazy(() => import("../pages/posts/PostEditPage.jsx"));
const ProfileEditPage = lazy(() => import("../pages/user/ProfileEditPage.jsx"));
const PasswordEditPage = lazy(() => import("../pages/user/PasswordEditPage.jsx"));

function page(element) {
    return <PageBoundary>{element}</PageBoundary>;
}

function AppRoutes() {
    return (
        <Routes>
            <Route path="/" element={<Navigate to="/posts" replace />} />

            <Route element={<PublicOnlyRoute />}>
                <Route path="/login" element={page(<LoginPage />)} />
                <Route path="/signup" element={page(<SignupPage />)} />
            </Route>

            <Route element={<ProtectedRoute />}>
                <Route path="/posts" element={page(<PostsPage />)} />
                <Route path="/posts/new" element={page(<PostCreatePage />)} />
                <Route path="/posts/:postId" element={page(<PostDetailPage />)} />
                <Route path="/posts/:postId/edit" element={page(<PostEditPage />)} />
                <Route path="/profile/edit" element={page(<ProfileEditPage />)} />
                <Route path="/password/edit" element={page(<PasswordEditPage />)} />
            </Route>

            <Route path="*" element={<Navigate to="/posts" replace />} />
        </Routes>
    );
}

export default AppRoutes;
```

### 코드 일부와 바로 아래 설명: lazy import

```jsx
const LoginPage = lazy(() => import("../pages/auth/LoginPage.jsx")); // 필요할 때 LoginPage module을 읽는 React component를 만든다.
const SignupPage = lazy(() => import("../pages/auth/SignupPage.jsx")); // SignupPage도 처음 route에 들어갈 때 읽는다.
```

정적인 `import LoginPage from "..."`는 module 평가 시 파일을 바로 포함합니다. 여기의
`import("...")`는 함수처럼 실행되는 **동적 import**이며 module이 준비되면 Promise를
반환합니다. `lazy`는 그 Promise를 React가 렌더링할 수 있는 component 형태로 감쌉니다.
따라서 `lazy`가 없으면 Promise 자체를 `<LoginPage />`처럼 사용할 수 없습니다. `lazy`가
준비 중일 때는 아래 `PageBoundary` 안의 `Suspense fallback`이 대신 표시됩니다.

```jsx
function page(element) {
    return <PageBoundary>{element}</PageBoundary>; // 전달받은 page element를 오류·로딩 경계의 children으로 넣는다.
}
```

`page(<PostsPage />)`는 JavaScript 함수 호출입니다. 이 함수가 반환한 결과는
`<PageBoundary>{<PostsPage />}</PageBoundary>`와 같은 React element 구조입니다. React가
자동으로 `PageBoundary`를 붙이는 문법이 아니라, 이 프로젝트의 `page` 함수가 직접
`PageBoundary`를 감싼 것입니다. `{element}`는 JSX 안에서 JavaScript 변수의 값을 자식으로
삽입하는 문법입니다.

### 코드 일부와 바로 아래 설명: route grouping

```jsx
<Routes> // 현재 URL과 자식 Route를 비교해 하나의 route element를 선택한다.
    <Route path="/" element={<Navigate to="/posts" replace />} /> // 루트 접근을 게시글 목록으로 이동시킨다.

    <Route element={<PublicOnlyRoute />}> // element 자체는 URL이 아니라 guard wrapper다.
        <Route path="/login" element={page(<LoginPage />)} /> // 비로그인 전용 화면이다.
        <Route path="/signup" element={page(<SignupPage />)} /> // 비로그인 전용 화면이다.
    </Route>

    <Route element={<ProtectedRoute />}> // 로그인 여부를 먼저 판단하는 guard wrapper다.
        <Route path="/posts" element={page(<PostsPage />)} /> // 로그인 후 게시글 목록이다.
        <Route path="/posts/:postId" element={page(<PostDetailPage />)} /> // :postId는 URL parameter다.
    </Route>

    <Route path="*" element={<Navigate to="/posts" replace />} /> // 앞에서 매칭되지 않은 URL의 fallback이다.
</Routes>
```

중첩 `Route`에 path가 없어도 `element`는 부모 route가 매칭된 뒤 실행되는 wrapper가 될 수
있습니다. wrapper가 `Outlet`을 반환하면 현재 매칭된 자식 route element가 그 자리에
렌더링됩니다. 따라서 `/posts` 요청은 `ProtectedRoute` → `PageBoundary` → `PostsPage`
순서로 내려갑니다.

`/posts/:postId`의 `:postId`는 실제 문자열이 아니라 React Router가 URL에서 추출하는
parameter 이름입니다. 상세 page가 실제 값 `123`을 얻는 방식은 15번 문서에서
`useParams`와 함께 확인합니다.

`Navigate`는 현재 route를 다른 경로로 이동시키는 React Router component입니다.
`replace`가 있으면 history stack에 현재 잘못된 경로를 별도 entry로 남기지 않습니다.
즉 `/`에서 `/posts`로 이동한 뒤 뒤로가기를 눌렀을 때 같은 redirect가 반복되는 것을
줄이는 설정입니다.

## 12.8 `ProtectedRoute.jsx`: 로그인 필요한 자식 route의 관문

### 파일을 지금 읽는 이유

게시글·회원정보 route가 실제 page를 렌더링하기 전에 access token 존재 여부를 검사하는
지점입니다. 이 파일을 이해해야 `<Outlet />`이 왜 필요한지, guard가 실제 page를 직접
import하지 않고도 자식 route를 통과시키는 이유를 알 수 있습니다.

### 파일 책임과 연결

- 실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/src/routes/ProtectedRoute.jsx`
- 호출하는 파일: `AppRoutes.jsx`의 `<Route element={<ProtectedRoute />}>`
- 호출되는 파일: `authStorage.isLoggedIn()`, 통과 시 React Router의 현재 child route
- 외부 입력: 현재 route와 localStorage의 access token
- 생성·변경 값: redirect element 또는 child route element
- 반환값 사용 위치: 부모 `Route`가 반환된 element를 화면에 렌더링합니다.
- 예외 지점: localStorage 접근 오류가 나면 상위 ErrorBoundary로 전파될 수 있습니다.
- 다음 파일: `PublicOnlyRoute.jsx`

### 전체 실제 코드

```jsx
import { Navigate, Outlet } from "react-router-dom";

import { authStorage } from "../auth/authStorage.js";

function ProtectedRoute() {
    if (!authStorage.isLoggedIn()) {
        return <Navigate to="/login" replace />;
    }

    return <Outlet />;
}

export default ProtectedRoute;
```

### 코드 일부와 바로 아래 설명

```jsx
function ProtectedRoute() {
    if (!authStorage.isLoggedIn()) { // localStorage access token이 있는지 확인한다.
        return <Navigate to="/login" replace />; // 없으면 자식 page 대신 로그인 URL로 이동한다.
    }

    return <Outlet />; // 로그인 조건을 통과하면 현재 매칭된 자식 Route element를 이 자리에 넣는다.
}
```

`ProtectedRoute`는 사용자가 직접 만든 function component이고, `Navigate`와 `Outlet`은
`react-router-dom`이 제공하는 component입니다. `return`은 현재
`ProtectedRoute()` 실행을 끝내며, 조건이 참이면 `<Navigate />` element를 부모 Route에
반환합니다. 조건이 거짓이면 `<Outlet />`을 반환합니다.

`Outlet`은 자동으로 모든 페이지를 보여주는 문법이 아닙니다. `AppRoutes.jsx`에서
`ProtectedRoute`를 부모 `Route element`로 지정했기 때문에 React Router가 현재 URL에
해당하는 자식 route element를 그 outlet 위치에 전달합니다. 예를 들어 `/posts`는
`ProtectedRoute`가 통과한 뒤 `page(<PostsPage />)`가 `<Outlet />` 위치에 렌더링됩니다.

`authStorage.isLoggedIn()`은 현재 구현상 token의 유무만 확인합니다. token의 서명 유효성,
만료, 실제 백엔드 인증은 `api.js` 요청과 백엔드 JWT filter에서 별도로 처리되며, 그 전체
흐름은 13번 이후 인증 API 문서와 기존 인증 문서에서 연결합니다.

## 12.10 `PageBoundary.jsx`: 페이지별 lazy loading과 오류 경계

### 파일을 지금 읽는 이유

`AppRoutes.page()`가 모든 page element를 이 component로 감싸므로, lazy module이 준비될
때 표시할 loading 화면과 해당 page에서 발생한 render 오류의 복구 UI가 여기서 결정됩니다.

### 파일 책임과 연결

- 실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/src/components/layout/PageBoundary.jsx`
- 호출하는 파일: `AppRoutes.jsx`의 `page(element)` 함수
- 호출되는 파일: `ErrorBoundary`, `Suspense`, `ErrorView`, `LoadingView`, `useLocation`, `useNavigate`
- 외부 입력: `children` page element, 현재 location
- 생성·변경 값: error boundary instance와 loading/error fallback 화면
- 반환값 사용 위치: `page()`가 반환하고 nested Route가 렌더링합니다.
- 예외 지점: child page render 또는 lazy import 오류
- 다음 파일: `PageLayout.jsx`, `AuthLayout.jsx`

### 전체 실제 코드

```jsx
import { Suspense } from "react";
import { ErrorBoundary } from "react-error-boundary";
import { useLocation, useNavigate } from "react-router-dom";

import ErrorView from "../common/ErrorView.jsx";
import LoadingView from "../common/LoadingView.jsx";

function PageBoundary({ children }) {
    const location = useLocation();
    const navigate = useNavigate();

    return (
        <ErrorBoundary
            key={location.key}
            fallbackRender={({ resetErrorBoundary }) => (
                <ErrorView
                    message="페이지를 다시 열거나 게시글 목록으로 이동해주세요."
                    onRetry={() => {
                        resetErrorBoundary();
                        navigate(0);
                    }}
                />
            )}
        >
            <Suspense fallback={<LoadingView />}>
                {children}
            </Suspense>
        </ErrorBoundary>
    );
}

export default PageBoundary;
```

### 코드 일부와 바로 아래 설명: props와 Router Hook

```jsx
function PageBoundary({ children }) { // 호출자가 JSX 사이에 넣은 값을 children prop으로 구조분해한다.
    const location = useLocation(); // BrowserRouter의 현재 location 객체를 읽는다.
    const navigate = useNavigate(); // 현재 history location을 이동시키는 함수를 받는다.
```

`{ children }`은 객체에서 `children` property를 꺼내는 JavaScript 구조분해 문법입니다.
`AppRoutes`의 `page(<PostsPage />)`가 반환한 `<PageBoundary>{<PostsPage />}</PageBoundary>`에서
안쪽 page element가 `children` 값이 됩니다. `useLocation`과 `useNavigate`는 Router
context가 제공하는 Hook이므로 `BrowserRouter` 바깥에서 호출하면 안 됩니다.

### 코드 일부와 바로 아래 설명: ErrorBoundary

```jsx
<ErrorBoundary
    key={location.key} // URL 이동마다 location key가 바뀌면 경계를 새 React instance처럼 다시 시작한다.
    fallbackRender={({ resetErrorBoundary }) => ( // 오류 시 실행할 fallback 함수를 받는다.
        <ErrorView
            message="페이지를 다시 열거나 게시글 목록으로 이동해주세요."
            onRetry={() => {
                resetErrorBoundary(); // 현재 경계의 오류 상태를 초기화한다.
                navigate(0); // 현재 URL을 다시 탐색해 page를 재렌더링한다.
            }}
        />
    )}
>
```

`ErrorBoundary`는 `react-error-boundary`가 제공하는 component입니다. 자식 render 중
예외가 발생하면 정상 child 대신 `fallbackRender`의 결과를 보여줍니다.

`key`는 React가 같은 component를 같은 instance로 볼지 결정하는 식별자입니다.
`location.key`가 바뀐다는 것은 Router가 다른 history location을 만들었다는 뜻이므로,
이 경계를 이전 오류 상태를 가진 instance로 계속 재사용하지 않고 새로 시작하게 합니다.
이 값이 바뀐다고 페이지 요청이 자동으로 두 번 실행된다는 뜻은 아닙니다.

`resetErrorBoundary()`는 오류 상태를 초기화하고, `navigate(0)`은 현재 위치를 다시 탐색해
page를 재실행합니다. 두 호출은 각각 “경계 상태 초기화”와 “현재 route 재로딩”이라는
별도 역할입니다.

### 코드 일부와 바로 아래 설명: Suspense와 children

```jsx
<Suspense fallback={<LoadingView />}> // lazy page가 준비될 때까지 LoadingView를 표시한다.
    {children} // 준비가 끝나면 page()가 전달한 실제 page element를 이 자리에 렌더링한다.
</Suspense>
```

`Suspense`는 React가 제공하는 loading 경계입니다. `lazy(() => import(...))`가 아직
module을 준비하지 못했을 때 lazy component가 “준비 중” 상태를 알리고, Suspense가
`fallback`을 대신 렌더링합니다. Promise를 화면에 직접 넣는 것이 아니라 `lazy`가 만든
React component를 children으로 넣는 구조입니다.

`children`은 Suspense가 자동으로 만들어 주는 값이 아닙니다. `AppRoutes`의 `page()`가
`PageBoundary`에 전달한 실제 page element가 함수 parameter를 거쳐 여기까지 온 것입니다.
module이 준비되면 같은 children element가 정상 화면으로 표시됩니다.

```jsx
    backTo = "/posts", // 뒤로가기 Link의 기본 목적지다.
    profileImage, // Header가 바로 사용할 수 있는 profile image 값이다.
    children, // page 본문 element다.
}) {
```

parameter 객체를 `{ ... }`로 구조분해하고 default value를 함께 지정하는 JavaScript
문법입니다. `showBack = false`와 `backTo = "/posts"`는 호출자가 prop을 생략했을 때만
사용됩니다. `children`은 PageLayout 태그 사이에 작성된 page 본문입니다.

```jsx
<ErrorBoundary fallback={<ErrorView title="헤더를 표시하지 못했습니다." />}>
    <AppHeader // Header 하나에서 오류가 나도 page main 전체를 대체하지 않는다.
        title={title} // 부모 prop을 Header prop으로 전달한다.
        showBack={showBack}
        backTo={backTo}
        showProfile // 값 없이 작성한 boolean prop은 true다.
        profileImage={profileImage}
    />
</ErrorBoundary>
<main className={mainClassName}>{children}</main> // 본문은 Header 경계 밖의 main 위치에 표시한다.
```

`showProfile`처럼 값 없이 작성한 JSX prop은 `true`가 됩니다. Header 오류를 별도
`ErrorBoundary`로 감싸는 이유는 Header 문제를 page 본문 전체 오류와 분리하기 위해서입니다.
PageLayout 자체가 return한 element는 호출한 page가 다시 반환하고, 최종적으로
`PageBoundary`의 children으로 이어집니다.

## 12.12 `AuthLayout.jsx`: 로그인·회원가입 공통 골격

### 코드 일부와 바로 아래 설명

```jsx

```

`...intro`는 JSX spread attribute입니다. 예를 들어 `intro`가 `{ title, description }`이면
`<AuthIntroPanel title={intro.title} description={intro.description} />`처럼 전달됩니다.

```jsx

</ErrorBoundary>
```

소개 영역 오류와 form 오류를 별도 경계로 나눈 이유는 한 영역이 실패해도 다른 영역의
fallback을 표시할 수 있게 하기 위해서입니다. `{children}`은 AuthLayout이 자동으로
생성하는 화면이 아니라 LoginPage·SignupPage가 전달한 form element입니다.

### 코드 일부와 바로 아래 설명: state·ref·초기값

```jsx
const navigate = useNavigate(); // Router history를 변경하는 함수를 받는다.
const menuRef = useRef(null); // DOM의 header-profile element를 가리킬 mutable ref다.
const [isMenuOpen, setIsMenuOpen] = useState(false); // 메뉴 표시 여부와 setter를 만든다.

```

`useState`는 state 값과 값을 바꾸는 setter를 배열로 반환합니다. setter가 실행되면
component가 다시 render되고 새 state가 JSX 조건문에 반영됩니다. `useRef`의 `current`는
렌더링 사이에도 유지되지만 값을 바꿔도 render를 일으키지 않습니다. 그래서 DOM 밖을
클릭했는지 검사할 element 참조에 사용합니다.

`??`는 nullish coalescing 연산자입니다. 왼쪽이 `null` 또는 `undefined`일 때만 오른쪽
값을 사용하므로 빈 문자열이나 유효한 image URL은 유지합니다.

### 코드 일부와 바로 아래 설명: 프로필 API Effect

```jsx
useEffect(() => {
    if (!showProfile) { // 이 Header가 profile menu를 사용하지 않는 layout이면 요청하지 않는다.
        return; // 현재 Effect callback만 종료한다.
    }

    if (profileImage !== undefined) { // 부모가 prop을 전달했다면 API 결과를 기다리지 않는다.
        setResolvedProfileImage(profileImage); // 전달된 image를 state에 반영한다.
        return; // 이 Effect의 cleanup은 아직 만들지 않았다.
    }

    const controller = new AbortController(); // 이 Effect가 시작한 fetch를 취소할 객체를 만든다.
    userApi.getMyInfo({ signal: controller.signal }) // API module에 취소 signal을 전달한다.
        .then((user) => {
            setResolvedProfileImage(user?.profileImage ?? null); // 성공 응답에서 image만 state로 저장한다.
        })
        .catch((error) => {
            if (controller.signal.aborted || error?.name === "AbortError") { // cleanup에 의한 취소인지 확인한다.
                return; // 취소된 요청의 늦은 실패를 정상 오류로 표시하지 않는다.
            }
            setResolvedProfileImage(null); // 다른 API 오류에서는 빈 프로필 상태로 되돌린다.
        });

    return () => {
        controller.abort(); // dependency가 바뀌거나 unmount될 때 이 요청을 취소한다.
    };
}, [profileImage, showProfile]); // 두 값이 바뀔 때 Effect를 cleanup 후 다시 실행한다.
```

`useEffect`는 render 결과를 계산하는 함수가 아니라 render 이후 외부 시스템과 동기화하는
React Hook입니다. 여기서는 user API 요청이라는 외부 작업을 시작하고, cleanup에서 같은
Effect가 만든 요청을 취소합니다.

`[profileImage, showProfile]`은 dependency array입니다. 최초 mount와 두 값의 변경 때
Effect가 실행됩니다. 변경 시 React는 이전 Effect의 cleanup을 먼저 실행한 뒤 새 Effect를
시작합니다. cleanup의 `abort()`는 이전 요청을 취소하고, 이미 응답이 도착한 경우에도
`signal.aborted` 검사로 낡은 응답이 state를 덮어쓰는 것을 막습니다.

`user?.profileImage`의 `?.`는 optional chaining입니다. `user`가 null/undefined이면
오류를 던지지 않고 undefined를 만들고, `?? null`이 최종 state를 null로 정리합니다.

### 코드 일부와 바로 아래 설명: 문서 클릭과 cleanup

```jsx
useEffect(() => {
    function closeMenu(event) {
        if (menuRef.current && !menuRef.current.contains(event.target)) { // 메뉴 바깥 클릭인지 확인한다.
            setIsMenuOpen(false); // 바깥이면 메뉴를 닫는다.
        }
    }

    document.addEventListener("mousedown", closeMenu); // document에 전역 이벤트 listener를 등록한다.
    return () => document.removeEventListener("mousedown", closeMenu); // unmount 시 같은 함수 등록을 제거한다.
}, []); // mount 시 한 번 등록하고 unmount cleanup만 실행한다.
```

`addEventListener`에 전달한 함수와 `removeEventListener`에 전달한 함수가 같아야 listener가
제거됩니다. 그래서 `closeMenu`를 Effect 안에서 만들고 같은 함수 reference를 cleanup에서
사용합니다. 빈 dependency array는 이 Effect가 현재 component instance의 mount/unmount
수명에 연결된다는 뜻입니다.

### 코드 일부와 바로 아래 설명: 로그아웃과 DOM 조건부 렌더링

```jsx
async function handleLogout() {
    try {
        await authApi.logout(); // 백엔드 세션 revoke 요청이 끝날 때까지 기다린다.
    } finally {
        authStorage.removeAccessToken(); // API 성공·실패와 관계없이 브라우저 access token을 지운다.
        navigate("/login", { replace: true }); // 현재 화면을 로그인 route로 바꾼다.
    }
}
```

`async` 함수는 Promise를 반환하고, `await`는 logout Promise가 settle될 때까지 함수의
나머지 실행을 잠시 중단합니다. `finally`는 성공과 예외 모두에서 실행되므로, 서버 요청이
실패해도 로컬 인증 상태를 지우고 로그인 화면으로 이동합니다. 실제 `authApi.logout()`의
HTTP 요청과 refresh 처리는 13번 문서에서 전체 module로 확인합니다.

```jsx
{showProfile && ( // showProfile이 true일 때만 profile DOM subtree를 만든다.
    <div className="header-profile" ref={menuRef}> // ref.current가 이 div DOM을 가리키게 된다.
        <button onClick={() => setIsMenuOpen((open) => !open)}> // 이전 state를 받아 반대로 바꾼다.
            {resolvedProfileImage && ( // image 값이 있을 때만 img element를 만든다.
                <img src={resolvedProfileImage} alt="프로필 이미지" />
            )}
        </button>
        <nav className={`profile-menu ${isMenuOpen ? "is-open" : ""}`.trim()}> // state에 따라 CSS class를 만든다.
```

`&&` 조건부 렌더링에서 왼쪽이 falsy이면 오른쪽 JSX가 렌더링되지 않습니다. `onClick`
화살표 함수는 클릭 시점의 이전 state를 setter callback parameter `open`으로 받고 반전합니다.
template literal의 `${...}`는 JavaScript 값을 문자열에 삽입하는 문법이고, 삼항 연산자는
메뉴가 열렸을 때만 `is-open` class를 추가합니다.

## 12.15 `ErrorView.jsx`와 `LoadingView.jsx`: 경계가 표시하는 fallback

두 파일은 PageBoundary와 layout ErrorBoundary가 실제로 렌더링하는 UI입니다. API 호출이나
route 선택을 담당하지 않으므로 이 문서에서는 전체 원문과 fallback 연결만 확인합니다.

### `ErrorView.jsx` 전체 실제 코드

실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/src/components/common/ErrorView.jsx`

```jsx
function ErrorView({
    title = "화면을 표시하지 못했습니다.",
    message = "잠시 후 다시 시도해주세요.",
    onRetry,
}) {
    return (
        <section className="error-view" role="alert">
            <h2>{title}</h2>
            <p>{message}</p>
            {onRetry && (
                <button type="button" onClick={onRetry}>
                    다시 시도
                </button>
            )}
        </section>
    );
}

export default ErrorView;
```

```jsx
function ErrorView({ title = "화면을 표시하지 못했습니다.", message = "잠시 후 다시 시도해주세요.", onRetry }) {
    // fallback이 전달하지 않은 title/message를 기본 문장으로 채운다.
    return (
        <section role="alert">
            <h2>{title}</h2> // 전달된 오류 제목을 출력한다.
            <p>{message}</p> // 전달된 오류 설명을 출력한다.
            {onRetry && <button onClick={onRetry}>다시 시도</button>} // callback이 있을 때만 재시도 button을 만든다.
        </section>
    );
}
```

`onRetry`는 함수 prop입니다. PageBoundary는 `resetErrorBoundary()`와 `navigate(0)`을
실행하는 함수를 이 prop으로 전달하고, 단순 fallback은 prop을 생략해 버튼을 표시하지
않습니다.

### `LoadingView.jsx` 전체 실제 코드

실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/src/components/common/LoadingView.jsx`

```jsx
function LoadingView({ message = "화면을 불러오는 중입니다." }) {
    return (
        <div className="loading-view" role="status" aria-live="polite">
            {message}
        </div>
    );
}

export default LoadingView;
```

```jsx
<Suspense fallback={<LoadingView />}> // lazy module 준비 전 LoadingView element를 fallback으로 사용한다.
    {children} // 준비가 끝나면 이 위치가 실제 page element로 바뀐다.
</Suspense>
```

`LoadingView`는 자체적으로 API를 기다리지 않습니다. `Suspense`가 lazy module의 준비 상태를
감지해 fallback을 렌더링할 때만 표시됩니다. API 요청 중 로딩 화면은 각 page의 state와
`LoadingView` 사용 여부에 따라 별도 흐름이며, 여기의 lazy module 대기와 동일하다고
간주하지 않습니다.

## 12.16 `authStorage.js`: route guard가 읽는 token 저장소

### 파일을 지금 읽는 이유

`ProtectedRoute`와 `PublicOnlyRoute`가 호출하는 `authStorage.isLoggedIn()`의 선언 위치를
확인해야 route guard가 무엇을 검사하는지 추측하지 않게 됩니다.

### 파일 책임과 연결

- 실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/src/auth/authStorage.js`
- 호출하는 파일: `ProtectedRoute`, `PublicOnlyRoute`, `AppHeader`, 이후 `api.js`·`authApi.js`
- 호출되는 API: browser `localStorage`
- 외부 입력: localStorage의 `accessToken` 값
- 생성·변경 값: token 저장·삭제
- 반환값 사용 위치: `isLoggedIn()`은 route redirect 조건, `getAccessToken()`은 request header 흐름에 사용됩니다.
- 예외 지점: 브라우저 storage 접근이 불가능한 환경에서는 storage API 오류가 날 수 있습니다.
- 다음 파일: 13번 문서의 `api.js`, `authApi.js`, 인증 화면

### 전체 실제 코드

```javascript
const ACCESS_TOKEN_KEY = "accessToken";

export const authStorage = {
    getAccessToken() {
        return localStorage.getItem(ACCESS_TOKEN_KEY);
    },

    setAccessToken(accessToken) {
        localStorage.setItem(ACCESS_TOKEN_KEY, accessToken);
    },

    removeAccessToken() {
        localStorage.removeItem(ACCESS_TOKEN_KEY);
    },

    isLoggedIn() {
        return Boolean(authStorage.getAccessToken());
    },
};
```

### 코드 일부와 바로 아래 설명

```javascript
const ACCESS_TOKEN_KEY = "accessToken"; // localStorage에서 사용할 key 문자열을 한 곳에서 공유한다.

export const authStorage = { // 여러 module이 같은 storage 기능 객체를 named import한다.
    getAccessToken() {
        return localStorage.getItem(ACCESS_TOKEN_KEY); // 저장된 문자열 또는 null을 반환한다.
    },
    isLoggedIn() {
        return Boolean(authStorage.getAccessToken()); // token 값이 있으면 true, null/빈 값이면 false다.
    },
};
```

`localStorage`는 브라우저가 제공하는 key-value 저장 객체입니다. `getItem`의 반환값은
문자열 또는 `null`이고, `Boolean(...)`은 이를 명시적인 boolean으로 변환합니다. 현재
`isLoggedIn()`은 JWT를 decode하거나 만료를 검증하지 않고 **저장된 값의 존재만** 확인합니다.
실제 서버 인증은 API 요청의 Authorization header와 백엔드 JWT 검증이 담당합니다.

`authStorage`는 사용자가 만든 객체이며 `localStorage`는 browser API입니다. `export const`
로 named export했으므로 `import { authStorage } from "..."` 형태로 가져옵니다. 이 파일의
`setAccessToken()`과 `removeAccessToken()`이 실제 로그인·로그아웃 시 언제 호출되는지는
13번 `authApi.js`와 form 흐름에서 이어서 확인합니다.

## 12.17 애플리케이션 시작부터 페이지 표시까지 전체 실행 흐름

### 비로그인 상태에서 `/login`에 접근하는 경우

```text
브라우저가 index.html 요청
→ <div id="root">와 /src/main.jsx 로드
→ main.jsx의 createRoot().render()
→ StrictMode
→ 전역 ErrorBoundary
→ BrowserRouter
→ App
→ AppRoutes
→ PublicOnlyRoute
→ authStorage.isLoggedIn() == false
→ Outlet
→ /login Route
→ page(<LoginPage />)
→ PageBoundary
→ lazy LoginPage module 대기
→ 준비 전 LoadingView
→ 준비 완료 후 LoginPage
```

### 로그인 상태에서 `/posts`에 접근하는 경우

```text
BrowserRouter가 현재 URL을 제공
→ AppRoutes가 /posts Route를 선택
→ ProtectedRoute 실행
→ authStorage.isLoggedIn() == true
→ Outlet
→ page(<PostsPage />)
→ PageBoundary의 ErrorBoundary·Suspense
→ PostsPage 표시
```

여기서 route guard의 token 존재 확인과 백엔드의 실제 JWT 검증은 서로 다른 단계입니다.
프론트 guard가 통과해도 API 요청의 token이 만료되었으면 `api.js`가 401 응답을 받고 refresh
흐름으로 이어질 수 있습니다. 그 HTTP module은 13번에서 설명합니다.

### 작성 순서와 실행 순서의 차이

- 작성·의존성 순서: `package.json`에서 라이브러리를 선언하고, `main.jsx`에서 App을 감싼 뒤,
  `AppRoutes.jsx`에서 route를 선언합니다.
- 실제 실행 순서: 브라우저가 `index.html`을 읽고 `main.jsx`를 실행한 뒤 React가 현재 URL에
  맞는 guard와 page를 render합니다.
- `lazy` page module은 AppRoutes 파일을 평가할 때 page source 전체를 즉시 실행하지 않고,
  해당 route element가 실제로 렌더링될 때 동적 import를 시작합니다.
- `PageBoundary`는 route를 선택하지 않습니다. 이미 선택된 page element의 loading/error
  경계를 제공합니다.

## 12.20 모범 답안

1. `index.html`의 `<div id="root">`를 `document.getElementById('root')`가 찾아 `createRoot()`에 전달하고, `.render()`가 React tree를 그 안에 삽입합니다.
2. `BrowserRouter`가 제공하는 context를 `Routes`, `Navigate`, `Outlet`, `useLocation`, `useNavigate`가 사용하기 때문입니다.
3. 정적 import는 module 평가 시 바로 읽고, lazy 동적 import는 해당 component가 필요한 시점에 Promise로 module을 읽습니다.
4. 프로젝트의 `page(element)` 함수가 직접 `<PageBoundary>{element}</PageBoundary>`를 반환합니다.
5. 부모 Route인 `ProtectedRoute`가 매칭된 자식 Route의 element를 Outlet 위치에 렌더링합니다.
6. 프론트는 localStorage에 값이 있는지만 보고, 백엔드는 서명·만료·authVersion 등 token의 유효성을 검증합니다.
7. `AppRoutes`의 `page(<Page />)`가 PageBoundary의 children으로 전달한 실제 page element입니다.
8. React가 이전 오류 상태를 가진 boundary를 재사용하지 않고 새로운 instance로 취급해 다시 시작합니다.
9. Effect가 끝나거나 dependency가 바뀐 뒤 이전 요청의 늦은 응답이 현재 state를 덮어쓰지 않게 요청을 취소합니다.
10. layout이 공통 header와 본문 배치를 담당하고, 실제 LoginForm·PostsPage 같은 page는 children으로 주입하기 위해서입니다.
11. 현재 구현은 `accessToken` 값의 존재만 boolean으로 확인하며 JWT 서명·만료 검증은 하지 않습니다.
12. React development StrictMode가 부작용을 찾기 위해 render와 Effect setup/cleanup을 추가로 확인하기 때문이며 production 동작과 동일하다고 볼 수 없습니다.
