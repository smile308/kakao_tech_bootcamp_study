## 2. 현재 문서의 문제 진단

### 2.1 실행 순서와 학습 순서가 섞여 있습니다

04장은 “실행 순서와 학습 순서를 분리하지 않는다”고 명시하지만, 실제로는 `LoginPage`에서 시작한 뒤 중간에 Filter 설정, DTO 선언, `CustomUserDetails`, Service, Controller가 섞여 있습니다. 코드를 작성할 때 먼저 선언된 순서와 HTTP 요청이 실행되는 순서를 구분해서 읽어야 하는 목표와 충돌합니다.

수정 후 각 문서는 다음 두 부분을 명확히 분리합니다.

1. **실행 지도**: 사용자의 동작부터 응답까지 실제 runtime 순서
2. **코드 읽기 순서**: 위 실행을 이해하기 위해 먼저 읽을 타입·Bean·method의 순서

### 2.2 하나의 실행 흐름이 여러 문서의 중간 절로 흩어져 있습니다

현재 예시는 다음과 같습니다.

- 로그인은 04장에서 `api.js`의 로그인 부분을 보고, `SecurityConfig`, `SessionOriginInterceptor`, DTO, Service, Controller를 순서대로 보지만 Refresh·logout body는 다른 장의 중간으로 이동합니다.
- Refresh는 06장에서 `api.js`의 `request` 일부와 `performRefresh`를 분리해 보고, `SessionController`, `SessionService`, `AuthSession`, Repository, DTO를 다시 연결해야 합니다.
- Cookie 만료는 07장의 logout뿐 아니라 08장의 `UserController` 비밀번호 변경·탈퇴에서도 사용됩니다.
- `AuthSessionRepository`는 refresh의 row lock, logout의 revoke, scheduler의 expired delete가 서로 다른 장에 나뉘어 있습니다.

수정 후에는 한 문서가 한 완성된 실행 흐름을 끝까지 담도록 합니다. 같은 파일을 여러 흐름에서 사용하는 경우에도 해당 흐름에 필요한 실제 method와 호출 위치를 그 문서 안에 함께 둡니다. 공통 class의 전체 원문을 무조건 반복하지 않고, 반복되는 부분은 “앞에서 본 전체 코드”라고 표시하되 현재 흐름에 필요한 호출·반환값은 생략하지 않습니다.

### 2.3 실제 코드 대신 다른 장으로 넘기는 자리표시자가 있습니다

04장의 `SessionController` 부분에는 Refresh와 logout method의 body를 다음 장에서 읽으라는 주석형 placeholder가 있습니다.

```java
// 06장에서 전체 body를 읽는다.
// 07장에서 전체 body를 읽는다.
```

이는 파일 전체를 읽으려는 목적과 맞지 않습니다. 수정 후에는 각 실행 흐름 문서에 해당 method의 실제 body를 배치하고, 다른 장으로 넘길 때는 중복되는 문법만 참조합니다. 설명용 축약 코드를 실제 원문처럼 표시하지 않습니다.

### 2.4 교안 원문과 실제 소스가 어긋난 부분이 있습니다

검수 중 확인한 대표 사례입니다.

- 현재 05장 `SecurityConfig` 코드 블록에는 `SecurityFilterChain` import가 중복되어 있습니다. 실제 `SecurityConfig.java`에는 한 번만 있습니다.
- 현재 04장에는 로그인 흐름에 필요한 코드와 Refresh·logout 선언부가 한 파일에 같이 들어가고, 실제 method body는 다른 장에 자리표시자로 남아 있습니다.
- 현재 각 장의 진행률은 04장 37/213, 05장 41/213, 06장 46/213, 07장 50/213, 08장 52/213으로 기록되어 있습니다. 공통 파일을 장마다 다르게 집계하는 기준이므로 전체 학습 진행률을 신뢰하기 어렵습니다.
- 04~08 통합 문서는 전체 지도를 제공하지만 세부 문서의 절 번호에 의존합니다. 문서가 재배치되면 링크와 절 번호가 쉽게 낡습니다.

수정 시 실제 source를 다시 읽어 코드 블록을 만들고, 코드 블록·설명·호출 위치를 같은 변경 단위에서 검증합니다.

### 2.5 테스트가 실행 흐름과 떨어져 있습니다

현재 테스트가 08장에 목록 형태로 모여 있어, 로그인·Access Token·Refresh·logout 각각의 어느 단계가 검증되는지 한 번 더 찾아야 합니다. 수정 후 각 흐름 문서 끝에 해당 흐름의 test file과 test method를 배치하고, 마지막에 통합 테스트 범위와 검증하지 않는 부분을 표로 정리합니다.

현재 소스에서 확인되는 제한도 그대로 표시합니다.

- Refresh 동시성에 대한 실제 다중 transaction integration test는 확인되지 않습니다.
- Origin 테스트는 `SecurityConfigTest`에서 주로 `POST /sessions`를 검증하며, `POST /sessions/refresh`와 `DELETE /sessions`의 Origin 조합을 모두 직접 검증하지는 않습니다.
- `SessionServiceTest`는 Mockito 단위 테스트이므로 실제 DB lock·transaction을 증명하지 않습니다.
- frontend `refreshPromise`를 실행하는 자동화 test는 현재 테스트 목록에서 확인되지 않습니다.

## 4. 코드 배치 원칙

### 4.1 실행 흐름 문서 안에서의 고정 순서

각 기능 문서는 다음 구조를 고정합니다.

1. 사용자 동작 또는 scheduler trigger
2. 프론트 entry point
3. API module
4. 공통 request/filter/interceptor 진입
5. Controller
6. DTO 역직렬화·검증
7. Service method
8. provider·entity·repository 호출
9. DB·Cookie·SecurityContext 변경
10. 반환 DTO·HTTP status·header
11. 프론트 응답 처리
12. 정상·예외·동시성 테스트

코드 선언 순서가 runtime 순서와 다를 때는 별도의 “선언된 곳” 표를 두고, 본문은 호출 순서로 읽습니다.

### 4.2 파일 단위로 묶되, 같은 파일의 실행 method는 흐름 안에 둡니다

`SessionService.java`처럼 여러 기능을 담당하는 파일은 파일 전체를 한 장에 몰아넣지 않습니다. 대신 `createSession`, `refreshSession`, `deleteSession`을 각각 해당 실행 흐름 문서에 실제 body와 함께 둡니다. 각 block에 다음을 표시합니다.

- 실제 파일 절대 경로
- method 호출자
- 매개변수의 최초 출처
- 내부 collaborator 호출
- 반환값 사용처
- 예외 이동 경로
- 같은 파일의 다른 method가 어느 문서에 있는지

이것은 코드를 임의로 나누는 것이 아니라, 한 method가 실제로 하나의 기능 흐름에서 사용되는 위치를 기준으로 읽기 위한 배치입니다.

### 4.3 반복 문법은 최초 설명 위치에서만 자세히 설명합니다

- Spring Bean·생성자 주입·Controller annotation: 새 04/05에서 최초 설명
- React state·event·async/await: 새 05에서 최초 설명
- JWT parser·record·Filter chain: 새 06에서 최초 설명
- Cookie·`@JsonIgnore`·`@Transactional`·JPA lock: 새 07에서 최초 설명
- CORS·Interceptor·scheduler·MockMvc: 새 08/08-1에서 최초 설명

반복 파일에는 “앞의 문법”만 쓰지 않고, 현재 위치에서 달라지는 매개변수·반환값·예외를 반드시 설명합니다.

### 4.4 실제 원문과 설명용 축약을 분리합니다

- 전체 method body를 보여주는 block에는 실제 source 그대로 적습니다.
- 다른 flow에서 이미 본 공통 함수는 실제 path와 method 이름을 적고, 현재 필요한 호출 구간만 별도 발췌합니다.
- 발췌 block에는 `실제 코드 발췌`라고 명시하고, 임의로 만든 주석형 placeholder를 사용하지 않습니다.
- import는 실제 source와 대조해 중복·누락을 정리합니다. import 자체가 핵심 문법이 아니면 설명은 짧게 하되 코드에는 실제 import를 유지합니다.
