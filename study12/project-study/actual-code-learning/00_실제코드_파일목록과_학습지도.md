## 권장 학습 순서

이 순서는 파일이 놓인 폴더 순서가 아니라, 기반 개념을 먼저 만든 뒤 실제 기능의
입력·처리·저장·응답을 따라가도록 재배치한 순서다. 각 단계 안의 괄호는 해당 단계에서
처음 정독할 파일 묶음이다.

### 0. 지도와 실행 전제

파일 목록, 실제 import·route·문자열 참조 검색, 백엔드·프론트·배포 의존 그래프를 먼저
확정한다. 이 단계에서는 코드를 학습하지 않고, 참조되지 않는 파일을 임의로 스킵하지
않는다.

### 1. 백엔드 빌드·설정·시작

`settings.gradle` → `build.gradle` → Gradle wrapper는 버전·plugin·의존성의 역할만
확인한다. 그 다음 `application.yaml` → `application-local.yaml` →
`application-prod.yaml` → `src/test/resources/application-test.yaml` 순서로 공통값,
profile 병합, 환경변수 placeholder, 테스트 profile을 확인하고,
`SpringdatajpaApplication.java`에서 `main`, component scan, configuration properties,
scheduler 등록으로 연결한다. `data.sql`은 local profile의 SQL 초기화 설정이 실제로
읽는 시점을 이 단계에서 확인하되, 테이블 구조 자체는 Flyway 장에서 다시 대조한다.

### 2. 프론트 빌드·브라우저 진입점·라우팅 뼈대

`package.json` → `vite.config.js` → `index.html` → `src/main.jsx` → `src/App.jsx` →
`src/routes/AppRoutes.jsx` 순서로 브라우저가 React tree와 route를 만드는 과정을 확인한다.
그 다음 `ProtectedRoute.jsx` → `PublicOnlyRoute.jsx` → `PageBoundary.jsx` →
`PageLayout.jsx`·`AuthLayout.jsx`·`AppHeader.jsx` 순서로 Outlet, lazy, Suspense,
ErrorBoundary, route guard와 layout 책임을 설명한다.

### 3. 공통 HTTP 오류·검증 기반

`ErrorResponseDto.java` → `ApiErrorCode.java` → `GlobalExceptionHandler.java` →
`ErrorResponseWriter.java` 순서로 Controller 예외와 Filter/Interceptor 예외의 응답 경로를
분리해 이해한다. 이어 `exception/*`은 첫 RuntimeException 계열에서 문법을 설명하고,
각 예외의 발생 Service와 HTTP status만 확인한다. `ImageDataUrlValidator.java`는
회원가입과 게시글 입력 양쪽에서 사용되므로 이 단계에서 먼저 정독한다.

### 4. 가장 작은 백엔드 기능: 회원가입

`entity/User.java` → `dto/user/UserRequestDto.java` → `dto/user/UserResponseDto.java` →
`repository/UserRepository.java` → `service/UserService.java` →
`controller/UserController.java` 순서로 읽는다. Entity 상태 변경, DTO 역직렬화·검증,
Repository 조회, Service 업무 순서, Controller JSON 응답을 한 기능으로 완성한다.

### 5. 인증 모델과 로그인 준비물

기존 인증 문서 04~08은 세부 원문과 참고 설명으로 보존하고, 사용자의 현재 주 학습은
`04-08_인증_통합_실행흐름.md` 하나를 기준으로 진행한다. 이 통합 문서는 파일 순서가
아니라 요청 하나의 실행 흐름을 먼저 보여준 뒤 필요한 파일과 개념을 연결한다.

`SessionRequestDto.java` → `SessionResponseDto.java` → `SessionRefreshResponseDto.java` →
`CustomUserDetails.java` → `CustomUserDetailsService.java` → `JwtProvider.java` →
`AccessTokenClaims.java` → `RefreshTokenProvider.java` → `RefreshCookieProvider.java` →
`AuthSession.java` → `AuthSessionRepository.java`.

`CustomUserDetails`를 Filter보다 앞에 두는 이유는 Filter가 이 객체를 생성하고,
Controller의 `@AuthenticationPrincipal`도 이 객체를 받기 때문이다. 이것은 요청 실행
순서가 아니라 선행 개념을 먼저 읽는 학습 순서다.

### 6. 로그인·세션 HTTP 흐름과 보안 연결

주 학습 문서 `04-08_인증_통합_실행흐름.md`의 5~11장을 따라 로그인 → 보호 요청 →
Refresh → 로그아웃 → Origin/CORS·요청 로그 → 인증 무효화 → 만료 세션 정리 순서로 읽는다.
각 흐름 안에서 `SessionService.java`, `SessionController.java`, `SecurityConfig.java`,
`JwtAuthenticationFilter.java`, `CorsOriginProvider.java`, `WebConfig.java`,
`SessionOriginInterceptor.java`, `InterceptorConfig.java`, `RequestLogInterceptor.java`,
`AuthSessionCleanupScheduler.java`를 필요한 시점에 연결한다.

### 7. 게시글·댓글 도메인 모델

## 인증 흐름의 현재 주 학습 문서

인증은 이제 `04-08_인증_통합_실행흐름.md` 하나를 주 학습 문서로 사용한다. 이 문서는
다음 순서로 하나의 시스템을 따라간다.

```text
로그인
→ 보호 요청과 Access Token
→ Refresh Token 재발급과 원래 요청 재시도
→ 로그아웃과 Cookie 만료
→ Origin·CORS·요청 로그
→ 비밀번호 변경·회원 탈퇴에 따른 인증 무효화
→ 만료 AuthSession 정리
```

통합 문서의 각 흐름은 목표 → 최소 선행 개념 → 전체 지도 → 짧은 코드 구간 → 선언 위치·
호출자·인자·반환값·예외 설명 → checkpoint 순서로 작성한다. 기존
`04_인증_로그인_자격증명과_세션생성.md`부터 `08_인증_세션정리_요청로그_테스트.md`까지는
삭제하지 않고 전체 원문과 세부 설명을 대조하는 참고 문서로 둔다.

### 통합 문서에서 시작하는 위치

처음부터 파일을 읽지 않고 `04-08_인증_통합_실행흐름.md`의 1~5장을 읽어 로그인 흐름을
완성한다. 그 다음 checkpoint를 확인한 뒤 6장 보호 요청, 7장 Refresh, 8장 로그아웃,
9~11장 부가 흐름으로 이동한다.

```text
LoginPage.handleSubmit
→ authApi.login
→ api.request
→ SessionController.createSession
→ SessionService.createSession
→ AuthenticationManager.authenticate
→ CustomUserDetailsService.loadUserByUsername
→ JwtProvider·RefreshTokenProvider
→ AuthSessionRepository
→ JSON·Set-Cookie
```

이 순서는 학습 순서입니다. 실제 요청에서는 Filter·Interceptor·Controller가 framework에
의해 실행되지만, 각각의 역할과 호출 시점을 통합 문서에서 따로 구분합니다.

## 진행률 기준

전체 학습 단계를 16개 큰 흐름으로 나누어 계산한다. 파일 목록과 지도는 별도 준비 단계이며, 실제 흐름 문서가 완성된 단계만 진행률에 포함한다.

이 숫자는 전체 코드의 29%를 봤다는 뜻이 아니다. 백엔드 관련 파일 133개와 프론트/배포 관련 파일 80개를 합쳐 최소 213개 파일이 학습 대상이며, 각 파일은 정독·연결 확인·중복 스킵 판정을 따로 해야 한다.

실제 파일 진행률은 앞으로 다음 세 가지로 기록한다.

- 정독 완료 파일 수
- 호출 관계만 확인한 파일 수
- 중복 근거를 확인하고 스킵한 파일 수

문서 단계가 끝났다는 이유만으로 전체 파일 진행률을 올리지 않는다.

문서 통합 여부와 사용자의 흐름 이해 여부는 별도로 기록한다. 9~15번 문서가 작성되어도
각 문서의 checkpoint를 통과하지 않으면 사용자의 이해가 완료된 것으로 기록하지 않는다.

현재 파일 집계: **116개 확인 완료 / 최소 학습 대상 213개 = 약 54.5%**

9번 Entity·10번 DTO/Repository·11번 Service/Controller·12번 프론트 실행/라우팅·13번
프론트 공통 요청/인증 화면·14번 게시글 목록/페이지네이션·15번 게시글 상세/작성/수정/댓글/회원정보 문서에서
중복 제거 후 실제 원문·호출·반환값·예외를 확인한 파일을 반영한 수치다.

이 수치는 문서에 실제 원문을 확인하고 설명한 파일만 중복 제거해 계산했다. 다음 목록·페이징
파일처럼 아직 전체 원문을 정독하지 않은 파일은 포함하지 않았다.

각 단계는 파일 전체를 훑은 뒤, 실제 호출 관계와 반환값을 확인하고 다음 단계로 이동한다. 같은 문법을 만났다는 이유만으로 파일을 생략하지 않고, “완전히 동일한 구조인지” 확인한 뒤 스킵한다.

각 코드 묶음은 실제 코드 하나에 라인별 설명 주석과 번호별 상세 설명 주석을 함께 넣는다. 별도의 전체 주석본·목차 주석본을 중복해서 만들지 않는다. 코드 구간 앞에는 `/* 1. ... */` 형식으로 실행 흐름·호출 위치·새 문법을 설명하고, 필요한 줄에는 `//`로 값과 역할을 설명한다. 한 코드 구간이 여러 항목에 동시에 해당하면 `//2,4`처럼 병합 번호를 사용할 수 있지만, 번호가 먼 코드 위치에 흩어지지 않도록 메서드·생성자·조건문 단위로 코드를 세분화한다. `package`와 `import` 줄에는 주석을 달지 않는다.
호출 코드를 설명할 때는 반드시 호출 파일의 전체 경로, 호출 메서드명, 가능하면 실제 라인 위치를 코드 앞에 표시한다.

## 문서 완료 전 필수 검수표

각 파일 문서를 완료로 표시하기 전에 다음 항목을 실제로 확인한다.

- [ ] 실제 파일 경로와 문서의 파일 경로가 일치한다.
- [ ] 실제 원문 순서가 유지되어 있다.
- [ ] 전체 주석본이 있다.
- [ ] 설명 주석본이 있다.
- [ ] 두 코드 블록의 실행 코드가 실제 원문과 일치한다.
- [ ] 새 문법·annotation·라이브러리 개념이 설명 주석본 안에 표시되어 있다.
- [ ] 각 주석이 결과만 말하지 않고 값의 출처·실행 주체·작동 이유·다음 전달 위치까지 설명한다.
- [ ] framework가 내부에서 이어서 처리하는 경우 DispatcherServlet·Jackson·Servlet response 등 실제 처리 주체를 적는다.
- [ ] 코드 바로 아래에 번호별 상세 설명이 있다.
- [ ] 각 public 메서드의 호출 파일·호출 메서드·매개변수·반환값·예외가 적혀 있다.
- [ ] 설명이 실제 검색 결과와 일치한다.
- [ ] 파일 진행률이 중복 없이 갱신되어 있다.

체크하지 못한 항목이 하나라도 있으면 해당 파일을 완료로 보고하지 않는다.

## 기능별 최종 흐름

- 회원가입: SignupForm → authApi → api.js → UserController → UserRequestDto → UserService → UserRepository/User → UserResponseDto → JSON → 화면

- 인증 요청: api.js → Authorization header → JwtAuthenticationFilter → JwtProvider → CustomUserDetailsService → SecurityContext → Controller
- Refresh: 401 → refreshPromise → SessionController → SessionService → AuthSessionRepository lock → rotate → 새 token → 원래 요청 재시도
- 게시글 목록: PostsPage → postApi → api.js → PostController → PostService → PostRepository/Pageable → Page DTO → state/observer
- 조회수: 상세 화면 → PostService/view updater → Redis key/dirty set → flush scheduler → PostViewCountRepository
- 배포: GitHub Actions → image → SSM → deploy script → Compose → health → Nginx blue/green

문서에 포함된 파일 수는 중복 제거해 집계한다. 다른 문서에서 이미 전체 설명한 파일을 다시 발췌한 경우에는 새 파일로 계산하지 않는다.

현재 `actual-code-learning` 폴더의 Markdown은 20개이며, 9번·11번은 기존 파일을 수정해
파일 수가 늘지 않았다. 남은 큰 흐름을 3개 문서로 추가하면 최종 문서 수는 **23개**다.
`auth-legacy-backup`의 9개 파일은 복구용 사본이라 학습 문서 수에 포함하지 않는다.

## 현재 코드에서 확인된 핵심 의존 관계

아래 연결은 import와 실제 method 호출을 검색해 확인한 시작 지도다. 이후 각 흐름 문서에서 호출 method와 반환값을 다시 원문으로 대조한다.

~~~text
SpringdatajpaApplication
├─ @ConfigurationPropertiesScan → ViewCountProperties
├─ @EnableScheduling → RedisViewCountFlushScheduler/AuthSessionCleanupScheduler
└─ @SpringBootApplication → component scan

UserController
└─ UserService
   ├─ UserRepository
   ├─ PasswordEncoder
   └─ ImageDataUrlValidator

SessionController
└─ SessionService
   ├─ AuthenticationManager/CustomUserDetailsService
   ├─ JwtProvider
   ├─ RefreshTokenProvider
   ├─ RefreshCookieProvider
   └─ AuthSessionRepository

PostController
└─ PostService
   ├─ PostRepository/CommentRepository/LikeRepository/PostReportRepository
   ├─ ImageDataUrlValidator
   └─ ViewCountUpdater

frontend Page
└─ feature API module
   └─ api.js request()
      └─ fetch()
~~~

이 지도에 없는 파일은 아직 “사용되지 않음”으로 결론내리지 않는다. route, 문자열 이름, reflection, Spring annotation, workflow 참조는 단순 import 검색만으로 놓칠 수 있으므로 해당 단계에서 별도로 확인한다.

## 스킵 기준

- 예외 class: 첫 `RuntimeException` 상속과 생성자에서 문법을 설명하고 나머지는 사용 위치/status만 확인한다.
- DTO: 첫 Request/Response DTO에서 annotation, getter, 생성자를 설명하고 나머지는 field/호출 위치만 확인한다.
- 공통 UI: props/JSX/callback이 동일하면 실제 사용처와 표시 차이만 본다.
- CSS/asset/font: 코드 흐름에 새 개념이 없으면 import와 적용 위치만 확인한다.
- wrapper 내부: 고정된 Gradle 실행기라 프로젝트 업무 코드 흐름과 무관하다.
- 현재 참조되지 않는 파일: import, route, 문자열, workflow 참조를 검색한 뒤에만 “사용되지 않음”으로 표시한다.
