# 14. 프론트 게시글 목록·페이지네이션·무한 스크롤

## 14.1 이 문서의 범위와 실행 흐름

12번에서 `/posts` route가 `PostsPage`를 선택하고 `PageLayout`을 렌더링하는 기반을
확인했고, 13번에서 `api.js`가 모든 HTTP 요청·401·Refresh를 공통 처리하는 구조를
확인했습니다. 이번 문서는 그 두 기반 위에서 게시글 목록을 실제로 가져오고, 페이지를
추가하고, 화면에 표시하는 흐름을 다룹니다.

```text
사용자가 /posts에 진입
→ AppRoutes가 PostsPage를 lazy loading
→ PostsPage useEffect가 page 0 요청
→ postApi.getPosts({ page: 0, size: 10, signal })
→ URLSearchParams로 /posts?page=0&size=10 생성
→ api.request() → api.js의 fetch·Authorization·401 처리
→ PostController GET /posts
→ PostService PageRequest.of(page, size)
→ PostRepository Page<Post>와 posts.hasNext()
→ { posts, hasNextPage } JSON
→ postApi가 각 post를 normalizeListPost로 정규화
→ PostsPage state에 첫 페이지 저장
→ PostBoard → PostList → PostListItem 렌더링
→ sentinel이 보이면 IntersectionObserver가 다음 page 요청
```

이번 문서에서 새로 전체 원문을 확인하는 파일은 8개입니다.

- `src/api/postApi.js`
- `src/api/postNormalizer.js`
- `src/pages/posts/PostsPage.jsx`
- `src/components/posts/PostBoard.jsx`
- `src/components/posts/PostList.jsx`
- `src/components/posts/PostListItem.jsx`
- `src/components/posts/ActivityBars.jsx`
- `src/utils/formatter.js`

`AppRoutes.jsx`, `PageLayout.jsx`, `ErrorView.jsx`, `api.js`의 공통 규칙은 앞 문서에서
확인했으므로 이번에는 목록 흐름에 필요한 호출 위치만 연결합니다. `PostController`,
`PostService`, `PostRepository`, 게시글 page DTO는 백엔드에서 이미 읽은 파일이지만, 프론트
query와 응답 field가 어디서 만들어지는지 확인하기 위해 필요한 코드만 다시 발췌합니다.

## 14.2 백엔드 목록 API 계약: 프론트가 보내고 받는 값

### 이 코드를 지금 확인하는 이유

프론트의 `page`, `size`, `posts`, `hasNextPage`가 임의로 정해진 값인지 백엔드 계약에서
확인해야 합니다. 프론트만 보면 `hasNextPage`가 어디서 생성되는지 알 수 없고, 백엔드만
보면 브라우저가 다음 페이지를 언제 요청하는지 알 수 없습니다.

### `PostController.java`의 목록 endpoint 발췌

실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/controller/PostController.java`

`@RequestParam`은 `/posts?page=2&size=10`의 query parameter를 Java method parameter로
변환합니다. 프론트가 값을 명시하므로 정상 흐름에서는 default가 사용되지 않지만, 직접
curl을 보내거나 query를 생략하면 backend default가 적용됩니다. Controller의 반환값은
`PostPageResponseDto`이고, `@RestController`의 Jackson 직렬화가 JSON body로 바꿉니다.

### `PostService.java`의 페이지 생성 발췌

실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/service/PostService.java`

```java

            .findByDeletedFalseAndReportCountLessThanOrderByPostIdDesc(

                    pageable

    for (Post post : posts.getContent()) {
        result.add(PostResponseFactory.createListResponse(post));
    }

    return PostResponseFactory.createPageResponse(result, posts.hasNext());
}
```

```java

Page<Post> posts = postRepository.findByDeletedFalseAndReportCountLessThanOrderByPostIdDesc( // 삭제·신고 기준을 적용해 내림차순 조회한다.
        Post.REPORT_BLOCK_THRESHOLD, // 신고 수가 이 기준 미만인 글만 조회한다.
        pageable // LIMIT/OFFSET 계산에 사용할 Pageable을 전달한다.
);

for (Post post : posts.getContent()) { // 현재 page의 실제 Post 목록만 꺼낸다.
    result.add(PostResponseFactory.createListResponse(post)); // Entity 하나를 목록 Response DTO 하나로 변환한다.
}

return PostResponseFactory.createPageResponse(result, posts.hasNext()); // 목록과 다음 page 존재 여부를 함께 반환한다.
```

`PageRequest.of(page, size)`의 `page`는 0부터 시작합니다. 따라서 프론트의 첫 요청
`page=0`은 첫 묶음이고, 다음 요청은 `page=1`입니다. `Page<Post>`는 현재 page의
`getContent()`와 다음 page가 있는지를 알려 주는 `hasNext()`를 함께 보관합니다.
프론트의 `hasNextPage`는 이 `posts.hasNext()`가 DTO field로 옮겨진 값입니다.

실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/repository/PostRepository.java`

```java
@EntityGraph(attributePaths = { "user", "postImages", "postCounter", "postViewCount" }) // 목록 DTO가 읽을 연관 데이터를 함께 준비한다.
@Query("""
        SELECT post
        FROM Post post
        WHERE post.deleted = false
          AND post.postCounter.reportCount < :reportCount
        ORDER BY post.postId DESC
        """) // Entity field 이름을 사용하는 JPQL로 활성·신고 기준과 정렬을 선언한다.
Page<Post> findByDeletedFalseAndReportCountLessThanOrderByPostIdDesc( // 결과 타입을 Page<Post>로 요청한다.
        @Param("reportCount") int reportCount, // JPQL의 :reportCount에 threshold를 바인딩한다.
        Pageable pageable // Spring Data가 page 번호·크기를 query의 offset/limit로 반영한다.
);
```

이 query의 `ORDER BY post.postId DESC` 때문에 page 0에는 최신 postId부터 들어옵니다.
프론트는 받은 page를 단순히 뒤에 붙이므로, backend가 page마다 일관된 정렬을 보장하는
것이 중요합니다. `@EntityGraph`와 신고 기준의 세부 JPA 동작은 10·11번에서 이미
설명했으므로 이번에는 프론트 field와 연결되는 범위만 확인합니다.

## 14.3 `src/api/postApi.js`: 목록 endpoint와 응답 정규화 연결

### 파일을 지금 읽는 이유

`PostsPage`가 직접 URL 문자열을 조립하거나 `fetch`를 호출하지 않고, `postApi.getPosts()`에
page·size·signal을 넘기는 구조를 확인합니다. 같은 module에 상세·작성·수정·좋아요·댓글
method도 있지만, 이번 장의 핵심은 목록 method입니다.

### 파일 책임과 연결

- 실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/src/api/postApi.js`
- 호출하는 파일: `PostsPage.jsx`; 다른 method는 상세·작성·수정·댓글 화면
- 호출되는 파일: 13번의 `api.js` `request()`, `postNormalizer.js`
- 외부 입력: page number, size, AbortSignal, postId와 mutation payload
- 생성·변경 값: query string, HTTP Promise, 정규화된 post/comment object
- 반환값 사용 위치: `PostsPage`의 `result.posts`, `result.hasNextPage`
- 예외 지점: `request()`의 fetch·HTTP·JSON·Abort 오류가 그대로 전파됨
- 다음 파일: `postNormalizer.js`

### 전체 실제 코드

```javascript
import { request } from "./api.js";
import {
    normalizeComment,
    normalizeDetailPost,
    normalizeListPost,
} from "./postNormalizer.js";

export const postApi = {
    async getPosts({ page = 0, size = 10, signal } = {}) {
        const params = new URLSearchParams({
            page: String(page),
            size: String(size),
        });
        const result = await request(`/posts?${params.toString()}`, { signal });

        return {
            posts: Array.isArray(result?.posts)
                ? result.posts.map(normalizeListPost)
                : [],
            hasNextPage: result?.hasNextPage === true,
        };
    },

    async getPost(postId, { signal } = {}) {
        return normalizeDetailPost(await request(`/posts/${postId}`, { signal }));
    },

    createPost(payload) {
        return request("/posts", {
            method: "POST",
            body: JSON.stringify(payload),
        });
    },

    updatePost(postId, payload) {
        return request(`/posts/${postId}`, {
            method: "PATCH",
            body: JSON.stringify(payload),
        });
    },

    deletePost(postId, version) {
        return request(`/posts/${postId}`, {
            method: "DELETE",
            body: JSON.stringify({ version }),
        });
    },

    reportPost(postId) {
        return request(`/posts/${postId}/reports`, { method: "POST" });
    },

    likePost(postId) {
        return request(`/posts/${postId}/likes`, { method: "POST" });
    },

    unlikePost(postId) {
        return request(`/posts/${postId}/likes`, { method: "DELETE" });
    },

    async createComment(postId, commentContent) {
        return normalizeComment(await request(`/posts/${postId}/comments`, {
            method: "POST",
            body: JSON.stringify({ commentContent }),
        }));
    },

    async updateComment(postId, commentId, commentContent) {
        return normalizeComment(await request(`/posts/${postId}/comments`, {
            method: "PATCH",
            body: JSON.stringify({ commentId, commentContent }),
        }));
    },

    deleteComment(postId, commentId) {
        return request(`/posts/${postId}/comments`, {
            method: "DELETE",
            body: JSON.stringify({ commentId }),
        });
    },
};
```

### 코드 일부와 바로 아래 설명: 목록 method의 매개변수

```javascript
export const postApi = { // 여러 post endpoint method를 하나의 named export object로 묶는다.
    async getPosts({ page = 0, size = 10, signal } = {}) { // 인자를 생략해도 기본 page·size로 동작한다.
        const params = new URLSearchParams({ // query parameter 객체를 URL encoding 가능한 객체로 만든다.
            page: String(page), // 숫자 page를 문자열 query 값으로 변환한다.
            size: String(size), // 숫자 size를 문자열 query 값으로 변환한다.
        });
        const result = await request(`/posts?${params.toString()}`, { signal }); // 13번 공통 request로 GET을 보낸다.
```

`getPosts({ page = 0, size = 10, signal } = {})`에는 세 문법이 함께 있습니다.
첫째 parameter object destructuring으로 필요한 property를 이름으로 받습니다. 둘째
`page = 0`, `size = 10`은 해당 property가 `undefined`일 때의 기본값입니다. 셋째
마지막 `= {}`는 호출자가 argument object 자체를 생략했을 때 사용할 기본 객체입니다.
`signal`은 `AbortController.signal`이며, API module은 요청 취소 객체를 보관하지 않고
`request()`에 전달합니다.

`URLSearchParams`는 query string을 직접 `?page=`로 이어 붙이는 대신 URL encoding과
문자열 변환을 담당하는 브라우저 내장 객체입니다. 여기서는 `params.toString()` 결과가
`page=0&size=10`이 되어 `/posts?page=0&size=10` endpoint가 됩니다.

### 코드 일부와 바로 아래 설명: 응답 배열과 boolean의 안전한 변환

```javascript
return {
    posts: Array.isArray(result?.posts) // 응답 posts가 실제 배열인지 먼저 검사한다.
        ? result.posts.map(normalizeListPost) // 배열이면 각 원소를 목록 shape로 변환한다.
        : [], // 없거나 배열이 아니면 화면이 map을 호출할 수 있도록 빈 배열을 반환한다.
    hasNextPage: result?.hasNextPage === true, // 정확히 true일 때만 다음 요청을 허용한다.
};
```

`result?.posts`의 `?.`는 응답이 null/undefined여도 property 접근 오류를 막습니다.
`Array.isArray`는 배열 여부를 boolean으로 확인합니다. `map`은 원본 배열을 순회해 새
배열을 만들며, 각 element는 `normalizeListPost` 함수에 전달됩니다. `=== true`는 truthy
문자열이나 숫자를 다음 page 허용으로 바꾸지 않고, backend가 보낸 boolean `true`만
인정하려는 조건입니다.

### 코드 일부와 바로 아래 설명: 다른 endpoint method와 공통 request

```javascript

createPost(payload) {

    });

```

이 method들은 이번 목록 화면에서 호출되지 않지만 같은 `postApi` object에 속합니다.
새 문법을 반복 설명하지 않고, 상세·작성·수정·댓글 화면에서 어떤 method와 response가
연결되는지만 다음 문서에서 확인합니다.

## 14.4 `src/api/postNormalizer.js`: 응답 데이터를 화면용 shape로 고정

### 파일을 지금 읽는 이유

백엔드가 null field나 누락 field를 보내더라도 화면 컴포넌트가 매번 null 검사를 하지
않도록 API 경계에서 기본값을 정합니다. 목록은 `normalizeListPost`, 상세는
`normalizeDetailPost`, 댓글은 `normalizeComment`를 사용합니다.

### 파일 책임과 연결

- 실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/src/api/postNormalizer.js`
- 호출하는 파일: `postApi.js`의 `getPosts`, `getPost`, `createComment`, `updateComment`
- 호출되는 외부 코드: JavaScript optional chaining·nullish coalescing·Array.map
- 외부 입력: backend response object 또는 null/undefined
- 생성·변경 값: 화면에서 사용할 새 object와 배열; 원본 response는 변경하지 않음
- 반환값 사용 위치: `PostsPage`, 상세 page, 댓글 component
- 예외 지점: 대부분 optional chaining으로 null을 흡수하며 함수 자체는 throw하지 않음
- 다음 파일: `PostsPage.jsx`

### 전체 실제 코드

```javascript
function normalizeImageUrls(imageUrls) {
    return Array.isArray(imageUrls) ? imageUrls.filter(Boolean) : [];
}

export function normalizeComment(comment) {
    return {
        commentId: comment?.commentId ?? null,
        content: comment?.content ?? "",
        authorNickname: comment?.authorNickname ?? "삭제된 사용자",
        authorProfileImage: comment?.authorProfileImage ?? null,
        createdAt: comment?.createdAt ?? "",
        isMine: comment?.isMine === true,
    };
}

export function normalizeListPost(post) {
    return {
        postId: post?.postId ?? null,
        title: post?.title ?? "",
        likeCount: post?.likeCount ?? 0,
        reportCount: post?.reportCount ?? 0,
        commentCount: post?.commentCount ?? 0,
        viewCount: post?.viewCount ?? 0,
        createdAt: post?.createdAt ?? "",
    };
}

export function normalizeDetailPost(post) {
    return {
        postId: post?.postId ?? null,
        version: post?.version ?? null,
        title: post?.title ?? "",
        content: post?.content ?? "",
        imageUrls: normalizeImageUrls(post?.imageUrls),
        likeCount: post?.likeCount ?? 0,
        reportCount: post?.reportCount ?? 0,
        commentCount: post?.commentCount ?? 0,
        viewCount: post?.viewCount ?? 0,
        createdAt: post?.createdAt ?? "",
        isMine: post?.isMine === true,
        isLiked: post?.isLiked === true,
        isReported: post?.isReported === true,
        comments: Array.isArray(post?.comments)
            ? post.comments.map(normalizeComment)
            : [],
    };
}
```

### 코드 일부와 바로 아래 설명: 목록 기본값

```javascript
export function normalizeListPost(post) { // 목록 한 건을 새 화면 객체로 변환한다.
    return {
        postId: post?.postId ?? null, // id가 없으면 null로 고정한다.
        title: post?.title ?? "", // title이 없으면 빈 문자열로 만든다.
        likeCount: post?.likeCount ?? 0, // 통계 누락을 0으로 만든다.
        reportCount: post?.reportCount ?? 0,
        commentCount: post?.commentCount ?? 0,
        viewCount: post?.viewCount ?? 0,
        createdAt: post?.createdAt ?? "", // 날짜 누락을 빈 문자열로 만든다.

```

`??`는 왼쪽 값이 `null` 또는 `undefined`일 때만 오른쪽을 사용합니다. 따라서 count가
유효한 `0`이면 0을 유지하지만, `||`를 사용했을 때처럼 false 취급해 다른 값으로 바꾸지
않습니다. `post?.title`의 optional chaining은 post 자체가 null이어도 안전하게
undefined를 반환합니다. 이 함수가 새 object를 만들기 때문에 backend response object를
직접 mutation하지 않습니다.

## 14.5 `src/pages/posts/PostsPage.jsx`: 목록 state와 페이지 요청 조정자

### 전체 실제 코드

```jsx
import { useCallback, useEffect, useRef, useState } from "react";

import { postApi } from "../../api/postApi.js";
import ErrorView from "../../components/common/ErrorView.jsx";
import PageLayout from "../../components/layout/PageLayout.jsx";
import PostBoard from "../../components/posts/PostBoard.jsx";
import { getErrorMessage } from "../../utils/errorMessage.js";
import "../../styles/posts.css";

function PostsPage() {
    const [posts, setPosts] = useState([]);
    const [hasNextPage, setHasNextPage] = useState(true);
    const [loadError, setLoadError] = useState(null);
    const [failedPage, setFailedPage] = useState(null);
    const loadingRef = useRef(false);
    const requestControllerRef = useRef(null);
    const nextPageRef = useRef(0);

    const loadPage = useCallback(async (page) => {
        if (loadingRef.current) {
            return;
        }

        const controller = new AbortController();
        requestControllerRef.current = controller;
        loadingRef.current = true;

        try {
            setLoadError(null);
            const result = await postApi.getPosts({
                page,
                size: 10,
                signal: controller.signal,
            });

            if (controller.signal.aborted) {
                return;
            }

            setPosts((previous) => page === 0 ? result.posts : [...previous, ...result.posts]);
            setHasNextPage(result.hasNextPage);
            nextPageRef.current = page + 1;
            setFailedPage(null);
        } catch (requestError) {
            if (controller.signal.aborted || requestError?.name === "AbortError") {
                return;
            }
            if (requestControllerRef.current !== controller) {
                return;
            }
            setLoadError(requestError);
            setFailedPage(page);
        } finally {
            if (requestControllerRef.current === controller) {
                requestControllerRef.current = null;
                loadingRef.current = false;
            }
        }
    }, []);

    const cancelCurrentRequest = useCallback(() => {
        requestControllerRef.current?.abort();
        requestControllerRef.current = null;
        loadingRef.current = false;
    }, []);

    const loadNextPage = useCallback(() => {
        void loadPage(nextPageRef.current);
    }, [loadPage]);

    useEffect(() => {
        void loadPage(0);

        return () => {
            cancelCurrentRequest();
        };
    }, [cancelCurrentRequest, loadPage]);

    function retryLoadPage() {
        const page = failedPage ?? 0;
        setLoadError(null);

        if (page === 0) {
            nextPageRef.current = 0;
            setPosts([]);
            setHasNextPage(true);
        }

        void loadPage(page);
    }

    return (
        <PageLayout
            pageClassName="posts-page"
            mainClassName="posts-main"
            title="대나무숲"
        >
            {loadError ? (
                <ErrorView
                    title="게시글 목록을 불러오지 못했습니다."
                    message={getErrorMessage(loadError, "잠시 후 다시 시도해주세요.")}
                    onRetry={retryLoadPage}
                />
            ) : (
                <PostBoard
                    posts={posts}
                    hasNextPage={hasNextPage}
                    onLoadMore={loadNextPage}
                />
            )}
        </PageLayout>
    );
}

export default PostsPage;
```

### 코드 일부와 바로 아래 설명: state와 ref의 역할

```jsx
const [posts, setPosts] = useState([]); // 화면에 그릴 정규화된 post 배열이다.
const [hasNextPage, setHasNextPage] = useState(true); // sentinel을 계속 관찰할지 결정한다.
const [loadError, setLoadError] = useState(null); // 현재 목록 오류; null이면 정상이다.
const [failedPage, setFailedPage] = useState(null); // 실패한 page를 retry에 사용한다.
const loadingRef = useRef(false); // 렌더링 없이 중복 요청 여부를 즉시 보관한다.
const requestControllerRef = useRef(null); // 현재 AbortController identity를 보관한다.
const nextPageRef = useRef(0); // 다음에 요청할 page 번호를 렌더링 없이 보관한다.
```

`useState` 값이 바뀌면 화면을 다시 렌더링하지만, `useRef`의 `.current`를 바꾸는 것은
렌더링을 발생시키지 않습니다. `loadingRef`와 `nextPageRef`는 화면에 직접 표시할 값이
아니라 요청 중복 방지·다음 page 계산용 제어 값이므로 ref로 관리합니다.

`requestControllerRef`는 단순히 controller를 저장하는 것뿐 아니라, catch/finally에서
“지금 처리 중인 요청이 이 controller인지”를 비교하는 identity token 역할도 합니다.

### 코드 일부와 바로 아래 설명: `loadPage`의 중복 방지와 AbortController

```jsx
const loadPage = useCallback(async (page) => { // page 하나를 가져오는 callback identity를 고정한다.
    if (loadingRef.current) {
        return; // 이미 요청 중이면 두 번째 요청을 시작하지 않는다.
    }

    const controller = new AbortController(); // 브라우저 fetch 취소 신호의 새 owner를 만든다.
    requestControllerRef.current = controller; // 현재 요청의 identity를 저장한다.
    loadingRef.current = true; // observer가 연속 호출해도 중복 요청을 막는다.
```

`useCallback`은 dependency가 바뀌지 않는 동안 같은 함수 객체를 반환합니다. 이 코드의
dependency 배열은 `[]`이므로 mount 이후 같은 `loadPage` identity를 사용합니다. 함수
identity가 안정적이면 `useEffect`와 `loadNextPage`가 불필요하게 재생성되지 않습니다.

`AbortController`는 `signal`을 fetch에 전달하고 나중에 `abort()`를 호출해 요청을 취소할
수 있게 하는 브라우저 API입니다. 여기서 controller는 page 진입 때마다 새로 만들고,
cleanup이 현재 controller를 abort합니다.

### 코드 일부와 바로 아래 설명: 요청 성공과 page append

```jsx

    page, // 현재 요청할 0-based page 번호
    size: 10, // 한 요청에 10개를 받도록 backend query에 전달한다.
    signal: controller.signal, // unmount 시 fetch 취소에 사용할 signal
});

    return; // 취소된 요청의 늦은 결과는 state에 반영하지 않는다.
}

setHasNextPage(result.hasNextPage); // backend Page.hasNext() 결과를 다음 observer 조건으로 저장한다.
nextPageRef.current = page + 1; // 성공한 page 다음 번호를 준비한다.
setFailedPage(null); // 성공했으므로 retry 대상 page를 제거한다.
```

page 0은 새로 진입하거나 첫 page를 retry한 결과이므로 기존 목록을 교체합니다. page 1
이후는 이미 화면에 있는 목록을 유지한 채 새 배열을 뒤에 붙입니다. `[...previous, ...result.posts]`
는 두 배열의 원소를 새 배열에 복사하는 spread 문법이며, 기존 state 배열을 직접
`push`로 변경하지 않는 React 불변성 규칙을 따릅니다.

### 코드 일부와 바로 아래 설명: 오류·현재 요청 확인·정리

```jsx
} catch (requestError) {
    if (controller.signal.aborted || requestError?.name === "AbortError") {
        return; // 정상적인 취소는 사용자에게 목록 오류로 표시하지 않는다.
    }
    if (requestControllerRef.current !== controller) {
        return; // 이미 다른 요청이 현재 owner가 되었다면 오래된 요청은 state를 바꾸지 않는다.
    }
    setLoadError(requestError); // 실제 네트워크/HTTP 오류를 ErrorView 입력으로 저장한다.
    setFailedPage(page); // 같은 page를 retry할 수 있도록 기억한다.
} finally {
    if (requestControllerRef.current === controller) {
        requestControllerRef.current = null; // 현재 요청이 맞을 때만 owner를 지운다.
        loadingRef.current = false; // 다음 요청을 허용한다.
    }
}
```

`AbortError`는 fetch가 abort되었을 때 발생할 수 있는 오류 이름입니다. 취소를 일반 오류로
처리하면 화면에 불필요한 “목록을 불러오지 못했습니다”가 표시되므로 먼저 return합니다.
두 번째 identity 비교는 예전 요청이 새 요청의 오류 상태를 덮어쓰지 못하게 하는 안전장치입니다.
`finally`는 성공·실패·return 여부와 상관없이 실행되지만, 현재 owner일 때만 ref를 지웁니다.

### 코드 일부와 바로 아래 설명: 다음 page와 첫 진입 Effect


`void`는 반환된 Promise를 의도적으로 사용하지 않는다는 표현입니다. 요청 자체는

### 코드 일부와 바로 아래 설명: retry와 화면 분기

```jsx
function retryLoadPage() {
    const page = failedPage ?? 0; // 실패 page가 없으면 첫 page를 다시 요청한다.
    setLoadError(null); // ErrorView를 닫고 재시도 상태로 만든다.

    if (page === 0) {
        nextPageRef.current = 0; // 첫 page retry는 다음 page 기준도 초기화한다.
        setPosts([]); // 이전 목록을 비운다.
        setHasNextPage(true); // 새 목록이 더 있을 수 있다고 초기화한다.
    }

    void loadPage(page); // 실패했던 같은 page를 다시 요청한다.
}

{loadError ? (
    <ErrorView
        title="게시글 목록을 불러오지 못했습니다."
        message={getErrorMessage(loadError, "잠시 후 다시 시도해주세요.")}

) : (
```

## 14.7 `src/components/posts/PostList.jsx`: IntersectionObserver와 목록 item 경계

### 파일 책임과 연결

- 실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/src/components/posts/PostList.jsx`
- 호출하는 파일: `PostBoard.jsx`

- 외부 입력: posts 배열, hasNextPage boolean, onLoadMore callback

### 전체 실제 코드

```jsx
import { useEffect, useRef } from "react";

import { ErrorBoundary } from "react-error-boundary";
import PostListItem from "./PostListItem.jsx";

function PostItemFallback() {
    return <div className="item-error-view">이 게시글을 표시할 수 없습니다.</div>;
}

function PostList({ posts, hasNextPage, onLoadMore }) {
    const observerTargetRef = useRef(null);

    useEffect(() => {
        const target = observerTargetRef.current;
        if (!target || !hasNextPage) {
            return;
        }

        const observer = new IntersectionObserver((entries) => {
            if (entries[0]?.isIntersecting) {
                onLoadMore();
            }
        });
        observer.observe(target);
        return () => observer.disconnect();
    }, [hasNextPage, onLoadMore]);

    return (
        <>
            <section className="posts-list">
                {posts.map((post) => (
                    <ErrorBoundary
                        key={post.postId}
                        fallback={<PostItemFallback />}
                    >
                        <PostListItem post={post} />
                    </ErrorBoundary>
                ))}
            </section>
            {hasNextPage && <div ref={observerTargetRef} className="scroll-observer-target" />}
        </>
    );
}

export default PostList;
```

### 코드 일부와 바로 아래 설명: observer 대상과 조기 return

```jsx

useEffect(() => {
    const target = observerTargetRef.current; // 현재 render가 만든 sentinel DOM을 읽는다.
    if (!target || !hasNextPage) {
        return; // sentinel이 없거나 backend가 마지막 page라고 했으면 observer를 만들지 않는다.
    }
```

ref에 `ref={observerTargetRef}`를 붙이면 React가 해당 DOM node를 `.current`에 넣습니다.
초기 render에는 node가 없을 수 있으므로 `target` 확인이 필요합니다. `hasNextPage`가
false인데도 observer를 계속 두면 마지막 page 이후 불필요한 요청이 발생할 수 있습니다.

### 코드 일부와 바로 아래 설명: IntersectionObserver의 실행 시점과 cleanup

```jsx
const observer = new IntersectionObserver((entries) => { // viewport와 target의 교차 변화를 감시하는 browser 객체다.
    if (entries[0]?.isIntersecting) { // 첫 관찰 entry가 화면에 들어왔는지 확인한다.
        onLoadMore(); // PostsPage.loadNextPage가 nextPageRef.current를 읽어 요청을 시작한다.
    }
});
observer.observe(target); // sentinel 관찰을 시작한다.
return () => observer.disconnect(); // effect 재실행·unmount 시 관찰을 해제한다.
```

`IntersectionObserver` callback은 render 중 실행되는 것이 아니라 브라우저가 target의
교차 상태 변화를 감지한 뒤 실행합니다. `onLoadMore`는 page 숫자를 직접 받지 않습니다.
이 component는 “더 볼 수 있는 시점”만 부모에 알리고, 실제 page 숫자와 중복 요청은
PostsPage가 관리합니다. cleanup에서 `disconnect()`하지 않으면 route를 떠난 뒤에도 오래된
observer가 callback을 실행할 수 있습니다.

### 코드 일부와 바로 아래 설명: item key와 마지막 sentinel

```jsx
{posts.map((post) => (
    <ErrorBoundary key={post.postId} fallback={<PostItemFallback />}> // post 하나의 render 오류를 격리한다.
        <PostListItem post={post} /> // 정규화된 post object를 item에 전달한다.
    </ErrorBoundary>
))}

{hasNextPage && <div ref={observerTargetRef} className="scroll-observer-target" />} // 다음 page가 있을 때만 관찰 대상 DOM을 만든다.
```

`map`은 post 배열을 React element 배열로 변환합니다. `key`는 React가 여러 item의 동일성
을 추적하는 식별자이며, 이 프로젝트에서는 backend의 `postId`를 사용합니다. sentinel은
목록 아래에 하나만 생성되고, 다음 page를 받은 뒤에도 같은 ref를 통해 관찰됩니다.

## 14.9 `src/components/posts/ActivityBars.jsx`: 통계값의 시각화 계산

### 파일을 지금 읽는 이유

목록 item에 전달된 좋아요·댓글·조회수·신고 수가 화면 아래 bamboo segment와 leaf로
변환되는 과정을 확인합니다. 이 파일은 목록 요청이나 page state를 변경하지 않고, 하나의
post에 대한 표시용 계산만 수행합니다.

### 파일 책임과 연결

- 실제 파일: `/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/src/components/posts/ActivityBars.jsx`
- 호출하는 파일: `PostListItem.jsx`
- 호출되는 파일: React `useMemo`, `Math`, `Array.from`
- 외부 입력: postId와 네 가지 count
- 생성·변경 값: counts, leaves, segments, inline style/class
- 반환값 사용 위치: PostListItem 안의 ground DOM
- 예외 지점: 숫자가 아니거나 음수인 count를 0으로 보정; leaf 수를 24개로 제한
- 다음 파일: `formatter.js`

### 전체 실제 코드

```jsx
import { useMemo } from "react";

const BAMBOO_MAX_VALUE = { like: 100, view: 100, report: 5 };
const BAMBOO_SEGMENT_MAX_PERCENT = { like: 50, view: 35, report: 15 };
const BAMBOO_LEAF_MAX = 24;

function createLeaves(commentCount, postId) {
    const leafCount = Math.min(Math.max(Number(commentCount) || 0, 0), BAMBOO_LEAF_MAX);

    return Array.from({ length: leafCount }, (_, index) => {
        const colorClass = Math.random() < 0.5 ? "a" : "b";
        const isDownward = Math.random() < 0.15;
        const angle = isDownward
            ? 150 + Math.random() * 60
            : -55 + Math.random() * 110;

        return {
            key: `${postId ?? "post"}-${index}`,
            colorClass,
            left: Math.random() * 92,
            angle,
        };
    });
}

function ActivityBars({ postId, likeCount, commentCount, viewCount, reportCount }) {
    const counts = {
        like: Math.max(Number(likeCount) || 0, 0),
        view: Math.max(Number(viewCount) || 0, 0),
        report: Math.max(Number(reportCount) || 0, 0),
        comment: Math.max(Number(commentCount) || 0, 0),
    };
    const leaves = useMemo(
        () => createLeaves(counts.comment, postId),
        [counts.comment, postId],
    );

    const segments = ["like", "view", "report"]
        .map((type) => {
            const ratio = Math.min(counts[type], BAMBOO_MAX_VALUE[type])
                / BAMBOO_MAX_VALUE[type];

            return {
                type,
                percent: ratio * BAMBOO_SEGMENT_MAX_PERCENT[type],
                isFull: ratio >= 1,
            };
        })
        .filter((segment) => segment.percent > 0);
    return (
        <div className="post-card__ground" aria-hidden="true">
            {segments.length > 0 && (
                <div className="post-card__bamboo-bar">
                    {segments.map((segment) => (
                        <span
                            key={segment.type}
                            className={`post-card__bamboo-segment post-card__bamboo-segment--${segment.type} ${segment.isFull ? "is-full" : ""}`.trim()}
                            style={{ width: `${segment.percent}%` }}
                        />
                    ))}
                </div>
            )}
            {leaves.map((leaf) => (
                <span
                    key={leaf.key}
                    className={`post-card__bamboo-leaf post-card__bamboo-leaf--${leaf.colorClass}`}
                    style={{
                        left: `${leaf.left}%`,
                        bottom: "8px",
                        transform: `rotate(${leaf.angle}deg)`,
                    }}
                />
            ))}
        </div>
    );
}

export default ActivityBars;
```

### 코드 일부와 바로 아래 설명: count 보정과 leaf 개수

```jsx

    like: Math.max(Number(likeCount) || 0, 0), // 숫자로 변환하고 NaN·음수를 0 이상으로 보정한다.
    view: Math.max(Number(viewCount) || 0, 0),
    report: Math.max(Number(reportCount) || 0, 0),
    comment: Math.max(Number(commentCount) || 0, 0),
};

const leafCount = Math.min(
    Math.max(Number(commentCount) || 0, 0), // comment count를 숫자·최솟값 기준으로 보정한다.

```

`Number(value)`는 문자열 숫자도 number로 변환하고, 변환할 수 없으면 `NaN`을 만듭니다.


```javascript
export function formatCount(count) {
    const number = Number(count) || 0;
    return number >= 1000 ? `${Math.floor(number / 1000)}k` : String(number);
}

export function formatDateTime(value) {
    if (!value) {
        return "";
    }

    const date = new Date(value);
    if (Number.isNaN(date.getTime())) {
        return "";
    }

    const parts = [
        date.getFullYear(),
        String(date.getMonth() + 1).padStart(2, "0"),
        String(date.getDate()).padStart(2, "0"),
    ];
    const time = [
        String(date.getHours()).padStart(2, "0"),
        String(date.getMinutes()).padStart(2, "0"),
        String(date.getSeconds()).padStart(2, "0"),
    ];

    return `${parts.join("-")} ${time.join(":")}`;
}
```

### 코드 일부와 바로 아래 설명: count 변환

```javascript
export function formatCount(count) {
    const number = Number(count) || 0; // 숫자로 바꾸지 못하면 0으로 사용한다.
    return number >= 1000
        ? `${Math.floor(number / 1000)}k` // 1000 이상이면 내림한 천 단위 문자열을 만든다.
        : String(number); // 그보다 작으면 일반 문자열로 변환한다.
}
```

삼항 연산자 `조건 ? 참일 때 값 : 거짓일 때 값`은 두 결과 중 하나를 반환합니다.
`Math.floor(2500 / 1000)`은 2가 되어 `2k`가 됩니다. 이 formatter는 정확한 숫자 표가
아니라 목록 카드에 맞춘 짧은 표시 형식을 담당합니다.

### 코드 일부와 바로 아래 설명: 날짜 검증과 배열 join

```javascript
const date = new Date(value); // backend date 문자열을 Date 객체로 파싱한다.
if (Number.isNaN(date.getTime())) {
    return ""; // 파싱할 수 없는 날짜는 화면에 잘못된 문자열을 표시하지 않는다.
}

const parts = [
    date.getFullYear(),
    String(date.getMonth() + 1).padStart(2, "0"), // 월은 0부터 시작하므로 1을 더하고 두 자리로 채운다.
    String(date.getDate()).padStart(2, "0"),
];
const time = [
    String(date.getHours()).padStart(2, "0"),
    String(date.getMinutes()).padStart(2, "0"),
    String(date.getSeconds()).padStart(2, "0"),
];

return `${parts.join("-")} ${time.join(":")}`; // 배열을 날짜·시간 구분자로 이어 붙인다.
```

JavaScript `Date`의 월은 0부터 시작하므로 `getMonth() + 1`을 사용합니다. `padStart(2,
"0")`는 한 자리 문자열 앞에 0을 채워 두 자리로 만들고, `join`은 배열 원소를 구분자와
함께 하나의 문자열로 합칩니다. 이 함수의 timezone·서버 날짜 생성 규칙은 backend와
브라우저 실행 환경의 영향을 받으며, 이 문서에서는 현재 코드의 변환 로직만 확인합니다.

## 14.11 게시글 목록 정상 실행 흐름

1. 사용자가 `/posts` URL로 진입하면 `AppRoutes.jsx`의 lazy `PostsPage` element가
   `PageBoundary` 안에서 렌더링됩니다. lazy·Suspense·route 선택은 12번에서 확인했습니다.
2. `PostsPage`가 mount되면 `useEffect`가 `loadPage(0)`을 시작합니다. 이 호출은 화면이
   그려진 뒤 실행되므로 render 중 HTTP 요청을 시작하지 않습니다.
3. `loadPage(0)`은 `loadingRef.current`를 확인하고 새 `AbortController`를 만든 뒤,
   `postApi.getPosts({ page: 0, size: 10, signal })`을 호출합니다.
4. `postApi`가 `URLSearchParams`로 `/posts?page=0&size=10`을 만들고 13번의
   `api.request()`에 전달합니다. `api.js`가 access token header, Cookie credentials,
   fetch, 401 refresh와 최종 Error 변환을 담당합니다.
5. backend `PostController`가 query를 `int page`, `int size`로 받고 `PostService`에
   전달합니다. Service는 `PageRequest.of(0, 10)`을 만들고 Repository `Page<Post>`를
   조회합니다.
6. Service는 현재 `Page`의 Post를 `PostListResponseDto`로 만들고 `posts.hasNext()`를
   `hasNextPage`로 묶어 JSON으로 반환합니다.
7. `postApi.getPosts()`가 응답의 `posts` 배열을 `normalizeListPost`로 변환하고, 정확히
   `true`인 `hasNextPage`만 통과시켜 `{ posts, hasNextPage }`를 반환합니다.
8. `PostsPage`가 abort되지 않았음을 확인한 뒤 page 0이면 posts를 교체하고, 다음 page
   cursor를 1로 저장합니다. `PostBoard`에 세 props를 전달합니다.
9. `PostBoard`가 toolbar·header·`PostList`를 렌더링하고, `PostList`가 각 post를
   `PostListItem`으로 변환합니다. item은 title·날짜·통계를 표시하고 `ActivityBars`에
   count를 전달합니다.
10. `hasNextPage`가 true이면 목록 아래 sentinel이 만들어지고, `IntersectionObserver`가
    sentinel이 viewport에 들어오는 순간 `onLoadMore()`를 호출합니다.
11. `onLoadMore`가 `nextPageRef.current`(현재는 1)를 읽어 `loadPage(1)`을 호출합니다.
    성공하면 `[...previous, ...result.posts]`로 page 1을 뒤에 붙이고 cursor를 2로 바꿉니다.

## 14.12 추가 page·취소·오류 흐름

### 추가 page

page 1 이후의 요청도 같은 `loadPage`를 사용합니다. `loadingRef.current`가 true인 동안
observer가 여러 번 callback을 실행해도 즉시 return하므로 같은 page의 동시 요청을 막습니다.
요청이 끝나면 `finally`에서 false로 되돌리고, 다음 sentinel 진입이 다음 page를 요청할 수
있게 됩니다. backend가 `hasNextPage: false`를 보내면 `PostList`는 sentinel 자체를 만들지
않고 더 이상 observer도 생성하지 않습니다.

### route 이탈 또는 component 정리

`PostsPage` cleanup이 `cancelCurrentRequest()`를 호출합니다. 이 함수는 현재 controller의
`abort()`를 호출하고 ref와 loading flag를 초기화합니다. fetch가 나중에 rejection되어도
`controller.signal.aborted` 또는 `requestError.name === "AbortError"` branch에서 return하므로
취소를 사용자 오류로 표시하지 않습니다.

### 네트워크·HTTP 오류

abort가 아닌 오류이고 여전히 같은 controller가 current owner이면 `loadError`와 `failedPage`에
저장됩니다. `PostsPage`는 목록 대신 `ErrorView`를 렌더링하고 `getErrorMessage()`로 code·
status를 사용자 문구로 바꿉니다. Retry 클릭은 실패 page가 0인지 확인해 전체 목록을
초기화할지, page 1 이상만 다시 요청할지 결정합니다.

### ErrorBoundary와 API 오류의 구분

- `api.request()` rejection: `PostsPage`의 `try/catch`가 처리합니다.
- `PostBoard`, `PostList`, `PostListItem` render 오류: 각 `ErrorBoundary`가 fallback을 렌더링합니다.
- `IntersectionObserver` 자체와 browser API 오류: 현재 코드에는 별도 catch가 없으므로
  실제 browser 지원 여부는 실행 환경에서 확인해야 합니다.

## 14.15 모범 답안과 오답 정리

### 1번

- 모범 답안: page 0은 새 목록의 시작이므로 이전 데이터를 버리고 결과로 교체합니다. page
  1 이상은 이전 page를 유지하면서 다음 데이터를 이어 붙여 무한 스크롤 목록을 만듭니다.
- 오답 포인트: 모든 page를 교체하면 사용자가 스크롤할 때 앞에서 본 글이 사라집니다.

### 2번

- 모범 답안: backend `PostService`가 `Page<Post>.hasNext()`를 읽어
  `PostPageResponseDto.hasNextPage`로 만들고, `postApi`가 그 값을 정확한 boolean으로
  받아 PostsPage state에 저장합니다.
- 오답 포인트: 프론트가 현재 배열 길이로 마지막 page를 추측하는 구조가 아닙니다.

### 3번

- 모범 답안: loading 여부는 화면에 표시할 값이 아니라 observer의 중복 callback을 막는
  제어 값입니다. ref는 `.current` 변경으로 재렌더링을 일으키지 않으므로 요청 중 즉시
  확인·변경할 수 있습니다.
- 오답 포인트: state로 두면 반드시 틀린 것은 아니지만, 여기서는 요청 lock을 위해 ref로
  명시한 현재 구현을 놓치게 됩니다.

### 4번

- 모범 답안: AbortController는 route 이탈·effect cleanup 때 fetch가 늦게 state를 바꾸지
  않도록 취소합니다. controller identity 비교는 오래된 요청의 catch/finally가 새 요청의
  오류나 loading 상태를 덮어쓰지 못하게 합니다.
- 오답 포인트: abort만 하면 모든 늦은 응답 문제가 자동으로 해결된다고 단정하면 안 됩니다.
  현재 코드는 signal 확인과 identity 확인을 함께 사용합니다.

### 5번

- 모범 답안: IntersectionObserver는 sentinel이 viewport에 들어왔다는 사실만 callback으로
  알리고 page 숫자는 모릅니다. `PostsPage.nextPageRef.current`가 다음 page를 보관하고
  `loadNextPage`가 그 값을 `loadPage`에 전달합니다.
- 오답 포인트: `PostList`가 내부에서 page를 1씩 증가시킨다고 보면 실제 책임 분리를 놓칩니다.

### 6번

- 모범 답안: React 목록과 ActivityBars가 count를 바로 계산·렌더링할 수 있도록 누락값을
  0으로 고정합니다. `post?.likeCount ?? 0`은 유효한 0은 유지하고 null/undefined만 대체합니다.
- 오답 포인트: count가 없을 때 문자열 `"0"`을 보내는 것이 아니라 number 0을 만듭니다.

### 7번

- 모범 답안: 응답의 posts가 배열이 아니면 `.map`을 호출할 수 없습니다. `Array.isArray`
  검사 후 아니면 빈 배열을 반환해 목록 render가 배열을 전제로 동작하도록 합니다.
- 오답 포인트: optional chaining만으로 배열이라는 사실까지 보장된다고 생각하면 안 됩니다.

### 8번

- 모범 답안: ErrorBoundary는 자식 render/lifecycle 중 발생한 React rendering error의
  fallback 경계입니다. `fetch` Promise rejection은 PostsPage `try/catch`에서 `loadError`로
  처리됩니다.
- 오답 포인트: HTTP 401·500을 ErrorBoundary가 자동으로 잡는다고 보면 안 됩니다.

### 9번

- 모범 답안: article 자체를 focus 가능하게 만들고 Enter/Space에서도 상세 route로 이동하게
  해 키보드 사용자가 마우스 클릭과 같은 기능을 사용할 수 있게 합니다.
- 오답 포인트: `tabIndex`가 post API 요청을 제어한다고 보면 안 됩니다. 표시·접근성 계층입니다.

### 10번

- 모범 답안: PostsPage가 `hasNextPage`를 false로 저장하고, PostList의 effect가 조기 return하며,
  sentinel도 `hasNextPage && <div ref={observerTargetRef} className="scroll-observer-target" />` 조건 때문에 렌더링되지 않습니다. 따라서 다음 page 요청
  callback이 더 이상 발생하지 않습니다.
- 오답 포인트: 이미 만들어진 observer가 계속 살아 있다고 생각하면 cleanup·조건을 놓칩니다.
