# 04~08 인증 통합 실행 흐름

이 문서는 04~08장의 원문을 다시 복사하는 문서가 아닙니다. 각 장의 대표 코드가 실제 요청의 어느 위치에서 연결되는지 한 번에 찾는 지도입니다. 세부 코드와 문법은 다음 문서에서 파일별로 한 번만 정독합니다.

- 04장: 로그인 자격증명과 세션 생성
- 05장: Access Token 검증과 보호 요청
- 06장: Refresh Token·AuthSession·rotation
- 07장: 로그아웃·Cookie 만료·Origin/CORS
- 08장: 요청 로그·세션 정리·인증 무효화·테스트

## 1. 먼저 구분할 세 가지 실행 시점

### 애플리케이션 시작 시 한 번 실행되는 코드

~~~~text
SpringdatajpaApplication.main
→ SpringApplication.run
→ @Component/@Configuration Bean 생성
→ @Value YAML 주입
→ SecurityFilterChain 등록
→ Interceptor registry 등록
→ @EnableScheduling scheduler 등록
~~~~

여기서 `JwtProvider`가 SecretKey를 만들고, `CorsOriginProvider`가 Origin Set을 만들고, `SecurityConfig`가 Filter chain을 조립합니다. 이 method들이 HTTP 요청마다 다시 실행되는 것은 아닙니다.

### HTTP 요청마다 실행되는 코드

~~~~text
Servlet container request/response 생성
→ Spring Security Filter chain
→ MVC Interceptor
→ DispatcherServlet이 Controller 호출
→ Service·Repository
→ Controller 반환값/response header
~~~~

JWT Filter는 Security 단계, Origin·로그 interceptor는 MVC 단계입니다. Filter에서 직접 401을 쓰면 Controller와 `GlobalExceptionHandler`까지 가지 않을 수 있습니다.

### HTTP와 관계없이 scheduler가 실행하는 코드

~~~~text
@Scheduled tick
→ AuthSessionCleanupScheduler.deleteExpiredSessions
→ AuthSessionRepository.deleteAllExpiredAtOrBefore
→ 만료 row bulk DELETE
~~~~

## 4. 보호 요청: token 문자열이 현재 요청의 principal이 된다

~~~~text
localStorage Access Token
→ api.js가 Authorization: Bearer header 생성
→ SecurityConfig의 Filter chain
→ JwtAuthenticationFilter
→ Bearer 형식 확인
→ JwtProvider.getAccessTokenClaims
   ├─ secretKey signature 검증
   ├─ expiration/형식 검증
   └─ subject→userId, authVersion→record
→ CustomUserDetailsService.loadUserByUserId
→ User deleted/suspended/authVersion 확인
→ UsernamePasswordAuthenticationToken(userDetails, null, authorities)
→ SecurityContextHolder.setAuthentication
→ filterChain.doFilter
→ anyRequest().authenticated 통과
→ @AuthenticationPrincipal CustomUserDetails
→ Controller
~~~~

### header가 없을 때와 잘못된 token일 때

| 상태 | Filter | 다음 처리 |
|---|---|---|
| header 없음/`Bearer ` 아님 | chain을 계속, 인증을 만들지 않음 | 보호 endpoint면 Security entry point 401 |
| Bearer token invalid | catch에서 context clear + `ErrorResponseWriter` | Controller로 보내지 않고 401 |
| User 삭제/정지/version 불일치 | Filter에서 실패 | `INVALID_TOKEN` 401 |
| 인증은 됐지만 권한 부족 | Filter 통과 | Security access denied 403 |

`filterChain.doFilter`를 호출한 뒤의 `return`은 현재 method만 끝냅니다. 호출한 chain 내부의 다음 Filter/DispatcherServlet을 취소하지 않습니다. 반대로 오류 catch에서는 chain을 호출하지 않으므로 Controller에 가지 않습니다.

### 세부 문서

원문과 문법: `05_인증_AccessToken_요청인증.md` 1~8절.

## 5. Refresh: Cookie 원문을 다시 보내지 않고 hash만 DB와 비교한다

~~~~text
보호 요청 401
→ api.request가 endpoint가 제외 대상인지 확인
→ refreshPromise 공유
→ sendRequest("/sessions/refresh", POST, includeAccessToken=false)
→ credentials: include로 browser Cookie 전송
→ SessionController.refreshSession @CookieValue
→ SessionService.refreshSession
→ hashRefreshToken(원문)
→ AuthSessionRepository.findByRefreshTokenHash + PESSIMISTIC_WRITE
→ row 존재·isActive·User 상태 확인
→ AuthSession.rotate(newHash, newExpiry)
→ JwtProvider.createAccessToken
→ SessionRefreshResponseDto
→ Set-Cookie 새 원문 + JSON 새 Access Token
→ localStorage 교체
→ 원래 API 재시도
~~~~

### 동시성의 두 층

- `refreshPromise`: 한 frontend module에서 동시에 401을 받은 요청들이 Refresh HTTP 요청 하나를 공유합니다.
- `PESSIMISTIC_WRITE`: backend DB transaction들이 같은 `AuthSession` row를 동시에 조회·변경하는 경쟁을 제어합니다.

둘은 다른 범위의 문제입니다. 현재 코드와 테스트만으로 여러 backend 인스턴스·모든 DB isolation에서의 결과를 자동으로 보장한다고 단정하지 않습니다.

### 세부 문서

원문과 문법: `06_인증_RefreshToken_재발급과_세션Rotation.md` 1~10절.

## 6. 로그아웃: 서버 상태와 브라우저 상태를 각각 바꾼다

~~~~text
DELETE /sessions
→ JWT Filter 제외 + Security permitAll
→ Origin 검사
→ @CookieValue refreshToken(없어도 진입)
→ SessionService.deleteSession
   ├─ null/blank면 no-op
   ├─ 원문 hash
   ├─ AuthSession row 조회
   └─ 있으면 revoke(revokedAt)
→ Controller createExpiredRefreshTokenCookie
→ Set-Cookie name/path 동일 + Max-Age=0
→ browser가 기존 Cookie 삭제
~~~~

DB revoke가 Cookie를 직접 지우는 것은 아니고, `Max-Age=0` header가 DB row를 revoke하는 것도 아닙니다. 둘을 같은 Controller 요청에서 각각 호출해야 server와 browser의 상태가 모두 정리됩니다.

### 세부 문서

원문과 문법: `07_인증_로그아웃_Cookie_Origin_CORS.md` 1~4절.

## 7. Origin/CORS: 같은 목록을 쓰지만 책임은 다르다

~~~~text
application YAML cors.allowed-origins
→ CorsOriginProvider 생성자
→ comma split/trim/filter/Set
├─ WebConfig → Spring MVC CORS allowedOrigins/methods/headers/credentials
└─ SessionOriginInterceptor → Cookie session request의 Origin 실제 차단
   ├─ 허용 → true → Controller 계속
   └─ null/불일치 → ErrorResponseWriter 403 → false → Controller 중단
~~~~

- CORS 설정은 browser가 cross-origin 요청을 처리할 수 있는 규칙입니다.
- Origin Interceptor는 Cookie가 자동 전송되는 세션 endpoint를 서버에서 실제로 처리할지 결정하는 추가 경계입니다.
- `InterceptorConfig`는 RequestLogInterceptor를 `/**`, SessionOriginInterceptor를 `/sessions`, `/sessions/refresh`에 등록합니다. `DELETE /sessions`도 path가 `/sessions`라 registry 대상이고 내부 method 조건에 포함됩니다.

### 세부 문서

원문과 문법: `07_인증_로그아웃_Cookie_Origin_CORS.md` 5~9절.

## 8. 비밀번호 변경·탈퇴: 기존 credential의 무효화

~~~~text
PATCH /users/password
→ Filter가 현재 CustomUserDetails 제공
→ UserController.setPassword
→ UserService.setPassword
→ current password 검증
→ User.changePassword(newHash)
   └─ authVersion++
→ AuthSessionRepository.revokeAllActiveByUser
→ Cookie 만료 header
→ 다음 보호 요청: JWT authVersion ≠ DB authVersion → 401 INVALID_TOKEN
→ 다음 Refresh: revoked session → 401 INVALID_REFRESH_TOKEN

DELETE /users
→ UserController.deleteUser
→ UserService.deleteUser
→ User.delete(deleted=true)
→ active AuthSession revoke
→ Cookie 만료
→ 다음 보호 요청: deleted=false 조회 실패 → 401 INVALID_TOKEN
~~~~

nickname/profile image만 수정하는 `PATCH /users`는 authVersion을 증가시키지 않고 session revoke도 호출하지 않습니다. 현재 source에서 password 변경과 탈퇴에만 인증 무효화 코드가 있습니다.

## 10. 오류 응답의 위치

~~~~text
Filter·Security·MVC Interceptor에서 직접 차단
→ ErrorResponseWriter.write(HttpServletResponse, status, ApiErrorCode)
→ response status/content-type/body 직접 기록
→ chain 또는 Controller 진행 중단

Controller·Service까지 도달한 뒤 예외 발생
→ GlobalExceptionHandler
→ 예외 type에 맞는 JSON response
~~~~

예를 들어 invalid Bearer JWT는 Filter가 `INVALID_TOKEN`을 직접 작성하고, invalid Refresh Cookie는 Controller/Service에서 `AuthException`이 발생한 뒤 `GlobalExceptionHandler`가 `INVALID_REFRESH_TOKEN`으로 바꿉니다. 같은 “인증 실패”라도 실패 위치가 다르므로 오류 code와 처리 주체가 다릅니다.

세부 `ErrorResponseWriter` 원문은 05장 6절, Controller 예외 연결은 04장 예외 설명과 08장 테스트 범위에서 확인합니다.

## 12. 현재 코드와 문서에서 확인한 제한

- Access Token 원문은 backend DB/Redis에 저장되지 않습니다. 현재 요청의 `SecurityContext`에만 검증 결과가 임시로 저장됩니다.
- logout은 Refresh Session과 Cookie를 무효화하지만, 이미 발급된 Access Token 자체를 blacklist로 삭제하는 코드는 없습니다.
- password 변경은 `authVersion++`과 active Refresh Session revoke를 함께 수행합니다. nickname/profile image 수정은 현재 소스에서 인증 무효화를 수행하지 않습니다.
- Origin 검사 대상은 현재 source의 `/sessions`, `/sessions/refresh` 세 method/path 조합입니다. 모든 API의 Origin을 검사한다고 설명하면 안 됩니다.
- `ErrorResponseWriter`는 Filter·Security·Interceptor의 직접 응답 경로이고, `GlobalExceptionHandler`는 Controller/Service 예외 경로입니다.
- 인증 테스트에는 별도의 다중 backend Refresh 동시성 integration test가 확인되지 않습니다. row lock annotation의 존재와 동시성 보장은 같은 말이 아닙니다.
- 이 통합 문서와 04~08 문서는 실제 소스·현재 test source를 정적으로 대조해 작성한 학습 자료입니다. 문서 작성 중 전체 테스트나 실제 배포 환경을 실행한 것은 아닙니다.
