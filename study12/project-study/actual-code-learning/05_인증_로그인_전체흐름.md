# 05장. 로그인 전체 흐름: 입력값이 Access Token과 Refresh Session으로 바뀌는 과정

이 장은 사용자가 로그인 화면에서 제출한 이메일·비밀번호가 `POST /sessions`로 전송되고,
백엔드가 자격 증명을 확인한 뒤 Access Token과 Refresh Token Session을 만들고,
브라우저가 두 값을 서로 다른 저장소에 보관하기까지를 한 흐름으로 읽습니다.

> 이 문서는 재구성 계획에 따라 새로 만든 로그인 기준 문서입니다. 계획에는 기존
> `04_인증_로그인_자격증명과_세션생성.md`를 임시 보존한다고 적었지만, 현재 작업 트리에서는
> 그 파일이 이미 삭제 상태입니다. 기존 `05_인증_AccessToken_요청인증.md`는 아직 새 06장으로
> 이동하지 않았으므로 여기서 덮어쓰지 않았습니다.

## 이 장에서 완성할 실행 지도

~~~~text
사용자가 LoginForm 제출
→ LoginPage.handleSubmit
→ authApi.login
→ api.request
→ api.sendRequest → fetch("POST /sessions")
→ JwtAuthenticationFilter가 POST /sessions를 제외
→ SecurityConfig가 POST /sessions를 permitAll
→ SessionOriginInterceptor가 허용 Origin 확인
→ SessionController.createSession
→ @RequestBody JSON을 SessionRequestDto로 역직렬화·검증
→ SessionService.createSession
→ AuthenticationManager.authenticate
→ CustomUserDetailsService.loadUserByUsername
→ UserRepository.findByEmailAndDeletedFalse
→ Spring Security가 password hash 비교
→ CustomUserDetails 반환
→ JwtProvider.createAccessToken
→ RefreshTokenProvider가 원문·hash·만료시각 생성
→ AuthSession 생성
→ AuthSessionRepository.save
→ SessionResponseDto 생성
→ Controller가 refresh 원문을 Set-Cookie header에 기록
→ Controller 반환값이 JSON body로 직렬화
~~~~

이 장에서 설명하지 않는 것과 다음 장의 위치도 먼저 분리합니다.

- JWT를 **보호 요청에서 검증**하는 `JwtAuthenticationFilter.doFilterInternal` 전체는 새 06장에서 읽습니다. 여기서는 로그인 요청이 왜 그 Filter를 건너뛰는지만 확인합니다.
- Refresh Token으로 **재발급·rotation**하는 `SessionService.refreshSession`은 새 07장에서 읽습니다. 이 장에서는 로그인 때 최초 Session을 만드는 `AuthSession` 생성만 읽습니다.
- 로그아웃의 `deleteSession`, 계정 변경에 따른 `authVersion` 증가는 새 08장에서 읽습니다.
- `GlobalExceptionHandler`와 `ErrorResponseWriter`의 전체 공통 구조는 03장과 새 04장에서 이미 확인했으므로, 이 장에서는 로그인 오류가 어느 handler로 가는지 필요한 부분만 연결합니다.

## 실행 순서와 코드 읽기 순서

### 실제 실행 순서

1. 브라우저가 `LoginPage`를 렌더링하고 `LoginForm`에 `handleChange`, `handleSubmit`을 전달합니다.
2. 사용자가 입력을 바꾸면 `form`과 `errors` state가 갱신됩니다.
3. 사용자가 제출하면 `handleSubmit`이 먼저 프론트 검증을 하고 `authApi.login`을 호출합니다.
4. `api.request`가 `fetch`를 실행합니다. `credentials: "include"` 때문에 응답의 Cookie 처리가 가능합니다.
5. 백엔드의 Filter와 Security 공개 규칙, Cookie Session Origin Interceptor를 통과해야 Controller에 도달합니다.
6. Controller가 JSON을 DTO로 만들고 Service에 전달합니다.
7. Service가 Spring Security 인증을 요청하고, 성공한 User를 바탕으로 Access Token과 AuthSession을 생성합니다.
8. Controller는 Access Token·userId를 JSON body로, 원문 Refresh Token을 `Set-Cookie` header로 분리합니다.
9. 프론트는 JSON의 Access Token만 `localStorage`에 저장하고 게시글 화면으로 이동합니다. Refresh Token 원문은 프론트 JavaScript가 읽지 않는 HttpOnly Cookie입니다.

### 이 장에서의 코드 읽기 순서

호출이 시작되는 화면부터 읽되, 백엔드에서 실제로 호출되는 타입을 끊지 않습니다.

1. `LoginPage.jsx`의 state·`handleChange`·`handleSubmit`
2. `LoginForm.jsx`의 form event 연결
3. `authApi.js`의 `login`
4. `api.js` 전체 공통 요청·응답·오류 경계
5. `authStorage.js`의 Access Token 저장 위치
6. 새 04장의 Filter skip·`permitAll`·Origin 통과 지점
7. `SessionRequestDto`와 `UserRepository`
8. `CustomUserDetails`와 `CustomUserDetailsService`
9. `SessionService.createSession`
10. `JwtProvider`, `RefreshTokenProvider`, `AuthSession`
11. `SessionResponseDto`, `RefreshCookieProvider`, `SessionController`
12. `GlobalExceptionHandler`와 로그인 Service 테스트

선언된 파일의 순서가 아니라, 앞 method의 반환값이 다음 method의 입력이 되는 순서입니다.

## 1. 화면에서 로그인 입력과 제출을 만든다

### 실제 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/src/pages/auth/LoginPage.jsx`

### 코드 원문

~~~~jsx
import { useState } from "react";
import { useNavigate } from "react-router-dom";

import { authApi } from "../../api/authApi.js";
import { authStorage } from "../../auth/authStorage.js";
import ConfirmModal from "../../components/common/ConfirmModal.jsx";
import LoginForm from "../../components/auth/LoginForm.jsx";
import AuthLayout from "../../components/layout/AuthLayout.jsx";
import {
    getErrorMessage,
    hasErrorCode,
} from "../../utils/errorMessage.js";
import { isValidEmail, isValidPassword } from "../../utils/validation.js";
import "../../styles/auth.css";

const EMAIL_EMPTY_MESSAGE = "*이메일을 입력해주세요.";
const EMAIL_INVALID_MESSAGE = "*올바른 이메일 주소 형식을 입력해주세요.";
const PASSWORD_EMPTY_MESSAGE = "*비밀번호를 입력해주세요.";
const PASSWORD_INVALID_MESSAGE = "*비밀번호 형식을 확인해주세요.";

function getFieldError(name, value) {
    if (name === "email") {
        const trimmedEmail = value.trim();

        if (!trimmedEmail) {
            return EMAIL_EMPTY_MESSAGE;
        }
        if (!isValidEmail(trimmedEmail)) {
            return EMAIL_INVALID_MESSAGE;
        }
    }

    if (name === "password") {
        if (!value) {
            return PASSWORD_EMPTY_MESSAGE;
        }
        if (!isValidPassword(value)) {
            return PASSWORD_INVALID_MESSAGE;
        }
    }

    return "";
}

function LoginPage() {
    const navigate = useNavigate();
    const [form, setForm] = useState({ email: "", password: "" });
    const [errors, setErrors] = useState({ email: "", password: "" });
    const [isSubmitting, setIsSubmitting] = useState(false);
    const [isSuspendedModalOpen, setIsSuspendedModalOpen] = useState(false);
    const [suspendedMessage, setSuspendedMessage] = useState("");
    const isValid = isValidEmail(form.email.trim()) && isValidPassword(form.password);

    function handleChange(event) {
        const { name, value } = event.target;
        setForm((previous) => ({ ...previous, [name]: value }));
        setErrors((previous) => ({
            ...previous,
            [name]: getFieldError(name, value),
        }));
    }

    async function handleSubmit(event) {
        event.preventDefault();

        if (!isValid) {
            setErrors({
                email: getFieldError("email", form.email),
                password: getFieldError("password", form.password),
            });
            return;
        }

        try {
            setIsSubmitting(true);
            setErrors({ email: "", password: "" });
            const result = await authApi.login({
                email: form.email.trim(),
                password: form.password,
            });
            authStorage.setAccessToken(result.accessToken);
            navigate("/posts", { replace: true });
        } catch (error) {
            if (hasErrorCode(error, "SUSPENDED_ACCOUNT")) {
                setSuspendedMessage(getErrorMessage(error));
                setIsSuspendedModalOpen(true);
                return;
            }
            setErrors((previous) => ({
                ...previous,
                password: `*${getErrorMessage(
                    error,
                    "이메일 또는 비밀번호를 확인해주세요.",
                )}`,
            }));
        } finally {
            setIsSubmitting(false);
        }
    }

    return (
        <AuthLayout
            pageClassName="login-page"
            sectionClassName="login-section"
            intro={{
                eyebrow: "Anonymous Bamboo Forest",
                title: "이름을 숨긴 고민에, 이름 있는 위로를 건네는 밤",
                items: [
                    { title: "익명의 고백", description: "게시글에서는 누구인지 드러내지 않고 마음을 털어놓아요" },
                    { title: "책임 있는 위로", description: "댓글은 계정으로 남겨 서로에게 조심스러운 온기를 건네요" },
                ],
            }}
        >
            <LoginForm
                form={form}
                errors={errors}
                isSubmitting={isSubmitting}
                isValid={isValid}
                onChange={handleChange}
                onSubmit={handleSubmit}
                signupTo="/signup"
            />
            <ConfirmModal
                isOpen={isSuspendedModalOpen}
                title="정지된 계정입니다"
                description={suspendedMessage}
                confirmText="확인"
                onConfirm={() => {
                    setIsSuspendedModalOpen(false);
                    setSuspendedMessage("");
                }}
            />
        </AuthLayout>
    );
}

export default LoginPage;
~~~~

### 코드 바로 아래 설명

- `LoginPage`는 로그인 화면의 상태와 업무 시작을 담당합니다. `LoginForm`이 API를 호출하는 것이 아니라 부모가 `handleSubmit`을 만들어 child prop으로 내려보냅니다.
- `useState`는 `[현재값, 값을 바꾸는 setter]` 배열을 반환합니다. 따라서 `form`은 입력 객체, `setForm`은 그 객체를 갱신하는 함수입니다.
- 현재 이 화면의 `errors` 구조는 `{ email: "", password: "" }`입니다. 회원가입 화면의 `passwordCheck`, `nickname`이 자동으로 들어오는 구조가 아니므로 로그인에서 존재하는 오류 key는 두 개뿐입니다.
- `isValid`는 별도 state가 아니라 렌더링 때마다 `form`에서 계산되는 상수입니다. 이메일은 `trim()`한 값으로 검사하고, 비밀번호는 입력값을 그대로 검사합니다.
- `handleChange`의 `const { name, value } = event.target`은 객체 구조 분해입니다. `<input name="email">`이면 `name`이 `email`이 되어 `[name]` 위치에 email property를 갱신합니다.
- `{ ...previous, [name]: value }`에서 `...previous`는 기존 입력을 복사하고, 뒤의 computed property가 현재 field만 덮어씁니다. password를 입력할 때 email 값을 잃지 않는 이유입니다.
- `handleSubmit`의 `event.preventDefault()`는 브라우저 기본 form 전송과 새로고침을 막습니다. 이후 HTTP 요청은 React가 아니라 `authApi`와 `fetch`가 수행합니다.
- `isValid`가 false이면 오류 문자열을 state에 넣고 `return`합니다. 이 `return`은 `handleSubmit`만 끝내므로 이 분기에서는 `authApi.login`이 호출되지 않습니다.
- `await authApi.login(...)`이 반환하는 값은 백엔드의 JSON body입니다. 성공하면 `result.accessToken`만 `authStorage`로 보내고, Refresh Token은 body에서 받지 않습니다.
- `try/catch/finally`는 비동기 요청의 성공·예외·공통 마무리를 나눕니다. `finally`는 성공하거나 실패해도 `isSubmitting`을 false로 되돌립니다.
- 서버가 `SUSPENDED_ACCOUNT`를 반환하면 modal을 열고, 그 외 오류는 password field의 오류 문구를 바꿉니다. 이 오류 code가 백엔드에서 어떻게 만들어지는지는 뒤의 `LoginFailedException`과 `GlobalExceptionHandler` 연결에서 확인합니다.

### 이 함수의 호출·값·반환

- 호출자: `LoginForm`의 `<form onSubmit={onSubmit}>`를 통해 React가 호출합니다.
- 입력값: `event`는 browser submit event, `form`은 이 컴포넌트의 state입니다.
- 호출 대상: `authApi.login` → `api.request` → `fetch`.
- 성공 반환값 사용: `result.accessToken` → `authStorage.setAccessToken` → browser `localStorage`.
- 예외 도착 위치: `api.request`가 만든 `Error`가 `catch (error)`로 들어옵니다.
- 다음 파일: `LoginForm.jsx`에서 이 함수가 form event에 연결되는 것을 확인합니다.

### 코드 바로 아래 설명

- `LoginForm({ ... })`의 parameter는 부모가 전달한 props 객체를 구조 분해한 것입니다. `LoginPage`가 넘긴 `form`, `errors`, `onChange`, `onSubmit`이 여기서 각각 같은 이름의 local parameter가 됩니다.
- `<form noValidate onSubmit={onSubmit}>`에서 `noValidate`는 browser의 기본 HTML validation popup을 끄고, `LoginPage`의 `isValid`·`getFieldError`를 사용하게 합니다. `onSubmit`은 `LoginPage.handleSubmit`의 함수 참조입니다.
- `value={form.email}`과 `onChange={onChange}`가 함께 있으므로 controlled input입니다. 실제 값은 DOM이 아니라 부모 `form` state가 소유합니다.
- `name="email"`과 `name="password"`가 부모의 `event.target.name`으로 돌아갑니다. 그래서 부모의 computed property가 어느 field를 바꿀지 알 수 있습니다.
- `errors.email`, `errors.password`는 객체 property 접근입니다. 이 화면의 오류 field가 두 개로 고정되는 근거가 실제 prop 사용 위치에 있습니다.
- `disabled={!isValid || isSubmitting}`는 두 조건 중 하나라도 true이면 submit button을 비활성화합니다. 다만 사용자가 강제로 HTTP 요청을 만들 수 있는 경우까지 막는 보안 장치는 아니며, 서버 DTO 검증이 별도로 필요합니다.

### 책임과 다음 호출

- 호출자: `LoginPage`의 JSX.
- 호출하는 UI component: `FormField`, `TextInput`, `ActionButton`, `AppLink`. 이 공통 UI의 내부 구현은 로그인 HTTP 흐름을 바꾸지 않으므로 프론트 공통 UI 문서에서 별도로 확인합니다.
- 이 component의 반환값: React element tree입니다. HTTP response나 token을 반환하지 않습니다.
- 실제 API 호출을 시작하는 함수: prop으로 받은 `onSubmit`, 즉 `LoginPage.handleSubmit`입니다.
- 다음 파일: `authApi.js`의 `login`이 URL과 body를 어떻게 조립하는지 확인합니다.

## 3. `authApi.login`은 로그인 endpoint와 JSON body를 조립한다

### 실제 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/src/api/authApi.js`

### 코드 원문

~~~~js
import { refreshAccessToken, request } from "./api.js";

export const authApi = {
    login({ email, password }) {
        return request("/sessions", {
            method: "POST",
            body: JSON.stringify({ email, password }),
        });
    },

    logout() {
        return request("/sessions", { method: "DELETE" });
    },

    refresh() {
        return refreshAccessToken();
    },

    signup(payload) {
        return request("/users", {
            method: "POST",
            body: JSON.stringify(payload),
        });
    },
};
~~~~

### 코드 바로 아래 설명

- `export const authApi = { ... }`는 여러 인증 API 함수를 하나의 객체로 묶어 다른 module에서 import할 수 있게 합니다. `LoginPage`는 그중 `authApi.login`만 호출합니다.
- `login({ email, password })`의 중괄호 parameter는 호출자가 넘긴 객체에서 두 property를 꺼내는 구조 분해입니다. `handleSubmit`이 넘긴 `{ email: form.email.trim(), password: form.password }`가 이 parameter로 들어옵니다.
- `JSON.stringify`는 JavaScript object를 HTTP request body에 넣을 문자열로 바꿉니다. 이 함수는 backend Controller를 직접 호출하지 않고, `request`의 Promise를 그대로 반환합니다.
- `request`를 `return`하므로 `LoginPage`의 `await`가 fetch 완료와 JSON parsing 완료까지 기다립니다. 반환값을 중간에서 바꾸지 않습니다.
- 같은 파일의 `logout`, `refresh`, `signup`은 실제로 존재하지만 이 장의 로그인 호출 경로에는 사용되지 않습니다. `authApi.refresh()`는 현재 frontend source에서 호출 위치가 확인되지 않고, 401 재발급은 `api.js`의 `refreshAccessToken()`을 직접 호출합니다. 삭제하지 않고 “현재 흐름에서 사용되지 않음”으로 기록합니다.

### 메서드 계약

- 호출자: `LoginPage.handleSubmit`.
- 입력: email/password 문자열.
- 내부 호출: `request("/sessions", options)`.
- 반환: `request`가 반환하는 Promise. 성공 시 backend JSON, 실패 시 `Error` reject.
- 다음 파일: `api.js`가 실제 header, Cookie, fetch, response parsing을 담당합니다.

## 4. 공통 `api.js`가 실제 HTTP 요청과 오류를 처리한다

### 실제 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Front/src/api/api.js`

### 코드 원문: 현재 파일 전체

~~~~js
import { authStorage } from "../auth/authStorage.js";

const API_BASE_URL = import.meta.env.VITE_API_BASE_URL ?? "http://localhost:8080";
const PUBLIC_PATHS = ["/login", "/signup"];
const NO_REFRESH_REQUESTS = new Set([
    "POST /sessions",
    "POST /sessions/refresh",
    "DELETE /sessions",
    "POST /users",
]);

let refreshPromise = null;

function isRefreshExcludedRequest(endpoint, options = {}) {
    const method = (options.method ?? "GET").toUpperCase();
    return NO_REFRESH_REQUESTS.has(`${method} ${endpoint}`);
}

async function sendRequest(endpoint, options = {}, includeAccessToken = true) {
    const accessToken = authStorage.getAccessToken();
    const headers = {
        "Content-Type": "application/json",
        ...options.headers,
    };

    if (includeAccessToken && accessToken) {
        headers.Authorization = `Bearer ${accessToken}`;
    }

    const response = await fetch(`${API_BASE_URL}${endpoint}`, {
        ...options,
        headers,
        credentials: "include",
    });

    return {
        response,
        data: await readResponseData(response),
    };
}

async function readResponseData(response) {
    const contentType = response.headers.get("content-type");
    const responseText = await response.text();

    if (!responseText) {
        return null;
    }

    return contentType?.includes("application/json")
        ? JSON.parse(responseText)
        : responseText;
}

function createRequestError(response, data) {
    const errorCode =
        typeof data === "string"
            ? data
            : data?.code ?? data?.message ?? "UNKNOWN_ERROR";
    const errorMessage =
        typeof data === "string"
            ? data
            : data?.message ?? "요청 처리에 실패했습니다.";

    const error = new Error(errorMessage);
    error.code = errorCode;
    error.status = response.status;
    error.data = data;
    return error;
}

function clearAuthentication() {
    authStorage.removeAccessToken();

    if (!PUBLIC_PATHS.includes(window.location.pathname)) {
        window.location.replace("/login");
    }
}

async function performRefresh() {
    const result = await sendRequest(
        "/sessions/refresh",
        { method: "POST" },
        false,
    );

    if (!result.response.ok) {
        throw createRequestError(result.response, result.data);
    }

    if (!result.data?.accessToken) {
        throw new Error("액세스 토큰 재발급 응답이 올바르지 않습니다.");
    }

    authStorage.setAccessToken(result.data.accessToken);
    return result.data;
}

export function refreshAccessToken() {
    if (!refreshPromise) {
        refreshPromise = performRefresh().finally(() => {
            refreshPromise = null;
        });
    }

    return refreshPromise;
}

export async function request(endpoint, options = {}) {
    let result = await sendRequest(endpoint, options);

    if (
        result.response.status === 401 &&
        !isRefreshExcludedRequest(endpoint, options)
    ) {
        try {
            await refreshAccessToken();
            result = await sendRequest(endpoint, options);
        } catch (error) {
            if (error.status === 401) {
                clearAuthentication();
            }

            throw error;
        }
    }

    if (!result.response.ok) {
        if (result.response.status === 401) {
            clearAuthentication();
        }

        throw createRequestError(result.response, result.data);
    }

    return result.data;
}
~~~~

### 코드 바로 아래 설명: 로그인에 실제로 사용되는 부분

- `API_BASE_URL`은 Vite의 `import.meta.env.VITE_API_BASE_URL`을 읽고, 값이 `null` 또는 `undefined`일 때만 `http://localhost:8080`을 사용합니다. `??`는 빈 문자열까지 기본값으로 바꾸지 않는다는 점이 `||`와 다릅니다.
- `sendRequest(endpoint, options, includeAccessToken)`은 실제 `fetch`를 실행하는 내부 함수입니다. 로그인 호출에서는 `endpoint`가 `/sessions`, `options.method`가 `POST`이고, 기본값인 `includeAccessToken=true`지만 저장된 token이 없으면 Authorization header가 추가되지 않습니다.
- `headers`의 `...options.headers`는 기본 JSON header와 호출자가 전달한 header를 합칩니다. `fetch` options의 `...options`는 method와 body를 실제 요청에 복사합니다.
- `credentials: "include"`는 cross-origin 요청에서도 Cookie를 포함하고 응답의 `Set-Cookie`를 browser가 처리하도록 요청하는 옵션입니다. 로그인 응답에서 Refresh Cookie를 받으려면 이 옵션이 필요합니다.
- `readResponseData`는 response body를 한 번 `text()`로 읽습니다. 비어 있으면 `null`, content type에 `application/json`이 있으면 `JSON.parse` 결과, 아니면 문자열을 반환합니다.
- `request`는 먼저 `sendRequest`를 호출합니다. 로그인 `POST /sessions`가 401이어도 `NO_REFRESH_REQUESTS`에 포함되어 있으므로 자동 Refresh를 시도하지 않습니다. 로그인 실패가 다시 Refresh를 부르는 재귀를 막기 위한 실제 조건입니다.
- `createRequestError`는 backend JSON의 `code`, `message`, HTTP `status`, 원본 `data`를 하나의 JavaScript `Error` 객체에 추가합니다. 그래서 `LoginPage.catch`가 `hasErrorCode(error, "SUSPENDED_ACCOUNT")`를 확인할 수 있습니다.
- `clearAuthentication`은 Access Token을 localStorage에서 제거하고, 현재 화면이 `/login`·`/signup`이 아니면 `window.location.replace("/login")`으로 이동시킵니다. 로그인 endpoint 자체가 실패했을 때는 이미 public path일 수 있으므로 이동이 생략될 수 있습니다.
- `performRefresh`, `refreshAccessToken`은 이 장의 로그인 성공 요청에서는 호출되지 않습니다. 하지만 같은 파일에 실제로 존재하고, 401 보호 요청에서 사용됩니다. 새 07장에서 원래 요청 재시도와 함께 다시 설명합니다.

### 로그인 호출의 입력·반환·예외

| 구분 | 실제 값과 이동 |
|---|---|
| endpoint | `authApi.login` → `"/sessions"` → `API_BASE_URL + endpoint` |
| method | options의 `"POST"` → fetch request |
| body | `{ email, password }` → `JSON.stringify` → `SessionRequestDto` |
| Cookie | `credentials: "include"` → backend `Set-Cookie` 수신 가능 |
| 성공 반환 | JSON data → `request` → `authApi.login` → `LoginPage.result` |
| 실패 반환 | response/data → `createRequestError` → `catch(error)` |

## 7. JSON body를 `SessionRequestDto`로 역직렬화하고 서버에서 다시 검증한다

### 실제 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/dto/user/SessionRequestDto.java`

### 코드 원문

~~~~java
package kr.adapterz.springdatajpa.dto.user;

import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Pattern;
import lombok.Getter;
import lombok.NoArgsConstructor;

@Getter
@NoArgsConstructor
public class SessionRequestDto {
    @NotBlank
    @Email
    private String email;

    @NotBlank
    @Pattern(
            regexp = "^(?=.*[A-Z])(?=.*[a-z])(?=.*\\d)(?=.*[!@#$%^&*()_+\\-=\\[\\]{};':\"\\\\|,.<>\\/?~]).{8,20}$"
    )
    private String password;
}
~~~~

### 코드 바로 아래 설명

- `@RequestBody`가 Controller의 JSON body를 이 class의 `email`, `password` field에 넣습니다. 이 JSON→Java 변환을 역직렬화라고 합니다.
- `@NoArgsConstructor`는 Jackson이 먼저 빈 객체를 만들 수 있는 기본 생성자를 Lombok이 생성하게 합니다. 그 다음 JSON property가 field에 반영됩니다.
- `@Getter`는 `getEmail()`, `getPassword()`를 compile time에 생성합니다. `SessionService`에서 호출하는 getter가 source에 직접 보이지 않아도 사용할 수 있는 이유입니다.
- `@Valid`가 Controller parameter에 붙으면 `@NotBlank`, `@Email`, `@Pattern`을 실행합니다. 프론트 `isValid`는 사용자 경험용이고, API를 직접 호출할 수 있으므로 서버 검증이 반드시 별도로 실행됩니다.
- 정규식의 lookahead는 대문자·소문자·숫자·특수문자를 각각 하나 이상 요구하고, 마지막 `.{8,20}`은 전체 길이를 8~20자로 제한합니다. 정확한 정규식의 기준은 이 source 문자열이며 프론트 validation과 다를 수 있습니다.
- 검증 실패 시 `SessionController.createSession` method body가 실행되기 전에 `MethodArgumentNotValidException`이 발생하고 `GlobalExceptionHandler.handleValidationException`이 400 `INVALID_REQUEST`로 바꿉니다.

### 값의 이동

`LoginPage.form` → `JSON.stringify` → HTTP body → `@RequestBody SessionRequestDto request` → `request.getEmail()`·`request.getPassword()` → `AuthenticationManager`입니다.

## 9. `SessionService.createSession`이 인증 성공 후 token과 Session을 만든다

### 실제 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/service/SessionService.java`

### 코드 원문: class 선언과 로그인 method

아래 method는 실제 source의 `createSession` body입니다. 같은 `SessionService`에 있는
`refreshSession`, `deleteSession`은 각각 새 07·08장에서 실제 body를 읽으므로 여기서
placeholder로 바꾸지 않고, 로그인 method만 이 흐름에 배치합니다. package/import와
다른 두 method는 이 흐름의 호출에 필요하지 않아 생략했으며, 생략한 위치와 다음 읽을
문서를 아래에 명시합니다.

~~~~java
@Service
@RequiredArgsConstructor
@Transactional
public class SessionService {

    private final AuthenticationManager authenticationManager;
    private final JwtProvider jwtProvider;
    private final RefreshTokenProvider refreshTokenProvider;
    private final AuthSessionRepository authSessionRepository;

    public SessionResponseDto createSession(SessionRequestDto request) {
        try {
            Authentication authentication = authenticationManager.authenticate(
                    new UsernamePasswordAuthenticationToken(
                            request.getEmail(),
                            request.getPassword()
                    )
            );

            CustomUserDetails userDetails = (CustomUserDetails) authentication.getPrincipal();

            String accessToken = jwtProvider.createAccessToken(
                    userDetails.getUserId(),
                    userDetails.getAuthVersion()
            );
            String refreshToken = refreshTokenProvider.createRefreshToken();
            String refreshTokenHash = refreshTokenProvider.hashRefreshToken(refreshToken);

            AuthSession authSession = new AuthSession(
                    userDetails.getUser(),
                    refreshTokenHash,
                    refreshTokenProvider.createExpirationTime()
            );
            authSessionRepository.save(authSession);

            return new SessionResponseDto(
                    accessToken,
                    refreshToken,
                    userDetails.getUserId()
            );

        } catch (DisabledException e) {
            throw new LoginFailedException("Suspended_Account");
        } catch (AuthenticationException e) {
            throw new LoginFailedException("Login_Failed");
        }
    }
}
~~~~

### 코드 바로 아래 설명: 실행 순서

1. `@Service`가 Spring Bean으로 등록하고 `@RequiredArgsConstructor`가 네 개의 `final` 의존성을 받는 생성자를 만듭니다. `@Transactional`은 이 method의 DB 작업이 하나의 transaction 경계 안에서 실행되도록 합니다.
2. `new UsernamePasswordAuthenticationToken(request.getEmail(), request.getPassword())`는 Spring Security가 제공하는 Authentication 구현체를 만들고, 여기서는 email과 입력 평문 password를 인증 입력으로 담습니다. 이 객체가 DB에 저장되는 것이 아닙니다.
3. `authenticationManager.authenticate(...)`가 앞에서 본 `CustomUserDetailsService.loadUserByUsername`을 호출합니다. 성공하면 password 비교가 끝난 `Authentication`을 반환하고, 실패하면 `AuthenticationException` 계열을 던집니다.
4. `authentication.getPrincipal()`의 정적 반환 type은 일반 `Object`이므로 `(CustomUserDetails)` 형변환을 합니다. 형변환이 성공해야 `getUserId`, `getAuthVersion`, `getUser`를 호출할 수 있습니다. 실제 principal type이 다르면 `ClassCastException`이 발생하며 현재 catch 대상은 아닙니다.
5. `jwtProvider.createAccessToken`은 User ID와 현재 authVersion을 받아 Access Token 문자열을 만듭니다. JWT의 claim과 서명·검증 원리는 새 06장에서 다시 읽습니다.
6. `refreshTokenProvider.createRefreshToken()`은 browser에 보낼 **원문**을 만들고, `hashRefreshToken(refreshToken)`은 DB에 저장·검색할 **hash**를 만듭니다. 원문은 Cookie로 나가고 DB에는 hash만 들어가므로 DB 유출 시 Cookie 원문을 그대로 보관하지 않습니다.
7. `new AuthSession(user, refreshTokenHash, expiration)`은 사용자의 Refresh Session Entity를 메모리에 생성합니다. `authSessionRepository.save`는 `AuthSessionRepository`가 상속한 `JpaRepository`의 공통 `save` method이며, 이 Entity를 persistence context에 저장 대상으로 등록합니다. `AuthSessionRepository` source에 `save` 선언이 직접 없는 이유가 상속 때문입니다.
8. `return new SessionResponseDto(...)`에는 Access Token, 원문 Refresh Token, userId가 들어갑니다. 이 원문은 Controller가 Cookie header를 만드는 데 필요하지만 `@JsonIgnore` 때문에 JSON body에는 나오지 않습니다.
9. method가 정상 종료되어 transaction이 commit될 때 JPA가 `AuthSession` INSERT를 flush합니다. `save`의 반환값을 별도 변수에 받지 않아도 저장 대상 등록 자체는 실행됩니다. DB INSERT 실패는 이 `try-catch`의 `AuthenticationException` 대상이 아니므로 `Login_Failed`로 무조건 숨겨지지 않습니다.

### 예외가 이동하는 경로

- `DisabledException`: `LoginFailedException("Suspended_Account")` → `GlobalExceptionHandler.handleLoginFailedException` → HTTP 401 + `SUSPENDED_ACCOUNT` JSON.
- 그 밖의 `AuthenticationException`: `LoginFailedException("Login_Failed")` → 같은 handler → HTTP 401 + `LOGIN_FAILED` JSON.
- DTO validation 실패: Service까지 오지 않고 `MethodArgumentNotValidException` → 400 `INVALID_REQUEST`.
- Origin 거부: Controller까지 오지 않고 `ErrorResponseWriter`가 직접 403을 작성합니다.
- JWT/Refresh provider 또는 DB 오류: 현재 코드가 모두 `Login_Failed`로 변환한다고 말할 수 없습니다. 실제 catch가 `DisabledException`과 `AuthenticationException`만 감싸므로, 나머지는 별도 handler 또는 기본 오류 경로를 추가로 확인해야 합니다.

## 10. Access Token을 생성하는 `JwtProvider`

### 실제 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/auth/JwtProvider.java`

### 코드 원문: 생성에 사용되는 실제 class와 method

package/import와 token 검증 method는 이 장의 로그인 발급 호출에 필요하지 않아 생략한
실제 source 발췌입니다. 전체 파일 경로는 위에 적었고, 검증 method는 새 06장에서
발급 결과가 어떻게 소비되는지와 함께 읽습니다.

~~~~java
@Component
public class JwtProvider {
    private static final String AUTH_VERSION_CLAIM = "authVersion";

    private final SecretKey secretKey;
    private final long accessExpirationMillis;

    public JwtProvider(
            @Value("${jwt.secret}") String secret,
            @Value("${jwt.access-expiration-millis}") long accessExpirationMillis
    ) {
        this.secretKey = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
        this.accessExpirationMillis = accessExpirationMillis;
    }

    public String createAccessToken(Long userId, long authVersion) {
        Date now = new Date();
        Date expiration = new Date(now.getTime() + accessExpirationMillis);

        return Jwts.builder()
                .subject(String.valueOf(userId))
                .claim(AUTH_VERSION_CLAIM, authVersion)
                .issuedAt(now)
                .expiration(expiration)
                .signWith(secretKey)
                .compact();
    }
}
~~~~

### 코드 바로 아래 설명

- `@Component`가 이 provider를 Spring Bean으로 만들고, constructor의 `@Value`가 YAML의 `jwt.secret`, `jwt.access-expiration-millis`를 주입합니다. `secretKey`는 constructor에서 문자열 bytes를 HMAC용 `SecretKey`로 한 번 바꿔 저장합니다.
- `AUTH_VERSION_CLAIM`은 JWT payload 안에서 User의 현재 인증 버전을 저장할 key입니다. 로그인 당시 User의 version이 token에 들어가고, 나중에 비밀번호 변경으로 version이 증가하면 새 06장의 Filter가 불일치를 거부할 수 있습니다.
- `Date now`는 발급 시각, `expiration`은 현재 시각에 설정된 milliseconds를 더한 만료 시각입니다.
- `Jwts.builder()`는 JWT builder를 만들고 `.subject(String.valueOf(userId))`에 사용자 ID를 문자열 subject로 넣습니다. `.claim(...)`은 표준 claim이 아닌 프로젝트 custom claim을 추가합니다.
- `.signWith(secretKey)`는 같은 SecretKey로 서명하고 `.compact()`가 최종 JWT 문자열을 반환합니다. 로그인 Service는 이 문자열을 `SessionResponseDto.accessToken`에 넣습니다.
- 이 장에서 provider가 반환하는 것은 JWT 문자열 하나입니다. provider가 localStorage나 Cookie를 직접 조작하지 않으며, 저장 위치를 결정하는 것은 Controller와 frontend입니다.

### 새 문법·개념

- `@Value("${...}")`: Spring property placeholder를 constructor parameter에 주입합니다. 같은 이름의 parameter와 YAML key가 자동으로 연결되는 것이 아니라, annotation 안의 문자열이 연결 key입니다.
- `SecretKey`: JWT HMAC 서명에 사용할 비밀 키 타입입니다. 실제 문자열은 YAML/env에서 오고 `Keys.hmacShaKeyFor`가 library 객체로 변환합니다.
- `record`와 JWT 검증 결과 `AccessTokenClaims`는 새 06장에서 처음 자세히 읽습니다. 로그인에서는 `createAccessToken` 호출과 반환 문자열만 사용합니다.

## 11. Refresh Token 원문·hash·만료시각을 만든다

### 실제 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/auth/RefreshTokenProvider.java`

### 코드 원문

~~~~java
@Component
public class RefreshTokenProvider {

    private static final int TOKEN_BYTE_LENGTH = 32;

    private final SecureRandom secureRandom = new SecureRandom();
    private final Duration refreshExpiration;

    public RefreshTokenProvider(
            @Value("${jwt.refresh-expiration-millis}") long refreshExpirationMillis
    ) {
        this.refreshExpiration = Duration.ofMillis(refreshExpirationMillis);
    }

    public String createRefreshToken() {
        byte[] tokenBytes = new byte[TOKEN_BYTE_LENGTH];
        secureRandom.nextBytes(tokenBytes);

        return Base64.getUrlEncoder()
                .withoutPadding()
                .encodeToString(tokenBytes);
    }

    public String hashRefreshToken(String refreshToken) {
        try {
            MessageDigest messageDigest = MessageDigest.getInstance("SHA-256");
            byte[] tokenHash = messageDigest.digest(
                    refreshToken.getBytes(StandardCharsets.UTF_8)
            );

            return HexFormat.of().formatHex(tokenHash);
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException("SHA-256 is not available", e);
        }
    }

    public LocalDateTime createExpirationTime() {
        return LocalDateTime.now().plus(refreshExpiration);
    }
}
~~~~

### 코드 바로 아래 설명

- `TOKEN_BYTE_LENGTH = 32`는 원문을 32 random bytes로 만드는 설정입니다. 이 값은 Data URL의 길이 검증 같은 값이 아니라 Refresh Token random byte 길이입니다.
- `SecureRandom`은 예측하기 어려운 random 값을 만드는 Java security class입니다. `nextBytes`가 배열을 random bytes로 채우고, Base64 URL encoder가 Cookie에 넣기 쉬운 문자열로 변환합니다.
- `.withoutPadding()`은 Base64 끝의 `=` padding을 제거합니다. 반환 문자열에는 raw bytes가 그대로 노출되지 않고 URL-safe 문자로 표현됩니다.
- `MessageDigest.getInstance("SHA-256")`은 SHA-256 digest 객체를 얻는 호출입니다. `digest`가 원문 UTF-8 bytes를 32-byte hash로 바꾸고 `HexFormat`이 64자리 hex 문자열로 바꿉니다.
- DB에는 `hashRefreshToken`의 반환값만 저장하고, Cookie에는 `createRefreshToken`의 원문이 들어갑니다. Refresh 요청이 오면 같은 hash 과정으로 DB row를 찾습니다.
- `createExpirationTime`은 현재 시각에 YAML에서 받은 `refreshExpiration`을 더합니다. `LocalDateTime`은 DB `refresh_expires_at` 비교에 사용됩니다.
- `NoSuchAlgorithmException`은 Java runtime에 SHA-256이 없을 때의 checked exception입니다. 현재 구현은 이를 `IllegalStateException`으로 감싸며, 일반 로그인 실패 code로 변환하는 Service catch는 아닙니다.

### 값의 최초 출처와 사용 위치

| 값 | 생성 method | 로그인에서 사용되는 곳 |
|---|---|---|
| `refreshToken` 원문 | `createRefreshToken` | `SessionResponseDto` → `RefreshCookieProvider` |
| `refreshTokenHash` | `hashRefreshToken(refreshToken)` | `AuthSession` → `AuthSessionRepository.save` |
| 만료 시각 | `createExpirationTime` | `AuthSession.refreshExpiresAt` |

## 12. `AuthSession` Entity가 Refresh 원문의 hash와 만료 정보를 보관한다

### 실제 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/entity/AuthSession.java`

### 코드 원문

~~~~java
@Getter
@Entity
@Table(
        name = "auth_sessions",
        indexes = {
                @Index(name = "idx_auth_sessions_user_id", columnList = "user_id"),
                @Index(name = "idx_auth_sessions_refresh_expires_at", columnList = "refresh_expires_at")
        }
)
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class AuthSession {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "auth_session_id")
    private Long authSessionId;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id", nullable = false)
    private User user;

    @Column(name = "refresh_token_hash", nullable = false, unique = true, length = 64)
    private String refreshTokenHash;

    @Column(name = "refresh_expires_at", nullable = false)
    private LocalDateTime refreshExpiresAt;

    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @Column(name = "revoked_at")
    private LocalDateTime revokedAt;

    public AuthSession(
            User user,
            String refreshTokenHash,
            LocalDateTime refreshExpiresAt
    ) {
        this.user = user;
        this.refreshTokenHash = refreshTokenHash;
        this.refreshExpiresAt = refreshExpiresAt;
        this.createdAt = LocalDateTime.now();
        this.revokedAt = null;
    }

    public boolean isActive(LocalDateTime now) {
        return revokedAt == null && refreshExpiresAt.isAfter(now);
    }

    public void rotate(
            String refreshTokenHash,
            LocalDateTime refreshExpiresAt
    ) {
        this.refreshTokenHash = refreshTokenHash;
        this.refreshExpiresAt = refreshExpiresAt;
    }

    public void revoke(LocalDateTime revokedAt) {
        if (this.revokedAt == null) {
            this.revokedAt = revokedAt;
        }
    }
}
~~~~

### 코드 바로 아래 설명

- `@Entity`와 `@Table(name = "auth_sessions")`는 이 class가 `auth_sessions` table과 연결된 JPA Entity임을 나타냅니다. 로그인 Service가 `new AuthSession(...)`을 만들면 이 객체가 저장 대상이 됩니다.
- `@ManyToOne(fetch = FetchType.LAZY)`와 `@JoinColumn(name = "user_id")`는 여러 AuthSession이 하나의 User를 참조하는 관계입니다. login constructor의 첫 번째 인자가 이 `user` field에 들어갑니다.
- `refresh_token_hash`에 `unique = true`가 있으므로 서로 다른 Session이 같은 hash를 가질 수 없다는 DB 제약이 모델에 선언됩니다.
- 두 `@Index`는 사용자별 Session 조회와 만료 Session 정리 조회를 빠르게 하기 위한 DB index입니다. Entity field가 두 개 더 생기는 것이 아니라 table 조회 경로를 위한 index 구조입니다.
- 생성자는 user, hash, expiresAt을 받고 `createdAt`을 현재 시각으로, `revokedAt`을 null로 초기화합니다. login 최초 생성에서는 아직 revoke되지 않았기 때문입니다.
- `isActive`, `rotate`, `revoke`는 로그인 이후 Refresh/logout 흐름에서 사용됩니다. 이 장에서 생성자와 `save`를 이해하기 위해 전체 source를 확인했지만, 각 method의 호출 흐름은 새 07·08에서 다시 연결합니다.

### 13.2 `RefreshCookieProvider`

### 실제 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/auth/RefreshCookieProvider.java`

### 코드 원문

~~~~java
@Component
public class RefreshCookieProvider {

    public static final String COOKIE_NAME = "refreshToken";

    private final Duration refreshExpiration;
    private final boolean secure;
    private final String cookiePath;

    public RefreshCookieProvider(
            @Value("${jwt.refresh-expiration-millis}") long refreshExpirationMillis,
            @Value("${jwt.refresh-cookie-secure}") boolean secure,
            @Value("${jwt.refresh-cookie-path}") String cookiePath
    ) {
        this.refreshExpiration = Duration.ofMillis(refreshExpirationMillis);
        this.secure = secure;
        this.cookiePath = cookiePath;
    }

    public ResponseCookie createRefreshTokenCookie(String refreshToken) {
        return ResponseCookie.from(COOKIE_NAME, refreshToken)
                .httpOnly(true)
                .secure(secure)
                .sameSite("Strict")
                .path(cookiePath)
                .maxAge(refreshExpiration)
                .build();
    }

    public ResponseCookie createExpiredRefreshTokenCookie() {
        return ResponseCookie.from(COOKIE_NAME, "")
                .httpOnly(true)
                .secure(secure)
                .sameSite("Strict")
                .path(cookiePath)
                .maxAge(Duration.ZERO)
                .build();
    }
}
~~~~

### 코드 바로 아래 설명

- `COOKIE_NAME`은 backend가 발급·읽기·만료 처리에서 공유하는 Cookie 이름입니다. Controller의 `@CookieValue(name = RefreshCookieProvider.COOKIE_NAME)`와 같은 상수를 사용하므로 문자열을 따로 복사하지 않습니다.
- constructor의 property는 YAML/env에서 주입됩니다. `refreshExpiration`은 Cookie의 max-age, `secure`는 HTTPS 전송 여부, `cookiePath`는 Cookie가 전송될 URL path입니다.
- `createRefreshTokenCookie`는 기존 Cookie를 수정하는 것이 아니라 `ResponseCookie`라는 새 header 값 객체를 만듭니다. Controller가 그 객체를 `toString()`으로 바꿔 현재 response의 `Set-Cookie` header에 넣을 때 browser가 Cookie를 저장합니다.
- `.httpOnly(true)`는 browser JavaScript가 Cookie를 읽지 못하게 하고, `.sameSite("Strict")`는 cross-site 전송을 제한합니다. 이 설정이 Access Token localStorage와 Refresh Cookie를 분리하는 보안 이유입니다.
- `createExpiredRefreshTokenCookie`도 새 Cookie 객체를 만들지만 같은 name/path를 사용하고 `maxAge(Duration.ZERO)`를 넣습니다. Browser는 이 Set-Cookie를 받아 기존 Cookie를 즉시 삭제합니다. 이전 객체를 서버 메모리에서 지우는 동작이 아닙니다.
- 이 장에서 login은 `createRefreshTokenCookie`를 사용하고, expired Cookie method는 새 08장의 logout·계정 변경에서 사용합니다.

## 14. `SessionController`가 Service 결과를 JSON body와 `Set-Cookie` header로 나눈다

### 실제 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/controller/SessionController.java`

### 코드 원문: class와 login method

package/import와 같은 파일의 Refresh·logout method는 로그인 응답에 필요한 부분이
아니므로 생략한 실제 source 발췌입니다. `createSession`의 body와 반환·header 연결은
이 장에서 끝까지 설명하고, 나머지 method는 새 07·08에서 다시 배치합니다.

~~~~java
@RestController
@RequestMapping("/sessions")
@RequiredArgsConstructor
public class SessionController {
    private final SessionService sessionService;
    private final RefreshCookieProvider refreshCookieProvider;

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public SessionResponseDto createSession(
            @Valid @RequestBody SessionRequestDto request,
            HttpServletResponse response
    ){
        SessionResponseDto sessionResponse = sessionService.createSession(request);

        response.addHeader(
                HttpHeaders.SET_COOKIE,
                refreshCookieProvider
                        .createRefreshTokenCookie(sessionResponse.getRefreshToken())
                        .toString()
        );

        return sessionResponse;
    }
}
~~~~

### 코드 바로 아래 설명

- `@RestController`는 이 class의 반환값을 view name이 아니라 JSON response body로 직렬화하도록 Spring MVC에 알립니다.
- `@RequestMapping("/sessions")`와 method의 `@PostMapping`이 합쳐져 `POST /sessions`가 됩니다. `@ResponseStatus(HttpStatus.CREATED)` 때문에 현재 성공 status는 201입니다.
- `@Valid @RequestBody SessionRequestDto request`에서 `request`는 Controller가 `new`로 만든 값이 아닙니다. Spring MVC가 HTTP JSON을 역직렬화하고 validation을 통과시킨 객체를 method parameter로 넣습니다.
- `HttpServletResponse response`도 사용자가 선언한 일반 객체가 아닙니다. Servlet container가 현재 HTTP 요청에 대해 만들고 Spring MVC가 parameter로 주입한 response 객체입니다.
- `sessionService.createSession(request)`의 반환값은 `SessionResponseDto`입니다. Service는 Cookie header를 직접 만들지 않고 업무 결과를 반환합니다.
- `HttpHeaders.SET_COOKIE`는 Spring이 제공하는 `"Set-Cookie"` header 이름 상수입니다. `refreshCookieProvider.createRefreshTokenCookie(...)`가 만든 새 `ResponseCookie`를 `.toString()`으로 header 형식 문자열로 바꿔 `response.addHeader`에 전달합니다.
- `response.addHeader`가 response 객체에 header를 기록한 뒤에도 Controller method는 계속 실행되어 `return sessionResponse`를 합니다. 두 동작은 서로 다른 response 영역입니다. header는 이미 같은 response 객체에 추가되었고, return 값은 JSON body로 직렬화됩니다.
- 결과적으로 browser는 JSON body에서 `message`, `accessToken`, `userId`를 받고, `Set-Cookie` header에서 HttpOnly Refresh Cookie를 받습니다. `refreshToken`은 `@JsonIgnore` 때문에 body에는 들어가지 않습니다.
- 같은 class의 `refreshSession`, `deleteSession`도 실제로 존재하지만 이 문서에서는 login method의 완성된 호출만 다룹니다. 두 method의 전체 body는 새 07·08에 각각 배치합니다.

~~~~text

→ JSON response body
~~~~

### Controller의 호출·반환·예외

- 호출자: Spring MVC의 `DispatcherServlet`이 URL/method mapping을 보고 호출합니다. `LoginPage`가 Java method를 직접 호출하는 것은 아닙니다.
- 입력: HTTP JSON body, Servlet response 객체.
- 호출 대상: `SessionService.createSession`, `RefreshCookieProvider.createRefreshTokenCookie`.
- 반환: `SessionResponseDto` → Spring MVC/Jackson JSON body.
- 직접 response 변경: `response.addHeader` → `Set-Cookie`.
- 예외: validation은 method 진입 전, `LoginFailedException`은 method 내부 Service에서 발생 후 `GlobalExceptionHandler`, Origin 거부는 Controller 진입 전 `ErrorResponseWriter`입니다.

## 15. 로그인 예외가 HTTP JSON으로 변환되는 위치

### 실제 파일

`/Users/miles/Documents/GitHub/KTB4_Miles_Week12_Back/src/main/java/kr/adapterz/springdatajpa/controller/GlobalExceptionHandler.java`

### 코드 원문: 로그인과 직접 연결되는 method

package/import와 게시글·회원 기능의 다른 exception handler는 이 로그인 흐름에 필요하지
않아 생략한 실제 method 발췌입니다. 전체 class는 03장에서 확인했고, 여기서는 로그인
Service에서 전파된 예외가 도착하는 두 handler와 공통 `error` method만 다시 연결합니다.

~~~~java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(LoginFailedException.class)
    public ResponseEntity<ErrorResponseDto> handleLoginFailedException(LoginFailedException e) {
        return error(HttpStatus.UNAUTHORIZED, e.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponseDto> handleValidationException(MethodArgumentNotValidException e) {
        return error(HttpStatus.BAD_REQUEST, "INVALID_REQUEST");
    }

    private ResponseEntity<ErrorResponseDto> error(HttpStatus status, String rawCode) {
        ApiErrorCode errorCode = ApiErrorCode.from(rawCode);
        ErrorResponseDto response = new ErrorResponseDto(
                errorCode.getCode(),
                errorCode.getMessage(),
                status.value()
        );
        return ResponseEntity.status(status).body(response);
    }
}
~~~~

### 코드 바로 아래 설명

- `@RestControllerAdvice`는 여러 Controller에서 전파된 예외를 공통으로 가로채는 Spring MVC advice입니다. 이 handler는 Controller/Service 경계에서 나온 예외에 적용됩니다.
- `LoginFailedException`은 Service가 인증 실패를 업무 code로 바꾼 결과입니다. handler가 HTTP 401과 raw message를 `error`에 전달합니다.
- `MethodArgumentNotValidException`은 DTO validation 실패입니다. Controller method body까지 도달하지 않으므로 Service의 catch가 아니라 별도 validation handler가 처리합니다.
- `ApiErrorCode.from`은 `Suspended_Account`, `Login_Failed`처럼 내부에서 전달한 raw code를 대문자·underscore 형식으로 정규화해 enum을 찾습니다. enum에 없는 값이면 `UNKNOWN_ERROR`가 됩니다.
- `ErrorResponseDto`를 body에 넣은 `ResponseEntity`가 Spring MVC를 통해 JSON으로 직렬화됩니다. 이 경로는 Filter/Interceptor가 `ErrorResponseWriter.write`로 response를 직접 끝내는 경로와 다릅니다.

### 로그인 오류 이동 비교

| 발생 지점 | Controller 도달 여부 | 응답 생성자 | status/code |
|---|---:|---|---|
| DTO `@Valid` 실패 | 아니오(Controller body 전) | `GlobalExceptionHandler` | 400 / `INVALID_REQUEST` |
| Origin 불허 | 아니오 | `ErrorResponseWriter` | 403 / `FORBIDDEN_ORIGIN` |
| 인증 실패 | 예, Service에서 예외 | `GlobalExceptionHandler` | 401 / `LOGIN_FAILED` 또는 `SUSPENDED_ACCOUNT` |
| 정상 | 예 | Controller return + response header | 201 / JSON + Set-Cookie |

- `SessionService.refreshSession`, `deleteSession`: 실제 source에 존재하지만 login 최초 생성 method와 다른 실행 흐름입니다. 임의 placeholder로 줄이지 않고 해당 장에 실제 body를 배치할 예정입니다.
