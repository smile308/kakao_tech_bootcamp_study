# study11 PostCounter 교차 간섭 테스트 증거

## 1. 테스트 목적

study11은 한 게시글의 `view_count`, `like_count`, `reply_count`, `report_count`를 `post_counters`의 동일한 행에 저장한다.

이 구조에서는 조회 요청이 `view_count`만 변경하고 댓글 요청이 `reply_count`만 변경하더라도, 두 요청이 동일한 DB 레코드의 쓰기 락을 두고 경쟁할 수 있다. 이를 확인하기 위해 댓글 요청량은 동일하게 유지하고 조회 트래픽 유무만 바꾼 두 조건을 비교했다.

```text
조건 A: 댓글 생성·삭제만 실행
조건 B: 동일한 댓글 생성·삭제 + 동일 게시글 조회 200회/초
```

## 2. 테스트 대상과 환경

- 대상 버전: `study11_baseline`
- 대상 게시글: `post_id=1`
- 사전 댓글 카운터: 100
- 사전 실제 댓글 행: 100
- 실행 장비와 컨테이너 구성: 조회수 Hot Row 용량 테스트와 동일
- 부하 생성기: `grafana/k6:2.0.0`
- 백엔드: Spring Boot 4.0.6, Java 26, 컨테이너 1개
- 데이터베이스: MySQL 8.4, 컨테이너 1개
- Docker 가용 자원: CPU 10개, 메모리 약 7.75GiB
- 실행 방식: k6 `constant-arrival-rate`
- 실행 시간: 조건별 60초
- 인증 방식: 모든 VU가 동일한 테스트 계정의 JWT 사용

## 3. 댓글 생명주기를 사용한 이유

댓글 생명주기 1회는 다음 두 요청으로 구성된다.

1. 댓글 1개 생성: `reply_count + 1`
2. 방금 생성한 댓글 삭제: `reply_count - 1`

각 조건에서 초당 5개의 생명주기를 시작했다. 생성한 댓글을 바로 삭제하는 것은 실제 사용자 행동 비율을 재현하기 위한 것이 아니라, 60초 동안 계속 댓글 쓰기를 발생시키면서 댓글 수와 게시글 상세 응답 크기를 100개로 유지하기 위한 통제 방법이다.

유효 실행에서는 댓글 생명주기 300~301개를 처리했다. 혼합 3차에서 예정된 iteration 1개가 시작되지 않아 300개였고, 나머지 실행은 301개였다.

## 4. 비교 조건

| 조건 | 댓글 생명주기 | 게시글 상세 조회 | 전체 HTTP 요청 |
|---|---:|---:|---:|
| 댓글 전용 | 5회/초 | 0회/초 | 실행별 602 |
| 조회+댓글 혼합 | 5회/초 | 200회/초 | 실행별 12,590~12,603 |

각 조건을 3회 실행했다. 1차는 댓글 전용 후 혼합, 2차는 혼합 후 댓글 전용, 3차는 다시 댓글 전용 후 혼합 순서로 실행해 순서 영향을 확인했다.

| 차수 | 댓글 전용 실행 시각 | 혼합 실행 시각 |
|---|---|---|
| 1차 | `2026-07-30 16:01:38 KST` | `2026-07-30 16:04:16 KST` |
| 2차 | `2026-07-30 16:30:40 KST` | `2026-07-30 16:27:08 KST` |
| 3차 | `2026-07-30 16:33:14 KST` | `2026-07-30 16:35:48 KST` |

유효한 6회 실행은 모두 HTTP 실패와 댓글 생명주기 실패가 0이었다.

## 6. MySQL 행 락 3회 측정

| 조건 | 지표 | 1차 | 2차 | 3차 | 중앙값 |
|---|---|---:|---:|---:|---:|
| 댓글 전용 | 행 락 대기 증가 | 0회 | 0회 | 0회 | **0회** |
| 댓글 전용 | 누적 락 대기시간 증가 | 0ms | 0ms | 0ms | **0ms** |
| 혼합 | 행 락 대기 증가 | 1,400회 | 2,105회 | 1,658회 | **1,658회** |
| 혼합 | 누적 락 대기시간 증가 | 15,299ms | 37,730ms | 24,607ms | **24,607ms** |
| 혼합 | 관측 중 `current_waits` 최대 | 9 | 9 | 9 | **9** |
| 혼합 | 한 시점의 대기 관계 최대 | 45 | 45 | 45 | **45** |
| 혼합 | 수집한 `wait_detail` | 67행 | 215행 | 155행 | **155행** |

세 혼합 테스트에서 수집한 `wait_detail`은 모두 다음 대상을 가리켰다.

| 항목 | 값 |
|---|---|
| 테이블 | `bamboo_loadtest.post_counters` |
| 인덱스 | `PRIMARY` |
| 락 종류 | `RECORD` |
| 락 모드 | `X,REC_NOT_GAP` |

즉, 세 번의 댓글 전용 테스트에는 없었던 DB 행 락 대기가 세 번의 혼합 테스트에서 반복됐고, 실제 대기 대상도 매번 `post_counters`의 기본키 레코드였다.

## 9. 결론

1. 조회 트래픽이 없는 세 번의 테스트에서는 MySQL 행 락 대기가 모두 0회였다.
2. 동일한 댓글 부하에 조회 200회/초를 추가한 세 번의 테스트에서는 행 락 대기가 매번 발생했고 중앙값은 1,658회, 누적 대기시간 중앙값은 24.607초였다.
3. 실제 락 상세 정보는 모든 실행에서 `post_counters`의 동일 기본키 레코드를 가리켰다.
4. 댓글 생명주기 p95 중앙값은 22ms에서 52ms로 약 2.36배, p99 중앙값은 29ms에서 181.21ms로 약 6.25배 증가했다.
5. 원자적 UPDATE는 조회수·댓글 수 유실을 방지했지만, 서로 다른 카운터가 한 행에 모여 발생하는 쓰기 직렬화와 교차 간섭까지 제거하지는 못했다.
6. 따라서 개선 목표는 데이터 정확성을 유지하면서 조회수 쓰기 경로를 댓글 카운터가 있는 MySQL 행에서 분리하는 것이다.

## 10. 해석의 한계와 다음 검증

1. 혼합 조건은 조회수 UPDATE 외에도 게시글·댓글 조회, JSON 직렬화, 네트워크 전송 부하를 추가한다.
2. Performance Schema 기록은 대기 레코드는 알려 주지만 어떤 HTTP 엔드포인트의 트랜잭션이 기다렸는지까지 표시하지 않는다. 포착한 행 락 대기 전부를 댓글 요청의 대기라고 표현하지 않는다.
3. 다만 조회 유무만 달리한 세 번의 통제 비교에서 댓글 꼬리 지연과 동일 `post_counters` 행의 락 대기가 반복됐으므로, 동일 행 쓰기 경합이 병목 원인 중 하나라는 근거는 확보했다.
4. 부하 생성기, 백엔드, MySQL이 같은 로컬 Mac의 자원을 공유하므로 운영 환경의 절대 처리량이 아니라 동일 환경의 study11/study12 상대 비교 자료로 사용한다.
5. 이후 study12에서 조회수 쓰기 경로를 분리한 뒤 동일한 두 조건을 각각 3회 실행한다.

## 11. 원본 증거 파일

### 표와 원본 파일의 연결

| 문서의 표·주장 | 원본 | 계산·확인 방법 |
|---|---|---|
| 댓글 생성·삭제·생명주기 지연시간 | 두 조건의 `__k6-summary.json` | `comment_create_duration`, `comment_delete_duration`, `comment_lifecycle_duration`의 `avg`, `med`, `p(90)`, `p(95)`, `p(99)`, `max` |
| 요청 수와 HTTP 성공 여부 | 두 조건의 `__k6-summary.json` | 상태별 Counter, `http_reqs`, `http_req_failed`, `checks` |
| 행 락 대기 횟수와 시간 | 두 조건의 `__mysql-locks.txt` | 첫 표본과 마지막 표본의 `Innodb_row_lock_waits`, `Innodb_row_lock_time` 차이 |
| 실제 락 대상 | 혼합 조건의 `__mysql-locks.txt` | `wait_detail`의 `object`, `index`, `lock_type`, `lock_mode` |
| 종료 후 댓글 카운터·행 개수·조회수 | 2·3차 `__run-metadata.txt`, 1차 실행 터미널 출력 | 실행 전후 값과 성공 요청 수 비교 |

1차 실행 후 증거 보존 문제를 발견해 2·3차부터 실행기가 `__run-metadata.txt`에 테스트 전후 댓글 카운터, 실제 댓글 행, 조회수, 종료 상태를 자동 저장하도록 보완했다. 이 변경은 1차 실행에 소급 적용하지 않았다.
