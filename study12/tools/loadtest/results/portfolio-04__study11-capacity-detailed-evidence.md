# study11 인기 게시글 조회수 Hot Row 용량 테스트 증거

## 1. 테스트 목적

사용자가 많이 몰린 인기 게시글 하나를 여러 사용자가 동시에 조회하는 상황을 재현했다.

study11의 게시글 상세 조회 API는 조회할 때마다 MySQL의 `post_counters` 행에 다음 원자적 UPDATE를 실행한다.

```sql
UPDATE post_counters
SET view_count = view_count + 1
WHERE post_id = ?
```

동일한 게시글을 향한 모든 요청이 같은 `post_id`의 행을 수정하므로, 요청이 많아지면 하나의 행이 쓰기 경합 지점인 **Hot Row**가 될 수 있다. 이 테스트의 목적은 다음 세 가지를 확인하는 것이다.

1. study11이 정상적으로 감당하는 부하와 처리 한계가 나타나는 부하의 차이
2. 부하 증가 시 응답시간과 처리하지 못한 요청이 어떻게 변하는지
3. 병목이 발생할 때 실제 MySQL 락 대기 대상이 `post_counters`의 동일 레코드인지

이 테스트는 단순히 “HTTP 200이 나오는가”만 확인하지 않는다. 성공한 요청 수와 조회수 증가량이 같은지도 비교하여 성능과 데이터 정합성을 함께 검증한다.

## 2. 테스트 대상과 요청 한 건의 동작

- 대상 코드: 수정 전 기준 버전 `study11_baseline`
- 대상 API: 인증이 필요한 `GET /posts/1`
- 대상 데이터: 게시글 1개, 댓글 100개
- 요청 집중 방식: 모든 가상 사용자가 동일한 `post_id=1` 조회
- 애플리케이션 인스턴스: 1개
- MySQL 인스턴스: 1개
- Redis·캐시·로드 밸런서: 사용하지 않음

상세 조회 요청 한 건은 대략 다음 순서로 처리된다.

1. JWT 액세스 토큰을 검증한다.
2. `post_counters`에서 대상 게시글의 `view_count`를 1 증가시킨다.
3. 게시글과 작성자 등 상세 정보를 조회한다.
4. 게시글의 댓글 100개와 댓글 작성자 정보를 조회한다.
5. 로그인 사용자의 좋아요·신고 여부를 확인한다.
6. 게시글 상세 JSON 응답을 반환한다.

따라서 이 실험은 실제 상세 조회 흐름을 측정한다. 조회수 UPDATE만 따로 실행하는 DB 마이크로 벤치마크가 아니다. 댓글 100개를 둔 이유도 실제 인기 게시글처럼 응답 데이터와 조회 작업이 있는 조건을 만들기 위해서다.

## 5. 부하 생성 방식

k6의 `ramping-arrival-rate` 실행기를 사용했다. 이 방식은 “가상 사용자 한 명이 응답을 받은 뒤 다음 요청을 보내는 방식”이 아니라, 서버 응답이 느려져도 정해진 초당 요청 시작률을 맞추려고 새로운 가상 사용자를 추가하는 **개방형 부하 모델**이다.

### 비교용 정상 부하

| 구간 | 시간 | 목표 요청률 |
|---|---:|---:|
| 유지 | 15초 | 10 req/s |
| 증가 | 30초 | 10 → 50 req/s |
| 증가 | 30초 | 50 → 100 req/s |
| 증가 | 30초 | 100 → 200 req/s |
| 감소 | 10초 | 200 → 0 req/s |

- 예정 요청 수: 8,800회
- 사전 할당 VU: 50
- 최대 VU: 500
- 실제 테스트 시간: 1분 55초

### 처리 한계 확인용 용량 부하

| 구간 | 시간 | 목표 요청률 |
|---|---:|---:|
| 유지 | 15초 | 200 req/s |
| 증가 | 25초 | 200 → 500 req/s |
| 증가 | 30초 | 500 → 1,000 req/s |
| 감소 | 10초 | 1,000 → 0 req/s |

- 예정 요청 수: 39,250회
- 사전 할당 VU: 100
- 최대 VU: 1,000
- 부하 구간: 1분 20초
- 종료 대기 포함 최대 실행시간: 1분 30초
- 요청 제한시간: 10초

요청률을 한 번에 1,000 req/s로 올리지 않고 단계적으로 높여, 어느 구간부터 응답 지연과 필요한 VU가 급증하는지 관찰했다.

## 6. 동시에 수집한 지표

부하를 발생시키는 동안 별도 관측 프로세스가 약 1초 간격으로 MySQL Performance Schema를 조회했다.

| 관측 대상 | 의미 |
|---|---|
| k6 `http_req_duration` | 실제 시작된 HTTP 요청의 응답시간 |
| k6 `http_req_failed` | 시작된 요청 중 HTTP·네트워크 실패 비율 |
| k6 `dropped_iterations` | 예정 시각에 시작조차 하지 못한 요청 수 |
| k6 `vus`, `vus_max` | 요청률을 맞추는 데 필요했던 동시 가상 사용자 수 |
| `Innodb_row_lock_waits` | InnoDB 행 락을 기다린 누적 횟수 |
| `Innodb_row_lock_time` | InnoDB 행 락을 기다린 누적 시간 |
| `data_lock_waits` | 관측 순간 실제 대기·차단 중인 트랜잭션 관계 |
| `data_locks` | 대기 중인 테이블·인덱스·레코드·락 모드 |

MySQL의 전역 행 락 지표는 이전 실행 값이 누적될 수 있으므로 절대값이 아니라 **테스트 직전 값과 직후 값의 차이**를 사용했다.

### 실제 포착된 락 대상

| 항목 | 값 |
|---|---|
| 포착한 `wait_detail` 행 | 1,661 |
| 스키마·테이블 | `bamboo_loadtest.post_counters` |
| 인덱스 | `PRIMARY` |
| 락 종류 | `RECORD` |
| 락 모드 | `X,REC_NOT_GAP` |
| 한 관찰 시점의 최대 락 대기 관계 | 45 |

- `X`: 다른 트랜잭션의 쓰기를 막는 배타적 락
- `RECORD`: 테이블 전체가 아니라 특정 인덱스 레코드에 걸린 락
- `PRIMARY`: `post_id` 기본키로 찾은 `post_counters` 행
- `REC_NOT_GAP`: 인덱스 사이 범위가 아니라 실제 레코드에 걸린 락

현재 MySQL 원자적 UPDATE 방식은 높은 경합에서도 조회수를 유실하지 않았다. 성능 개선 후에도 이 정합성을 유지하거나, 최종 일관성 범위와 복구 방식을 명확히 정의해야 한다.

## 12. 결론

1. 최대 200 req/s에서는 실패 없이 빠르게 처리했지만 MySQL 행 락 대기는 이미 발생했다.
2. 용량 테스트에서는 응답시간과 행 락 대기가 함께 급증했다.
3. 순간 락 정보에서 `post_counters` 기본키 레코드의 배타적 락 대기가 직접 확인됐다.
4. 실제 전송된 요청은 모두 성공했지만 목표 요청의 23.62%는 시작하지 못했다.
5. 조회수 정합성은 유지됐으므로 개선은 성능뿐 아니라 동일한 정확성도 검증해야 한다.
6. 부하 생성기, 백엔드, MySQL이 같은 로컬 Mac에서 실행됐으므로 절대 운영 용량이 아니라 동일 환경의 study11/study12 상대 비교 자료로 사용한다.

## 13. 해석 시 주의점

1. 이 테스트는 동일 게시글의 조회가 집중되는 상황을 재현한 것이며 여러 게시글에 고르게 분산되는 일반 조회 트래픽을 뜻하지 않는다.
2. 상세 API에는 조회수 UPDATE 외에도 댓글 조회, 좋아요·신고 여부 조회, JSON 직렬화가 포함된다. 응답시간 전체를 오직 행 락 시간이라고 해석하면 안 된다.
3. 다만 테스트 중 실제 대기 락이 `post_counters`의 동일 기본키 레코드에서 포착됐으므로, Hot Row가 병목 원인 중 하나라는 직접적인 근거는 확보했다.
4. 로컬 단일 장비 결과이므로 “운영에서 초당 500건이 한계”라고 단정하지 않는다. 동일 환경의 개선 전후 변화율을 비교하는 용도로 사용한다.
5. `k6_status=0`은 설정된 HTTP 성공률 조건을 통과했다는 뜻이다. 지연시간과 `dropped_iterations`에 대한 임계값은 당시 설정하지 않았으므로 용량 목표까지 통과했다는 뜻이 아니다.
6. 모든 VU가 같은 테스트 계정의 토큰을 재사용했다. 상세 조회의 Hot Row 경합을 만드는 데는 문제가 없지만, 서로 다른 로그인 세션에서 발생하는 인증 비용 차이까지 재현한 테스트는 아니다.
