# 동시성·트래픽 고도화 작업 인수인계

이 파일은 다른 컴퓨터나 새로운 Codex 대화에서 작업을 이어가기 위한 컨텍스트다.
새 대화에서는 이 파일을 먼저 읽고, 아래의 목표와 진행 규칙을 유지한다.

## 1. 사용자의 최우선 목표

- 현재 게시판 프로젝트를 포트폴리오 수준으로 고도화한다.
- 가정할 트래픽은 **특정 게시글에 요청이 집중되는 바이럴/논란 게시글 Hot-Key 트래픽**이다.
- 기술을 먼저 적용하지 않고 다음 순서로 진행한다.

```text
현재 상태 측정
→ 결과 분석
→ 실제로 확인된 병목 하나 선택
→ 개선 방법 비교
→ 코드 수정
→ 같은 조건으로 재측정
→ 다음 병목으로 반복
```

- 사용자가 코드를 직접 이해하고 학습하는 것이 가장 중요하다.
- 사용자가 나중에 변경 이유와 동작 원리를 스스로 설명할 수 있어야 한다.
- 별도의 포트폴리오 보고서 작성이나 면접 예상 질문 작성은 현재 작업 범위가 아니다.

## 2. 반드시 지킬 협업 규칙

### 트래픽 테스트

- Codex가 트래픽 테스트를 대신 실행하지 않는다.
- Codex는 테스트 도구 사용법, 실행 명령, 테스트 스크립트, 데이터 준비 방법, 확인할 지표를 설명한다.
- 사용자가 직접 테스트를 실행하고 결과를 Codex에 전달한다.
- Codex는 사용자가 전달한 실제 결과를 근거로 병목을 분석한다.
- 측정 결과가 나오기 전에 개선 기술을 확정하지 않는다.

### 코드 수정

모든 코드 수정은 한 번에 작은 단위로 진행한다.

수정 전에 반드시 설명할 내용:

1. 관측된 문제와 근거
2. 현재 코드에서 문제가 발생하는 이유
3. 고려할 수 있는 해결 방법
4. 선택할 방법과 선택하지 않은 방법
5. 변경할 파일
6. 예상되는 SQL, 트랜잭션, 잠금 변화
7. 장점과 단점

수정 후 반드시 설명할 내용:

1. 실제로 변경된 파일과 메서드
2. 변경 코드의 역할
3. 트랜잭션 시작과 종료 지점
4. 잠금 또는 원자적 연산이 발생하는 시점
5. 동시 요청의 처리 순서
6. 예외와 롤백 과정
7. 기존 동작과 달라진 점
8. 사용자가 직접 실행할 검증 방법

- 여러 개선을 한꺼번에 적용하지 않는다.
- 개선 하나를 적용한 뒤 사용자가 동일한 조건으로 다시 측정한다.
- 사용자가 결과를 전달하면 다음 단계를 결정한다.

## 3. 확정된 주제와 범위

### 통합 주제

> 바이럴·논란 게시글에 Hot-Key 트래픽이 집중될 때 조회수, 좋아요, 댓글, 신고, 차단 및 삭제의 데이터 정합성을 유지하면서 처리량과 응답 시간을 개선한다.

### 포함 범위

- 게시글 상세 조회
- 조회수 증가
- 좋아요 및 좋아요 취소
- 댓글 등록 및 삭제
- 신고와 신고 임계점 차단
- 게시글 수정 및 삭제
- 동일 게시글의 Hot Row 경합
- 댓글 조회 방식과 페이지네이션
- 트래픽 지연으로 발생할 수 있는 중복 요청과 멱등성
- 잠금 순서와 데드락 가능성

단, 댓글 페이지네이션과 멱등성은 미리 적용하지 않고 측정 결과 및 재현 결과를 보고 적용 여부를 결정한다.

### 명시적으로 제외한 범위

- 조회 캐시
- Cache Stampede
- 인기글 랭킹
- 알림 시스템
- 기술 과시만을 위한 메시지 브로커 도입
- 현재 측정으로 필요성이 확인되지 않은 선제적 카운터 샤딩

## 5. 현재까지 발견한 핵심 가설

아래 내용은 아직 트래픽 측정으로 확정된 결론이 아니라 검증해야 할 가설이다.

### 조회 요청이 쓰기 요청으로 변환됨

`PostService.getPostView()`는 게시글 상세 조회마다 `viewCount`를 UPDATE한다.
따라서 특정 게시글에 조회가 집중되면 모든 조회 요청이 같은 `PostCounter` 행을 변경한다.

### 단일 `PostCounter` Hot Row

조회수, 좋아요 수, 댓글 수, 신고 수가 하나의 `PostCounter` 행에 있다.
서로 다른 기능의 요청도 같은 행 변경을 두고 경쟁할 가능성이 있다.

### 댓글 전체 조회

게시글 상세 조회 시 해당 게시글의 댓글을 전부 조회한다.
댓글이 많아지면 상세 조회 응답 시간과 메모리 사용량에 영향을 줄 가능성이 있다.

### 잠금 순서 차이

신고는 게시글을 먼저 잠근 뒤 카운터를 변경하고, 삭제는 카운터를 잠근 뒤 flush 과정에서 게시글을 변경할 가능성이 있다.
신고와 삭제 또는 신고와 다른 상호작용이 겹칠 때 잠금 순서 역전으로 데드락이 발생할 가능성을 검증해야 한다.

### H2와 MySQL 차이

현재 로컬 기본 환경과 일부 테스트는 H2를 사용한다.
최종 동시성 및 트래픽 판단은 운영과 동일한 MySQL 환경에서 수행해야 한다.

## 6. 지켜야 할 데이터 불변식

- 좋아요 카운터는 실제 좋아요 행 개수와 일치해야 한다.
- 댓글 카운터는 실제 댓글 행 개수와 일치해야 한다.
- 신고 카운터는 실제 신고 행 개수와 일치해야 한다.
- 사용자 한 명은 게시글 하나에 좋아요를 하나만 생성할 수 있다.
- 사용자 한 명은 게시글 하나를 한 번만 신고할 수 있다.
- 카운터는 음수가 될 수 없다.
- 차단이 먼저 확정된 경우 이후 좋아요와 댓글은 생성되면 안 된다.
- 삭제가 먼저 확정된 경우 이후 상호작용은 생성되면 안 된다.
- 게시글 차단 상태 전환은 한 번만 확정되어야 한다.
- 수정과 삭제의 충돌 결과가 요청 순서와 버전 정책에 맞아야 한다.

## 7. 테스트 진행 순서

### 1단계: 현재 요청 흐름 학습

- 게시글 상세 조회 한 번의 서비스 호출 흐름 확인
- 발생하는 쿼리와 트랜잭션 확인
- 현재 원자적 UPDATE와 잠금의 의미 학습

### 2단계: 테스트 환경 구성

- k6 사용 방법 안내
- MySQL 기반 테스트 환경 준비
- 실행 환경과 자원 조건 고정
- 결과 저장 방법 준비

### 3단계: 테스트 데이터 준비

- Hot Post 1개
- 충분한 테스트 사용자
- 좋아요/댓글/신고용 사용자
- 신고 수가 임계점 직전인 게시글
- 테스트별 데이터 초기화 방법

### 4단계: Smoke Test

- 작은 요청으로 인증과 각 API 정상 동작 확인
- 트래픽 스크립트 자체의 오류 제거

### 5단계: 단일 기능 Baseline

다음 순서로 사용자가 직접 실행한다.

1. 게시글 상세 조회 집중
2. 서로 다른 사용자의 좋아요 집중
3. 댓글 등록 집중
4. 댓글이 많은 게시글의 상세 조회
5. 신고 임계점 경계 테스트

### 6단계: 혼합 트래픽 Baseline

하나의 게시글에 상세 조회, 좋아요, 댓글, 신고가 함께 들어오는 상황을 실행한다.
이전에 논의한 `조회 85% / 좋아요 8% / 댓글 5% / 신고 2%`는 후보일 뿐이며 단일 테스트 결과를 보고 조정한다.

신고는 5건이면 게시글이 차단되므로 장시간 비율 부하에 그대로 섞지 않을 수 있다.
지속 부하와 신고 임계점 경계 테스트를 분리하는 방식을 우선 고려한다.

### 7단계: 동시성 경계 재현

- 삭제와 댓글 등록
- 삭제와 좋아요
- 5번째 신고와 댓글 등록
- 5번째 신고와 좋아요
- 신고와 삭제
- 수정과 삭제

### 8단계: 결과 분석

- TPS
- 평균, p95, p99 응답 시간
- 실패율과 HTTP 상태 코드
- 애플리케이션 CPU 및 메모리
- DB 커넥션 사용량과 대기
- Row lock wait
- Deadlock
- 주요 SQL 실행 시간
- 테스트 후 데이터 불변식

### 9단계: 첫 번째 병목 선택

측정 근거를 바탕으로 하나만 선택한다.

후보:

- 조회수 UPDATE Hot Row
- 단일 `PostCounter` 경합
- 게시글 상태 전환
- 잠금 순서
- 댓글 전체 조회
- 중복 요청
- 트랜잭션 범위

### 10단계: 첫 번째 개선 및 재측정

- 수정 전 상세 설명
- 코드 수정
- 수정 후 상세 설명
- 사용자가 동일 조건으로 재테스트
- 변경 전후 비교

### 11단계: 반복

실제 결과에서 다음 병목이 확인되는 동안 같은 순서를 반복한다.

### 12단계: 최종 정합성 검증과 코드 정리

- 모든 불변식 재검증
- 전체 요청 흐름 재설명
- 남은 한계 정리

## 8. 다음 대화에서 바로 시작할 작업

아직 애플리케이션 코드는 수정하지 않는다.

다음 순서로 시작한다.

1. 이 인수인계 파일을 읽는다.
2. `PostService.getPostView()`와 관련 Repository를 다시 확인한다.
3. 게시글 상세 조회 한 번이 발생시키는 트랜잭션과 SQL을 사용자에게 설명한다.
4. 사용자가 실행할 MySQL 기반 트래픽 테스트 환경을 정한다.
5. k6 설치 및 가장 작은 Smoke Test 준비로 넘어간다.

## 9. Git 작업 시 주의사항

이 파일을 만들기 전부터 `.DS_Store` 관련 변경 및 미추적 파일이 존재했다.
이는 사용자의 기존 파일이므로 임의로 수정, 삭제, 스테이징하지 않는다.

현재 컨텍스트 파일:

```text
CONCURRENCY_WORK_HANDOFF.md
```

새 대화에서 Git 작업을 요청받으면 이 파일과 사용자가 명확히 지정한 파일만 대상으로 삼고, 기존 `.DS_Store` 변경은 건드리지 않는다.
